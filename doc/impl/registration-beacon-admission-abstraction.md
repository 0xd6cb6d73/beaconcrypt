# Arbitrary initial-response delivery at the Beacon boundary

This package connects the existing complete native Beacon initial-response operation to an additive local symbolic admission process. The source remains `ProviderBeacon::finish_registration` in `beaconcrypt/src/beacon.rs`. The twelve Lean statements retain the complete optional reply, native owner and callback state. The ProVerif process permits arbitrarily many configured Beacon owners and arbitrarily scheduled raw deliveries. It proves eight local correspondences; a ninth diagnostic about the history behind a closed call remains inconclusive. This is a local operational boundary, not a Server-origin authentication theorem or completion of the whole symbolic/computational composition.

## What the source statements establish

`inactive_owner` rejects a finish call outside `InitSent` before any parser or cryptographic callback. `finish_inactive` covers every actual publication or abort result. `attempt_inactive` follows the complete original active operation through all supported callback outcomes, and `no_retry` uses the exact reached owner to reject every later finish call without another callback. `active_failure` identifies the full terminal abort state on any failed active outcome. The shared callback state is the actual state reached before failure; abort does not undo primitive effects. The predicate `Inactive` also includes a never-started owner, so it alone does not prohibit a separate constructor or bundle operation. The no-retry statement concerns later finish calls on the returned owner.

`successful_path` joins the actual preparation, optional root, typed 64-byte initializer, deferred application getter, full raw receive and final publication in one supported execution. It retains every intermediate callback state and the actual resulting raw owner. It does not recover a session, root or kernel from equal public bytes. `raw_success_receipt` then identifies the original decoded sequence-one frame, actual sender pin, returned optional plaintext and exact kernel that will be installed.

`raw_wrong_target` proves that a successfully decoded non-one target cannot pass the later registration gate, even if its raw opening succeeds. `wrong_target_continuation` lifts this fact to an equality of complete computations with an arbitrary continuation. The complete raw execution, returned raw state and primitive poststate occur on both sides. This justifies the model's pure dispatch on the immutable decoded target without moving rejection ahead of derivation or opening.

`opened_binding` consumes the actual extracted authentication result. The opened sender equals the candidate's Server identifier; the first eight plaintext bytes equal the little-endian encoding of the assigned identifier; the application suffix is nonempty and otherwise unrestricted. `published_shape` consumes the actual publication result and installs that assigned identifier, the candidate's associated data and the exact received kernel while returning only the suffix. This concerns the initial authenticated binding. It does not assert equality between claimed and assigned identities elsewhere in the protocol.

`native_calls` retains the existing complete native limit of 69 typed callbacks and proves zero callbacks for an inactive finish. The complete accounting is twelve collection callbacks, one temporary shared-input erasure callback, one root callback, one 64-byte initializer, one application getter and up to 53 expanded raw callbacks. The raw allowance includes at most 51 private KDF derivations, one commitment hash and one AEAD opening, even when the later sequence policy rejects. The existing interpreted bound charges each callback's primitive, codec and local work explicitly; the 69 bound does not make these costs free. Every delivered API request remains an attempt, including those with zero internal callbacks. No cryptographic reduction loss is introduced by these operational statements.

## Replicated local process and its exact scope

`registration-beacon-admission.pv` accepts a caller-supplied public pin and configured Server identifier for each new owner. The existing honest Server public identity is also available on the network. Each owner starts at the published `InitSent` boundary with source-ordered identity, prekey, KEM and one-time generation and the three original signatures. The process has one private owner token and replicated public delivery requests. Origin events and the existing origin-table insertion are observations only; they never authorize admission. This model also allows attacker-owned configured Server identities.

The preparation order is decode and typed field checks, public/private identity conversion, KEM decapsulation, DH1 through DH4, core pin/nonzero checks, root processing, both initial directional projections, the deferred application field, full raw receive, sequence-one policy, eight-byte binding and publication. The shared-input-clear observation is placed before inspecting the pure core result, using the existing `afterInputs_complete` equality: the actual erasure callback occurs on both core success and failure. It is not a physical erasure claim. Every modeled destructor failure returns failure and reinstalls the aborted token instead of leaving an inaccessible owner blocked.

The model uses the unchanged generated initial-receive plans for every accepted raw target 1 through 51. The one branch uses the same generated first plan; the other branch computes the complete target plan and attempts opening before rejecting registration. Zero and targets beyond the cache bound reject through the same plan interface. Successful registration retains the actual first-step next receive chain, unchanged initial send chain and empty skipped-key cache. Failed registration discards the local candidate kernel and terminally aborts the owner.

The numbered failure selector is conservative control over optional source callbacks. Some failures are unavailable under a stronger total primitive or typed callback contract; allowing them only adds rejecting paths. It cannot force success, inject plaintext into an opening, supply a root, bypass a pin, or reset a consumed owner. The model returns the actual optional application suffix to its API caller. Therefore these correspondences are admission and state properties, not application-plaintext secrecy statements.

The eight proved correspondences cover return-to-attempt causality, sequence-one opening with the exact assigned binding, committed state from the actual prepared/raw plan, failure-to-attempt causality, decapsulation before completed DH, raw plan before opening, DH/temporary-clear before pin rejection, and the exact root/initial/step projection formula for committed chains and empty cache. The separate `ClosedRejected`-to-prior-`Attempt` diagnostic is recorded as unknown. It supplies no symbolic uniqueness, linearity or history theorem. The checked source abort/no-retry statements and finite controls are reported separately.

`preciseLetExpand = false` selects ProVerif's documented direct process-let expansion; it avoids unnecessary term expansion without changing these process branches. `maxHyp = 2` is a sound Horn overapproximation and can lose precision. It is not a session cutoff. The [official ProVerif manual](https://bblanche.gitlabpages.inria.fr/proverif/manual.pdf), sections 6.6 and 6.7, describes these settings. Unknown results are never counted as proofs.

## Concrete controls and validation boundary

The control fixture starts after the actual `InitSent` guard has succeeded. It computes a complete valid response with the existing primitive constructors and runs the original preparation and raw tail once. Except for the long-chain sequence-51 edge, a second finite call consumes the actual returned private phase. The sequence-51 fixture runs the same complete preparation once and checks six outcomes; it does not assert a second-call result. This avoids duplicating a large symbolic chain in trace reconstruction. These are concrete scheduled active-tail traces, not a restriction of the replicated process. The controls use an attacker-owned configured Server identity, so successful paths require no honest-Server origin assertion. The response computation uses the public Beacon keys, the chosen Server/ephemeral secrets and KEM encapsulation coins.

Controls exercise a successful first response, targets 0, 2, 51 and 52, wrong binding, empty suffix, unframed plaintext, unframed record, malformed response, wrong pin and all fifteen optional failure points. The 25 retry fixtures observe first-call success/failure, retry success/failure, actual opening, pin rejection, completed DH and shared-input clearing. The single-call sequence-51 fixture observes the same events except retry outcomes. The finite retry input uses ProVerif’s `precise` annotation so trace reasoning retains the single input occurrence; this changes verification precision, not which state token the process consumes. Explicit parentheses make the reply observer parallel to the complete retry execution, including its successful branch. Three temporary sensitivity variants remove the sequence gate, remove the binding comparison, or retain `InitSent` after failure. Their reconstructed traces show that the controls detect those changes. None modifies maintained production code or a legacy model.

The checker requires exact ordered queries, verdicts, one verification summary and the expected number of reconstructed traces. It normalizes only bound-variable alpha names, preserving repeated-variable equality and distinct-variable relationships. Focused regression tests reject missing, duplicate, altered and incorrectly classified results. Reviewed textual source-order and model-anchor checks detect drift; the unchanged general-plan generator is checked too. Those drift checks are not a Rust parser, serialization implementation proof or applied-pi compiler.

## Remaining composition and permanent contracts

The separate reviewed Server consumed-registration and pending-response gates remain unchanged. Their complete trace/interface composition with this local Beacon process and arbitrary accepted-record schedules is still required for the final F2/F7/F14 closure. This package does not establish cryptographic-session origin, honest accepted-record origin, injective agreement, public-ID secrecy, or later assigned-ID equality. It does not replace any existing sequence-one, registration, post-registration or negative-control gate.

The inherited `crypto.pvl` theory still carries its explicitly documented idealizations: joint Ed25519/X25519 use, free-constructor key/material distinctions, ML-KEM public-key binding beyond ordinary IND-CCA, and the existing CTX/BLAKE2b ROM behavior. This operational package neither proves those assumptions from primitive names nor changes their computational contracts. Abstract frame and response decoding remain codec interfaces. Primitive correctness, native implementations and compiler contracts remain external. No primitive internal proof, serialization implementation proof, saved-state or persistence model is added.
