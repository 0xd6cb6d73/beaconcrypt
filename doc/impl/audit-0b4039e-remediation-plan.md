## 6. Milestone B: design and review request

### Experiment

The experiment samples the Server's Ed25519 identity seed inside the game and gives the adversary only its public key. The target Beacon's identity seed, signed prekey scalar, one-time scalar and ML-KEM key pair are also sampled inside the game, and its Phase 1 is published. The adversary may:

- ask the honest Server to process any Phase 1 bytes, any number of times up to a declared budget, receiving the Phase 2 response (the Server computes DH1 = DH(IK_S, SPK), DH2 = DH(EK, IK), DH3 = DH(EK, SPK), DH4 = DH(EK, OPK), encapsulates to the supplied ML-KEM key, derives the root from the 192-byte input `FF^32 || DH1 || DH2 || DH3 || DH4 || SS`, and seals the sequence-one registration record);
- deliver any Phase 2 bytes to the target Beacon's finish;
- query the idealised functions (below) and the public real HMAC;
- reveal the root or chains of any Server session that is not a partner of the target (partners are Server sessions whose root input equals the target Beacon's).

The winning event is: the target Beacon completes registration, and no Server session accepted the target's validated Phase 1 fields and produced a response equal to the accepted one up to the X25519 functional equivalence of the ephemeral encoding. A second stage extends the event to later records the Beacon accepts, using Milestone C.

Two details of that event matter. First, the documented high-bit flip is not the only X25519 encoding alias. Adding a point of order 2, 4 or 8 also leaves every clamped X25519 output unchanged; for example, replacing the ephemeral u-coordinate by 1/u mod p (adding the order-2 point) gave identical nonzero outputs for 20 of 20 random scalar pairs in an RFC 7748 check run for this plan. libsodium rejects only small-order inputs and all-zero outputs, so production accepts these encodings as well. An event stated only modulo the high bit would therefore be won by a relay adversary that changes nothing a key depends on. The event instead identifies two ephemeral encodings when they give equal outputs under every scalar, which is the premise `SameDhReplies` already used in `L/Model/Pqxdh/ResponseEncodingAlias.lean`. Second, partnering compares the validated Phase 1 fields (identity key, tagged prekey, one-time and ML-KEM keys) rather than raw bytes, because the decoder is a callback and a re-encoded message with the same content would otherwise count as a different Phase 1.

Negative control: the same experiment with a flag that also gives the adversary the Server seed. An explicit adversary then computes a fresh Phase 2 for the target's Phase 1 itself, and the event must be reachable with probability at least one minus the KEM correctness error. This is checked in Lean from the functional correctness laws, so the authentication statement cannot be vacuous.

### Why a new assumption is needed

Only DH1 is unknown to an adversary that chooses its own ephemeral and encapsulates to the Beacon's KEM key itself. The KEM, the existing HB-111 root game and the existing joint weak-EUF game therefore do not help. The adversary also gets Server sessions on Phase 1 bundles containing the Beacon's own prekey (or its X25519 aliases) under its own identity, so the reduction must answer those sessions without the Server key.

### Proposed assumptions (review required before use)

Recommended route R1, standard assumptions in the random-oracle model:

1. Extract random oracle. Zero-salt HKDF-Extract, that is HMAC-SHA-512 with the 64-byte zero key, restricted to 192-byte PQXDH root inputs, is modelled as a programmable classical random oracle that the adversary can query. HKDF-Expand and every other HMAC use stay real and keep the existing HMAC-PRF and Extract games. This is an idealisation, not a consequence of any existing assumption, and it would be stated at every claim site together with the existing BLAKE2b random oracle.
2. Anchored two-sided strong CDH on X25519, stated by the existing generic game `PqxdhJointGapDh.game` (`C/PqxdhJointGapDh.lean:98-107`): given the Server's identity public key and the Beacon's prekey, with decision services answering whether a supplied candidate equals the DH of a chosen peer with one of the two hidden secrets, output their cross DH. The reduction makes no signing request, so it uses only the CDH-with-two-fixed-secret-decision-oracles part of that game. It strengthens Gap-DH (Okamoto and Pointcheval, PKC 2001): the decision services also answer on the quadratic twist under the same clamped scalar, which is plausible because the twist of Curve25519 is secure (Bernstein, PKC 2006), and each service is the strong-DH oracle of Abdalla, Bellare and Rogaway (CT-RSA 2001). It is new as a headline assumption in this repository and would be added to both assumption lists.
3. A functional X25519 class law, not a hardness assumption: if two peer encodings give the same X25519 output under one scalar, they give the same output under every scalar. For clamped X25519 this holds because equal outputs imply that the two points differ by a cofactor-torsion point or by negation, which every clamped scalar maps to the same output. The reduction needs it to decide, without either secret, whether two Server sessions share a root input. It would be added as an explicit primitive contract beside `dh_comm`.

The bound would then be the Gap-DH recovery advantage of an explicit scanning reduction, plus the existing joint weak-EUF, Extract PRG-type, HMAC PRF and CTX INT-CTXT/IND$ advantages for the first-record key, collision terms, and the KEM correctness error.

Alternatives for the reviewer:

- R2: a PRF-ODH-style assumption stated directly on zero-salt HMAC-SHA-512 over `FF^32 || DH(s, V) || m` with the same two anchored oracles, in the standard model. It avoids the random oracle but is stronger and less standard; Brendel, Fischlin, Günther and Janson (CRYPTO 2017) relate such PRF-ODH variants to strong-DH-type assumptions only in the random-oracle model.
- R3: keep the existing related-DH Extract endpoint (`C/PqxdhJointDhExtractFamily.lean`) and prove that its random-oracle version is bounded by the Gap-DH recovery advantage of a scanning reduction, using the existing two-coordinate matcher (`C/PqxdhJointGapDh.lean:252-490`). The endpoint as currently defined keeps HMAC real in both worlds, so it cannot be shown small without an idealisation; R3 is R1 applied to that endpoint, reusing its exact source equalities.

A design exploration of the existing Lean components found further ways to change a response or a Phase 1 without changing anything a key depends on: an ML-KEM ciphertext change that keeps the decapsulated secret (excluding it needs a ciphertext-binding property that the abstract `MlKemScheme` does not state), non-canonical re-encodings accepted by the abstract decoder callbacks, and Ed25519 signature malleability, which weak-EUF does not exclude. The recommended event therefore partners a Beacon completion with a Server session when both derived their root from the same 192-byte root input and bound the same assigned key ID. With that partnering, reveals of non-partner Server sessions need no further restriction and the Beacon's weak-EUF assumption is not needed; partnering on validated Phase 1 content would instead need both the class law and weak-EUF for alias-prekey bundles.

Reusable components identified for the experiment: the Server prefix `PqxdhServerRootPreparation.collect` interpreted by `PqxdhServerStaticDhSource.nativeImpl` (the seed enters only through `staticDh`), the extracted `server_accept` path of `PqxdhServerRelatedRootConsumer.nativeStage`, the response tail `PqxdhServerRegistrationPublication.build`, the Beacon finish `PqxdhBeaconPhase2Publication.nativeOwner` with the selected-prekey interpretation `PqxdhPhase2GapDhSource.nativeImpl`, and the shared BLAKE2b cache `RawCtxSharedPrimitive.SharedState`. The root is currently computed by a monolithic `source.crypto.hkdf` call at three sites (Server, Beacon and the refinement's root law), so route R1 needs one shared lazily sampled Extract table threaded through those sites, a patched public HMAC on 192-byte zero-salt inputs, and a lemma that no other zero-salt Extract call has a 192-byte input. The negative control needs functional laws that the current interfaces do not all state together (scalar-scalar X25519 agreement, nonzero honest DH, codec round trips for the Phase 1 and Phase 2 writers and decoders, and CTX seal/open correctness through the shared cache), and they must be jointly satisfiable, which ties it to the F6 instance work.

Because the experiment's KDF idealisation itself depends on the route the reviewer chooses (R1 and R3 add an Extract random oracle, R2 does not), no Lean experiment is committed before the review. Milestone C proceeds in the meantime.

Open design choices for the reviewer: whether partners are defined by equal root input and key ID (recommended) or by the validated Phase 1 fields, whether the Beacon's identity, one-time and KEM secrets may be revealed (authentication only relies on DH1, so allowing them would give key-compromise-impersonation resistance), and the per-experiment budget on Server sessions.

Review decision (2026-09-29). The reviewer chose route R1: the CTX proofs already work in the random-oracle model, and Signal's PQXDH specification assumes Gap-DH. Key-compromise-impersonation resistance is not wanted, so the experiment does not reveal the Beacon's long-term secrets; the remaining reveal set and the partnering rule must follow what the Rust reference implementation actually stores, exposes and binds, because the claim covers both the protocol and its reference implementation. The Server-session budget stays a parameter of the bound and is evaluated in the documentation at a few tens of sessions. Partnering is by identical root key derivation: a Beacon completion is partnered with a Server session exactly when both derived their root from the same root input, so byte-level variations of Phase 2 that leave the derivation unchanged are not counted as attacks. Whether the Server-assigned key identifier must also match is decided from the Rust source (whether it enters the keys, the associated data or the transcript).

### Owner decisions on the staged design (2026-09-30)

The owner approved the four recommendations of the staged design. The X25519 scalar-spread law and the nonzero-honest-DH law are adopted as functional contracts (`PqxdhServerAuthAssumptions.X25519ScalarSpread`, used for the session-collision term, and `NonzeroHonestDh`, used only by the negative controls). The Server is modelled with two oracles, accept and build, as the public Rust `ProviderServer` trait exposes them (`beaconcrypt/src/server.rs:118-121`), with a pending list, so accept-without-build sessions and builds after the Beacon's finish are covered; a build consumes its pending entry. The Gap-DH assumption is described as a Gap-DH-type assumption whose decision services answer on every 32-byte input X25519 accepts, a strengthening of textbook Gap-DH whose plausibility rests on Signal's Gap-DH assumption and on the twist security of Curve25519 (Bernstein, PKC 2006; RFC 7748).

### Design grounded in the Rust implementation (2026-09-29)

A read-only survey of the reference implementation (`beaconcrypt/src/{beacon,server,ratchet,persistence,ser,cbinds,pybinds}.rs` and `beaconcrypt-core/src`) fixes the experiment as follows. It supersedes the event, partnering and reveal sentences above where they differ.

Keys and partnering. The Beacon's root, both initial chains and every record key are a function of the 192-byte root input alone (`beacon.rs:450-460`, core `pqxdh.rs:380-407`, `pqxdh.rs:46-59`, core `concrete.rs:64-87`). The Server-assigned key identifier enters neither the root input, the ratchet KDF, the associated data (built from the pinned Server identity and the Beacon's own identity, core `pqxdh.rs:552-555`) nor the sequence-one commitment; it is carried as the 8-byte prefix of the sequence-one plaintext, which the Beacon compares with the outer key identifier (`server.rs:463-470`, `beacon.rs:473-484`). A Server session therefore partners the target Beacon exactly when both derived the root from the same root input, and the key identifier is not part of the partner or freshness predicate. Adding it would admit a trivial attack: revealing the root of a same-root-input session with a different key identifier would let the adversary seal its own key identifier for the target.

Winning event. The target Beacon's single finish succeeds and either (W1) no Server session has the target's root input, or (W2) the partner exists and the Beacon's key identifier, payload or associated data differ from what the partner sealed. W2 is bounded by the first-record CTX integrity term and needs no new assumption: the partner seals exactly one sequence-one record (`server.rs:471-477`), and the Beacon requires sequence one and the pinned sender (`beacon.rs:468-470`, `ratchet.rs:510-513`). Ephemeral encodings with equal X25519 replies, KEM ciphertexts with the same shared secret and message re-encodings leave the root input and the sealed fields unchanged and are not attacks.

Reveals. The Server never stores or returns a root, root input, DH value, KEM secret or ephemeral (`server.rs:39-42, 410, 422, 456`). Per session it exposes only the ratchet state after the sequence-one seal (send chain after one step and receive chain), through `encrypt_and_update`, `decrypt_and_update`, their persistence wrappers and the C, Go and Python bindings (`ser.rs:195-213`, `server.rs:504-532`). The experiment therefore offers a state reveal of any Server session, including the partner, returning that post-registration state; it never yields the initial send chain or the sequence-one key. The experiment models the raw Server object. Persistence (snapshots, exports and their digests) is outside the scope of the proof and not accessible to the adversary, and the threat model gives the adversary no access to the running code, so accessors that return secrets are not part of the adversary's interface and need no assumption in the theorem. Giving the Server seed to the adversary is the negative control. No Beacon secret is revealed (no KCI).

Sessions and roles. The Server identity key is long-term and the Server accepts any identity signing any X25519 prekey, including the target's prekey or its aliases (`server.rs:343-353`, `server.rs:375-376`), so the experiment gives the adversary up to Q Server sessions on arbitrary Phase 1 bytes with an adversary-chosen non-empty payload (accept and build combined, as in `cbinds.rs:280-291`); Q is a parameter of the bound, evaluated at a few tens. The Beacon's prekey, one-time key and ML-KEM key are per Beacon object and used for one Phase 1 and one finish attempt (`beacon.rs:306-334, 403-406, 488-491`), so the finish oracle is single-shot. One target Beacon suffices; a multi-Beacon statement follows by a union bound. Replay protection and key-identifier uniqueness are not used. Availability is not covered: anyone can consume the target's registration at the Server or abort the Beacon by delivering garbage first.

Assumption detail. libsodium is the canonical cryptographic library of beaconcrypt and is assumed correct; nothing about it is proved, and the proof does not reason about its point validation (its documentation states that it rejects malformed points). The Gap-DH game used by R1 (`PqxdhJointGapDh.game`) is stated on libsodium's X25519 function as a black box over 32-byte strings; its plausibility is the Gap-DH assumption on Curve25519 that Signal's PQXDH specification makes. The X25519 class law is still needed for the reduction to decide DH1 equality with its own scalar. The only zero-salt HKDF-Extract on a 192-byte input is the root derivation (`pqxdh.rs:50`; the ratchet's Extract calls take 32-byte inputs, `ratchet.rs:89`), so the random oracle can be restricted to 192-byte inputs.
