## How to read this ledger

The classifications follow the survey. **L** is a published Lean statement over extracted definitions and approved abstract interfaces, with an exact `#guard_msgs` guard over `#print axioms` allowing only `propext`, `Classical.choice` and `Quot.sound`; an L join relates the hand-written Computational transcription of an unextracted Rust adapter to the experiment's handler, not the Rust code itself. **RT** (reviewed transcription) means that no Rust-to-Computational declaration check pins the link: the transcription was written and reviewed against the Rust source, and that review is the evidence. **T** is an existing finite check (named) or a proposed one (marked proposed; none of the proposed checks is implemented, by lane decision D-4). **E** is an existing external contract or an approved scope decision of the owner. A row can carry several classifications at once: an L join for the transcription, RT for its match to Rust, T for a Rust-side check that constrains the Rust but does not anchor the Lean, and E for a contract the theorem keeps as a parameter or premise.

Paths: Lean modules are under `beaconcrypt-core/proofs/lean/BeaconcryptCore/Computational/`; `server.rs`, `beacon.rs`, `ratchet.rs`, `pqxdh.rs` and `persistence.rs` are in `beaconcrypt/src/` (the unextracted adapter); "core" files are in `beaconcrypt-core/src/` (extracted by Aeneas). Message numbers (#nnn) are coordination messages; the section "Lane decisions and coordination messages" glosses each one.

### PB-11: the gap check

The survey planned a module `PqxdhBoundaryRecordRoles` for row 11 (exact role arguments, 153-byte associated data, sequence and sender below `2^64` for the sealing and record contexts). It was not built, and the check made for this ledger finds no gap that it would close. Role arguments: the Server prelude and executors (`PqxdhBoundaryRecordPrelude.server_exact`, `PqxdhBoundaryRecordExecution.executeServer_exact`, `PqxdhBoundaryRecordSend.executeServer_exact`) read the sender with the shared complete reader, build the associated data with the extracted `build_associated_data` from the actual Server and peer identities and select that same peer; the Beacon versions (`beacon_exact`, both `executeBeacon_exact`) use the stored associated-data array and the pinned control target, and take the sender from the outer `identity_key_kid` without equating it with the assigned ID; `PqxdhBoundaryRecordSend.executeArguments_exact` keeps the target handle (`SealContext.targetId`) apart from the encoded sender (`SealContext.senderId`).
