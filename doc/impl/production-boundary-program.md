# Adaptive source executor

`PqxdhBoundaryProgram` supplies the generic execution helper for PB-D. It makes no protocol or security conclusion. A later concrete consumer must identify its source command implementation and prove every required command equality using the actual protocol operations.

A `Step` receives the original typed query and a state, then returns a probabilistic computation containing a `RustM` reply and the complete poststate. The state sits outside `RustM`, so effects already performed before a failure or divergence tag are retained. `execute` traverses the original adaptive `OracleComp` client structurally. It sends a successful reply into that client's actual continuation. Failure and divergence stop immediately with their returned poststate; they do not manufacture a reply, restart the source command, or execute a later client command. Ordinary optional rejection remains an ordinary typed reply when the command returns it successfully.

`execute_pure` and `execute_query` expose the exact execution equations. `execute_bind` proves that an arbitrary prefix and continuation have the same complete execution as sequential execution with these Rust outcomes. `execute_fail` and `execute_div` separately establish immediate propagation of the exact poststate. The divergence result is the existing extracted semantic tag; this module does not prove runtime termination or supply a distribution conditioned on termination.

`execute_congr` composes pointwise equal command computations, including all reply and state fields. `liftStep` wraps only the actual native reply in `.ok` and leaves the native computation and state untouched. Structural induction proves `execute_lift`: the entire adaptive lifted execution equals the original `simulateQ` execution with the same full final result and state. This includes whatever counters, caches or private reveal logs the concrete state actually contains; the generic helper does not select or erase them.

`source_exact` applies those results when the consumer supplies a proved operational equality for every query and state. `source_continuation` then retains an arbitrary probabilistic continuation of the complete Rust result and state. The operational premise is an explicit composition input to be discharged by the concrete protocol proof. It is not a primitive assumption, authentication premise, origin premise, or proof that the whole BeaconCrypt source matches CE. In particular, a chosen projection of protocol state does not establish the required equality for an omitted state component.

All original primitive work remains inside each actual step. The helper adds pure control flow and result wrapping, with no new oracle call. The equality is at `OracleComp` syntax, not only probability or final Boolean level; no ambient work is declared free and no extra query bound is assumed. Concrete source/reduction budgets and the preserved complete classical/later game values belong to the subsequent PB-D consumers.

The module imports only the generic Aeneas/CoreModels Rust outcome and VCVio execution interfaces. It changes no Rust implementation, primitive contract, compiler/runtime contract or scope decision. The existing nonadaptive `BoundaryExecution` refinement operates on fixed action lists and functional KDF correctness; it does not provide this adaptive Rust-result executor. All thirteen theorems (the nine above and the four adapter theorems below) have exact guarded axiom checks; the PB statement and direct-reference scans, each with a deliberately failing control, are recorded in the receipt. No new Rust extraction, source-fidelity test, mutation run or full-matrix result is claimed here.

## Result-returning executors (decision D-3)

The published record and finish executors (`PqxdhBoundaryRecordSend.executeServerSend`, `executeBeaconSend`, `PqxdhBoundaryRecordExecution.executeServerRaw`, `executeBeaconRaw`, `PqxdhBoundaryRegistrationFinish.executeNativeFinish`) return `ProbComp (RustM (reply × state))`: their poststate sits inside the Rust result, so a failure carries no poststate. `outcome entry` turns such a result into the step form: `ok (reply, state)` becomes `(ok reply, state)`, and `fail` or `div` is reported with the entry state, the only state available. `ofResult` applies this to a whole executor family. The placeholder entry state is never observed for these executors: each of them is published as `(fun result => ok result) <$>` of the CE native command, and for such normal-returning executors `outcome_ok` and `ofResult_ok` show that the adapter is exactly `liftStep` of the native command, while `outcome_normal` and `ofResult_normal` show that every supported adapted outcome is `ok` with a supported native reply and poststate. A concrete PB-D consumer therefore discharges the `operational` premise of `source_exact` for these commands from the published equalities, with no reachability invariant and no assumption about failures. If a reviewer prefers no placeholder at all, the fallback is an executor variant that stops without a poststate; it is not needed for the published executors.
