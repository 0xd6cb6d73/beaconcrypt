# Phase 2 X25519 response-encoding counterexample

The production protocol accepts a first-sequence registration response whose decoded ephemeral public-key bytes differ from the server-issued response. An attacker flips the high bit of the final byte of `ephemeralKey`, keeps every other decoded Phase 2 field unchanged, and delivers the modified response. The native X25519 interface computes the same three ephemeral-dependent DH outputs. The same root, registration frame, binding, and ratchet state therefore authenticate successfully.

This refutes the historical exact decoded-response origin property even at sequence one. It also refutes the two historical registration-session and accepted-record correspondences, because their session argument retains the exact decoded ephemeral bytes. HB-89 preserves all three original query bodies as negative controls and gives the maintained authentication statements a separate projection. The original authenticated record is replayed unchanged in this witness; neither plaintext secrecy nor origin of those record bytes alone is disproved. This is separate from the already known later-record assigned-ID relabel behavior.

## Native evidence

`beaconcrypt/tests/registration_response_alias.rs` runs 16 fresh, ordinary server/beacon sessions. It obtains an actual server response, changes only `ephemeralKey[31] ^= 0x80`, serializes and decodes the candidate again, and checks that the server identity, KEM ciphertext, complete application frame, and assigned ID remain identical. It checks that the changed ephemeral field is different and the nested frame has sequence one. The real `Beacon::finish_registration` returns the original application plaintext, its receive sequence becomes one, and subsequent application traffic succeeds in both directions.

The source boundary is explicit. `beaconcrypt/src/beacon.rs` parses `response.get_ephemeral_key()` through the native public-key wrapper and supplies its bytes to the DH2, DH3 and DH4 calls. `beaconcrypt-core/src/pqxdh.rs` builds the root input from those DH outputs and the KEM shared secret. The raw ephemeral encoding is not added separately to that root input or the record associated data. The native fixture exercises decoding and protocol behavior directly; no primitive implementation proof is attempted.

The published X25519 input contract requires this final-byte bit to be masked. The corresponding output encoding clears it, so the native witness changes a canonical server output into a distinct accepted encoding of the same valid input coordinate. Both encodings denote the honest generated point; ordinary invalid-point and all-zero-result rejection checks do not distinguish them. This is specified behavior of a correct primitive with the required checks, not an invalid-point attack or primitive implementation defect. [RFC 7748, section 5](https://www.rfc-editor.org/rfc/rfc7748.html#section-5).

The attacker observes one genuine response, performs one public bit flip, and delivers one candidate. It makes no identity, KEM, root, chain or skipped-key reveal and no extra primitive-oracle query. No session guessing or successful forgery of a signature, KEM secret, AEAD record or CTX commitment is needed. The witness succeeds whenever the underlying honest registration succeeds under the stated functional alias; no negligible collision event is used.

Run the native witness with `cargo test --locked -p beaconcrypt --test registration_response_alias --all-features`.

## Exact symbolic statements

`proofs/pro-verif/exact-registration-origin-queries.pvl` preserves the original sequence-one query `inj-event(BeaconCommitted(transcript)) ==> inj-event(ServerCommitted(transcript))`. In `environment.pvl`, the 18-field free `establishment_transcript` retains both the server ephemeral field and complete response. The beacon constructs it from the received fields; the server constructs it from the issued fields. Their terms differ under the public encoding alias.

`environment.pvl` also retains `establishment_session`, whose 14-field projection still retains `mr_ephemeral`. Consequently the two queries from `BeaconRegistrationCompleted` to `ServerRegistrationSessionCommitted` and `RegistrationRecordSent` also demand the unavailable raw ephemeral equality. Quotienting public-key encodings by their DH behavior would change these stated event arguments and the advertised property; it is not an existing representation map.

The new `phase2-x25519-alias-control.pv` invokes one unchanged `HonestBeacon`, one unchanged `Server`, and the unchanged private-state handler. This finite execution is a reachable instance of the replicated baseline. The checker extracts the three exact registration correspondence queries from the saved original query file, whose bodies remain unchanged. It separately extracts the three corrected authentication queries from the maintained `queries.pvl`. It runs the identical process and queries with the original cryptographic theory and then with only the X25519 section replaced by `phase2-x25519-alias-theory.pvl`.

The additional interface exposes a public high-bit flip between two distinct encodings and gives them identical DH evaluation rules. It preserves the correlated identity conversion, all KEM/signature/KDF/AEAD/CTX equations, and all protocol role code. The canonical run proves all three correspondences. The alias run refutes all three and reconstructs a concrete trace for each. The checker rejects missing, duplicated or reordered results, reversed polarity, missing reconstructed traces, and traces without the public alias operation. It does not reinterpret `cannot be proved` as a counterexample. HB-89 adds canonical and alias runs of the three corrected projected queries; all six results must be TRUE. Five raw-result negative controls and six projected-result negative controls reject missing, extra, reordered, false or misidentified evidence.

Run `python3 beaconcrypt-core/proofs/pro-verif/check-phase2-x25519-alias.py --output-dir /tmp/beaconcrypt-phase2-alias-checked` inside the locked proof environment. The additive Make and CI scenario is `phase2-x25519-alias`; all existing scenarios remain enabled.

## Checked protocol congruence

`Model/Pqxdh/ResponseEncodingAlias.lean` defines replacement of exactly the decoded ephemeral field. `SameDhReplies` states the ordinary functional interface equality for the two encodings; it makes no authentication or secrecy assertion. `beaconDHs_eq` preserves the complete ordered four-DH tuple. `beaconFinish_eq` then proves equality of the full modeled registration result and retained state on every branch, including rejection. `distinct_response_same_outcome` combines that equality with the explicit inequality of the two decoded encodings.

These theorems are protocol-wiring results conditional on the stated functional alias. The native test independently checks the particular high-bit alias in production. The two guarded dependency reports contain only `propext` and `Quot.sound`. No custom axiom, security assumption equivalent to authentication, or proof of X25519 internals is introduced.

## Consequence for the maintained model

The bridge cannot establish the three historical exact-byte correspondences for unchanged production. This is an overstrong representation claim, not evidence that PQXDH requires an additional signature on its initial message or that peer authentication or secrecy fails. The underlying point, root, authenticated record and resulting state agree in this witness. Following the clarified intended scope, production remains unchanged and the computational bridge continues toward session and record agreement with an accurate representation relation. The original exact-byte queries remain useful negative regression controls. The [HB-89 event projection](registration-event-projection.md) retains the pinned identity, authenticated Phase-1 fields, actual root, associated data and exact authenticated-record values without assuming injectivity of DH from its ordinary security contract. Replay and freshness still need the complete computational composition and schedule argument. Component proofs remain useful within their reviewed scopes; the remaining computational composition and source-adapter obligations are still required.
