# Opaque KEM value in the actual Server continuation

Thirty-one statements connect a private KEM marker to the actual resumed Server source operations. The executable continuation carries the marker and actual remaining source fields. Selected KEM bytes are materialized only in the mathematical source comparison and the private root interpreter. The result preserves the complete native state, including cache and instrumentation, and separately identifies the real fixed-HKDF source callback. It is an operational compiler result, not an Extract/HMAC security hop or a completed authenticated-root theorem.

`KemOpaqueSuffix.after_replace` proves that the literal post-encapsulation collector issues the same public conversion, private conversion and four DH requests for every retained KEM word, including every optional rejection and callback continuation. The only changed field is the final `Inputs.kem`. `Prepared` retains the original verified record, ephemeral scalar/public key, ciphertext, converted identity and four DH results while replacing that byte field by the existing `Phase2DecapsulationRouting.Shared` marker. Its `challenge` case contains no KEM bytes; `known` retains an ordinary already-available secret. `materialize_erase` is the exact field reconstruction. `program_native` runs the actual suffix with a fixed local dummy, erases that unused dummy, and recovers the original complete program after interpreting the marker. `compiled_native` proves the same equality through the existing initialized compiler, retaining the whole consumed-registration poststate. It asserts no probabilistic independence or entropy property.

`KemOpaqueCore.cleared_shape` derives the actual extracted acceptance result: the four DH values determine admission, and a rejected nonzero test produces the original `InvalidDhOutput`. On success the complete control state and cleared pending token remain. The KEM field is not part of this test. `cleared_replace` therefore proves that changing only that field preserves the entire cleared acceptance result. `accept_native` identifies the executable marker branch with the literal extracted branch for every candidate, and `accepted_original` recovers the actual original token before clearing. These facts do not replace the production branch test with a protocol assumption.

`KemOpaqueClient.accepted_bytes` identifies the interpreter's bytes with the actual accepted `FF32 || DH1 || DH2 || DH3 || DH4 || KEM` input. The marker-only `client` executes source erasure, acceptance, root processing, input erasure and consumed-ID insertion in their original order and returns the full cleared pending token and root. Only the private root request carries the internal prepared record; it is not a network or adversary-visible capability. `rom_root_native` and `client_native` recover the complete existing initialized native computation. Its restricted Extract-ROM cache, original derivation/HMAC observations and session touch are retained. Logical erasure remains the existing experiment's no-op callback; no physical erasure property is inferred.

`KemOpaqueReal.root_source` and `client_source` interpret the same executable client with the existing actual fixed-HKDF source consumer. The exact root, primitive history/cache and arbitrary original auxiliary callback effects are retained. This interpretation is distinct from the current initialized scheduler's restricted zero-salt/192-byte Extract-ROM backend. These two functional equalities do not relate the real and ROM distributions, change public HMAC behavior, or charge a cryptographic advantage. The native root implementation and the fixed-HKDF implementation remain their explicit existing contracts.

`KemOpaqueTail.forward_run` preserves the complete marker-client execution under the larger bookkeeping interface. `tail_native` connects it to the actual original `ServerAccept.tail`: every attempt allocates its session index and installs the actual consumed set, rejected attempts retain that allocation, and only a successful root/consume return publishes the exact pending token. Bookkeeping requests return only unit. The root implementation's full private poststate remains inside its interpreter while the publication updates the original pending slot.

`KemOpaqueResume.prefix_run` and `tail_run` preserve both halves under one combined interface when the prefix interpreter's target is the native game. `lift_prefix`, `lift_tail` and `resume_lift` prove the join in general. The outer monad is arbitrary as long as the native game maps into it by a monad morphism, and the prefix interpreter is any interpreter of the exposed interface in that monad. `resume_lift` states that the resumed opaque execution equals the original saved suffix, with the KEM candidate materialized, followed by the original native tail carried over by the morphism. The suffix's optional failures and consumed state, every effect of the supplied prefix interpreter and the complete native continuation through publication stay in order. `resume_native` is the special case where the outer monad is the native game and the morphism is the identity; its statement is unchanged from the first version, but on its own it could not be applied to the actual service or reduction interpreters, whose monads are not the native game.

Five instantiations connect the general statement to the monads that actually occur. `resume_client` uses the exposed encapsulation-cut client monad of `KemEncapsulation.accept`. In it, prefix requests are forwarded with the native state unchanged (`forward_client`), and the native tail is embedded by the same `KemEncapsulation.lift` and `OpenBackend.native` composition that `accept` uses. `resume_actual` interprets the exposed interface with the real encapsulator `KemEncapsulation.actual` and identifies the suffix with the original open-backend raw-prefix callback. `resume_service` uses the actual accept state `Pool × NativeState` of `ServerAccept.run`: the real encapsulator and the stateful identity/KEM services `LiveKemBirth.impl` act on the private component, and the native tail acts on the native component through `onNative`. `resume_reply` takes the continuation saved by `KemSourceSuffix.suffix_cut`, resumes it with the ordinary challenge reply `KemResume.reply`, and follows it with the accept tail and arbitrary later source work. The result is the executable resumption with the challenge marker, which has no candidate argument, run under the private client interpreter; the candidate appears only in that interpreter. `resume_post` carries the `resume_reply` equality through the exact interpreter chain that `KemResume.post` applies: the real encapsulator, then the dynamic joint router into the ordinary CCA oracle interface. It follows from `resume_reply` by congruence. It bounds no advantage and says nothing about the KEM game's distribution.

None of these statements needs a successful suffix, honest candidate, key-byte injectivity, independent key coordinates or generator-order interchange premise. `resume_reply` and `resume_post` are stated for a continuation of the accept form that `KemEncapsulation.accept` produces after its preparation. Showing that the scan of the complete source program reaches a continuation of exactly that form is the raw-accept cut join, which is not proved here. The supplied initial state and private interpreter are still internal mathematical values; these theorems do not make that state suitable public context for the Extract game.

`KemOpaqueCosts.client_root` bounds the private root requests by one for every typed reply and every rejection branch. `client_calls` bounds the internal client requests by four: erase-shared, root, erase-input and consume. `tail_calls` adds at most two bookkeeping requests, for a total of six. These are compiler-interface request bounds, not six primitive calls. `client_uniform` retains the existing possible 64-byte uniform draw of the current restricted-ROM root interpreter. The source suffix's earlier primitive and uniform work stays in the executable program. This cohort does not re-derive the existing `server_prefix_uniform` and `accept_uniform` charges for `compiled` or `resume`, and it does not carry them over to those programs; doing so remains a separate obligation. This cohort adds no primitive security assumption, target-selection loss or claim that native or ambient work is free.

The marker uses the existing challenge/known representation so repeated processing of the challenge ciphertext is not rejected by this Server continuation. The actual dynamic Beacon finish compiler still needs its separate connection to the existing opaque decapsulation/root routing, with all alternate DH coordinates and repeated requests retained. No new schedule or freshness restriction is imposed here. The existing one-root `SecretInputKdf` endpoint gives its entire context to the distinguisher; the private history, saved source closure, candidate and target input cannot be passed into that context as if they were harmless. The exact joint sampler, publicly permitted context, private-state erasure/simulation, repeated related Extract calls, complete reveal/freshness selection and final real-HKDF hybrid remain to be proved. The existing correlated DH Extract family has a known KEM field and cannot silently be reused as a hidden-KEM endpoint.

The seven modules are `PqxdhRegistrationJointKemOpaqueSuffix` (four statements), `KemOpaqueCore` (four), `KemOpaqueClient` (three), `KemOpaqueReal` (two), `KemOpaqueTail` (two), `KemOpaqueResume` (twelve) and `KemOpaqueCosts` (four), where the shortened names retain the same `PqxdhRegistrationJoint` prefix.
