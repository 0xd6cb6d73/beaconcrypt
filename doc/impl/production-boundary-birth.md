# PB-01: generated Server birth and admitted Beacon creation

`PqxdhBoundaryBirth` gives the source order of the two constructors of the common deployment experiment: the generated-only Server birth and the Beacon creation command. Its eight guarded statements are exact operational equalities and query bills. They add no security game, primitive contract or cryptographic conclusion.

Server birth. The production reference is `Server::try_new` (`beaconcrypt/src/server.rs:154-168`) with no supplied seed: `ensure_init` first, then the generated Ed25519 identity key pair, then the extracted control initialization `ServerState::new`. `serverBirth` writes this order down: runtime initialization runs on the runtime state, a failed initialization returns `none` with the runtime it returned and makes no identity draw, and a successful one draws the identity seed and builds the initialized Server. `server_source` proves that CE's constructor `PqxdhLiveServerConstruction.construct … none` (the `supplied = none` instance used by the CE-12 games) is exactly this execution, and `server_continuation` carries it through every continuation of the result and the returned runtime, so the effects of a failed initialization are kept. `server_bills` transfers the existing bill `PqxdhLiveServerConstruction.construct_uniform`: the declared initialization bill `qInit` on every attempt plus the 32 uniform byte draws of the seed, under the same `initBound` premise form that the CE-12 headlines carry.

Beacon creation. The production reference is `Beacon::try_new` (`beaconcrypt/src/beacon.rs:65-82`): `ensure_init`, the width parse of the pinned Server identity key (`PublicKey::from_bytes`, `beacon.rs:68`), then the Ed25519 identity key pair, the X25519 prekey pair and the ML-KEM-768 key pair, in that order. The common experiment does not re-run runtime initialization at creation (its deviation D1, which stays an approved model deviation, E), so `beaconCreate` starts with the 32-byte pin parse: a wrong width returns `none` with no draw and the complete deployment state unchanged; otherwise it draws the identity seed, the prekey scalar and the ML-KEM key pair in that order and appends the fresh owner at the next handle, keeping every other field of the deployment state (Server, pending tokens, caches, counters, produced frames and the other owners). `beaconCreate_native` proves that an admitted pin runs exactly the published post-admission constructor `PqxdhRegistrationSchedule.create` on the registration state, `create_source` that the CE `create` command equals `beaconCreate` for every pin, key ID and deployment state, and `create_continuation` that this survives every continuation. `create_rejects` restates the wrong-width rejection on the source side. `create_bills` transfers `PqxdhRegistrationSchedule.create_uniform`: two 32-byte draws plus the declared ML-KEM generation and base-interpreter bill, and nothing for a rejected pin.

What stays outside. The public Rust constructors remain reviewed transcription (RT), including the evaluation order of the struct fields of `Beacon::try_new`. Generation failures of the native key generators are not modeled (the constructors' `KeyGenError` paths after `ensure_init`), and once-only runtime initialization is the existing approved scope (D1, and the proposed but not implemented PB-D1 check of the survey). The query bills count oracle calls only; deterministic validation, conversion and bookkeeping remain actual local work and are not declared free.
