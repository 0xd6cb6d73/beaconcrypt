# Deployment and primitive implementation boundary

This document records the concrete dependency and execution contracts reviewed for the security-gap remediation. These are implementation requirements, not a proof that the named primitives compose into protocol security; see [formal verification analysis](formal-verification-analysis.md).

## Reviewed dependency configuration

The adapter pins `libsodium-rs = "=0.2.4"`. The repository lockfile resolves `libsodium-sys-stable 1.24.0`, `zeroize 1.9.0`, and Cap'n Proto Rust crates 0.26. Use `cargo build --locked` and preserve the resolved dependency graph when reproducing this review. A downstream Cargo consumer has its own lockfile and must check that graph; the adapter's version requirement alone does not pin every transitive dependency.

The reviewed native source is the `LATEST.tar.gz` archive shipped inside `libsodium-sys-stable 1.24.0`, whose configure script declares libsodium 1.0.22 and whose SHA-256 is `b20a92e7ec25b285eafa349d721a5bb27e3a8ba94c0816630a127883f1d1b3ab`. The archive name does not imply a network fetch: the default build verifies the bundled archive. Enabling `fetch-latest`, selecting `SODIUM_LIB_DIR` or `SODIUM_USE_PKG_CONFIG`, or substituting a shared native library changes the reviewed implementation boundary. Audit and retest that selection, including symbol availability for ML-KEM-768 and HKDF-SHA-512. The wrapper's `version::VERSION_STRING` is a fallback constant and is not evidence of the linked version; `version::version_string()` calls the native runtime query.

This repository declares Rust 1.96 and uses Cap'n Proto's schema compiler at build time. The verification shell separately pins the Hax-compatible extraction compiler and proof tools. Tests of the adapter and extraction checks use those distinct toolchains for distinct purposes. The Windows GNU compatibility functions in `beaconcrypt/src/lib.rs`, system entropy backend, C toolchain and native link selection need platform-specific review; Linux validation does not certify those platforms.

## Primitive-call contracts

| Call family | Contract used by production | What remains outside the formal core |
| --- | --- | --- |
| Ed25519 and X25519 | Exact-width keys; signatures cover the tagged bytes selected by core requests; invalid conversions and DH failures reject the operation. | Signature security in the joint signing/converted-DH interface, implementation correctness and leakage. Separate Ed25519 EUF-CMA and X25519 assumptions do not by themselves justify shared-secret-key use. |
| ML-KEM-768 | Matching encapsulation and decapsulation agree; ciphertext/key sizes match the wrapper API. | IND-CCA instantiation and the additional cross-public-key binding assumption used by the symbolic theory. Invalid-ciphertext implicit rejection must not be confused with an authenticity decision. |
| HKDF-SHA-512 | No salt, exact production domain bytes, deterministic common output stream, initial 64-byte split and 76-byte record split. | Extraction for the actual secret-input distribution and side information, expand pseudorandomness, evolving-key composition and output collision losses. Public deterministic HKDF evaluation cannot be replaced globally by an indistinguishable random table. |
| ChaCha20-Poly1305 IETF | 32-byte key, 12-byte nonce, 16-byte retained tag; opening authenticates the exact AD/ciphertext and returns recovered plaintext or failure. | Primitive security with the required nonce discipline and its lift from one uniform key to actual correlated ratchet keys. |
| BLAKE2b-512 CTX and comparison | The full 64-byte commitment binds the core-built transcript; `memcmp` compares equal-length commitments. | Concrete hash assumptions, random-oracle idealizations and whole-protocol timing. No demonstrated timing attack is inferred from data-dependent protocol branches. |

[Libsodium's conversion documentation](https://doc.libsodium.org/advanced/ed25519-curve25519) explains the shared Ed25519/X25519 seed conversion and recommends separate signing and encryption keys where possible. Changing this protocol to independent identity keys would require a versioned signed-bundle/wire migration; the current conversion API alone is not a composition proof.

## Entropy and construction

`Beacon::try_new` and `Server::try_new` return `KeyGenError` for reported initialization, input-length and key-generation errors. Existing Rust `new` methods remain compatibility wrappers that panic on those errors. Persistent-server creation uses the fallible path; C returns null and Python raises `ValueError` for malformed constructor inputs instead of reaching these panicking wrappers. Go preserves its error-returning constructors.

The guarantee is deliberately limited to reported errors. `libsodium-rs 0.2.4` contains a load-time `ctor` initializer that panics if initialization fails, before beaconcrypt can return a result. The native RNG does not offer a recoverable error result for every failure, allocation can terminate the process, and release builds use `panic = "abort"`. No `catch_unwind` wrapper could soundly promise recovery from these failures. Removing the upstream load-time panic needs a reviewed dependency change; it is not solved by our constructor refactoring.

Fresh identity, prekey, one-time and KEM keys and snapshot lineages require an initialized operating-system CSPRNG. A deterministic server seed must contain 32 secret uniformly generated bytes, not a password or predictable identifier. Tests with fixed seeds are reproducibility fixtures, not deployment examples of entropy generation. Initialization must complete after the OS RNG is ready; repeated VM/container snapshots must not duplicate live cryptographic state or RNG state. The default RNG contract and the explicit VM snapshot caution are documented by [libsodium](https://doc.libsodium.org/generating_random_data); custom RNG selection changes that contract. The native initialization return values and startup behavior are documented in [libsodium usage](https://doc.libsodium.org/doc/usage).

## State ownership, persistence and erasure

`ServerSnapshot::validate_successor` supplies a reusable envelope check for the expected lineage, exact next generation and complete parent digest. The binding store uses it before replacing state. A store must perform this validation and comparison against its protected current head within a linearizable durable transaction; checking a supplied head cannot establish that it is current. A malicious store can satisfy every public byte check while replaying an old authentic history. Integrity requires protected storage or authenticated encryption/MAC with a protected key, rollback resistance requires an authoritative monotone head outside the rollback domain, and linearizability requires actual coordination. These are distinct obligations. See [persistence](persistence.md) for output-before-commit fencing and restore activation.

The C buffer destructor now uses `zeroize` to wipe the complete allocation capacity before freeing it. Go's temporary C input allocation is wiped with volatile stores before `free`; Rust-returned C buffers use the same native destructor. These changes reduce residual foreign allocations for plaintext, seeds and snapshots. They do not erase Go/Python-managed copies, previous reallocations, application logs, crash dumps, swapped pages, snapshots or secrets copied elsewhere. The Rust example's file store is a single-process demonstration, not a durable multi-owner rollback-resistant store.

The symmetric ratchet has no post-compromise recovery from a disclosed current chain. Retained skipped keys, snapshots, copied secrets and application plaintext limit past-message confidentiality. The 269 extracted-core normal-return certificates do not establish whole-application memory or runtime safety. Finally, validating a self-signed beacon identifies the signer; recipient authorization and task routing remain application policy.
