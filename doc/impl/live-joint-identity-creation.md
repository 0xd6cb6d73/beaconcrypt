# Live constructor through the joint identity service

`PqxdhLiveJointBirth` connects the existing normal-return Beacon constructor to the ordinary joint Ed25519/X25519 identity service. Its thirteen guarded statements add no security assumption or advantage loss. The production reference is `Beacon::try_new` in `beaconcrypt/src/beacon.rs`: initialization and pinned-key parsing precede identity generation, prekey generation and ML-KEM key generation in that order. No one-time pair is generated by the constructor.

The executable constructor asks the existing joint service to create one identity. It receives only a stable index and the actual correlated public identity, then runs the original prekey and KEM samplers locally. It never receives the identity seed. Its result is a private owner-construction value containing the actual prekey and KEM pair; it is not a public adversary API reply. The external owner interpreter must install this value and expose only the production public outputs. The internal public-identity reply is not an extra network message or a new opportunity for network scheduling inside an atomic constructor call.

`joint_complete` uses the existing lazy joint service directly. `coins_complete` retains every prior joint seed and observation while interpreting each local random query; private generator coins are not appended as public joint-service observations. `afterIdentity_complete` preserves both local generators in their original order and the entire preceding service state. `create_complete` equates the evaluated constructor with the original native constructor followed by the exact public-handle projection, retaining the newly generated seed only inside the joint interpreter. `create_continuation` extends that equation to an arbitrary complete evaluated continuation. This is not merely equality of a keypair marginal distribution, and no generator is moved across a later source action.

`created_seed` proves that the returned index names precisely the newly generated private seed in the retained service state. `created_prior` preserves every earlier index and seed. `fresh_source` installs the public identity handle in exactly the original native Fresh role while retaining its complete prekey/KEM payload, pin, identity identifier and instrumentation. These statements establish the local constructor relation; they do not assume or claim the entire dynamically allocated protocol schedule relation.

`coins_class` preserves the exact class of every local sampling request. `coins_bills` derives zero joint-service requests and the original local uniform allowance. `afterIdentity_bills` combines both primitive callbacks. `create_bills` charges one joint creation request and at most `qPrekey + qKeygen` local uniform queries, covering even an unavailable service reply. In the actual lazy service that reply cannot fail. `create_uniform` additionally charges its 32-byte seed sampler, giving `32 + qPrekey + qKeygen` uniform byte queries for the full evaluated constructor. The prekey and KEM sampling bounds apply to their complete evaluated callbacks, including ambient randomness. Their base-oracle queries, deterministic work and implementation costs still require the callbacks' ordinary resource contracts; the uniform allowance does not assign those costs zero.

The source correspondence uses the same normal-return, validated-binding constructor domain as `PqxdhLiveBeaconBirth`. Native initialization, parsing and correct primitive generation remain functional contracts; this is no availability or RNG-failure theorem. Interpreting the other owner operations, coupling dynamic allocation to target selection, routing compromises and substituting a selected KEM challenger remain consuming obligations. No primitive algorithm, new joint-security guarantee, snapshot or persistence behavior is proved.
