# Record origin: installed handles and source directions

`PqxdhRecordFactsOriginHandles` supplies structural facts needed to join ideal CTX acceptance to a counterpart handle. It reads the actual stored Server peer or established Beacon owner. It introduces no cryptographic contract, probability bound, oracle, or additional protocol capability.

`storedAhead_origin`, `handleSlot_step`, and `ownsLabel_step` show that the protocol history's actual forward transition preserves an already installed hidden slot at the same handle. `OwnsLabel` also records that a label's direction is the physical handle's sending direction: false for Server peers and true for Beacon owners. It does not claim that an arbitrary label is owned; the source send proof must establish that witness at production time. The transition premise is the existing `ProtocolHistory.Step`, whose native handler preservation is proved upstream. These lemmas transport its consequences to the ideal view; they do not add a global invariant premise or permit snapshot restoration.

`handleKernel` selects the actual stored kernel, returning none for absent peers and inactive owners. `handleKernel_origin` and `handleKernel_slot` identify its hidden installation tag with the ideal view's public handle-to-slot map. `handleKernel_oriented` obtains the existing source role and coordinate certificate from `ProtocolHistory.Safe`, and `handleRole_direction` computes the same physical direction as `handleDirection`. Caller-known kernels remain caller-known and never acquire a hidden slot through these statements.

`opening_oriented` uses the actual source material getter, the existing `EffectAttributed` certificate for the complete pending opening, and the stored kernel's orientation. It yields the exact source sequence, the installed slot, and the opposite physical sending direction for the returned material label. Both cached and future paths are covered by the existing `opening_attributed` getter theorem. `handle_opening_oriented` also joins the concrete control lookup, so its result names the receiving handle's slot. The [recursive receive proof](record-facts-origin-receive.md) carries `EffectAttributed` through the actual begin/resume callbacks; this module does not postulate that every arbitrary pending opening is attributed.

`counterpart_of_opposite` combines a source sender's `OwnsLabel` witness and the receiver's opposite direction into `Ideal.Counterpart`. This predicate checks the opposite sender's installed slot; the receiver's own slot is separately established by `handle_opening_oriented`. No equality of assigned IDs or inference from equal key bytes is used.

All ten theorems have exact axiom guards. Nine use only `propext`, `Classical.choice`, and `Quot.sound`; the direction computation uses no axioms. The direct Lean 4.34 check passes with no diagnostics. These operational lemmas add no random samples or query calls, hence no new query cost or selection loss. They do not complete `OriginStatement`: the companion [global invariant](record-facts-origin-invariant.md) now establishes dictionary attribution to produced frames and the receive module establishes the recursive receive join, while the accepted-transcript/publication joins and commitment-guessing accounting remain open. No Rust or ProVerif file changes.
