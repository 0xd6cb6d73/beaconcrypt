# Free-schedule ProVerif records, Server to Beacon (fs-records-s2b)

This guide records stage P2 of the staged ProVerif plan for audit findings F2, F13 and F11: the `fs-records-s2b` scenario, in which Server objects register Beacons and then send them records (taskings) under an attacker-chosen schedule, its targets, controls and witnesses, its result checker and the transcript-fidelity and inventory gates that pin it. It follows the [fs-registration guide](proverif-free-schedule-registration.md) of stage P1, whose vocabulary, serial verification group, checker and declaration policy it extends. The plain-English explanation of every result is in [What beaconcrypt's formal verification proves](../formal-verification-analysis.md#free-schedule-proverif-records-server-to-beacon-fs-records-s2b), and the meaning of every fs event as a Rust API outcome, with what each claim says about Rust, is in [the fs event-meaning reference](../proverif-fs-event-meaning.md).

Every fs result is a symbolic result (Dolev-Yao attacker, free constructors, ideal hash, KDF and AEAD) for a bounded process. None of them is a computational bound. Cap'n Proto is out of scope: messages are abstract byte strings that each side can decode. libsodium is a black-box functional contract. Persistence is out of scope, and the proof Server has perfect key management and no backup or restore (owner decision OD2). No axiom, restriction, lemma or proof-only process is used. Reading the results as statements about the Rust API rests on the paper arguments listed under [Pending paper arguments](#pending-paper-arguments); until they are written and reviewed, each result is cited as a symbolic result for the fs process, which models the Rust interface under these pending abstraction steps.

## Basis and decisions

The Rust basis is branch `codex/full-proof-composition` at `9e588c6`, whose Rust sources are identical to `959cdab` (the basis of the plan and of the P0 spike) and to `533901f` (the P1 basis): `git diff 959cdab 9e588c6 -- beaconcrypt/src beaconcrypt-core/src` is empty. The Rust code is authoritative: where the model and Rust differ, the model follows Rust. The decisions applied here are those of gate G0, the owner and the orchestrator for P2:

- OD1: bounded results are the ProVerif deliverable. OD2: one live Server state per identity key; the proof Server is idealised. OD7: at most 1800 s per target and a 10 GiB address space per run, the fs group serial and alone on the machine, about 3 h for the whole group. OD11: the serial run is the verification record.
- Theory `crypto.pvl`, the self-contained `fs-common.pvl` and the single allowlisted selection heuristic nx, all as in P1.
- The "v2" early-fresh form of the Server ephemeral secret and KEM coins, accepted with the written justification of [step 2](#model-steps-and-their-justifications).
- Bounds (K_s, K_r, T_max) = (2, 3, 3) with the far branch, and one bundle per Server object (K_reg = 1); witnesses and controls at the smallest K_r that exhibits them.
- C5 witnesses written as correspondences that are expected to be FALSE, because ProVerif 2.05 rejects time inequalities in reachability queries (G0 section 7).
- `FsReceiveRejected` emitted only in the rejection branches that the witnesses need ([step 9](#model-steps-and-their-justifications)).
- C-STALE, C-FAILMUT and the replay-rejected witness measured, with C-FAILMUT to be dropped under the plan's rule if ProVerif could not decide it within the caps. ProVerif decides it in seconds at K_r = 2, so it is kept.
- After the P2 review, the replay-rejected witness C5c witnesses a genuine replay: `FsReceiveRejected` carries the refused frame and the witness-only event `FsReceivedFrame` the accepted one, and C5c requires the refused frame to be a frame the same Beacon accepted earlier ([step 9](#model-steps-and-their-justifications), [Changes after the P2 review](#changes-after-the-p2-review)).
- The fail-stop form of the receive worker measured ([Fail-stop measurement](#fail-stop-measurement)), but C1 and C3 kept in the form in which failures are interleaved; no target uses fail-stop.
- L6 item 4 (adversary-chosen plaintexts): a tasking form with whole adversary-chosen plaintexts for the authentication claims if it fits the caps. It fits (C1, the largest, used 60% of the time cap and 66.5% of the address-space cap in the verification pass), so it is used ([step 5](#model-steps-and-their-justifications)).
- The record-form A1 together with C-NOGATE covers the HB-95 class (the sequence-one gate), and C-NOGATE keeps its application-prefix input.

## Pending paper arguments

The ProVerif verdicts are exact statements about the fs process. Their Rust readings rest on the following arguments of the plan, which are not settled unless stated:

- **L1, accept and build scheduling (pending).** In this scenario only the drop and the adjacency of accept and build on one object matter, because each object takes one bundle; case (iv), a token built on another live object with the same key, stays open as in P1.
- **L2, one registration per record object (pending).** A Rust Server object can install many peers and route records to each; the model gives every Server object one bundle and one peer, all with the key ID `fs_kid(1)`, and lets the attacker deliver a frame to any receive attempt. The argument must show that every Rust run of a multi-peer object maps to a run of the model with several objects that share the identity key (OD2), with the same events.
- **L3, failure neutrality and the far-target collapse (pending).** A failed receive keeps the exact entry state; Rust admits t ≤ r + 51 − |C|, which the model over-approximates above T_max by the far branch, after which the worker stops (OD4).
- **L4, the send relation (pending).** `FsSent` is the allocation of a sequence; the model outputs the frame even when Rust's seal or snapshot fails, which only strengthens the attacker.
- **L5, Beacon lifecycle (pending).** At most one bundle, at most one finish, and a failed finish aborts for good.
- **L6, event projection: reviewed** at the start of P2 ([review record](../proverif-fs-event-meaning.md#review-record)), except the two event changes made after the P2 review (`FsReceivedFrame` and the frame field of `FsReceiveRejected`), not yet reviewed; they are used only by the witnesses C5b and C5c and by the control C-FAILMUT, which reruns the C5b query, so no security result relies on them ([Changes after the L6 review](../proverif-fs-event-meaning.md#changes-after-the-l6-review)).
- **E20 (v2) and E19 (direction split): written here** ([steps 2 and 4](#model-steps-and-their-justifications)), not yet separately reviewed.

## Model structure and Rust mapping

Unbounded Server objects share the one honest Server identity and own key ID. Each object processes one registration bundle, builds the response when the attacker schedules it, and then sends two taskings to the peer it installed. Unbounded honest Beacons run alongside: each draws fresh keys, sends one bundle, finishes at most once and then makes K_r receive attempts. The attacker builds its own identities from public constructors, and the same Server code serves them. Every attacker input is `[precise]`, and honesty appears only in the queries.

## Model steps and their justifications

1. **One bundle per Server object (pending L2).** The record scenarios give each Server object one registration and one peer, with the key ID `fs_kid(1)`. Several model objects with the one identity key stand for one Rust object with several peers; the attacker delivers frames to any receive attempt, which over-approximates Rust's routing by the claimed sender.
2. **Early fresh Server coins (v2, E20).** Rust draws the ephemeral key pair at `server.rs:368` and the KEM coins at `:373`, after the bundle has been decoded and checked; the model draws both names when the object starts, before its first input. The justification, at one bundle per object: (a) neither name occurs in any input, test, event or output before the point where Rust draws it, and the attacker cannot know a restricted name before it is output, so moving `new n` above an input or a test that does not mention n gives the same labelled transitions (the attacker's input cannot contain n, because n has not been output); (b) if any check before `server.rs:368` fails, the Rust call returns `None` and the model object stops, and the names drawn early are never used, so the visible behaviour of both forms is the same; (c) with one bundle per object, each object draws exactly one ephemeral secret and one set of coins, as Rust does for that bundle. The two forms therefore have the same traces, events and attacker knowledge. The reorder changes only ProVerif's internal naming of the two names, which no longer carry the bundle as a session argument, and that made the C5 witnesses fit in memory in P0. P0 also measured that the Rust-ordered form (v1) gives the same verdicts wherever it terminates. This is a paper argument written here, not yet separately reviewed; with K_reg > 1 it would not apply, and fs-registration keeps the Rust order.
3. **The build input carries no test.** Any attacker input schedules the build, and withholding it is the dropped token. With one bundle per object, the object takes no further input after a drop, so a test on the input value, as in fs-registration, would select no further behaviour; measured on C4, such a test made saturation about 1.7 times slower for about the same number of clauses.
4. **Direction split (E19).** The scenario has no Beacon send worker and no Server receive worker. The argument for the Server-to-Beacon claims: (a) a Beacon send would output frames sealed under the Beacon-to-Server chain, which is `hkdf_second_32` of the root's HKDF output (`crypto.pvl:77-80`), whereas every Server-to-Beacon key comes from `hkdf_first_32` and its successors; in the free-constructor theory no term built from the second projection yields the first or a successor of it, so these frames give the attacker no Server-to-Beacon key and no Server-to-Beacon frame; (b) such frames carry the Beacon's assigned key ID as sender, which the Beacon's receive refuses, and a relabelled frame fails the CTX commitment, which binds the sender ID; (c) a Server receive outputs nothing in the model (the `Some`/`None` bit is not published) and changes only the receive fields of the peer state, which no Server send reads (`concrete.rs:171-182` against `refined.rs:700-778`); (d) the removed workers' events (`FsSent` and `FsReceived` in the other direction) do not occur in any query of this scenario, and the claim C3, whose direction is a variable, is only about Beacon acceptances here. Removing the workers therefore removes neither a Server-to-Beacon event nor any attacker knowledge that a Server-to-Beacon claim depends on. This is a paper argument written here for s2b, not yet separately reviewed; the b2s direction is stage P3.
5. **Two tasking forms (L6 item 4, E7).** Rust lets the application send any nonempty bytes. `fs-records-s2b-taskings.pvl` sends, at sequences 2 and 3, an 8-byte prefix chosen by the adversary (any binding-shaped value included) followed by fresh bytes; without that prefix the C-NOGATE mutant could not fail, because a fresh name never parses as a binding followed by a payload. `fs-records-s2b-taskings-chosen.pvl` lets the adversary choose, for each tasking, either that form or a whole plaintext of its choice, so every trace of the fresh form is also a trace of the chosen form. The authentication claims A1, C1, C3 and C4, and A2, run in the chosen form, so they cover adversary-chosen tasking plaintexts at sequences 2 and 3; the sequence-one plaintext stays the binding followed by a fresh registration payload (step 6). The secrecy result S1 and the witness S4 run in the fresh form, because with an adversary-chosen plaintext the attacker knows the plaintext and S1 would be false by construction. The witnesses and the controls also use the fresh form, which P0 measured and which is cheaper; because every trace of the fresh form is a trace of the chosen form, a witness or a FALSE control found in the fresh form holds in the chosen form too. Adversary-chosen plaintexts are any terms; a term that denotes the empty byte string would be refused by Rust before allocation (`ratchet.rs:421-423`), so the model has extra sends there, which only adds traces.
6. **Fresh registration payload.** As in fs-registration (its step 6), the response payload is a fresh name per build, so the sequence-one plaintext is the public binding followed by fresh bytes. Registration agreement (A1, whose field `p` is the payload) and the agreement and secrecy of the sequence-one record (C1 and S1 at t = 1) are therefore shown for fresh registration payloads only: an adversary-known or adversary-chosen `data`, and the public default payload `REGISTRATION_WITNESS` (the byte 0xFF) of a build without data, are not covered. The tasking form of step 5 does not change this, because it concerns sequences 2 and 3 only.
7. **The finish opens sequences 1 to T_max.** Rust's finish opens the response frame with the general receive on a fresh ratchet, which admits t in 1..51, and then aborts unless t = 1 (`beacon.rs:462-470`). The model opens t = 1, 2 and 3; for t = 2 or 3 it emits the witness `FsBeaconFinishOpenedLater` and continues with the gate library, whose real form ends the Beacon. A frame with t = 0 or t > T_max ends the Beacon without an open: in Rust such an open may succeed for t ≤ 51, but the gate aborts either way and nothing observable differs, so only the witness range is smaller (E14).
8. **Receive state and capacity.** The receive state is r and the flag `cached_2`: after the finish r = 1 and the cache is empty, so position 2 is the only position that can be cached below T_max = 3. Rust admits a target t > r if t ≤ r + 51 − |C| (`control.rs:223-245`); here |C| ≤ 1 and r ≥ 1, so every t ≤ T_max is admitted and the capacity never binds below T_max. Above T_max the far branch over-approximates admission: it accepts every t > T_max, where Rust admits only t ≤ r + 51 − |C|. It does not over-approximate Rust's acceptance as such, because it opens with model-only key material, `ratchet_material(fs_far_chain(chain_4, t))`, derived from the chain at T_max + 1 by a public function, whereas Rust opens with the material of the real chain at t; a frame sealed under Rust's material at t ≥ 4 would be refused there. Within these bounds the two agree: no process seals above sequence 3 (the Server sends sequences 1 to 3), and both materials are determined by the chain at T_max + 1, which no process outputs, so only a frame built from that secret chain could pass either. The branch emits only `FsFarAccepted` and the worker stops, so no claim says anything about a peer direction after its first far acceptance (OD4, pending L3). C4 shows that this never happens here. C4 is meaningful only while honest senders stay at or below T_max: if a later stage let an honest sender seal above T_max under the real chain, the far branch would refuse those genuine frames and C4 would hold for them by construction, so such a stage must raise T_max or derive the far material from the real chain.
9. **Where `FsReceiveRejected` is emitted (E22).** The event is emitted for every parsed frame from the pinned Server ID that is rejected at a target t ≤ T_max: an old target that is not cached (rejected before any open, `concrete.rs:270-274`), a failed cached open and a failed future open at 2 or 3. It is not emitted for a failed far open, which no witness needs. In this scenario the event therefore means a rejection at t ≤ T_max. Since the P2 review the event carries the refused frame (the call argument), and every `FsReceived`, the finish's sequence 1 included, is followed by the witness-only event `FsReceivedFrame` with the accepted frame. A witness can therefore say which frame was refused: C5c requires it to be a frame that the same Beacon accepted earlier. Before the review the event carried no frame, and the review showed that the earlier form of C5c was reachable at K_r = 1 by a frame the attacker built at sequence 1, so it did not witness a replay. ProVerif generates no clause for an event that the query does not mention (ProVerif 2.05 `pitransl.ml` translates such an event to nothing but a trace label), so the frame fields change no other target: s2b-A1 gave the same saturation statistics with and without them.
10. **Bounds for witnesses and controls.** The security results run at K_r = 3. Witnesses and controls run at the smallest K_r that exhibits them: A3, S4 and C-NOGATE at K_r = 1 (they need no receive after the finish), C5c at K_r = 1 (its replayed frame is the response frame that the finish accepted, so one receive attempt suffices), C5a and C5b at K_r = 2, C-RETAIN and C-STALE at K_r = 3 (a replay accepted twice needs three attempts), and C-FAILMUT at K_r = 2, the bound of the witness C5b that it controls. Each receive attempt waits for an attacker input, so a trace at a smaller K_r is also a trace at a larger one, and running a witness or a FALSE control at a smaller bound is not a weakening. C-FAILMUT is TRUE; its statement holds for K_r = 2 only, the bound at which C5b is witnessed.
11. **Control hooks.** The receive-window, gate and taskings libraries are hooks loaded before the process, like the consumed-set and binding hooks of fs-registration. The window hooks are three `letfun`s whose real bodies return the success state (`false`: the cached key is removed) and the entry state (r and `cached_2`) after a failed open; ProVerif inlines them. C-RETAIN keeps the cached flag after a successful cached open. C-STALE makes a failed open at t ≤ T_max restore the state left by the finish (r = 1, nothing cached); with K_r = 3 that is exactly "the state from before the previous success" of the plan: after one earlier success it is the state before that success, after none it is the entry state, and after two successes the restored state is that of the third and last attempt, which is never used. C-FAILMUT makes a failed open at t ≤ T_max consume its target as a success would: the cached key is removed, or r := t with position 2 cached when it is skipped; the far branch is unchanged. C-NOGATE replaces the gate's abort by the binding check and the commit, which is the behaviour of the branch `vcvio`.
12. **Fail-stop (E21): measured, not used.** In the fail-stop form a failed open of a parsed frame ends the receive worker. It was measured for C1, C3 and C4 ([Fail-stop measurement](#fail-stop-measurement)); every target runs in the form in which failures are interleaved, so no result relies on the fail-stop trace-mapping argument.
13. **Names, heuristic and precision.** Names keep their session arguments (the "na" form is not used). The selection heuristic nx and the `[precise]` inputs are those of P1 ([the heuristic paragraph](../formal-verification-analysis.md#the-fs-selection-heuristic-nx), [the precision settings](../formal-verification-analysis.md#proverif-precision-and-approximation-settings)); neither restricts traces.

Its class is control; the checker accepts a TRUE line without a trace only for a control marked as inverted, and the manifest has exactly one.

Measured traces of the FALSE results (all in one honest session unless stated): A3, the genuine sequence-3 tasking is spliced into the response in place of the sequence-one frame, and the finish opens it before the gate; S4, an attacker identity registers, the Server builds its response and sends it the sequence-2 tasking, which the attacker opens; C5a, the Beacon accepts 3 (caching 2) and then 2 from the cache; C5b, a forged frame at 3 is rejected and the genuine 3 is accepted; C5c, the finish accepts the genuine response frame at sequence 1 and the attacker delivers the same frame to the first receive attempt, which refuses it as an old target that is not cached, without an open; C-RETAIN, 3 is accepted, 2 is accepted from the cache, and the same frame at 2 is accepted again; C-STALE, 3 is accepted (caching 2), a forged frame at 2 fails the cached open and restores the state left by the finish, and the genuine 3 is accepted again; C-NOGATE, the Server's later tasking carries the prefix `RegistrationKeyIdBinding(sender_id_le64(a))` for an adversary value `a`, the attacker withholds the response and delivers one with outer key ID `a` and the sequence-3 tasking in place of the sequence-one frame, and the gate-less finish opens it, accepts the binding and commits (the HB-95 substitution, as in P0).

## What the bounds do not cover

The security results hold for unbounded Server objects, honest Beacons and attacker identities, each Server object processing one bundle and sending two taskings, and each Beacon making three receive attempts after its finish, with positions up to T_max = 3 materialised. A Server object's third or later tasking, a Beacon's fourth or later receive, and anything after a peer direction's first far acceptance are not covered; the arbitrary-depth facts are the Lean side's (OD1), and these bounded results do not discharge global closure item 1 (arbitrary reached committed states). The scenario has no Beacon-to-Server records (stage P3), no compromise or reveal (stage P7), and no strong secrecy (stage P5). The theory is `crypto.pvl`, so the results say nothing about same-role DH equalities, X25519 encoding aliases, low-order points or ML-KEM implicit rejection (F13, stage P4). The registration response payload is fresh, so A1 and the sequence-one record of C1 and S1 do not cover an adversary-known or adversary-chosen payload or the default byte 0xFF (step 6); S1 and S4 are about fresh tasking bytes behind any prefix, and the adversary-chosen prefix itself is never secret. The far branch admits every sequence above T_max but opens with model-only key material (step 8). Every model Beacon pins the honest Server key and ID, and every Server object has the modelled identity key and `server_kid` (E3, E23).

## Beacon pins

In this scenario a Beacon outputs nothing after its bundle: its finish and its receive attempts publish nothing (the `Some`/`None` bit is not published). The P1 argument therefore carries over: model Beacons that all pin the honest Server key produce exactly the bundles and the attacker knowledge of Beacons with arbitrary pins, so A2 (whose `FsBeaconStarted` pin is left free) and the Server-side S1 and S4 read as statements about any Beacon. A1, C1, C3 and C4 are about Beacons that pin the honest Server key, the deployment of the [threat model](../threat_model.md).

## Gates and wiring

- `PROVERIF_FS_SCENARIOS` holds `fs-registration` and `fs-records-s2b`; `check-proverif-fs` runs both runners with `-j1`, so every target of the group runs one after another. The parallel 35-scenario roster is unchanged.
- `check-proverif-fs-records-s2b` runs the checker regression test and then `check-free-schedule.py --scenario fs-records-s2b` with the fs timeout, address-space cap and optional log directory; `check-proverif-fs-registration` now passes `--scenario fs-registration`. Without `--scenario` the checker runs every target.
- The checker loads `production-transcript-interface.pvl`, `crypto.pvl`, `extraction/lib.pvl`, `fs-common.pvl`, the window, gate and taskings libraries, `fs-records-s2b-receive.pvl`, the bound file and `fs-records-s2b.pvl`, then the query file. It rejects any target that loads a mutant library unless it is a control, a control that loads none or more than one, a security result below K_r = 3, S1 or S4 with adversary-chosen plaintexts, an inverted target that is not a control, a query file of another scenario, and any record query file that no target uses. Before the P2 review the mutant rule let a security or witness target load two mutants, although this guide already said that it rejected them; no target did, and the regression test now covers the case for security, witness and control targets of both scenarios.
- ProVerif warnings: the checker rejects every line that starts with `Error` or `Warning` (ProVerif 2.05 prints every input, simplification and lemma warning that way) and every other line that mentions a warning, except the lines that start with `Termination warning: `. ProVerif's selection function (`selfun.ml`) prints such a line in one of two forms, followed by the clause and `Selecting n`, or by `Selecting an hypothesis matching the conclusion` and a suggested `noselect` declaration (the checker accepts both, and its regression test feeds both), when the only hypotheses it can select in a clause are ones that a `nounif` declaration (the reviewed heuristic nx, or one ProVerif adds itself) marks as best avoided or that match the clause's conclusion, so that saturation might not terminate. The selection function only orders resolution and is not an assumption, so such a line says nothing about a verdict that ProVerif reports after saturation ended; a run whose saturation does not end hits the timeout or the address-space cap and fails. The checker therefore accepts termination warnings in any number. In the record group s2b-A2 and s2b-S1 print them (six and two lines in the 63369de pass, all with an `attacker(app_prefix…)` or `attacker(plaintext)` conclusion, from the attacker inputs of the tasking libraries); no registration target does. Before the P2 review the checker accepted them only because they do not start with `Warning`, while its docstring said that it rejected every warning.
- The transcript-fidelity test now has 24 tests. `free_schedule_records_s2b_model_is_pinned` checks the order of the steps of the Server object (the Rust order except for the early draw of v2), the Beacon and the receive step, the exact text of every hook and control library and of the bound files, the counts of each event in the receive step, the frame fields of `FsReceivedFrame` and `FsReceiveRejected`, and fourteen mutations. The other fs tests now also pin the record roster and runner, the 84 record citations, the twelve fs events, the record target manifest with its classes, bounds and forms, and the checker's mutant and warning rules.
- `check-inventory.sh` records 148 handwritten ProVerif files, the `_to_bitstring` counts 20 and 23, 24 transcript-fidelity tests, and tripwires for the record runner and its place in the serial fs roster.

## Deviations from the plan

- **Files.** The plan named one shared `fs-records.pvl` with the send and receive macros and a single `fs-records-s2b.pv`. P2 uses scenario-specific libraries (the receive step, the bound files, the hook libraries and the process) and one query file per target, in the style of P1; P3 may factor out what the two record scenarios share.
- **Witnesses and controls at K_r = 1 or 2.** P0 ran every s2b query at K_r = 3. Following the orchestrator's decision, witnesses and controls run at the smallest K_r that exhibits them ([step 10](#model-steps-and-their-justifications)); this cut the cost of C5b from 1369 s at the memory edge in P0 to under a minute.
- **The build input carries no test** ([step 3](#model-steps-and-their-justifications)), unlike fs-registration, whose objects continue after a drop.
- **`FsReceiveRejected` is not emitted for a failed far open**, unlike the P0 spike, which emitted it in every rejection branch ([step 9](#model-steps-and-their-justifications)).
- **C-STALE restores the state left by the finish**, which is the plan's "state from before the previous success" at K_r = 3 ([step 11](#model-steps-and-their-justifications)).
- **C-FAILMUT is an inverted control.** The plan keeps it only if ProVerif proves the unreachability; its expected verdict is therefore TRUE, which the checker allows only for a control marked as inverted. Its mutant leaves the far branch unchanged.
- **The replay-rejected witness is named C5c**, and the s2b half of S4 is stated at sequence 2, so that it witnesses a later tasking rather than the registration payload. After the P2 review C5c ties the refused frame to an accepted one through the frame fields of step 9 and runs at K_r = 1.
- **A2 is re-proved** in the record process (G0 section 3.5), in the chosen tasking form.
- **Adversary-chosen plaintexts** (L6 item 4) are covered by a per-tasking choice between the fresh form and a whole adversary-chosen plaintext; the plan's single attacker-input send step would have covered only one sequence.
- **`fs-common.pvl` comments** were aligned with the reviewed L6 reference (field kinds, and the use of failure-cause events by controls). After the P2 review two event declarations changed: `FsReceiveRejected` gained the refused frame as its last field, and the witness-only event `FsReceivedFrame` was added; no other declaration changed.
- **The registration runner** now passes `--scenario fs-registration`, so that each runner checks only its own targets. The fs-registration targets and their expected results are unchanged.
- **The fail-stop form was measured but not used** ([step 12](#model-steps-and-their-justifications)).

## Changes after the P2 review

Three reviews of P2 (fidelity, soundness and integration) approved it with nits; their fourteen minor findings and nits are applied as follows.

- **The replay-rejected witness C5c.** The review showed that the earlier C5c ("every rejection at sequence t precedes every acceptance of t", expected FALSE) was already FALSE at K_r = 1 through a frame that the attacker built from its own values at the finish's sequence 1, so it witnessed neither a replay nor an acceptance after the finish, that it did not run at the smallest K_r that exhibits it, and that the analysis overstated it as "a replay is refused". C5c now witnesses a genuine replay refusal: `FsReceiveRejected` carries the refused frame, the witness-only event `FsReceivedFrame` carries every accepted frame, and the query requires the refused frame to be one that the same Beacon accepted earlier ([step 9](#model-steps-and-their-justifications)). It runs at K_r = 1, its smallest bound: the attacker replays the response frame that the finish accepted. This form was chosen over reclassifying C5c, because the plan's C5 item asks for a witness that a replayed frame is refused and the two frame fields provide it without touching any other target: ProVerif generates no clause for an event that a query does not mention.
- **The checker's mutant rule.** A security or witness target that loaded two mutants was accepted, contrary to [Gates and wiring](#gates-and-wiring); the checker now requires exactly one mutant for a control and none for any other target, with regression cases for both scenarios and a transcript-fidelity pin and mutation.
- **Termination warnings.** The checker's docstring said that it rejects warnings, but it accepted ProVerif's termination warnings, which s2b-A2 and s2b-S1 print, only because they do not start with `Warning`. The checker now rejects every other line that mentions a warning and accepts termination warnings explicitly, for the reason given under [Gates and wiring](#gates-and-wiring); every log of the 63369de pass satisfies the new warning rule.
- **Fail-stop and C5c.** Fail-stop can express C5c ([Fail-stop measurement](#fail-stop-measurement)); this guide and the L6 reference no longer say otherwise.
- **Wording.** The places that called the Server object's order the Rust order now name the early draw of v2; the analysis no longer calls the v2 values unused (the ephemeral secret enters DH2 to DH4 and the KEM coins the KEM secret, both before the response is output; what holds is that neither is used before the point where Rust draws it and neither is output before the response); the far branch is described as an over-approximation of the admitted sequences with model-only key material ([step 8](#model-steps-and-their-justifications)); the L6 reference no longer says that `FsReceiveRejected` is emitted for a failed far open in every record scenario; the registration-payload restriction now covers adversary-known and adversary-chosen payloads and names A1 and the sequence-one record ([step 6](#model-steps-and-their-justifications)); the analysis says that the witnesses and controls run in the fresh tasking form; and the P1 guide's Running section gives the current scope and time of `make check-proverif-fs`.
- **The verification pass.** The whole fs group ran again on the tree that applies these changes; [Results](#results-of-the-serial-verification-pass) records that pass, which replaces the pass on `63369de`.
- **The message of commit `c08dbf3`** says that all relative links and anchors in the documents it changed resolve. Two anchors in `doc/formal-verification-analysis.md`, both present before P2, do not: `impl/formal-verification-stage-4.md#L123-L127` (a line anchor into a rendered Markdown file) and `persistence.md#server-state-persistence` (`doc/persistence.md` has no such heading). They are left for a separate change.
