## Source order and actual replies

It serializes the completed message before publishing `InitSent`. The new `signingProgram` follows exactly that three-call order. Each call goes to the same created identity handle; the program never receives or reconstructs its seed. The three detached replies are attached to their original source messages to form all four complete field buffers.

The optional service interface has explicit missing-handle rejection. The program records the failed first request before returning `none`, and neither later signing call runs. This source service rejection is not a model of every native allocator or signing-library error. For an actual created seed, the stated perfect primitive functional interface returns each deterministic signature. Native serializer failure and role-state error paths still require their own adapter proof or explicit external contract. In particular, a failed native attempt may already have signed messages before serialization fails; a single successful registration does not establish an empty lifetime signing log.

The identities and key fields supplied to this block may be arbitrary. The source correspondence separately instantiates the public identity to the actual public key derived from the created seed. Equality of a public-key byte string never identifies a generated index or establishes source ownership.
