# Source chain coordinates

`PqxdhRecordLiftChainState` proves an operational R3 component for the existing extracted send and receive drivers. Its fourteen theorems track ghost coordinates through actual source admission, each skip/target continuation, rollback and send advancement. It adds no cryptographic assumption, advantage or resource bound. It does not yet prove the full dynamic record world, a persistent-table interpreter or evolving-chain secrecy.

A coordinate contains a slot, a direction and the last derived source sequence. Direction `false` is Server-to-Beacon, and `true` is Beacon-to-Server. Coordinates occupy the two chain payload fields of the existing polymorphic `RefinedRatchet`; the source control, cache, contexts and material values remain the original types. `advance` changes only the position. It is ghost bookkeeping, and no slot, direction or position is used to decide source admission. The two post-registration constructors put coordinate `(slot, false, 1)` in the Server send field and Beacon receive field, and coordinate `(slot, true, 0)` in the opposite pair. Thus the next Server-to-Beacon derivation belongs to sequence 2, while the first Beacon-to-Server derivation belongs to sequence 1. Failed registration processing remains outside this module in the CE lane.

`begin_tracked` proves that every source admission starts its first KDF request at the entry receive coordinate. Cached and rejected branches retain the original entry and context. The difficult callback theorem, `resume_tracked`, follows every branch of the existing receive-resume definition: the zero and final-count branches, target checks, skipped-slot validation, material staging and bounded arithmetic. When its supplied typed callback reply carries the successor coordinate and any material, a further KDF request has coordinate `advance entry.receive_chain skipped`, and a future opening has final coordinate `advance entry.receive_chain (skipped + 1)`. Every branch retains the complete original rollback entry and context. This premise specifies the callback to be implemented by the later coordinate compiler; it is not a freshness assumption or evidence that an arbitrary KDF reply has that coordinate.

`Aligned` says that each chain position agrees with its source control counter. `request_sequence` combines the proved tracking relation with the existing `PqxdhFirstRecordReplay.Admitted` window invariant to identify a pending request's position with the actual working receive counter. `future_sequence` similarly identifies the final future-chain position with the committed receive counter. These statements use explicit operational invariants; the module does not advertise them as facts of every unconnected dynamic-world state. The imported admission/window facts are generic source-control lemmas, not a supplied fixed family or a cryptographic endpoint.

`failed_open` proves that an absent opening result restores the entire entry kernel, including its two coordinates and every cached material. This is also the absence returned after a commitment failure at the surrounding opening interface. `failed_open_retry` then proves that retrying from that returned kernel executes exactly the same admission and therefore uses the same coordinate when another derivation is requested. Neither theorem modifies an external table. Keeping the persistent lazy table outside this operation's rollback state remains a construction obligation for the next compiler.

`send_begin_tracked` follows actual send admission, including exhaustion, and proves that an admitted send retains the original request coordinate, context, receive counter and receive cache while advancing the send control by one. `send_ready_kernel` identifies the whole advanced kernel: only the committed source control and successor send coordinate change. `send_ready_aligned` proves that both positions continue to agree with their source counters before the seal callback is invoked. The existing source send program returns that advanced state even if sealing returns no ciphertext; this module makes no assertion that a failed seal publishes a peer or frame.

Erasure is explicit. `erase` replaces the two ghost coordinates by chains through an arbitrary, potentially noninjective function and wraps the result as a concrete kernel. `admission_erasure` equates the actual extracted `begin_receive` on that concrete kernel with the complete erased ghost admission. `resume_erasure` transports the entire source skip/target effect under the same interpretation, with the stated successor chain and material as its typed reply. It does not claim that a particular backend computes that reply. `server_seed_erasure` and `beacon_seed_erasure` connect the two initial coordinate values to the exact already-proved production seed kernels, including every counter and empty cache cell. Their two chain-value equations are functional interpretation bindings for the seed, not security assumptions. `seeds_aligned` proves both constructors total and aligned.

The next join must construct the coordinate callback with the persistent full76 table, prove that its source chain/material interpretation matches the actual KDF arguments and complete replies, establish coherence when the table extends and a failed operation retries, and lift the operational invariants through the dynamic Server map and Beacon owner list in `PqxdhRecordLiftRoles`. It must also prove skipped-material table references, successful publication/consumption, all ordinary raw paths and the global query ledger in that same world. Aliases, selected-cut distributions, Extract/HMAC reductions and the evolving-chain security event are later obligations. None is replaced here by a new Frame, freshness or hidden-key assumption.
