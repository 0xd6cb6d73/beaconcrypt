The experiment. `PqxdhDeploymentSecrecy.game … bounds mode A` constructs the Server from a generated seed and runs the adversary of mode `mode` against the CE handler from an empty ledger. The CE handler is the trial's native handler behind the secrecy layer. The layer forwards every coin and command unchanged and records it with its mode O reply. `test handle left right` requires equal nonzero lengths. The first admitted test draws the hidden bit with one experiment coin and fixes the test handle. A later test is admitted only on the same handle or on a handle with the same public designation, computed on the transcript so far. An admitted test is one send of `left` or `right` by the bit. `fresh handle length` requires `min ≤ length ≤ max`, draws a uniform message of that many bytes with one coin per byte when the command is issued, keeps it private and sends it. A rejected secrecy command changes nothing but the transcript, and the experiment's own draws never enter the transcript. Mode P is mode O behind `observeFull`, whose replies are the mode P projections of the mode O replies (`observeFull_project`). `game_wrap` shows that the experiment is the trial's native game run on the wrapped adversary, with the ledger moved into the final state. Every record seal handed to the frame writer is logged with its command, including seals whose writer then fails, and `logged_forget` shows that the log changes no result.

The compile lemma. `compile_full_game` and `compile_full_source` state that the experiment in either mode equals the merged initialized execution of `compileFull A` (the trial compiler applied to the wrapped adversary) jointly over the Server's public data, the adversary's output, the whole ledger (transcript, test session, fresh messages), the whole deployment state with the produced frames, and the runtime state. They use exactly the trial's two codec contracts, `Phase1ReadBack` and `Phase2ReadBack`. Because the wrapped adversary draws the bit and the fresh messages at the same positions as the experiment, no sampling-swap lemma is needed.

Budget transport. `wrap_bound` and `compile_full_bound` transport per-class caps through the secrecy layer and the compiler; `PqxdhDeploymentCompileCaps.transported` gives the closed form. The compiled program and its tagged form at any raw-accept ordinal make at most `qCoin + qTest + qFreshBytes` coins with `qFreshBytes = ℓmax · qFresh`, the registration and HMAC caps unchanged, `qHash + S + R + qTest + qFresh` BLAKE2b queries, `qSS + qSR + qTest + qFresh` Server kernel reveals, `qBS + qBR + qTest + qFresh` established-kernel reads and no identity, KEM, prekey or one-time read. `tag_certified` is the `certified` premise of T4 at these caps, and `transported_room` its `room` premise for `count + 1 = qCreate + 1`.

Selection (CE-4). For a run with outcome space `Ω` and a public `designate : Ω → Option G`, `split` writes the probability of an event on eligible outcomes as the exact sum over targets of the probability of the event with that target designated; `guess` writes it as `card G` times the probability that a uniform guess drawn before the run is the designated target; `advantage` is the split form for a left-or-right bit with the eligibility-weighted half subtracted. `sum_eq_card_mul` and `signed` turn a sum of per-target probabilities or of signed per-target differences into `card G` times the probability or signed difference of the run with a uniformly guessed target; with signed per-target hops this gives the owner's `N · Adv(B_guess)` wording. All statements are exact and use the measure form `𝒟[f <$> run] {true}` of the KEM theorems.

Publicity (CE-5). `agree_game` shows that every outcome of the experiment, in either mode, satisfies `Agree`: the transcript summary counts exactly the native owners, the public phase of every handle is the class of its native phase, every created binding is the owner's pinned Server identity and key ID, every successful bundle in the transcript is the Phase 1 writer output of the candidate the owner signed with its own identity key and the KEM public key it holds until finish, and every successful build response is the Phase 2 writer output of fields carrying the Server identity, which never changes. `phase_public`, `owner_public` and `failure_public` are its readings for `phase`, `owner` and `NoBundleFailure`: a rejected bundle sets an owner's failure flag exactly when the owner is natively Fresh. `owner_kemIndex` shows that in the annotated execution of any program the owner created `k`-th holds KEM creation index `k` and the KEM pool has one key per owner.

Key match and ciphertext link (CE-5). `designate_keymatch` (with `Phase1ReadBack`): for a Server peer designated `(i, k)`, every verification of the accept bytes of session `i` yields owner `k`'s identity key and the PQ key owner `k` signed in its honest published bundle (`PublishedKey`), which owner `k` holds as its native KEM public key until finish. `owner_link` (with `Phase1ReadBack` and `Phase2ReadBack`): an owner designated `(i, c)` is natively Established and pinned to the protected key ID and to the Server's own identity; the response of session `i` is the Phase 2 writer output of fields carrying the Server identity; the ciphertext read from the owner's accepted finish input is the KEM ciphertext of those fields; and the PQ key verified at accept `i` is the one the owner published. `keymatch_game` and `link_game` state both on every outcome of the experiment. The step to `KeyMatchFinal k` in the annotated execution, through `owner_kemIndex` and the existing ownership invariant, is CE-9 work.

Freshness (CE-5). `approved_goodkem`: in the exact execution that T4 is stated for, the tagged compiled program of a budgeted complete-interface adversary, in either mode and at any raw-accept ordinal, ends every run with `GoodKem` for every KEM creation index. `kernel_reads_unrevealed`: in the same execution no identity index is ever revealed (`revealedAt` is false). Both follow from `quiet_initialized`: every annotated step other than an identity or KEM field read records only creation, signing, static DH and decapsulation observations, and the compiled program makes no such read.

## Unit A: decisions and deviations

- Layering. The secrecy commands and the transcript are a layer over the trial's native handler, and the CE handler is their flattened composition. The produced-frame log needs the record steps themselves, so the trial's native and compiled record commands were extended in place and every trial module was re-checked; no trial statement was weakened or removed, but the definitions of `State`, `Local`, `serverStep`, `beaconStep`, `serverLocal`, `beaconLocal` and `merge` now carry the produced frames, and the statements that mention them changed accordingly.
- Logs. The transcript stores the mode O reply of every query; the public mode P view is `Entry.view .P`. Publication and receipt are functions of the transcript, because they are exactly the send, test and fresh replies and the raw-receive entries. Produced frames are tagged with the producing command rather than with `(side, handle, seq)`: the command names the handle, and the frame carries its sequence number and sender.
- Secrecy commands. A rejected test or fresh command is recorded in the transcript with its `none` reply and changes nothing else. The fresh handle of a claim is the position of the admitted fresh message in the ledger. `Claim` has only the fresh-message claim, since the optional root-guess endpoint CE-RG is not built.
- Budgets. `qFreshBytes` is `ℓmax · qFresh`, the plan's per-message reading. The per-class transport charges one coin per test, although only the first admitted test draws the bit, and counts each test and fresh message both as a possible Server send and as a possible Beacon send, so the BLAKE2b cap exceeds the plan's `qHash + S + R` by `qTest + qFresh`. Both are sound; tightening them needs a bound of the composed per-query program instead of the per-class composition.
- Designation. The Server side compares the identity and PQ fields read from the accept bytes with those read from the owner's published bundle, rather than the full `RawSignatures.verified`; the two agree whenever the accept succeeded (`verified_origin`). The Beacon side requires the public Established phase, the protected key ID, the finish ciphertext equal to the ciphertext of session `i`'s build response, the Server identity in that response equal to the Beacon's pin, and the accepted PQ field equal to the Beacon's published one. The pin is compared with the identity in the build response because the adversary takes no input (D5); `owner_link` proves with `Phase2ReadBack` that it is the Server's own identity.
- Router. The Server header router stays a free parameter of the game, as in production, where the header router can route frames the full decoder rejects. The approved contract `RawCtxServerRouting.DecoderAgreement route codec.frameRead` is the premise for later claims that need it; no unit A statement uses it.
- Selection statements use the measure form over `ProbComp` runs; the event and guessing forms need `SampleableType G`, so the target domain must be nonempty.

### What is proved

Twelve modules under `beaconcrypt-core/proofs/lean/BeaconcryptCore/Computational/` define a first version of the common deployment experiment and prove that it compiles into an ordinary program of the existing initialized registration schedule (source14). The adversary talks to one Server, built from a generated seed, and to Beacons it creates with pins of its choice. It can issue coins, `create`, bundle, accept, build, finish, HMAC and BLAKE2b commands, and send and receive raw records on Server peers and Beacons. It gets no reveal command, no getter, no snapshot and no start input.

### Contracts used

The owner approved four codec contracts of the common experiment on 2026-10-06. They are listed in both assumption lists: the functional contracts under "Assumptions made by the proofs" in [the analysis](../formal-verification-analysis.md#assumptions-made-by-the-proofs) and "Primitive guarantees, additional assumptions and idealizations" in [the composition assumptions](../composition-assumptions.md#primitive-guarantees-additional-assumptions-and-idealizations).

- Used by CE-3 (premises of `compile_native`, `good_step`, `compile_game` and `compile_source`): `Phase1ReadBack`, which gives a Beacon's identity key from its bundle bytes, and `Phase2ReadBack`, which gives the Server identity from a build response.
- Approved but not yet used: `FrameReadBack`, and the one-codec rule with `RawCtxServerRouting.DecoderAgreement` for the Server header router. The experiment and the compiled program already share the codec's frame reader and writer by definition, and the router stays a free parameter.

These are abstract message-model laws about the codec parameter, not facts about Cap'n Proto or any serialization implementation. The trial adds no hardness assumption, idealization or advantage term.

### Plan changes recorded

- Read caps. The plan's section 8 table bounds Server reveals by `qBuild` and established-kernel reads by `min(qCreate, qFinish)`. `compile_bound` gives looser caps: reveals at most the budget of Server send and raw-receive commands, and kernel reads at most the budget of Beacon send and raw-receive commands. `peerKernel` and `ownerKernel` read whenever no local copy exists, including for key IDs that are not installed and Beacons that are not established, and an empty answer is not kept, so such reads repeat. Soundness is unaffected: T4 `actual_le_real` instantiates on `compile A` with `compile_bound` as its budget premise, and its creation-count premise uses only the create cap. Later bills that count reveals or kernel reads use the record-command budgets. Gating the reads on the public log would need an amortized whole-run count in place of the per-command `weighted_bound` argument and changes to several checked modules, so it was not done.
- The local Server metadata placeholder (plan section 8 b) is unnecessary: Server metadata is `Unit`, and the invariant proves that the sender ID equals `setup.serverKeyId`.
- A peer's identity needs only the identity parse of the accept bytes, not the full signature check.

### Open points

- F1, decided by the owner on 2026-10-06: option (a), recorded as deviation D5. The experiment's adversary takes no input; it learns the Server identity key through the protocol, for example by registering one of its own Beacons and reading the build response, which costs registration queries and shifts session ordinals and key IDs, so it is not an exact reduction from an adversary that receives the key as input. Background: The plan gives the adversary the Server's public identity key as input, but T4-T6, the report lines and `InitializedSchedule.source` run a fixed program with no input after the Server is generated, and no source14 command returns the Server key. In the trial the adversary therefore has no input and can learn the Server key only by parsing build responses. Learning it by registering first also shifts session ordinals and key IDs, so this is not an exact reduction from the plan's adversary. Options: (a) accept the input-free adversary as a recorded deviation, at no proof cost; (b) generalize the T4-T6 and report lines to programs that depend on the generated public identity; (c) add a Server-identity getter to source14 and re-prove the line over the extended interface. With the key as input only `Phase1ReadBack` would be needed; the trial needs `Phase2ReadBack` because it reads the Server identity from a build response.
- Post-run reveal mode. On 2026-10-06 the owner chose a post-run "later quantum" mode: after the run, every honest X25519 secret, every DH output and every honest Ed25519 identity secret is revealed, and only confidentiality is claimed. The interface stays open to it. Because `compile_game` equates the whole final deployment state, the mode can be added as a phase after the run that is a function of the final state, without changing `Command` or the compile cases. Open: on the compiled side the secrets are reachable only through source14's identity, prekey and one-time field reads, which `compile_bound` caps at zero, which interact with `revealedAt` and `GoodKem`, and which follow native erasure; the Server identity seed, ephemeral scalars and DH outputs have no read. Its cost is to be designed and confirmed before it is built.
- Not done: the `test` and `fresh` commands with the sampling swap, `CE.Logs`, mode P beyond the wrapper, the public functions `phase`, `owner`, `NoBundleFailure` and `designate`, the comparison of the transported caps with T4's ledgers, and the step from `compile A` to `tag work index`.
