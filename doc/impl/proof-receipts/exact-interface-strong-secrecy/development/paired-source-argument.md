# Paired interpretation of the exact-interface secrecy processes

Status: proposed symbolic source/context proof for independent review. The positive Kr3 biprocesses have not yet produced an equivalence verdict. This document does not assert a source-equivalence theorem in advance of that result. It concerns the existing selected-identity, pre-first-far, private-application profile; computational reductions and the public optional-plaintext experiment remain separate.

## Experiment and contextual statement

Fix one selected fresh Beacon identity and one protected Server signing identity, with the prior source-profile OD2 independent sampling/key-management contract. Actual reuse of the protected Server identity across objects is retained by the per-object host map; arbitrary hidden imports correlated with a selected secret are not added. Unselected source identities and their protocol work can be locally generated by the comparison context, as in the reviewed stronger source profiles. All actual protocol identities, numeric own/assigned IDs, raw message values and source ordering remain literal. Only host analysis handles are newly allocated.

The source host permits at most two target-direction allocations per installed peer and at most three receive attempts before that peer's first successful far opening. The reverse lane starts after consumed registration sequence one, so its near positions are two and three. The forward lane starts at zero, with near positions one and two. Sending, receiving and accepting on different objects may be scheduled in any public host order within the existing serial managed-call interface. Failed seals advance the send state; failed openings retain the receive/cache state. No snapshot/restore, data-race, codec-internal or deployment-storage behavior is claimed.

The host's challenge command supplies an ordinary/test bit and two equal-length, nonempty application alternatives. In b2s a test is eligible exactly when the selected Beacon's actual pinned signing identity is the protected Server identity. In s2b it is eligible exactly when the accepted peer's signing identity is the selected fresh Beacon identity. The acceptance remains arbitrary and fully verified; neither authentication nor root ownership is a freshness premise. Ineligible and ordinary calls use left in both worlds. Eligible calls use the left or right message selected by the common experiment bit. Application plaintext remains private and does not echo or influence public actions, future application inputs, imports or omitted-direction payloads. The public receive reply retains Some/None. This is not an optional-plaintext decryption oracle.

For every one adaptive symbolic source attacker/host program A, construct one comparison context C[A]. The same compiled context executes with either projection of the biprocess; it never receives the hidden bit. Later source inputs may be paired, ciphertext-dependent values obtained by A's program. They are not fixed to an identical ground input list across worlds. The intended statement is that each source projection has the same allowed public observations as C[A] applied to the corresponding comparison projection. Contextual closure would then transfer a proved comparison equivalence. Separate existence of a convenient source trace in each world would not suffice.

## Constructive worker and pending routing

The existing `builder` parameter is the required public worker handle. In both complete main files it occurs only in the input binder, the ghost `FsServerCommitted` object field and the installed worker argument. Every b2s receive guard and s2b send guard tests the corresponding `owner`; all continuations retain it. It does not occur in cryptographic inputs or protocol fields. The selected Beacon is nonreplicated and has one lifecycle. Thus the context can allocate a fresh analysis owner per build occurrence, rather than per real Server object, without modifying any protocol value or asking a private scheduler to distinguish equal-owner workers.

Maintain a pending-lifetime map and a peer map from `(real Server object lifetime, actual assigned ID)` to the selected analysis owner. For accept, allocate an injective analysis token and call label, submit the original candidate and actual own ID, and register the token only on Some. For build, remove the pending lifetime before every binding/counter/availability/host-failure check, preserving a token moved to another Server and consumption on failure. Supply the literal builder identity/own ID, assigned ID and application data. The native public counter and key-availability checks determine whether the comparison failure branch must be used. A fresh analysis owner is installed in the peer map only at successful source publication; production rejects an occupied assigned ID and therefore does not overwrite another entry. The comparison permits extra old workers/assignments, which the context does not use.

A Server send routes by the source caller's requested peer ID; a Server receive first performs the original public frame/sender decode, then routes by that ID in the actual Server's map. It submits the original frame. Missing handles/peers and malformed pre-routing inputs return the source None and install nothing. Object destruction removes its map; no later source call is sent to an obsolete worker. Repeated caller labels are translated through fresh internal labels and restored on return, never used as peer or pending identity. A unique analysis token selects one pending continuation and a unique owner selects one installed worker. Both choices follow only the context's host maps and public outcomes.

Source attempts omitted before routing still consume their source allowance; near calls consume a model slot including failure. Far calls evaluated by a public recipe consume a source slot even when they do not consume a model near slot. Consequently the context never exceeds Kr3, while the comparison's remaining unused slots are additional capability. Failed send allocations consume both source and modeled positions. All primitive, uniform/base and adapter costs remain in the computational source bill; symbolic omission is not free work.

The inherited finish helper omits the source nonempty-application guard. For contextual interpretation this omission cannot be handled merely by choosing not to schedule a failed finish. Instead, run the actual comparison finish internally, inspect its actual returned application value, and return source None and mark the source Beacon aborted if that value is empty. The resulting extra model worker receives no further input and has no autonomous output. Public source host-failure outcomes can similarly discard an internal success before installing a source route; the source failure decision must satisfy the existing bit-independent host/primitive-failure contract. This preserves the actual external reply and source lifecycle without claiming literal identity of the helper API or erasing a secret-dependent observation.

The context encapsulates the comparison channel and forwards actual transcript/API outputs on the external source channel. In a serial accept, the chain-pair disclosure precedes the unique accept reply. Other selected Beacon output phases are explicitly driven and cannot spontaneously produce a chain-pair message. For a nonselected identity the additional parallel root disclosure is drained before starting another accept; whether it exists is the same public exact-identity test. Thus each pair/root is saved under its actual pending lifetime using one public receive program, without inspecting a hidden root or choosing a different worker by world. Source host returns need not wait for any externally observable clock in this untimed symbolic model.

## Exact public response receipts

Each successful build stores its full public response and the associated accept's disclosed material in an immutable list, together with its analysis token/owner and actual host occurrence. When a selected Beacon finishes under the protected Server pin, the context first lets the actual comparison finish run and obtains the real Some/None result. On Some it searches the list for the first full response equal to the original input. This is a public equality test performed by one program; it does not inspect a root or a hidden origin witness.

Two scratch auxiliary checks now prove the stronger full-response/root correspondence in the same direction-specific Kr3 interface: `FinishedResponse(S,B,response,root) && SelectedIdentity(k) ==> BuiltResponse(S,B,response,root)`, where `B=ed_public(k)`. Their processes differ from the positive biprocess only by two nonpublic events and replacing both eligible `choice[left,right]` occurrences by `left`. The query retains exact original response and root. The s2b result is TRUE in 2.456 seconds and b2s is TRUE in 23.268 seconds; these are auxiliary reachability results, not equivalence verdicts.

This ordinary-message projection covers either bit world. In that world a challenge message is one of the two already caller-known alternatives. An instrumented attacker can put the actual chosen alternative into the ordinary-message slot at that call, leaving the original output/event/continuation intact. This implication is used only to prove a safety invariant of each projection, not to select separate contexts for the equivalence conclusion. The executable response-list search below remains the same public program in both projections.

The search terminates after a successful protected-pin finish because its exact response occurred in an earlier build. All matching entries have the same root and disclosed material: equality of the `kex_response` data term gives equality of its initial frame; equality of that frame's `aead_cipher` gives equality of the initial key; expanding that key gives `first(HKDF(first(HKDF(root,symmetric)),symmetric))`. Freeness/injectivity of these exact T0 constructors yields equality of roots, hence equality of both disclosed chain expressions. Therefore taking the first matching occurrence is sound even if there are several identical responses. This uses an explicit symbolic constructor idealization, not generic IND-CCA/PRF or a computational collision theorem. It needs no inference from equal roots to equal KEM key-generation indices.

The initial response has no challenge payload: its application suffix was supplied by the caller. If later adaptive inputs themselves contain earlier paired ciphertexts, the response and receipt values are paired accordingly and equality search still runs the same code. Under contextual equivalence public equality tests are preserved; the source proof does not assume identical future ground inputs or privately synchronize independent origin witnesses.

## Public evaluators for omitted operations

For protected selected sessions, the saved accept/response receipt supplies the literal opposite-direction initial chain and the target-direction first-far chain. It is available before each omitted operation. In s2b, Server b2s receive can precede Beacon finish and uses the chain from that Server accept immediately. A selected Beacon's omitted b2s sends start only after finish, when its public response lookup is defined. In b2s, Server s2b sends use their accept receipt, while the selected Beacon's omitted s2b receives use its successful-finish receipt. The source's own IDs and associated data remain stored independently of worker labels.

The context runs the exact public HKDF projection recipes, seal/open functions and finite receive planner on the original paired input and its public counter/cache bookkeeping. It records successful consumption and failed rollback exactly. The far-chain sequence is literal repeated `ratchet_next`; no `fs_far_chain` replacement or independent random table is used. It returns the original optional result bit and retains the private plaintext for the private application contract. If evaluation fails in only one projection, that is itself a public distinction of C[A], not something erased by the proof. The first far success ends that peer's near experiment as declared; subsequent target-direction operations are not claimed covered.

For an unselected locally generated identity/context, the interpreter knows its independently generated secrets and can perform the original source computation. Imported caller-known keys, including compound key terms, are handled by the known input recipe. For a selected Beacon pin different from the protected Server identity, the challenge branch is left/left but the source behavior must still be reproduced. An honest other Server is locally generated and its actual accept/build/root receipt is known to the interpreter. An attacker-built successful initial frame has a public initial key/root recipe by the exact-T0 ciphertext/commitment occurrence argument, with the current extra disclosures accounted for: disclosed chains derive descendants only, while an initial s2b key under another pin cannot equal a protected Server initial key or any later record key. The compiler may instrument A's own fresh restrictions and public constructor/destructor applications to retain these caller-known recipes; it does not reveal honest private application plaintext. A finite public-construction ledger records the root or its input recipe before the frame is submitted. An unknown imported hidden Server correlated with a selected key is outside the unchanged OD2 profile; an unissued hidden selected Beacon seed used merely as an arbitrary pin supplies no honest Server signing/response source.

The preceding other-pin recipe extension still needs independent finite-ledger review against the exact loaded T0 and output sites. It is not claimed to follow automatically from the older E3 hidden-reply lemma, whose output profile was different. In particular disclosure of post-near chains must never be used to claim their hidden root is available.

## Paired induction and remaining conditions

Induct over the adaptive source host program, using the same interpreter code in both worlds. Maps are updated by the actual reply of the selected public route, and both sides run the same source branch tests. Root/key/packet inputs remain literal paired values; private application outputs never become public control inputs. Generated source names are matched by the same source call and fixed independent symbolic alpha-renaming, not by a hidden successful event. Each retained call is the actual direction-specific process step. Each omitted call is the public evaluator described above, with all original state/cost consequences. Every returned frame/result and exposed protocol field is therefore the required source value under the maintained per-world state relation.

This induction requires completion/review of the other-pin recipe extension, a finite complete owner-use audit and maintained exact transformation/response-origin gates. A passing positive Kr3 equivalence is also still required. Until then these are proposed obligations and partial auxiliary checks, not a source-equivalence result. A later global experiment needs identity/record hybrids with explicit selection losses, reveal/freshness profiles and the computational ideal-component reductions. Neither this symbolic contextual argument nor ordinary private-application fresh-name secrecy closes the public optional-plaintext IND$ game.
