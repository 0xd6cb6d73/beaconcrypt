The initial hypotheses were partly confirmed. Production already used the extracted core's one-use KDF/open phases, request-owned material, and rollback-preserving finish operation; it was incorrect to describe those mechanisms as wholly absent. The remaining production adapter selected primitives and supplied their outcomes outside extraction. It also passed material, sequence, and context independently into `open_frame`, and separately reconstructed returned sender/sequence after finishing the request. Cap'n Proto `read_message` received a copied input slice, so it could accept the first complete message while ignoring trailing bytes. Existing one-key CTX forgery games required a typed target and an adversary-supplied claimed plaintext; their advantage bounds did not by themselves cover arbitrary raw receive attempts that return recovered plaintext.

## Implementation and security impact

`decode_crypto_frame` now consumes through a mutable slice and rejects remaining bytes. Both server sender routing and ratchet decryption use this decoder, so appending junk or a second complete frame is rejected before ratchet ownership moves. This is an exact-framing requirement, not a claim that Cap'n Proto has a unique canonical wire encoding. Ordinary complete messages retain their wire format. Applications that previously passed concatenated frames to the single-message API must frame them individually.

`OpenFrameContext::from_frame` validates the protected-payload length and splits the AEAD ciphertext/tag and outer commitment once, before taking the ratchet kernel. Fixed-width tag and commitment references and the AEAD ciphertext refer to the same parsed payload. The associated data remains a fixed-width input borrowed from the selected established peer; the frame cannot supply it.

`execute_open` now consumes `ReceiveOpen<OpenFrameContext>` directly. The caller cannot independently substitute material, sequence, or context into this executor. It obtains all three from the actual core request, builds the commitment transcript, compares the commitment, calls ChaCha20-Poly1305 on the same protected payload, and constructs `Decrypted` from the recovered plaintext and request-owned metadata. Only that primitive result is passed into `open.finish`. The surrounding loop installs the returned kernel before returning the output. Every normal cryptographic failure still calls `finish(None)`, which restores the entry kernel. This interface narrows the production correspondence obligation; it does not prove libsodium or the Rust glue semantically equivalent to Lean.

The change does not establish new network-forgery advantage bounds. Trailing-byte rejection removes a concrete parsing ambiguity. The field-provenance and executor changes make accidental internal field substitution harder and expose a smaller review boundary. No recipient-authorization policy, ratchet compromise recovery, snapshot protection, or timing claim is added.

## Plain-English proof explanation for integration into the maintained analysis

The new module defines a raw-byte receive endpoint rather than requiring a well-formed forgery target. `FrameDecoder` is an explicit external, pure decoder parameter returning the sender, sequence, and protected payload or failure. Its type does not prove Cap'n Proto traversal policy or exact consumption; those are separate Rust/parser obligations. Machine integer fields match the wire widths. `ValidFrame` checks the expected sender, excludes an empty encrypted body exactly as production does, and checks the session associated-data width. The session AD is supplied by the selected peer, not the adversary's frame.

`ctxOpenReply` reads the actual extracted request getters and applies the fixed byte-model CTX operation. That operation decodes the protected payload, verifies the commitment, and returns the AEAD's recovered plaintext. The adversary does not supply a plaintext claim. `rawReceive` runs this callback through the existing extracted `receiveNext` driver after decoding and validation.

`prepared_fields` handles the cached-key and future-key preparations separately. In each case it proves that the request retains the admitted context and exact target sequence. `ctxOpen_success` and `ctxOpenReply_success` expose the actual decryption output and the material and sequence returned by the extracted getters. `driver_success_request` combines those facts with the existing successful-execution classification. Its witness retains the prepared request, its material getter, exact context and sequence, and exact finish/publication equation. No callback-correctness hypothesis equivalent to successful authentication is introduced.

`validated_record_wf` derives field well-formedness from extracted fixed-width key/nonce material, machine integer bounds, and the runtime AD-length check. It does not ask an adversary to provide a well-formed target. `rawReceive_success` proves that any successful raw operation from a structurally valid kernel exposes the exact decoded frame, successful validation, actual prepared open request and material getter, exact request context and sequence, derived record well-formedness, exact inner-record decoding and re-encoding, a matching commitment, the base AEAD opening to the returned plaintext, and `ReceiveSuccess` for the target in the resulting kernel. The latter entails that the key was consumed.

`rawReceive_failure_entry` covers parser rejection, field-validation rejection, replay/window rejection, commitment failure, and AEAD failure by case analysis and the extracted driver's existing unconditional rollback theorem. Every rejection returns the exact entire entry kernel; this theorem does not require a structurally valid initial state. `rawReceive_success_replay` applies the extracted consumed-key replay result to show that a second submission of the same raw frame returns no plaintext and leaves the poststate unchanged. `rawReceive_total` combines total pure decoding with the unconditional extracted driver totality result. This is totality of the delimited mathematical wrapper, not whole-application panic freedom or a parser/runtime safety certificate.

No new primitive assumption, proof placeholder, or unchecked statement was introduced. The new success endpoint uses the byte-model cryptographic functions. It does not claim that the existing typed, claimed-plaintext one-key CTX advantage bounds already apply to this broader raw interface. In particular, manufacturing a typed target by inserting a secretly recovered plaintext into an adversary's output would not be a valid efficient reduction and is not done here.

## Focused validation

The development build used the installed Rust 1.96 toolchain, the existing Cap'n Proto 1.1.0 binary, and the available libsodium store library. `RUSTFLAGS='-C linker-features=-lld'` bypassed a local Rustup linker wrapper pointing to a collected Nix path. Builds used `/tmp/security-adapter-target`. Lean used the pinned 4.31.0 toolchain, an isolated copied project build directory, and existing dependency packages; this workstream launched no Nix shell/build, garbage collection, or complete mutation suite.

- `cargo fmt --all`: passed.
- `cargo test -p beaconcrypt --test raw_receive`: 3 passed. The tests cover every truncated frame prefix, trailing junk and concatenated messages, zero/extreme sequence fields, incorrect sender, all protected lengths through the empty-body boundary, body/tag/commitment corruption, future and cached-key retry/replay, server routing, and two sessions with the same sender and sequence.
- `cargo test -p beaconcrypt --lib raw_receive_tests`: 2 passed. A deliberately authenticated empty payload is rejected, and an AD mismatch preserves the full serialized ratchet before an authentic retry succeeds. The latter isolates AD failure using identical actual key material rather than relying on different-session keys.
- `cargo test -p beaconcrypt --test protocol`: all 51 existing protocol integration tests passed.
- `lake env lean BeaconcryptCore/Computational/RawCtxReceive.lean`: passed after every completed proof and the independent-review provenance strengthening.
- `lake build BeaconcryptCore.Computational.RawCtxReceive`: passed; only existing generated extraction naming warnings.
- `cargo clippy -p beaconcrypt --lib --test raw_receive --test protocol`: passed; only existing core style warnings.
- Both required role-specific `cargo check -p beaconcrypt --no-default-features --features pqxdh,<role> --lib` commands: passed; the beacon-only build retained existing dead-code warnings.

Forward secrecy still does not imply post-compromise recovery. Retained skipped keys, snapshots, copied secrets, and application plaintext constrain past-message confidentiality. Constant-time primitive use and commitment comparison do not prove constant-time protocol execution. Self-signed beacon authentication does not authorize tasking. This milestone changes none of those boundaries.
