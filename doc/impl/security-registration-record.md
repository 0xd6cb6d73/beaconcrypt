# Registration model fidelity milestone

## Ownership and reviewed baseline

The registration workstream starts from `10efd2b` through the shared M0 plan on branch `codex/security-registration`. It owns the ProVerif main registration extension, result checking, source/model synchronization fixtures, and dedicated production integration tests. The integration agent supplies the Make target and owns maintained analysis and trust-boundary inventory updates. No production registration behavior, wire format, cryptographic primitive, or generated extraction artifact changes in this milestone.

The finding is confirmed against `HonestBeacon` in the original main `environment.pvl`: it opens `appCipherText` using sequence-one material and requires sequence one. The production `finish_registration` instead invokes general ratchet receive and checks the decrypted eight-byte registration key-ID prefix against the outer response. The existing isolated later-sequence control already demonstrates one genuine sequence-three substitution, but the main process did not admit that completion schedule.

## Implementation and proof changes

The main baseline now runs replicated `MainLaterBeacon` and `MainLaterServer` scheduling branches alongside the existing roles. The later beacon retains the checked single-use initiation, signed bundle, pinned-server response parsing, ordered PQXDH input, root, and associated-data prefix. It derives sequence-three material, verifies the entire frame using the existing `open_frame`, validates the decrypted registration prefix, and establishes while retaining skipped sequence-one and sequence-two keys. This branch ends at establishment. The ordinary first-completion role retains its existing bounded application and compromise schedule.

The later server retains the full existing signature, replay-consumption, PQXDH derivation, original response publication, and first-two-record prefix, together with the original suffix after record three. Its application selects one of three sequence-three plaintext classes: a matching registration prefix, a different prefix equal to the pinned server key ID, or an unframed payload. All use the same production-shaped record seal and genuine same-session ratchet material. The peer's assigned ID is a fresh name, so it differs from the public pinned server ID in the wrong-prefix control. The new fixture compares the entire unchanged server prefix and suffix and the unchanged beacon initialization prefix against the existing checked roles. These source comparisons are maintenance tripwires, not a semantic extraction theorem.

`establishment_session` projects the existing 18-field proof transcript onto a 14-field cryptographic-session transcript. It retains the server and beacon identities, authenticated InitKex, registration identifier, selected prekey, one-time key, ML-KEM public key, server ephemeral key, exact KEM ciphertext, ordered root input, root, associated data, pinned server key ID, and registration origin. It removes exactly the application frame, complete response container, assigned numeric routing ID, and `session_label` derived using that routing ID. Removing those fields is a strictly delimited change in property; the original exact-response property does not extend to arbitrary accepted later completion.

The main safety queries prove injective correspondence from every modeled `BeaconRegistrationCompleted` to a committed cryptographic session and to the exact `RegistrationRecordSent` at the accepted sequence with the same complete authenticated plaintext and frame. Completion events record the claimed outer routing ID; server commitment and record-origin events record the server's actual assigned ID as a separate argument. The queries do not equate these two IDs. The original `BeaconCommitted` event remains restricted to sequence-one completion, where its exact 18-field response correspondence is still proved. `BeaconAnyCommitted` records both scheduling branches and deliberately fails the unqualified exact-response property in a checked negative control.

The eight main controls use the actual enlarged baseline process, rather than a separate witness-only process. They require reachable sequence-one and sequence-three completions; require reachable genuine-server emissions of each invalid payload class; prohibit completion of the exact invalid candidate response; exhibit failure of unqualified exact-response agreement; and require reachable outer-ID relabelling of a later genuine record. The result checker requires all eight exact queries and their respective outcomes. The earlier 18-query isolated sequence-three control remains enabled and passes unchanged.

## Newly confirmed routing-ID limitation

A genuine later application payload can begin with eight bytes encoding a value different from the server's assigned recipient ID. If an attacker substitutes that record into the response and changes the outer `keyId` to match those authenticated bytes, production registration succeeds and commits the claimed ID. The four production tests include this accepted case. Subsequent outgoing records carry that different sender ID and the original server cannot decrypt them through its original recipient routing entry. This is an authenticated same-session record and application-prefix confusion; it is not an AEAD or commitment forgery and does not establish an unauthorized-recipient plaintext disclosure.

The invalid-candidate controls use equality of the complete response, so they prove rejection of a wrong authenticated prefix when the outer ID remains the server's assigned ID. A separate positive control explicitly demonstrates that changing the outer ID changes the result. The cryptographic-session correspondence deliberately excludes the mutable claimed routing ID. The next concrete protocol step is a versioned authenticated registration envelope, or a design that authenticates the intended recipient ID in every record eligible to complete registration. Such a change must preserve intended later completion and requires wire/semantic compatibility design and corresponding binding updates; it is not silently imposed here.

## Validation evidence

- The dedicated `beaconcrypt/tests/registration_completion.rs` suite passes all four tests using Rust 1.96 and the repository's supported primitive implementation. It checks accepted completion at sequences 2, 3 and 51; exact retained-cache count; target replay rejection with unchanged ratchet metadata; delayed skipped-record recovery and one-time consumption; initial-frame recovery; and outbound operation after valid later completion.
- Invalid production cases cover a wrong authenticated ID prefix, too-short authenticated plaintext, changed outer ID with unchanged authenticated prefix, sequence 52 beyond the initial receive-cache bound, ciphertext corruption, and a genuine record from another session. Failed completion aborts the beacon, leaves no established ratchet, and prohibits retry or application sending.
- The accepted outer-relabel test proves that the newly documented limitation is reachable in production. These runtime tests do not establish symbolic-to-Rust correspondence or cryptographic security.
- All 14 source/transcript fidelity tests pass after synchronizing the two additional associated-data call sites and adding the main-schedule fixture. The new fixture preserves the original constructor, signature, replay, root, AD, and record-selection checks. The Make scenario count increases from 28 to 29 and remains checked.
- Direct ProVerif 2.05 validation proves all 14 final main safety queries, including the explicit claimed/server-assigned routing-ID event parameters, and all eight main reachability witnesses. Both strict result checkers pass within the existing 240-second per-scenario timeout.
- All eight final main controls and their strict result checker pass. Sixteen deliberate missing-query and reversed-result mutations of the control output are rejected by the checker. All 18 existing isolated later-sequence control queries and their unchanged strict result expectations pass. No timeout or unknown result is counted as proof success.
- `cargo fmt --all`, its final `--check`, `git diff --check`, and `cargo clippy --locked -p beaconcrypt --test registration_completion` pass. An optional stricter `-D warnings` run stopped on 38 existing core warnings; those warnings are outside this proof/model change and the repository-prescribed lint mode succeeds. No generated ProVerif extraction artifact was regenerated, and no new axiom, placeholder, disabled check, or unsupported primitive theorem was introduced. Full repository verification, inventory review, linting, and mutation testing belong to integrated milestone validation.

## Exact remaining boundaries

The main symbolic result covers replicated sessions with finite first- or third-sequence completion schedules and three modeled third-record application payload classes. It does not prove every production-accepted sequence, all possible application payloads, or arbitrary subsequent schedules after later completion. Production accepts sequences through the available cache limit; the regression checks at 2, 3, 51 and rejection at 52 do not generalize the symbolic theorem. The next formal step is a parameterized bounded receive/registration composition theorem, or a justified abstraction connecting all accepted sequence/payload choices to the cryptographic-session and record-origin events.

Cap'n Proto byte decoding, concrete cryptographic semantics, Rust execution, full beacon/PQXDH state publication, compiler correctness, persistence, crash recovery, and actual memory erasure remain outside the hand-written ProVerif correspondence. The finite cache constructor proof in the pre-existing isolated control and Rust fixture comparisons are separate evidence. Ideal KDF/hash injectivity and ML-KEM/public-key equations remain explicit symbolic assumptions, not computational primitive results. The symmetric ratchet does not recover from current-chain compromise; retained skipped keys, snapshots, copied secrets and retained application plaintext limit past-message confidentiality. Self-signed beacon authentication does not supply recipient authorization.
