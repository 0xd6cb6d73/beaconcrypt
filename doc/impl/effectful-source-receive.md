# Effectful source receive and one-owner raw interface (HB-91)

This focused checkpoint follows the published general-admission topic `db27d3da5cb67ce57e0f615a8c20b29c7977c195`. It adds thirty-eight checked operational statements in four Lean modules. It preserves production behavior and every ProVerif scenario. It does not complete the computational-symbolic bridge, authenticate a raw acceptance, or establish the native codec, dynamic peer lookup, correlated-key reduction or persistence boundary.

The source receive loop temporarily takes the whole ratchet, processes typed KDF capabilities, and consumes an opening capability with the actual optional result. It reinstalls the returned kernel before returning that result. A failed speculative derivation or opening restores the protocol kernel, while primitive queries, cache entries, randomness and instrumentation survive. The new interface carries those two states separately and retains both send and receive chains, counters and all cached material in a single owner.

## Actual interfaces and accounting

`RawCtxOwnerOracle.ReceiveSpec` is a private source-callback interface. Its left request is the extracted `SymmetricRatchetKdfRequest`, with an actual `RatchetKdfResponse`; its right request is the owning `ReceiveOpen`, with the actual optional output. It is not a new primitive security assumption or an adversarial oracle. The source program recursively evaluates the actual capability continuation. The normalizers use only already-proved totality and uniqueness; they add no timeout fallback. They are noncomputable mathematical selections with checked source equalities, not proposed executable replacements for the Rust adapter.

`RawCtxWholeOwner.PrimitiveSpec` makes the adapter boundary explicit: actual KDF requests and opening inputs containing source material, source sequence, original raw bytes, decoded fields and the selected owner's associated data. The opening result is optional plaintext bytes. The wrapper constructs `Decrypted` from that result and request metadata before `finish`; no recovered plaintext is inserted into an adversary-supplied target. The primitive interpreter is arbitrary and stateful. No authenticity, key independence, nonce uniqueness, collision bound or security advantage is assumed by these operational theorems.

One receive has at most `effectDepth effect` KDF callbacks and one source opening callback. For a KDF effect the existing rank is `remaining + 1`; rejected and ready-to-open effects have rank zero. This is an explicit source rank bound, not a newly proved tight global 51-query bound. An opening callback with missing material performs zero inner opening calls; one with material performs the displayed single optional opening operation. CTX hash/cache accesses, base-AEAD operations, randomness and Extract/HMAC query costs belong to their component interpreters and ledgers. They are not declared free or bounded merely by counting private callback names. Every outer raw call is separately counted, including parser, sender, shape, replay and failed cryptographic attempts. The raw-only adaptive schedule bounds those outer attempts by the caller's checked `qRaw` budget; it supplies no budget for additional ambient or reveal interfaces.

`rawReceive` explicitly checks empty bytes, external decoding, sender equality, protected-payload shape and associated-data width before source admission. Native associated data is an array of length 153; an instantiation with a dynamically represented list must establish that width. The selected owner retains a complete `ConcreteRatchetKernel` and arbitrary role metadata. `rawGame` keeps complete primitive state outside that owner. `ownerImpl` serializes both in one StateT state and returns only the actual optional API result to the client. This is an operational publication order, not a proof of locks, durable transactions or linearizable CAS.

## Scope and remaining composition

The source anchors are `decrypt_message_with_ratchet`, `execute_open` and `OpenFrameContext::from_frame` in `beaconcrypt/src/ratchet.rs`, plus the established Beacon and Server routing paths. The getter, admission, resume and publication equations are linked to the extracted core. The outer raw decoder and StateT adapter have been formally specified and independently compared with production source; this is not a proved extraction of Cap'n Proto, the mutable native owner slot, or the whole Server peer map. Success still needs the prepared-sequence/decoded-target relation and the actual selected key handle connected to its correlated record material in the probabilistic interface. Existing fixed-interpreter structural success/replay theorems are not silently generalized to arbitrary random replies by this rollback result.

The current schedule client has only the raw interface. Arbitrary session creation, attacker-owned registrations, concurrent sends, public cryptographic queries, network observations, reveals, compromises and persistence actions require the common experiment and their separate state transitions and accounting. Private randomness can be supplied by an outer caller, but the displayed theorem does not assert a complete caller-randomness interface. The current owner has already been selected by routing; it does not account for session or record target-selection losses. A dynamic multi-key reduction must preserve correlations and use the existing ordinary CTX/AEAD endpoints rather than sample an independent record-key table.

The API's optional plaintext is an explicit result carrier. If a confidentiality adversary receives its unknown target through this interface, that target is declassified or nonfresh. ProVerif's public network observation does not automatically expose every honest application's return value. Physical erasure, compiler and primitive implementation contracts, foreign copies, allocator/OS behavior and durable storage remain external. Integrity, rollback resistance, ownership, crash behavior and linearizable persistence require explicit deployment premises; an unkeyed snapshot digest supplies none of them.
