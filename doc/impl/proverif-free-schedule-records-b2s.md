# Free-schedule ProVerif records, Beacon to Server (fs-records-b2s)

This guide records stage P3 of the staged ProVerif plan for audit findings F2, F13 and F11: the `fs-records-b2s` scenario, in which Beacons register with Server objects and then send them records under an attacker-chosen schedule, its targets, controls and witnesses, and the checker, transcript-fidelity and inventory gates that pin it. It follows the [fs-registration guide](proverif-free-schedule-registration.md) of stage P1 and the [fs-records-s2b guide](proverif-free-schedule-records.md) of stage P2, whose vocabulary, serial verification group, checker, declaration policy and receive-window style it extends. The plain-English explanation of every result is in [What beaconcrypt's formal verification proves](../formal-verification-analysis.md#free-schedule-proverif-records-beacon-to-server-fs-records-b2s), and the meaning of every fs event as a Rust API outcome, with what each claim says about Rust, is in [the fs event-meaning reference](../proverif-fs-event-meaning.md#beacon-to-server-records-fs-records-b2s-stage-p3).

Every fs result is a symbolic result (Dolev-Yao attacker, free constructors, ideal hash, KDF and AEAD) for a bounded process. None of them is a computational bound. Cap'n Proto is out of scope: messages are abstract byte strings that each side can decode. libsodium is a black-box functional contract. Persistence is out of scope, and the proof Server has perfect key management and no backup or restore (owner decision OD2). No axiom, restriction, lemma or proof-only process is used. Reading the results as statements about the Rust API rests on the paper arguments listed under [Pending paper arguments](#pending-paper-arguments); until they are written and reviewed, each result is cited as a symbolic result for the fs process, which models the Rust interface under these pending abstraction steps.

## Basis and decisions

The Rust basis is branch `codex/full-proof-composition` at `d937aab`, whose Rust sources are identical to `959cdab` (the basis of the plan and of the P0 spike), `533901f` (P1) and `9e588c6` (P2): `git diff 959cdab d937aab -- beaconcrypt/src beaconcrypt-core/src` is empty. The Rust code is authoritative: where the model and Rust differ, the model follows Rust. The decisions applied here are those of gate G0, the owner and the orchestrator for P3:

- OD1: bounded results are the ProVerif deliverable. OD2: one live Server state per identity key; the proof Server is idealised. OD7: at most 1800 s per target and a 10 GiB address space per run, the fs group serial and alone on the machine, about 3 h for the whole group, of which about 77 minutes remained for this scenario after P2. OD11: the serial run is the verification record.
- Theory `crypto.pvl`, the self-contained `fs-common.pvl`, the single allowlisted selection heuristic nx and the "v2" early-fresh Server coins, all as in P2.
- Bounds (K_s, K_r, T_max) = (2, 3, 2) with the far branch (G0 section 3.3): each Beacon sends sequences 1 and 2, and each Server peer receive worker has K_r = 3 attempts from r = 0. Every record peer has the key ID `fs_kid(1)`, so any object's frames can reach any worker and only the AEAD and the CTX commitment separate peers. The Server routes on the claimed sender ID, as Rust does. Attacker-registered peers are served by the same Server code. Witnesses and controls run at the smallest K_r that exhibits them.
- G0 option B: C2 and C3 run in the form in which failed opens are interleaved with later receives; the fail-stop form is used only where documented and justified, here for C2 with adversary-chosen plaintexts and for C4 ([step 12](#model-steps-and-their-justifications)).
- UKSr (record identity agreement) replaces C2 as the record-form target of the C-UKS control, with its exact FALSE line (G0 section 7).
- A1 and A2 are re-proved in this process.
- E3: A1, A2, S2, UKSr and C4 run in a pin-free process, in which the attacker chooses every Beacon's pin; C2 and C3 run with honest pins only, and their pin independence rests on a written simulation argument that is not yet reviewed ([step 13](#model-steps-and-their-justifications)). Seven queries have been measured in both processes; pin-free C3 does not fit the budget next to pin-free UKSr, and pin-free C2 does not fit the per-target limit (chosen, fail-stop, measured) or the budget (fresh, extrapolated) (step 13).
- Adversary-chosen plaintexts (E7): S2 and UKSr run without the adversary-chosen send step, which would make them false by construction.
- C4 is meaningful only while no honest sender seals above T_max; here every Beacon sends sequences 1 and 2 only and no Server sends a record.
- Every verdict has a class (security, witness, control, definitional, limitation); a check that holds by construction is never counted as evidence.

## Pending paper arguments

The ProVerif verdicts are exact statements about the fs process. Their Rust readings rest on the following arguments, which are not settled unless stated:

- **L1, L2, L4 and L5 (pending)**, as in P2: accept and build scheduling, one registration per record object with routing over-approximated by merged key IDs, the send relation, and the Beacon lifecycle. In this scenario L2 also covers the Server receive: a Rust object with several peers routes a frame to the peer installed under its claimed sender, and the model lets the attacker deliver it to the receive worker of any object whose peer has that ID.

- **Written in this guide, not yet reviewed:** the Beacon-to-Server half of the direction split E19 ([step 4](#model-steps-and-their-justifications)), the deletion argument for the fail-stop form E21 ([step 12](#model-steps-and-their-justifications)) and the pin-independence argument E3 for C2 and C3 ([step 13](#model-steps-and-their-justifications)). ## Model structure and Rust mapping

Unbounded Server objects share the one honest Server identity and own key ID. Each object processes one registration bundle, builds the response when the attacker schedules it, and then makes three receive attempts for the peer it installed. Unbounded honest Beacons run alongside: each draws fresh keys, sends one bundle, finishes at most once and then sends two records, each when the attacker schedules it. The attacker builds its own identities from public constructors, and the same Server code serves them. Every attacker input is `[precise]`, and honesty appears only in the queries.

Server object (`FsB2sServer`): the registration prefix and the response build are those of `fs-records-s2b` ([records guide](proverif-free-schedule-records.md#model-structure-and-rust-mapping)), with the same citations; after the response the object starts its receive worker instead of sending taskings.

## Model steps and their justifications

1. **One bundle per Server object and routing on the claimed sender (pending L2).** Each Server object gives its one peer the key ID `fs_kid(1)`, and its receive worker accepts a frame only if the frame's claimed sender is that ID. In Rust the Server reads the claimed sender before touching any ratchet, selects the peer installed under it, rebuilds that peer's associated data from the stored identity, and opens with that same ID as expected sender (`server.rs:233-249`), so the expected-sender check of `ratchet.rs:510-513` always passes and the routing lookup is the real check. Because every model peer has `fs_kid(1)`, the attacker chooses which object's worker receives each frame, and only the AEAD and the CTX commitment, which bind the sender ID and the associated data, can reject a frame sealed for another peer. This over-approximates Rust's deterministic routing within one object.
2. **Early fresh Server coins (v2, E20).** As in fs-records-s2b ([records guide step 2](proverif-free-schedule-records.md#model-steps-and-their-justifications)): the registration prefix of the Server object is the same, one bundle per object, so the argument applies unchanged.
3. **The build input carries no test.** As in fs-records-s2b step 3: with one bundle per object, withholding the build input is the dropped token, and a test on its value would select no further behaviour.
4. **Direction split, the Beacon-to-Server half (E19).** The scenario has no Server send worker after the response and no Beacon receive window after the finish. The argument for the Beacon-to-Server claims: (a) a Server tasking would output a frame sealed under the Server-to-Beacon chain, which is `hkdf_first_32` of the root's HKDF output (`crypto.pvl:72-80`), whereas every Beacon-to-Server key comes from `hkdf_second_32` and its successors; in the free-constructor theory no term built from the first projection yields the second or a successor of it, so these frames give the attacker no Beacon-to-Server key and no Beacon-to-Server frame; (b) such a frame carries the Server's own key ID as sender, and the Server installs peers only under `server_kid + n` with n ≥ 1 (`pqxdh.rs:838-844`), so its own receive refuses the frame at the routing lookup (`server.rs:237-245`), a relabelled frame fails the CTX commitment, which binds the sender ID, and a Beacon's finish ends in the same terminal abort for every frame above sequence one (step 5); (c) a Beacon receive outputs nothing in the model (the `Some`/`None` bit is not published) and changes only the receive fields of the Beacon's ratchet (receive counter, chain and cache), which no Beacon send reads (`concrete.rs:171-182` against `refined.rs:700-778`), and a Server send changes only the send fields of the peer, which no Server receive reads; (d) the removed workers' events (`FsSent` at t ≥ 2 and `FsReceived` after the finish in the Server-to-Beacon direction) occur in no security query of this scenario: the security target C3 fixes the Beacon-to-Server direction and covers the Server receives, and the only query that mentions a Server-to-Beacon `FsReceived` is the definitional check C3-finish, which concerns the Beacon's finish at sequence one and holds here by construction only because the Beacon receive window is removed; fs-records-s2b covers the Beacon receives, the finish included. Removing the workers therefore removes neither a Beacon-to-Server event nor any attacker knowledge that a Beacon-to-Server claim depends on. This is a paper argument written here, not yet separately reviewed.
5. **The finish opens its frame only at sequence one.** Rust's finish opens the response frame with the general receive on a fresh ratchet, which admits t in 1..51, and then aborts unless t = 1 (`beacon.rs:462-470`); the abort returns `None` and every later call on the Beacon returns `None`. The model aborts before the open for every t ≠ 1. Nothing observable differs: both end the Beacon with no output, and neither emits an event of this scenario (the witness `FsBeaconFinishOpenedLater` and the sequence-one gate controls are fs-records-s2b's, where the Server sends later frames). This is the finish shape of fs-registration ([its step 4](proverif-free-schedule-registration.md#model-steps-and-their-justifications)).
6. **Two send forms (L6 item 4, E7).** Rust lets the application send any nonempty bytes (`beacon.rs:152-163`; `ratchet.rs:421-423`). `fs-records-b2s-sends.pvl` sends fresh bytes at sequences 1 and 2. `fs-records-b2s-sends-chosen.pvl` lets the adversary choose, for each record, either fresh bytes or a whole plaintext of its choice, so every trace of the fresh form is also a trace of the chosen form. A1, A2, C3 and the definitional check C3-finish run in the chosen form, and C2 and C4 run in it in the fail-stop form (step 12). S2, UKSr and the witness PINREAD run in the fresh form, because with an adversary-chosen plaintext the attacker knows the plaintext (S2 and PINREAD would hold or fail by construction) and can seal the plaintext it chose for an honest Beacon on a peer it registered itself (UKSr would fail by construction). C2 also runs in the fresh form in the failure-interleaving receive (G0 option B), because its chosen form does not fit the caps there: in a development run it ran out of memory at the 10 GiB cap after 933 s; C4's chosen form in the failure-interleaving receive was stopped after about 11.5 minutes, when its clause queue was shrinking too slowly to finish within 1800 s. The witnesses and the controls use the fresh form; a witness or a FALSE control found there exists in the chosen form too. Adversary-chosen plaintexts are any terms; a term that denotes the empty byte string would be refused by Rust before allocation, so the model has extra sends there, which only adds traces.
7. **Fresh registration payload.** As in fs-registration and fs-records-s2b, the response payload is a fresh name per build. A1 is therefore shown for fresh registration payloads only: an adversary-known or adversary-chosen `data`, and the default byte 0xFF, are not covered. The send forms of step 6 concern the Beacon records only.
8. **Receive state, capacity and the far branch.** The receive state is r and the flag `cached_1`: after the build r = 0 and the cache is empty, so position 1 is the only position that can be cached below T_max = 2 (it is cached when sequence 2 is accepted from r = 0). Rust admits a target t > r if t ≤ r + 51 − |C| (`control.rs:223-245`); here |C| ≤ 1, so every t ≤ T_max is admitted and the capacity never binds below T_max; sequence 0 is rejected as an old target that is not cached (`concrete.rs:264-274`). Above T_max the far branch over-approximates admission: it accepts every t > T_max but opens with model-only key material, `ratchet_material(fs_far_chain(chain_3, t))`, derived by a public function from the chain at T_max + 1, which no process outputs; Rust opens with the material of the real chain at t. Within these bounds no honest sender seals above T_max: every Beacon sends sequences 1 and 2 only (K_s = T_max = 2), and no Server sends a record (step 4). C4 is therefore meaningful here: it shows that the far branch never fires for a peer whose identity secret the attacker does not hold, and the witness FAR shows that it fires for an attacker peer. A later stage that lets an honest sender seal above T_max must raise T_max or derive the far material from the real chain, or C4 would hold for those frames by construction. The branch emits only `FsFarAccepted` and the worker stops, so no claim says anything about a peer direction after its first far acceptance (OD4, pending L3).
9. **Where `FsReceiveRejected` is emitted (E22).** The event is emitted for every parsed frame routed to the peer (claimed sender `fs_kid(1)`) that is rejected at a target t ≤ T_max: an old target that is not cached, rejected before any open (`concrete.rs:270-274`), a failed cached open and a failed future open at 1 or 2. It is not emitted for a failed far open or for a frame whose claimed sender selects no peer, which Rust refuses before touching a ratchet. Every `FsReceived` of a receive step is followed by `FsReceivedFrame` with the accepted frame, as in s2b. ProVerif generates no clause for an event that a query does not mention, so these witness-only fields change no other target.
10. **Bounds for witnesses and controls.** The security results run at K_r = 3. The Server peer starts at r = 0 with nothing accepted, so the out-of-order witness C5a (2, then the cached 1), the forged-then-genuine witness C5b and the replay witness C5c (a frame accepted, then delivered again) each need two receive attempts and run at K_r = 2; S4, FAR, PINREAD and C-UKS need at most one Server acceptance and run at K_r = 1; the definitional check C3-finish concerns only the Beacon's finish, which the Server receive bound does not reach, and runs at K_r = 1; C-RETAIN (2 accepted with 1 cached, 1 accepted from the cache, 1 accepted again) and C-STALE (2 accepted, a forged frame refused, 2 accepted again) need three and run at K_r = 3. Each receive attempt waits for an attacker input, so a trace at a smaller K_r is also a trace at a larger one, and running a witness or a FALSE control at a smaller bound is not a weakening.
11. **Control hooks.** The receive-window library has three `letfun` hooks, `fs_b2s_cached_after_success`, `fs_b2s_failed_r` and `fs_b2s_failed_cached_1`, whose real bodies return `false` (the cached key is removed) and the entry state after a failed open; ProVerif inlines them. C-RETAIN keeps the cached flag after a successful cached open. C-STALE makes a failed open at t ≤ T_max restore the state left by the build (r = 0, nothing cached); with K_r = 3 that is exactly "the state from before the previous success" of the plan, by the argument of the s2b guide (step 11): after one earlier success it is the state before that success, after none it is the entry state, and the state restored by the third attempt is never used. C-UKS loads `fs-control-uks.pvl` of fs-registration unchanged (DH3 in the DH2 slot of the root input, and associated data without the Beacon identity) in place of the binding library, and its target is UKSr, which replaces C2 as the record-form C-UKS target because C2's corruption disjunct excuses exactly the unknown-key-share events (G0 section 7).
12. **Fail-stop (E21) and the deletion argument.** In the fail-stop bound file a failed open of a parsed frame (a failed cached, future or far open) ends the receive worker; a parse failure, a frame for no peer and a rejected old target, which open nothing, continue with the next attempt in both forms. Every trace of the fail-stop form is a trace of the failure-interleaving form. Conversely, take any trace of the failure-interleaving form `-kr3`: a failed attempt there consists of the frame input, the tests, the failed open, at most one `FsReceiveRejected`, and the continuation with the next attempt instance at exactly the entry state (the real window hooks return r and `cached_1` unchanged, and the far branch passes them through); it outputs nothing. Delete every failed attempt and number the worker's remaining attempts consecutively; the attempt instances differ only in their continuations, so the result is a trace of `-kr3` with no failed open, hence a trace of `-kr3-failstop`, with every event of the original trace in the same order except the deleted `FsReceiveRejected` events, and with the same attacker knowledge at every remaining step. A query that does not mention `FsReceiveRejected` and is violated by the original trace (for an injective query, by the same events and matches) is therefore violated by the new one: such a query that holds in the fail-stop form holds in the failure-interleaving form. This is a model-level argument; it uses the failure neutrality that the failure-interleaving form has by construction, so the Rust reading of a fail-stop result rests on L3 exactly as that of a failure-interleaving result does. It is written here and not yet separately reviewed. It is used for two targets only, both with adversary-chosen plaintexts, whose failure-interleaving chosen forms do not fit the caps (step 6): C2, which also runs with fresh plaintexts in the failure-interleaving form, as G0 option B requires for C2 and C3, and C4, which option B leaves to the fail-stop form. Because every trace of the fresh form is a trace of the chosen form, the fail-stop C2 and C4 also imply their fresh failure-interleaving forms; C2's fresh failure-interleaving target is kept so that one C2 result does not rest on the deletion argument. The checker allows the fail-stop form only for these two query files, only for security results at K_r = 3 in the chosen form, and only if the query file does not mention `FsReceiveRejected`.
13. **Pin independence (E3).** Rust Beacons may pin any Server key and ID (`beacon.rs:59-83`), and every Beacon of `FsRecordsB2sMain` pins the honest key and ID. In this scenario a Beacon sends records after a finish that depends on its pin, so the P1 argument (the pin enters only the finish, which outputs nothing) does not carry over. `FsRecordsB2sMainAnyPin` lets the attacker choose the pinned key and ID of every Beacon; every trace of `FsRecordsB2sMain` is a trace of it, with the honest pin chosen for every Beacon, so a TRUE result in it implies the same query with honest pins, and a FALSE result with honest pins is also one in it. The security targets A1, A2, S2, UKSr and C4 (adversary-chosen plaintexts, fail-stop) run in it, and so do the definitional check C3-finish, the witness PINREAD, which shows that a Beacon pinning an attacker key really finishes and sends records the attacker reads, and the control C-UKS. C2 (both forms) and C3 run in `FsRecordsB2sMain`, as do the witnesses C5a, C5b, C5c, S4 and FAR and the controls C-RETAIN and C-STALE, which need no pin argument: a trace found with honest pins is a trace of the pin-free process. The checker requires every b2s query file to end with one of the two processes, and its regression test and the transcript-fidelity test pin which process each query file runs.

    Seven queries have been run in both processes, each in the form of its target, in development runs on 2026-10-05, each alone under the shared lock with the 1800 s timeout and the 10 GiB cap ([measurements](#fail-stop-and-pin-free-measurements)).     C2 and C3 are therefore the security results that run only with honest pins. Their pin independence rests on the following simulation argument, written here and not yet separately reviewed; until it is reviewed, C2 and C3 are statements about runs in which every Beacon pins the honest Server key and ID. Take a trace of `FsRecordsB2sMainAnyPin` and a Beacon B whose pin (S', id') is not (S, `SERVER_KEY_ID`), where S is the honest Server key. (a) B's bundle term does not contain or depend on its pin (`beacon.rs:335-357`). The pin is fixed before the bundle, in Rust at `Beacon::try_new` (`beacon.rs:65-83`) and in the model by the two inputs that precede `FsB2sBeacon`, and before the finish the model uses it only as the ghost field `S` of `FsBeaconStarted`. From the finish on, the model uses the pinned key S' in the pin check against the Server identity of the response, from which DH1 is computed, in the associated data `fs_associated_data(S', B)` with which the finish opens the response frame and every later record of B is sealed, as the associated-data field of `FsBeaconEstablished`, and as the field `S` of `FsBeaconEstablished`, of the finish's `FsReceived` and `FsReceivedFrame` and of every later `FsSent` of B; it uses the pinned ID id' as the expected sender of the response frame, in the frame match and in the open, whose CTX commitment binds it. (b) and (c) use these places. (b) If S' = S, then id' ≠ `SERVER_KEY_ID`, and B never finishes: its finish needs a frame with sender id' sealed under the Server-to-Beacon chain of a root whose first DH value is `x25519_shared(SERVER_IDENTITY_SECRET, prekey_B)`; the attacker holds neither secret and no process outputs that value, a root, a chain or a key, so the attacker cannot seal under that root, and the only processes that compute it, Server objects, seal under it only with their own ID `SERVER_KEY_ID`, which the CTX commitment binds (`open_frame` matches the exact CTX preimage). (c) If S' ≠ S and B finishes, its root's first DH value is `x25519_shared(k', prekey_B)` with S' = `ed_public(k')` (otherwise the identity conversion fails, `crypto.pvl:25-37`), so B's root is the root of no Server object, whose first DH value is `x25519_shared(SERVER_IDENTITY_SECRET, ·)`, and no honest process sealed the response frame B opened (Beacons seal only under their Beacon-to-Server chains): the attacker sealed it, which requires B's Server-to-Beacon chain and hence B's root, since the HKDF constructors are one-way. So the attacker can compute B's root before B's finish. Every frame B sends afterwards is `seal_frame` under B's root with the associated data of (S', B) and a sender ID taken from the attacker's response, so the attacker can compute it when B outputs it, except for the fresh plaintext, a name that occurs in no other process (in the chosen form the attacker chose it anyway). No Server peer accepts such a frame, because a peer's associated data names S, and B's own events all carry S' ≠ S. (d) Replace B by a Beacon of `FsRecordsB2sMain` with the same secrets that sends the same bundle and never receives a response, and let the attacker seal B's later frames itself with fresh names of its own. The result is a trace of `FsRecordsB2sMain` with the same events of every Server object and of every Beacon that pins (S, `SERVER_KEY_ID`), up to the renaming of B's fresh plaintexts, with B's `FsBeaconStarted` carrying S instead of S', and with no more attacker knowledge than the original up to that renaming. C2 and C3, the two security results that rely on the argument, mention Server events, whose Server key is the honest one; C2 also mentions a Beacon send with that same key, and C3 mentions Server receives only. So a violation of C2 or C3 in `FsRecordsB2sMainAnyPin` gives a violation in `FsRecordsB2sMain`, and C2 and C3 hold for Beacons with any pins. The argument applies in the same way to the other Server-side queries, C4, UKSr and A2, which ProVerif checks pin-free directly. If this argument is not accepted, C2 and C3 are statements about runs in which every Beacon pins the honest Server key and ID; A1, A2, S2, UKSr and C4 are pin-free by ProVerif in either case. An attempt to have ProVerif check the root step of (c) directly, as `event(FsBeaconEstablished(s,b,…)) ==> s = ed_public(SERVER_IDENTITY_SECRET) || attacker(root)` in `FsRecordsB2sMainAnyPin`, ended in "cannot be proved": ProVerif found the expected run in which a Beacon pins an attacker key and finishes on a root built from the attacker's values, and could not confirm it as a counterexample, because it does not derive an `attacker` conclusion from the hypotheses of a clause. Two checks through the frame recorded by `FsReceivedFrame` at the finish, one of (b) and one of (b) and (c) together, were started and stopped without a result; they are not targets (see [measurements](#fail-stop-and-pin-free-measurements)).
14. **Names, heuristic and precision.** The Beacon's fresh record plaintexts carry no session arguments (`new record_t[]`, the "na" form of G0), which only coarsens ProVerif's internal abstraction of names; a TRUE verdict stays sound and a FALSE verdict still needs a reconstructed trace. The selection heuristic nx and the `[precise]` inputs are those of P1 ([the heuristic paragraph](../formal-verification-analysis.md#the-fs-selection-heuristic-nx), [the precision settings](../formal-verification-analysis.md#proverif-precision-and-approximation-settings)); neither restricts traces.

A FALSE result must come with exactly one reconstructed trace, a TRUE result with none. The eight security targets state seven claims: C2 runs in two forms with one query file and counts once as a claim, and the checker's summary counts the same way (security targets, and distinct security claims, one per query file). Measured traces of the FALSE results: C5a, an honest Beacon sends records 1 and 2, and its Server peer accepts 2 (caching 1) and then 1 from the cache; C5b, a frame the attacker built at sequence 2 fails the future open, and the Beacon's genuine record 2 is accepted at the next attempt; C5c, the peer accepts the Beacon's record 2 and the attacker delivers the same frame again, which the peer refuses as an old target that is not cached, without an open; S4, an attacker identity registers, the Server builds its response, and the attacker's own record at sequence 2 is accepted; FAR, the same for a frame at sequence 3 sealed under the far material, which the attacker computes from the root of its own session; PINREAD, a Beacon pins `ed_public(a)` for an attacker value `a`, finishes on a response the attacker built, and sends a record whose plaintext the attacker opens; C-UKS, in the pin-free process, the attacker chooses the honest pin for a Beacon, an attacker identity signs that Beacon's prekey, one-time key and ML-KEM key, the Server accepts that bundle and builds a response for the attacker identity, the Beacon finishes with that response (under the mutant neither the root nor the associated data names the Beacon), and the Server peer of the attacker identity accepts the honest Beacon's record 2; C-RETAIN, on an attacker peer, 2 is accepted (caching 1), 1 is accepted from the cache and the same 1 again; C-STALE, on an attacker peer, 2 is accepted (caching 1), a forged frame at 1 fails the cached open and restores the state left by the build, and 2 is accepted again.

## What the bounds do not cover

The security results hold for unbounded Server objects, honest Beacons and attacker identities, each Server object processing one bundle and making three receive attempts after the build, and each Beacon sending two records after its finish, with positions up to T_max = 2 materialised. A Beacon's third or later record, a Server peer's fourth or later receive, and anything after a peer direction's first far acceptance are not covered; the arbitrary-depth facts are the Lean side's (OD1), and these bounded results do not discharge global closure item 1 (arbitrary reached committed states). The scenario has no Server-to-Beacon taskings (stage P2 covers them), no compromise or reveal (stage P7) and no strong secrecy (stage P5). The theory is `crypto.pvl`, so the results say nothing about same-role DH equalities, X25519 encoding aliases, low-order points or ML-KEM implicit rejection (F13, stage P4). The registration payload is fresh (step 7). S2 and UKSr are about fresh record plaintexts; C2 and C4 cover adversary-chosen plaintexts through the fail-stop form and the deletion argument (step 12). The far branch admits every sequence above T_max but opens with model-only key material (step 8). Every Server object has the modelled identity key and `server_kid` (E23). A1, A2, S2, UKSr and C4 hold whatever the Beacons pin; C2 and C3 are shown for runs in which every Beacon pins the honest Server key and ID, and cover other pins only through the pending argument of step 13.

## Deviations from the plan

- **Files.** As in P2, the scenario has its own libraries and one query file per target; the receive macro is specific to the Server side (routing, r from 0, one cacheable position), so nothing was factored out of the s2b files.
- **C2 runs twice, and C4 runs in the fail-stop form.** The plan has one C2 and one C4, both in the failure-interleaving form. Their adversary-chosen form does not fit the caps there (step 6), so C2 runs with fresh plaintexts in the failure-interleaving form and with adversary-chosen plaintexts in the fail-stop form, and C4 runs with adversary-chosen plaintexts in the fail-stop form only, as G0 option B allows for every claim other than C2 and C3 (step 12). The mitigation ladder of the plan was not applied to the chosen failure-interleaving forms: the scenario fits the budget at its planned bounds, so no bound was reduced, and the chosen forms are covered through the deletion argument. A selection heuristic that would let them run in the failure-interleaving form remains an open item.
- **The pin-free process.** The plan did not foresee it; it was added to settle E3 (step 13), with A1, A2, S2, C4, the definitional check C3-finish and the witness PINREAD as targets, and after the confirming review of the P3 fixes also UKSr and its control C-UKS.
- **C3 is split.** The plan's C3 leaves the direction free. In b2s its Server-to-Beacon instance, the Beacon's finish at sequence one, holds by construction, so after the P3 review the security target C3 fixes the Beacon-to-Server direction, and the finish is the definitional check C3-finish at K_r = 1, which is not counted as evidence. The controls C-RETAIN and C-STALE run the security query.
- **The plan's C4 (b2s form)** `event(FsFarAccepted(d,S,ed_public(k),kid,root,t)) ==> attacker(k)` is used with the direction fixed to Beacon-to-Server, the only direction with a far branch here.
- **The plan's S4 "an attacker peer's records are accepted by the same object"** is the witness S4 here, and the far branch's reachability for attacker peers is the extra witness FAR.
- **The replay-rejected witness C5c** runs at K_r = 2, its smallest bound here (step 10), with the frame tie of P2.
- **C-FAILMUT and C-RETAIN on C2 were not run** in b2s; the plan lists C-FAILMUT for s2b only, and C-RETAIN and C-STALE on C3 cover the receive-state mutations here.

## Open items for P4 to P8

- **Reviews.** The three arguments written here (the Beacon-to-Server half of the direction split E19, the deletion argument E21 and the pin-independence argument E3), the P3 changes to the [event-meaning reference](../proverif-fs-event-meaning.md#changes-in-stage-p3), including the corrections made after the P3 review, and the items left from P2: the arguments E19 (s2b) and E20, and the two event changes made after the P2 review.

- **Adversary-chosen records in the failure-interleaving form.** C2 and C4 with adversary-chosen records do not fit the caps in the failure-interleaving form and are covered through the fail-stop form and the deletion argument. The same holds for step 13 (b): two statements through `FsReceivedFrame` were stopped without a result, after about 3 and about 17 minutes ([measurements](#fail-stop-and-pin-free-measurements)).

- **P4 (F13).** The theory with low-order points and the all-zero check (an event that distinguishes the all-zero check from a DH refusal) for the record scenarios; same-role DH equalities are still not shown.
- **P5.** Strong secrecy of Beacon records (SS1), which must publish the `Some`/`None` bit of every receive and finish (E11), and SS2.
- **P6.** The verdict-classes manifest must include the eighteen b2s targets with their classes (eight security targets for seven claims, and the definitional C3-finish), the two fail-stop targets and the pin-free process.
- **P7.** Compromise and reveals between worker steps; the b2s Server receive worker is the place where a revealed peer state would matter.
- **P8.** The documentation consolidation should state, wherever the fs record results are cited, which targets are pin-free and which rest on E3 and E21.
