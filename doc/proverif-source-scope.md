## Common interpretation and observation boundary

The production roles remain the reference. The six source-projection groups in the catalogue below use the exact loaded T0 theory in `crypto.pvl` and the approved abstract-message contract. They preserve protocol identities and the actual own/assigned IDs as distinct values; source names are consistently renamed only at the symbolic level. The exact-far C4 transfer, described in its own section below, does not preserve actual assigned IDs: its legacy process gives every peer `fs_kid(1)`. The protected Server uses the existing OD2 independent-key/perfect-key-management premise. Caller-known imported identities and independent private Server identities are distinguished from unmodeled hidden host-derived correlations. Ed25519/X25519 reuse remains correlated use of the same identity material.

The current deployment profile excludes attacker access to running code and disclosure of the protected Server's secret state. Richer reveals in reusable computational components and intentional disclosures in stronger comparison processes do not expand that advertised profile. The [live getter audit](impl/live-getter-source-profile.md) records the actual host API: four Beacon secret fields across five phases, the Server identity getter, and the difference between a private pending root and a historical root label. It proves availability/projection facts, not forward secrecy or network access to those getters. P7 logical in-process compromise remains outside the authorized symbolic profile. Snapshot, persistence and restoration consequences are excluded; codec internals remain external to the abstract-message contract.

Origin projections below expose the actual optional plaintext of retained receive calls to a stronger symbolic observer. Their authentication results therefore survive private application handling, but this interface cannot support unrestricted secrecy of a plaintext that it deliberately returns publicly. The ordinary and strong secrecy projections instead keep plaintext private and expose the actual Some/None result, call label and input frame. Their explicit existing trusted-application premise excludes echoing private plaintext into public replies, later application inputs, key imports, omitted-direction payloads or secret-dependent public actions. These two observations are not interchangeable.

## Exact-far model-level transfer

The [exact far material](impl/proverif-exact-far-material.md) targets `far-b2s-C4` and `far-s2b-C4` are not source projections. They run the legacy fs entry points `FsRecordsB2sMainAnyPin` and `FsRecordsS2bMain` with one later receive attempt (K_r = 1). The only change to those processes is that the free far-chain constructor becomes the literal public HKDF recipes for every admitted first-far target, 3..53 for b2s and 4..54 for s2b. In those processes each Server object accepts one bundle (K_reg = 1) and builds its response on that same object, every assigned peer ID is the single value `fs_kid(1)`, each registration sends two records in the checked direction (K_s = 2), and receive replies are hidden. Both exact C4 formulas are TRUE there. In b2s, with arbitrary Beacon pins, a far acceptance under signing identity `ed_public(k)` implies `attacker(k)`. In s2b, with honest pins, no far acceptance occurs.

The reviewed receive-deletion argument maps any hidden-reply C4 violation with more later receive attempts to a violation at one attempt, within the same registration/send profile. That is a transfer between two models of the legacy process, not a reflection of Rust source traces. The checked receive-admission bound and ratchet iteration identity fix which literal far material is needed; they do not map a source run with many peers, delayed or moved builds, actual assigned IDs or returned replies into this process. A source interpretation of either row therefore remains conditional on the open legacy obligations in the [source-abstraction audit](impl/proverif-fs-source-abstraction.md): L1 (arbitrary accept/build scheduling and cross-object token transfer), L2 (many peers and their actual assigned IDs collapsed to `fs_kid(1)`) and E19 (a deduction-preserving direction split), together with the remaining entries of that audit's status table (the L3 global induction from reached states beyond the far material, L4 composition with the fs material interpretation, application inputs and the global trace relation, and L5's computational accounting) and the global source relation; closing L1, L2 and E19 alone would not be enough. The inventory scope of both rows says the same: a reviewed event/knowledge projection only, with no global source, API or computational theorem. Because replies are hidden, this is also not the newer public optional-plaintext or strong-secrecy interface.

## Exact conclusions and supporting obligations

In the following abbreviations, `S` is the protected Server signing identity, `B` the exact Beacon signing identity, `i` the assigned peer ID, `r` the root, `t` the sequence and `m` the actual plaintext. These abbreviations do not quotient IDs, roots, occurrence labels or converted X25519 identities. Exact formulas, argument order and loaded profiles are maintained by each named checker and the [verdict inventory](../beaconcrypt-core/proofs/pro-verif/verdict-classes.tsv).

**A2.** `ProvAccepted(ed_public(k), init, rid) ==> ProvPublished(ed_public(k), init, rid) || attacker(k)`. The target-key reflection is essential: enlarging knowledge must not manufacture the corruption disjunct for a formerly unknown key. The reviewed T0 occurrence proof handles non-atomic keys, arbitrary role-tagged DH peers, private failed signing attempts, early public getters and a hidden Server identity with no signing output. Its exact three-purpose tuple checks and controls are retained. This paper transfer is distinct from the computational joint-use EUF reduction and does not supply its cost or assumptions.

**A1.** `inj-event(FsBeaconEstablished(S,B,init,i,r,ad,p)) ==> inj-event(FsServerCommitted(obj,S,B,init,i,r,ad,p))`. The builder object is existential and need not be the accepting object. The target's identity/prekey/final-one-time/KEM secrets, protected Server identity and initial Server-direction root/material remain private through the target cut. The stronger process explicitly exposes the post-initial s2b chain and initial b2s chain, preserving their actual correlated HKDF expressions. Its source trace construction schedules commits only for real successful builds, so the model cannot repair a source violation by inventing a matching commit. Source failure/absent-token replies are known terms in this projection; this does not assert equality of every unsuccessful host API branch.

**Near origins.** `FsReceived(b2s,S,B,i,r,t,m) && L2SelectedIdentity(k)` implies `L2Published(b2s,S,B,i,r,t,m)`, with `B = ed_public(k)`. The s2b counterpart uses `S2bSelectedIdentity` and `S2bPublished`. `Published` denotes successful returned ciphertext, whereas the retained historical `FsSent` event denotes sequence allocation and can precede a failed seal. The two cannot be substituted. These source arguments preserve all matching publication occurrences, the actual original-frame plaintext and the selected identity's knowledge status. Stronger root disclosures classify another exact signing identity; converted-DH equality does not classify protocol identity.

For b2s injectivity, the reviewed same-process paper uses both target removal in the exact receive/cache state and equal-root→same-accept reasoning in T0. The latter relies explicitly on free HKDF/ML-KEM constructors and is not a computational uniqueness theorem. The inconclusive injective/C3 solver attempts remain excluded diagnostics. For s2b, one selected nonreplicated active finish creates one later receiver; its target-removal state argument establishes local occurrence uniqueness without cross-accept root injectivity. Neither paper result is recorded as an extra solver verdict.

**Fresh-name secrecy.** `FreshPublished(direction,S,B,i,r,t,mu) && SelectedIdentity(k) && attacker(mu)` is unreachable, using the direction's exact event names. The source construction retains that very independent target name through all later inputs, omitted operations and successful publication. It does not reuse the public-plaintext authentication argument as a secrecy proof. Public fresh-plaintext leak controls use the same formulas and show eligible successful publications are reachable.

**Strong secrecy.** The two `SSX` targets assert observational equivalence, not only secrecy of a name. The common context preserves adaptive ciphertext-dependent inputs and maps the actual Server-object/peer pair to its worker. Pending values are consumed before build validation; successful installation and response publication occur at the actual source point. A public full-response ledger chooses the same lookup algorithm in both worlds. Separate initial-origin checks justify existence; T0 constructor equality justifies agreement of the root/material across equal response entries. The [other-pin argument](impl/proverif-exact-interface-other-pin.md) covers that exact enlarged output profile. It is not inferred from the older hidden-reply pin lemma. In b2s a test is eligible only when the selected Beacon pins `S`; in s2b only when the accepted signing identity is selected `B`. Other calls use the left alternative in both worlds. This eligibility is an experiment definition, not an assumed authentication conclusion.

## Computational boundary still to be closed

T0 free-constructor equalities are explicit idealizations. The computational interpretation must account for fixed no-salt HKDF at the actual joint sampler and evolving correlated projections, Ed25519/X25519 related use, ML-KEM cross-public-key constructor properties, and the exact AEAD/CTX/hash interfaces. Ordinary EUF-CMA, IND-CCA, PRF or collision resistance does not by itself entail every symbolic equation or a programmable random oracle. The encoding-profile checks do not supply that general implication. No public-HKDF/random-table security interpretation is used by these source transfers.

The Lean lanes retain source-complete operations, query bounds and component reductions, but those facts must meet these same selected events, schedules and freshness/observation rules in the common experiment. All omitted source calls, failed work, public HKDF evaluations, primitive histories and ambient replicated work remain chargeable. These symbolic papers assert no numeric session/identity/record selection loss, finite-byte guessing or collision term, global query cap, efficient implementation of an arbitrary semantic predicate, or negligible nonce-refusal probability. Finite symbolic fresh names are not such bounds.

The common computational public optional-plaintext experiment remains separate from private-application symbolic confidentiality. It must retain challenger-produced optional plaintext, actual cache/replay/rollback behavior and its precise target-opening/release freshness with aliases and repeated attempts. A source event or state-product correspondence alone does not establish deduction preservation, paired-context equivalence or an end-to-end reduction. Closing that composition, within the owner's stated scope, remains proof work; this catalogue only prevents the already proved pieces from being overstated or overlooked.
