The engine (`discard_erase`). Let `H` be a stateful handler and `H₁` a pointed handler: each step of `H₁` returns its answer and an optional point of a lazily sampled cache, reached through a lens `L`. If every step of `H` has, in law, the form of the step of `H₁` followed by the completion of the point it reports (`factor`), and every step of `H₁` with the point forgotten commutes with completions (`oblivious`), then for every oracle program, every initial state and every continuation that cannot observe completions (`Blind`), simulating `H` and simulating the erased handler `fun q => Prod.fst <$> H₁ q` have the same law. The proof is an induction on the program: the completion produced by a step is moved past the whole erased remainder, which commutes with it by `commutes_simulateQ`, and is then removed by the blind continuation. `discard_erase_proj` is the special case in which the continuation keeps the result and a projection of the state that does not see the cache. The core fact is `complete_query_swap`: completing a point and then making one lazy query has the same law as making the query and then completing the point; when the two points differ and are both absent, the two fresh draws are exchanged (`lawEq_swap`).

The layout. `joinOutput (key32, nonce12) (next32, right32)` reassembles the 76-byte response from key, next chain and nonce with the existing `RawCtxKdfRequestTable.assemble` and appends the opposite chain; `splitOutput` is its inverse. `uniform_split` transports the uniform measure along the bijection `joinEquiv` (VCVio's `evalDist_bind_bijective_uniform_cross` with `SampleableType.evalDist_uniformSample`), on the discrete measurable structure of the two finite types.

The local part of C7 (`finish_erase_local`). For every lawful monad, primitive interpreter, send callback, application getter, frame decoder, prepared registration and slot factor, `PqxdhServerAuthBeaconFactor.factored` equals `finishErased` followed by the call `prim (.inr input)` on the reported opening input, with its reply discarded. `finishErased` runs the original body when the decoded frame has sequence one; otherwise it makes no primitive call, returns `none` and reports the opening input that the receive would reach (`discardedInput`). The proof follows the original receive: on a blank raw, a failed decode or an invalid frame the body rejects without a call; on a valid frame every KDF request is answered by the selected step without effect (`program_reached`), the reached effect is a rejection or an opening (`reached_cases`), the opening's input carries the decoded sequence (`reached_sequence`), so the opened message, if any, has that sequence, and `PqxdhBeaconPhase2Publication.afterOpening` rejects every sequence other than one.

The CTX-cache instance. With the native interpreter `PqxdhServerAuthBeaconFactor.nativePrim`, the discarded call changes the shared primitive state only by completing the point `openPoint input` of the CTX cache (`discarded_native`), so the hidden finish has the pointed form (`finish_pointed_native`). Every native primitive query, every labelled receive query and the erased finish commute with completions of the CTX cache (`nativePrim_commutes`, `primLabels_commutes`, `factoredBody_commutes`, `finishErased_commutes`, the last given an application getter that commutes). `finish_erase_native` instantiates `discard_erase` on `ctxLens` for the interface `FinishSpec`: an adaptive client chooses prepared registrations and slot factors for hidden finishes and queries BLAKE2b on the same lazily sampled cache; the real interface `finishOracle` and the erased interface `finishOracleErased` have the same output law. `finish_erase_codec` is the case of the experiment codec's pure application getter and frame decoder, with no premise left.

The labelled-kernel identities. The factored send and finish run labelled ratchet kernels with a hidden slot and turn them into concrete kernels only at the end (`resolve`). The existing labelled-to-native bridges need a target chain whose step is the challenge, which a uniform 108-byte value does not have, so these two identities compute the resolved kernels directly. `resolve_after_send`: if the labelled first send of the initial Server kernel `serverInitial right` (hidden send slot, known receive chain) requests a KDF, then `PqxdhRecordLiftSeed.serverKernel (nextChain output, right) = ok (resolve …)`, where `resolve …` is the kernel advanced on the selected step of the 76-byte response `fullResponse output`, resolved; `initial_send_requested` shows that this first send always requests the hidden slot. `resolve_after_receive`: let `k` be the kernel with `PqxdhRecordLiftSeed.beaconKernel (nextChain output, right) = ok k` (the hypothesis `hk`; `k` is the World's `kernel .beacon` of that seed, by `PqxdhRecordLiftWorld.kernel_exact`). Then, for every primitive interpreter and every observation that ignores the kernel of a failed receive, observing the resolved kernel after the labelled sequence-one receive from `PqxdhServerAuthBeaconFactor.initial right` is the same program as observing `k`. Both are proved by transport to the extracted computations `PqxdhRecordLiftSeed.sendOne_from_counters` and `receiveOne_from_counters`: with the hidden slot read as the unused chain, the labelled initial kernels resolve to the native zero-counter kernels (`serverInitial_native`, `beaconInitial_native`), and the extracted first send and sequence-one receive follow the labelled admission and resume (`send_native`, `receive_native`).

## CE-11a increment 1: decisions and deviations

- `LawEq` binds the continuation's result type explicitly: `∀ (β : Type) [MeasurableSpace β] (k : α → ProbComp β), …` instead of the implicit `∀ {β : Type} …` of the CE-11 design. With an implicit leading binder Lean instantiates `β` and its measurable space as soon as a `LawEq` proof is elaborated as a term, so `have h := …` and dot notation on `LawEq` proofs fail with stuck instance problems; downstream users would meet the same problem. The two forms state the same proposition.
- Helper theorems beyond the design list: `complete_of_none`, `complete_of_some`, `query_of_none`, `query_of_some`, `complete_query_swap`, `complete_comp` and `erase_tail` in the engine (35 increment-1 theorems instead of 28), and 22 helpers and instance theorems in the spike module (32 instead of the 10 theorems of the design's spike list).
- The spike went directly into the module `PqxdhDeploymentHiddenKernels`, which the design names as the 11a-2 module of the kernel identities, instead of a scratch file that 11a-2 would move. Its design statements are unchanged. The toy instance S1 was not built: `finish_erase_native` validates the engine on the real hidden finish instead.
- The CTX-cache instance and the native obliviousness lemmas (`finishErased_commutes` and the lemmas before it) were not in the spike list. They are the native-interpreter forms of two lemmas that the design plans for 11a-2, over the bare `SharedState Unit` instead of the `Services` wrapper of item 2's entry simulation: `finishErased_commutes_ctx`, the obliviousness of the erased hidden finish with respect to the CTX cache, and `finishFactor_pointed`, the pointed form of the hidden finish wrapper that the engine's `factor` premise needs.
- `finish_pointed_native` repeats the two cases of `factor_of_discard` instead of applying it: its left-hand side comes from `finish_erase_local`, whose `match` is a different auxiliary definition from the one in `factor_of_discard`, and Lean did not unify the two.
- Basis: central `d68e1ce4` instead of `7609c3c8`, at which the design was checked. The commits between them add only `PqxdhRecordLiftMaterialTable`, `PqxdhRecordLiftOrigins` and `PqxdhRecordLiftProjectionCut`, so every name and line that the design cites is unchanged.
- Documentation placement: the design named a new guide `doc/impl/deployment-ideal-world.md` and one receipt `doc/impl/proof-receipts/common-deployment-experiment-ce11a.json` with an entry per unit. This increment instead adds its sections to this guide, which the cooperation protocol with Codex names as the guide of handoff item 3, and writes one receipt per increment, `common-deployment-experiment-ce11a-inc1.json`, as the other CE stages do. The choice has no effect on any statement.

The wrappers. On a hidden entry, item 2 (its plan, `doc/impl/extract-composition-plan.md`, section 18) instantiates its two hidden services with the factored Server build and the factored Beacon tail at the entry's 108-byte value. `buildFactor m seed` and `finishFactor m seed` are those services at `joinOutput m seed`, the 108 bytes assembled from the environment material `m` (key32, nonce12) and the world seed (next32, right32), and they are literally the fields of `PqxdhServerAuthEntryFactor.factorServices`. `finishPointed` runs `PqxdhDeploymentHiddenKernels.finishErased` with the native primitives, and `finishFactor_pointed` states, as an equation of programs on the shared primitive state, that the factor-form finish is the pointed finish followed by the completion of the CTX point of the opening it discarded; this is the `factor` premise of the engine for a hidden finish.

Obliviousness. Each step has a named obliviousness lemma, so that the premises of the erasures are proved for the fixed steps and the real registration, not assumed. `nativeImpl_commutes` is the basic fact: in the shared native primitive interpreter the KDF and the base opening are pure and the BLAKE2b request is exactly the lazy query on the focused CTX cache, so every request commutes in law with completing any point of the cache (`LazyOracleDiscard.commutes_query`). Every interpreter built from it by an adapter commutes as well (`compose_commutes`), in particular the record primitives, the registration interpreter of the Server's response tail and the logged response tail, whose seal log is a frame of the cache. The generic Server build commutes whenever its send and auxiliary callbacks do (`genericBuild_commutes`, by its structure), so the factor-form build commutes with completions of the CTX cache of its seal state (`buildFactor_commutes_ctx`). In the native game, coins, BLAKE2b and the four record commands commute with completions of the CTX cache and of the seed table whatever the registration handler (`fixed_commute_ctx`, `fixed_commute_seed`), so the whole handler commutes whenever the registration handler does (`handlerWith_commutes_ctx`, `handlerWith_commutes_seed`). For the real registration all six commands commute (`realReg_commutes_ctx`): the build runs the logged response tail on the shared cache (`nativeBuild_commutes`), the finish runs its callbacks, including the finish-time receive, on the shared cache (`finish_commutes`), and creation, bundle, raw accept and HMAC are frames of the cache (`GameFrame`). The proofs use two generic tools: `commutes_focus` (a step that runs an inner program on a sub-state, where everything else it reads and writes is a frame of the cache, commutes when the inner program does) and `commutes_dispatch` (a step that first reads a frame of the cache commutes when every branch does).

The native game. `gameWith init reg` constructs the Server with the actual constructor and a generated seed, then runs the wrapped adversary (`PqxdhDeploymentSecrecy.wrap`, the secrecy layer as a program) against `handlerWith (reg created)` from `xinitial created (init created)`; the registration handler and the backend's initial value are chosen from the constructed Server. The real registration handler `realReg` answers every registration command as the LQ-F run-phase handler does (the logged native accept, the native handler otherwise) and captures the snapshot before a finish. `gameWith_real` shows that the game with `realReg` is exactly the LQ-F run phase `PqxdhDeploymentLaterServerGame.runPhase`, jointly over the Server's public data, the output, the ledger, the snapshot, the deployment state, the log and the runtime state, and `gameWith_classical` that, with the backend, the seed table and the LQ-F ghosts forgotten, it is exactly the classical experiment `PqxdhDeploymentSecrecy.game`.

C7 in generic form. A pointed registration handler for a lens `L` onto a lazily sampled cache of `XState` pairs a handler `reg` with a pointed handler whose every step reports an optional point of the cache: each command of `reg` is, in law, its pointed step followed by the completion of the reported point (`factor`), and every pointed step commutes with completions (`oblivious`). `erase_game` applies `LazyOracleDiscard.discard_erase_proj` to the whole native game: when the fixed steps commute with completions of the cache, the games with `reg` and with the erased handler have the same law of the Server's public data, the output, the ledger and every projection of the final state that does not see the cache. `erase_later` is the same for the LQ-F later game `laterWith`, with a pluggable post-phase handler that commutes with completions (pluggable because in the ideal game the post-phase HMAC is answered from the backend's R1 tables, not by the native HMAC) and a reveal that does not see the cache; the post phase is moved after the completion by `commutes_simulateQ` and the completion is then dropped by the projection (`laterTail_blind`). The CTX instance `FinishPair` needs nothing more (`erase_game_ctx`, `erase_later_ctx`), and compares final states with the CTX cache emptied (`fullX`). The real registration handler is a pair with no point (`realPair`), and `laterWith_real` shows that the later game with `realReg` and the real post phase `realPost` is exactly the LQ-F game `PqxdhDeploymentLaterServerGame.game`. Pointed steps compose: `factor_prefix` and `oblivious_prefix` put a prefix in front of a family of pointed steps (the pointed form needs nothing of the prefix, the obliviousness needs it to commute with completions), and `factor_suffix` and `oblivious_suffix` put a suffix that commutes with completions after a pointed step, which passes its point on. With `factor_focus` and `oblivious_focus` they give the pointed form of a step made of stateful, probabilistic steps, a focused pointed step and a commuting step after it, the shape expected for the ideal hidden finish of CE-11b (owner lookup, preparation coins, slot-service touch and root derivation before the hidden tail, and a commit after it).

The split and the deferral. `split_service_proj` is the 108-byte split at the first touch of a hidden slot: from a state in which material and seed are present together, the service that draws material and seed lazily is, in law, the lazy service on the joined table (`PqxdhDeploymentHiddenLayout.uniform_split`). `table_service_proj` shows that item 2's S7 table with its counts forgotten is the lazy service (`LazyOracleDiscard.impl_project`). For a registration core that reads slot outputs only through its service (`CoreNatural`), `represent` transports the whole game along a service projection with `lawEq_run_simulateQ_of_proj`, and `represent_split` compares the table and the split representations through the lazy one. `defer` is the seed deferral in generic form: an instance of `erase_game` at the hidden-seed lens, whose fixed steps commute by `fixed_commute_seed`. `defer_later` is the same deferral for the later game, an instance of `erase_later` at the hidden-seed lens; its premise that the post phase commutes with seed completions holds for the real post phase (`realPost_commutes_seed`), and the LQ-F reveal does not read the seed table.

The split forms and their kernel identities (unit 11a-2b). The factor-form hidden build and the erased hidden finish read the world seed (next32, right32) only through the kernel they publish or stage, and that kernel is the record world's kernel of the seed. The unerased factor-form finish does read the seed: on a frame whose sequence is 2 to 51 its receive derives chain steps from next32 and opens with the result before the sequence-one check rejects the frame, so the seed deferral applies only after the C7 erasure. `buildSplit m` and `finishSplit m` run the same programs on the material `m` with a fixed seed and publish or stage `placeholderKernel`; `build_factor_split` states that `buildFactor m seed` is `buildSplit m` with the published peer's kernel replaced by `PqxdhRecordLiftWorld.kernel .server seed` (`replaceRaw`, which acts only on a successful build, so a failed seal publishes nothing), and `finish_factor_split` that `finishErasedSvc m seed` is `finishSplit m` with the staged kernel replaced by `PqxdhRecordLiftWorld.kernel .beacon seed`. The proofs read every chain label as the unused chain: the first send of the hidden Server and the sequence-one receive of the hidden Beacon make one key derivation on the hidden slot, whose material (key32, nonce12) does not depend on the next chain (`decode_full`, `material_assemble`), and through the native admission and continuation the seal and the opening depend only on that material and on fields that hold no chain (`seal_unused`, `opening_unused`), so the sealed record and the opened reply are the same programs for every seed (`send_seal`, `reply_unused`). The kernels come from `resolve_after_send` and `resolve_after_receive` with `PqxdhRecordLiftWorld.kernel_exact`; on the Server side, `genericBuild_kernel` shows that two builds whose first sends are the same seal differ only in the kernel they publish.

The accounting of plan section 25. `finishRequests` is the finish-time receive of a hidden finish with its key-derivation and opening requests left as queries, and `factoredBody_requests` shows that the finish body runs exactly these requests under the labelled primitive interpreter. `finish_accounting` states, for every raw input, prepared registration and slot value: at most 51 chain-step KDF requests (`RawCtxChainReceiveBounds.receive_bound`), at most one opening request (`program_open_bound`), and, with the real HKDF and the BLAKE2b opening left as a CTX-oracle query (`romPrim`; `nativePrim_rom` shows that the native interpreter is this interpreter with BLAKE2b answered by the lazily sampled cache), at most one BLAKE2b query for the whole hidden finish (`finish_hash_bound`). `erased_le` and `erased_total_le` show that under any query-counting primitive interpreter the erased finish issues no more queries of any kind than the factor-form finish, and `erased_reject` that on a raw whose decoded sequence is not one it calls no primitive at all, in any monad; `finishErasedSvc_reject` is its native form, which leaves the shared state unchanged.

- `PointedReg` is generic in the lens; `FinishPair` is its CTX instance. `erase_game` and `erase_later` take any projection of the final state that does not see the cache; the CTX instances use the state with the CTX cache emptied. `defer` is the same theorem at the hidden-seed lens.

## CE-11a increment 3: decisions and deviations

- Stripping is structural: every environment step commits `strip` of its new registration state, so the CE-11 design's invariant `env_stripped` is `realStep_stripped` for the real environment and holds the same way for any environment whose steps commit through `onEnv` or the same pattern. Every kernel the environment holds is therefore `placeholderKernel`, no record operation runs on it, and `merge` fills it from the World.
- `EnvStep`, `realStep` and `envReal` are generic in the slot count `n`; the CE-11 design used `n = 0` for the real environment, which is an instance.
- The real environment installs with known kernels: a published peer by `installServer keyId identity (.known kernel)`, an established owner by `installBeacon owner shell (.known kernel)`, a bundle and an abort by `advanceOwner`. `create` appends the owner in the World by `appendOwner keyId pin .fresh` and returns the environment's own index (equal to the World's handle on admissible states).
- The BLAKE2b factoring of build and finish that the CE-11 design planned as `build_hash_factor` and `finish_hash_factor` is `tail_factor` and `owner_factor`, stated against `ctxEffects admin`, the reading of the environment's effects on a CTX cache with any interpretation `admin` of the administrative capabilities (the forwarded programs issue none). The generic `factor_program` takes a cache lens and a forwarded handler that never touches the lens.
- The first-touch classes are the accept (class 3) and the finish (class 5), `ceFirstTouch`, following plan section 35 (the Server slot is first read at the selected accept, a Beacon slot at its finish). The build is not a first-touch class, because item 2's skeleton keeps the material in its marks from the accept to the build. `allowanceG` and `frame_wrapped` take the first-touch classes as a parameter.
- `frame_wrapped` is stated for an environment built by `wrapStep table slotOf core`: at a command that touches a slot the slot's material is obtained by `touch` (a lazy lookup of the backend's material table, 44 coins on a miss) and passed to the core step. The CE-11 design stated its premises informally ("the core's per-class bounds", "material is drawn only at first-touch classes"); they are the hypotheses `coreBound` and `touches`. In this shape the slot is a function `slotOf` of the command and the pre-state. Under item 2 plan section 20 a Beacon slot comes from the first-touch coordinate-to-slot allocator, keyed by the 128-byte root-input coordinate that the finish computes only after preparation, decapsulation and DH, so the ideal environment's finish may not have this shape; CE-11b may then prove `PqxdhRecordLiftInterface.Frame envG (qInit + 32) (allowanceG core ceFirstTouch)` directly, since `allowanceG` is the core allowance plus 44 coins at the first-touch classes either way.
- `baseAllowance` takes the existing per-command uniform bills: create `64 + keygen` (CE's create does not re-run runtime initialization, deviation D1), bundle 32, accept `96 + encaps`, build 0 (its BLAKE2b miss moves to `.hash`), finish `69 * max 64 decaps` (this bound already covers the finish's BLAKE2b draw, which the World also charges through `.hash`: an overlap in the bound, not a second draw), HMAC 64; one `.hash` at build and finish; one administrative capability at create, bundle, build and finish.
- `c4_instance` is generic in the environment, the startup coins, the allowance and the server key ID; the form agreed with the record-lift line for the ideal environment is its instance at `setup.serverKeyId` and `qInit + 32`. Later-mode C4 adds the post-phase BLAKE2b budget as a separate summand and leaves `Caps` unchanged, as agreed with the record-lift line for R6.
- The split hidden wrappers in capability form: `buildSplitEnv` is `PqxdhServerAuthLoggedSendFactor.factored` at the environment material and the dummy seed on the forwarded logged tail, settled as the native build settles, followed by the hidden install of the published peer; `finishSplitFwd` is the erased hidden finish with the ROM-level primitives (`PqxdhDeploymentHiddenEntry.romPrim`) whose BLAKE2b query is forwarded as `.hash`; `finishSplitEnv` adds the source commit with its two pin checks (`PqxdhBeaconPhase2Publication.finish`) and the hidden install or the abort. Their costs are proved; their factoring against the CE-side split forms is an open point.
- The single-install lemmas `hidden_server_once` and `hidden_beacon_once` are not stated as run-level theorems: they need the routing law of item 2's registration core (which session builds and which owner finishes a slot), which does not exist yet. The per-step ingredients are proved for the real build and finish: a build consumes its session's token on every outcome and a build without a token issues nothing (`buildStep_consumes`, `buildStep_idle`); a finish from an initSent owner leaves it terminal, and a finish at a terminal owner issues nothing (`finishStep_terminal`, `finishStep_retry`).
- `merge` takes the World's whole Server record structure (identity and peer map) when the World's Server is initialized, and `fillOwner` changes only an established owner, so the Beacon-side reveal of the reassembled state is always the environment's (`revealOf_fill`). `Good` compares the Server's peers with the environment's up to their kernels (`stripPeer`) and the owners phase by phase up to their kernels (`stripPhase`).
- `Good` constrains neither the World's used markers nor its seed table, and `merge` reads neither. The World admits a hidden install only while its slot marker is unused, so the CE-11 design's clause "used markers = hidden installs performed" depends on how an environment records its installs, and enters as a parameter (review fix pass): `Splits created reg step inv` and the join theorems take an admissibility predicate `inv` conjoined with `Good`. `inv` must be `Stable` (it reads the World only through `fixedView`: the used markers, the seed table with its counts, the Server's sender, identity and peers up to their kernels, and the owners up to their kernels, which every fixed step keeps) and must hold at the constructed Server's initial environment state and the initialized fresh World. For one seed, `seed_bound` moves the A1 failure to the frozen journal (`native_frozen`, through `journal_erase` and `compiled_regs`), draws the target's material before the run (`swap`), localizes the eager run to `R_c` routed into the source14 handler on the singleton that the early draw creates and bundles (`localize`, which needs `compiled_unread`: the compiled program never reads an identity, KEM, prekey or one-time field), identifies that singleton with the typed constructor and first bundle of the original R1 singleton (`typed_draw`) and so with the root-audited run (`typed_root`, from `typed_audit` and `audited_root`), and shows on every root-audited outcome that the A1 failure of `c` is a common authentication failure (`root_failure`: `R_c`'s own journal is the public journal of the outcome, `Track` gives a successful finish and no session with an earlier publication of the accepted decoded record and an accept carrying the target's published keys, and `game_failure` concludes; the generation receipt with `Phase1ReadBack` fixes the published keys). No step was found false or unprovable.

Per-Beacon bound (`a1_bound`) and the sum (`a1_sum`, `ce_a1`). With the premises of `common_authentication_with_resources` and the query caps of `R_c` (`ReductionCaps`), `(𝒟[a1Decision … c <$> CE] {true}).toReal ≤ serverAuthBound … (serverAuthAdversary … c) qCoin Q qH qHash fallback signatureFallback`, which is `GapDH(scanClient R_c qH) + (Q choose 2)·64/2^256 + Σ_{j<Q+1}(recordLoss + scheduleLoss) + jointEUF(reduction R_c)`, together with `ReductionBills` of every constructed reduction. For a budget-respecting adversary CE-A1 occurs only below `qCreate` (`a1_range`), so the exact union gives `(𝒟[decide (∃ c, A1At c) <$> CE] {true}).toReal ≤ Σ_{c<qCreate} serverAuthBound(R_c)`, and `ce_a1` states it for `∃ c, A1NoPinnedMatch c`: on the support, `noPinnedMatch_noFailure` turns `A1NoPinnedMatch c` into `A1NoFailure c`, and `noFailure_a1At` turns that into `A1At c`.

Bills (`reduction_caps`, `ce_a1_billed`). For a budget-respecting adversary, every `R_c` makes at most `qAccept` accepts, `qFinish` finishes, `hashCap = (qHash + S + R + qTest + qFresh) + 69·qFinish` BLAKE2b queries, `romCap = qHmac + 69·qFinish` random-oracle HMACs, `coinCap = (qCoin + qTest + qFreshBytes) + (64 + keygenCost)·qCreate + 32·qBundle + 69·decapsCost·qFinish` coins and `totalCap = (qCoin + qTest + qFreshBytes) + (64 + keygenCost)·qCreate + 32·qBundle + qAccept + qBuild + (1 + 69·(decapsCost + 2))·qFinish + qHmac + (qHash + S + R + qTest + qFresh) + (qServerSend + qServerRaw + qTest + qFresh)` queries in all, where `S` and `R` are the send and receive totals of the transported caps. The step costs are charged per source14 query (`embed_weight`): a local finish is charged its full 69-callback allowance (`native_owner_bound`), each callback one BLAKE2b query, one HMAC and the decapsulation coins. `ce_a1_billed` is `ce_a1` at these caps.

Injectivity (`injective_bound`, `ce_a1_injective`). `SharedMatch c c'` says that two distinct Beacons accepted and one session matches both. At identity index 0, sessions are positional (`session_unique`, from CE-9's `Traced.positional`), so both matches use one accept and one accepted candidate, and by `Agree` and `Phase1ReadBack` each first published bundle carries the identity key of its owner's final identity seed (`keys_identity`); hence the two owners' identity keys are equal (`shared_collision`). The owners' identity seeds are drawn by their creates; drawing them before the run is a distribution equality (`seeds_eager`) and they then form a prefix of the drawn list (`eager_identities`), so the probability of equal identity keys is at most that of a collision among `qCreate + 1` independently drawn seeds (`owners_collision`, with `compiled_creates`). The collision reduction `B^coll_t = collider joint qCreate t` is the zero-query reduction of owner input 17: a joint-use weak-EUF adversary that receives the challenge identity at index `t`, draws the seeds of the other `qCreate` identities itself and, when the challenge's Ed25519 key equals the key of one of its own seeds at a lower index, signs the empty message with that colliding seed itself and returns the signature as its forgery (`colliderForgery`). It wins whenever the identity at index `t` collides with a lower index (`lower_wins`, by signing correctness `joint_correct`, from the source wiring and the attached-signature correctness of the source primitives, and because it never asks the signing oracle, so the message is fresh). Drawing the seed at index `t` first is a distribution equality (`PqxdhJointIdentityFamily.sampleFamily_target_first`), so the probability that index `t` collides with a lower index is at most `Adv^{jointEUF}(B^coll_t)` (`lower_le_advantage`); every collision is a collision of its higher index with a lower one (`collision_lower`), and the union bound over the higher index gives `ε_inj = Σ_{t<qCreate+1} Adv^{jointEUF}(B^coll_t)` (`collision_bound`). `B^coll_t` makes no signing and no static-DH query and at most `32·qCreate` uniform queries (the bytes of its own seeds) on every challenge identity, and its whole joint-use weak-EUF game makes at most `32·(qCreate + 1)` uniform queries (`collider_queries`, `collider_bills`, from `PqxdhJointIdentityFamily.sampleFamily_lift_bound` and `jointGame_uniform_bound`). `ce_a1_injective` combines both by the union bound: at identity index 0, `Pr[(∃ c, A1NoPinnedMatch c) ∨ ∃ c c', SharedMatch c c']` (real form) is at most `Σ_{c<qCreate} serverAuthBound(R_c) at the transported caps + Σ_{t<qCreate+1} Adv^{jointEUF}(B^coll_t)`, with the bills of every `R_c` (`ReductionBills`) and of every `B^coll_t` (`collider_bills`). `SharedMatch` keeps the public matching `MatchedAt`; a pinned match is a match (`pinned_matched`), so its injectivity covers the pinned matching too.

## CE-8: decisions and deviations

- Public matching, a smaller event than planned. The plan states CE-A1 as "no eleven-field common session that published the decoded record earlier". The eleven-field session is not a CE observable, so CE-A1 is stated with a public matching relation: `MatchedAt` (an accepted key-carrying accept and an earlier build with the accepted decoded record) and, in the headlines, `PinnedMatchAt` (the same with the Server identity of the build response). This relation is weaker than the plan's, so the bounded event is smaller. `root_failure` shows one direction only: the public A1 failure implies the ServerAuth common authentication failure on the same run, that is, an eleven-field common session that published the record gives a public match. The converse does not hold, so the bounded event (no public match) is a sub-event of the planned failure (no eleven-field common session). The public matching states no root agreement and nothing about the KEM ciphertext or the ephemeral key of the response that `c` accepted; in particular it does not give section 9's Beacon-side ciphertext link, which plan section 30 moves to CE-12 (next bullets). The first-pass text called this "a restatement, not a weakening" and said that the public failure "is" the ServerAuth failure; both were wrong.
- Pinned matching in the headlines (fix pass). `ce_a1`, `ce_a1_billed` and `ce_a1_injective` bound `A1NoPinnedMatch`, so the public matching of the headlines is pinned to the Server identity; see "CE-8: review fix pass" for why these statements are at least as strong as the first-pass ones.
- KEM-ciphertext link (plan section 30, Claude's decision of 2026-10-07). The ciphertext conjunct of CE-5's `Linked` is not expected to be provable at the CE-A1 bound, by an informal argument that is recorded as a negative control and is not a Lean statement: no term of `serverAuthBound` is a KEM-security advantage, and with a KEM whose decapsulation ignores the ciphertext an adversary that relays session `i`'s build response to `c` with only the ciphertext replaced makes `c` derive the same key and accept, so `i` still pin-matches `c` while no build response carries `c`'s ciphertext. CE-8 therefore integrates with the pinned public matching and without the ciphertext link. The link moves to the Beacon-side symbolic-eligibility corollary of CE-12, which is planned to charge a separate term `ε_ct` next to `ε_A1`. `ε_ct` is planned to cover the event that an established Beacon of owner `k` accepts with a ciphertext different from session `i`'s while its root input equals session `i`'s (ServerAuth's ghost `Partner`) and accept `i` verified `k`'s published key, and is planned to be bounded by a per-pair `(i, k)` IND-CCA reduction (the decapsulation oracle on the Beacon's ciphertext detects the shared-secret collision) plus the ideal-world probability of the same event, bounded statistically through R1 lazy sampling of the uniform key. That event is stated on root inputs, which the public pinned match does not carry, so CE-12 must also connect the public pinned match to ServerAuth's `Partner` ("CE-8: open points"). IND-CCA is an existing assumption; no new assumption or contract is planned. CE-5's `designate` keeps its ciphertext-equality conjunct, so CE-9 is unaffected. Plan section 9's justification ("the eleven fields carry the ciphertext and the PQ key") is wrong and is corrected in section 30: `Session` has no ciphertext field, and the root input carries the KEM shared secret, not the ciphertext.
- `NoBundleFailure_c`: option (b) of section 19. `ce_a1` is stated on `A1NoPinnedMatch`, which like `A1NoFailure` asks for no rejected bundle call of `c` in Fresh in the whole run; the per-index theorems use the weaker condition before the acceptance (`A1At`), which the run-wide one implies.
- Range of the sum. The sum is over `c < qCreate` (`Fin budget.create`), not `qCreate + 1`: `a1_range` shows that CE-A1 occurs only below `qCreate`. The injectivity sum is over `qCreate + 1` identity indices, as the plan states.
- `B^coll_t` is the zero-query reduction of plan section 10 and owner input 17 (second fix pass): it generates the other seeds itself, signs with the colliding seed itself and makes no signing query (`collider_bills`). It is built directly as a joint-use weak-EUF adversary rather than as `PqxdhJointIdentityFamily.reduction` of a family adversary, because a family adversary sees only public keys and could sign only through the family's signing oracle. Each `B^coll_t` wins only on a collision of index `t` with a lower index, so every colliding pair is charged once, at its higher index.
- Identity index. `a1_le_ordered`, `a1_bound`, `a1_sum`, `ce_a1` and `ce_a1_billed` hold for every identity index of the constructed Server. `session_unique`, `injective_bound` and `ce_a1_injective` are stated at index 0, the index of CE-9's trace invariant.
- The R1 Extract random oracle is charged with every local root: local Beacons compute their roots through the ServerAuth HMAC, so `romCap` counts them (the plan's "counted in qH").
- The ServerAuth game is used with `revealSeed = false` and the generated Server seed (`supplied = none`).

## CE-8: second fix pass

Plan section 30 (Claude's decision of 2026-10-07) settles the two points the first fix pass left open: the collision reduction of `ε_inj` becomes the zero-query reduction of owner input 17, and the KEM-ciphertext link of section 9's Beacon-side corollary moves to CE-12 with its own term `ε_ct` ("CE-8: decisions and deviations"). No module before CE-8 and no other CE-8 module changed.

- Definition `collider`. Before: the family collision finder `collider count publics`, a family adversary that sees only the family's public identities and signs the empty message once through the family's signing oracle; `B^coll_t` was `PqxdhJointIdentityFamily.reduction joint t (collider count)`, which forwards that signing query to the challenger when the signing identity is the target. After: `collider joint count t` is `B^coll_t` itself, a joint-use weak-EUF adversary that draws the other `count` seeds itself and signs with the colliding seed itself (`colliderForgery`).
- `collision_bound`. Before: `Pr[Collision joint pool | sampleSeeds (count + 1)] ≤ Σ_{t : Fin (count + 1)} advantage joint (PqxdhJointIdentityFamily.reduction joint t (collider count))`. After: `Pr[Collision joint pool | sampleSeeds (count + 1)] ≤ Σ_{t : Fin (count + 1)} advantage joint (collider joint count t)`.
- `collider_queries`. Before: `(collider count publics).IsQueryBoundP (familyClass (IsClass kind)) (if kind = .sign then 1 else 0)` for every family of public identities. After: `(collider joint count t jointPublic).IsQueryBoundP (IsClass kind) (if kind = .uniform then 32 * count else 0)` for every challenge identity.
- `collider_bills`. Before: for the family reduction, at most `32·count` uniform queries, at most 1 signing query and no static-DH query on every challenge identity, and at most `32·(count + 1)` uniform queries in its game. After: the same for the new `B^coll_t` with no signing query.
- `injective_bound` and `ce_a1_injective`. Before: `ε_inj = Σ_t Adv(PqxdhJointIdentityFamily.reduction setup.joint t (collider budget.create))`, and the bill conjunct of `ce_a1_injective` allowed 1 signing query. After: `ε_inj = Σ_t Adv(collider setup.joint budget.create t)`, and the bill conjunct states 0 signing queries; premises, the left-hand sides, the `R_c` terms and the other bills are unchanged.

Why the replacement is at least as strong. The right-hand sides name a different adversary, so as Lean propositions neither the old nor the new statements imply the others; they are replaced, as section 30 requires, not extended. As bounds to be used they are at least as strong: `ε_inj` is discharged by a joint-use weak-EUF assumption for adversaries within given bills, and every bill of the new `B^coll_t` is at most the old one's (uniform `32·qCreate`, signing 0 instead of 1, static-DH 0, game `32·(qCreate + 1)`). Any advantage bound `ε` for adversaries with at most one signing query also covers an adversary with none (`IsQueryBoundP.mono`), so every instantiation of the old statement gives the same `ε_inj ≤ (qCreate + 1)·ε` with the new one; the new one also gives it under the key-only form of the assumption (no signing query), which owner input 17 asks for and the old one could not use. Both sums are upper bounds on `Pr[Collision]`; each can include wins on fallback forgeries, and their exact values are not compared.

Statements: four new (`collider_game`, `lower_wins`, `lower_le_advantage`, `collision_lower`), two new definitions (`LowerCollision`, `colliderForgery`), and one removed: `probEvent_le_bind` ("an event that holds on every outcome of every continuation of the support points of another event is at least as likely"), a helper of the old `collision_bound` with no other use, never published. (3) `commands_le_real` replaces T4's event by the equivalent `RunEvent` with a clear disclosure history and moves it to the stopped router with the existing equality `PqxdhDynamicKemJointStopping.history_event`, which adds the condition that the stopped run's monitor is clear; it then drops that condition. Nothing is lost there: a completed run of the stopped router from a clear state always ends clear, because the stopped router answers the selected reveal only by stopping (`stopped_good`). (4) `run_le_real` splits the stopped run at the KEM cut of the selected accept. A run that stops before the cut, completes before the cut, or reaches a cut that encapsulates to a key other than the reserved key at index `selected` contributes `false` to both sides, so nothing is lost. At an active cut the real game counts every completed continuation with `decision ∧ accepted`, while T4's event also asks that the recorded raw bytes verify, which holds at every active cut, and that their verified PQ key, which is then the reserved key at index `selected`, be the key at index `selected` of the created prefix of the reserved list. The last condition fails exactly when creation index `selected` is never created during the run. These runs, in which the selected accept encapsulates to the reserved key of a creation index that the run never creates, are the only ones the proof discards.

The reverse chain. `real_le_run`, `real_le_commands` and `real_le_actual` run the same steps backwards, on the same games and under T4's own premises (the program's query budget `certified` and `room`) and no other: `Pr[sourceReal] ≤ Pr_actual[Decided ∧ GoodKem]`. The stopped run's event is `Completed decision ∧ Good`, where `Completed` is the final-state form of the real game's decision (the run completed, the selected accept returned a session and the decision holds); `real_le_run` checks the four cases of the split, using `finish_stopped` for the active cut and `stopped_good` for the monitor, and `real_le_commands` moves the event back to the ordinary router with `history_event`.

The equality and the defect. Together with T4, the reverse chain gives `Pr_actual[Decided ∧ GoodKem ∧ KeyMatchFinal] ≤ Pr[sourceReal] ≤ Pr_actual[Decided ∧ GoodKem]`. Hence, for every decision and with no further premise, `Pr[sourceReal] ≤ Pr_actual[Decided ∧ GoodKem ∧ KeyMatchFinal] + Pr_actual[Decided ∧ GoodKem ∧ ¬KeyMatchFinal]` (`real_le_actual_add`) and `|Pr[sourceReal] − Pr_actual[Decided ∧ GoodKem ∧ KeyMatchFinal]| ≤ Pr_actual[Decided ∧ GoodKem ∧ ¬KeyMatchFinal]` in real numbers (`actual_real_close`): every run that the proof of T4 discards is a run of `Decided ∧ GoodKem ∧ ¬KeyMatchFinal`. If, on the support of the actual execution, `Decided ∧ GoodKem` implies `KeyMatchFinal`, T4 is an equality (`actual_eq_real`). For the class that plan section 9 names, decisions that imply `accepted ∧ KeyMatchFinal ∧ GoodKem` (on the support, `Decided` implies `GoodKem ∧ KeyMatchFinal`; `Decided` contains `accepted`), the left side is simply `Pr_actual[Decided]` (`decided_eq_real`).

Without such a hypothesis the equality can fail. In a defect run the selected accept carries an ML-KEM public key equal to the reserved key of a creation index that the run never creates; T4's event excludes the run and the real game counts it. Its probability is the chance that an adversary-chosen PQ key equals a key the run never generated, and bounding it would need a min-entropy property of ML-KEM key generation, which is not an approved assumption: `MlKemScheme` does not exclude a key generation that puts positive mass on one public key, and with such a key generation a program that creates no Beacon and submits a verifying accept with that key, for the decision that is always `true` and creation index 0, has T4's left side 0 and a positive real game. This counterexample is an informal argument, not a Lean statement; no Lean statement depends on it.

The deployment decision is in the class. `decision_implies` shows that on the support of the actual execution of `tag (compileFull …) i` from empty pools with a generated Server seed, `Decided (decision … g)` implies `GoodKem (selectedKem budget g)`, by `PqxdhDeploymentQuiet.approved_goodkem_unbudgeted`, and `KeyMatchFinal (selectedKem budget g)`, by `PqxdhDeploymentKemTransfer.keymatch_point` under `Phase1ReadBack` (through the traced program, as in `eligible_actual`). So T4's defect for the per-target decision has probability zero (`defect_zero`), and steps 9.1-9.2 become one equality (`eligible_real`): for a budget-respecting adversary, `Pr_CE[happens event ∧ designated claim = some g] = Pr[sourceReal … (decision … g) (compileFull …) runtime qCreate (selectedKem budget g) i]`, at the transported caps of CE-9 (`transported`, `compile_full_certified`, `transported_room`).

Two-sided transfer. With the two-sided KEM hop `PqxdhDeploymentKemTransfer.kem_hop_close` (the certified hop `KemRawCertified.ideal_close` with T6), `kem_transfer_two_sided` states, for every event, claim and target `g = (i, k)`: `|Pr_CE[happens event ∧ designated claim = some g] − Pr[opaqueBranch … (decision … g) (compileFull …) runtime qCreate (selectedKem budget g) i false]| ≤ Adv^{IND-CCA}(KemRawCertified.adversary … (decision … g) …) + correctnessError setup`, in real numbers, with exactly the adversary and terms of `kem_transfer`. The game. `PqxdhDeploymentLater.laterGame setup codec checks route ensureInit identityIndex bounds mode A₁ A₂` constructs the Server from a generated seed, never a supplied one, as the classical game does, and then runs `laterExec` from the initial deployment state. First `A₁ : OracleComp (ModeSpec mode) X` runs against `laterHandler`, the CE handler with one ghost change. Then the reveal `revealOf owners snap` is computed from the final native owners and the snapshot. Then `A₂ : X → Reveal → OracleComp PostSpec Out` runs on `A₁`'s output and the reveal, under `postImpl`, from the final deployment state. The game returns the Server's public data, `A₂`'s output, the ledger, the snapshot and the deployment state after the post phase. The ghost change. `snapImpl` runs every command with the unchanged native handler; before a `finish c raw` it captures owner `c`'s current prekey and one-time fields in the snapshot. ## Later-quantum mode: what is revealed

`revealOf` holds one entry for every Beacon created through `create`, which is every owner of the native state, AnyPin Beacons included, in creation order (`revealOf_eq`, `revealOf_length`). The entry holds:

- the Beacon's Ed25519 identity seed, which stays live after finish;
- the Beacon's X25519 prekey scalar, drawn at `create`;
- the X25519 one-time scalar of the Beacon's successful bundle, if it has one.

Each scalar is the current field if the owner's phase still holds it, otherwise the value captured before finish or abort erased it. The Beacon's X25519 identity secret is not listed because it is the production conversion of the revealed seed. DH outputs are not listed either: every Beacon-side DH output is a public function of revealed scalars and public points, and so is the Server-side output of a session with an honest Beacon whose response was published, because the X25519 function commutes (`Pqxdh.Crypto.dh_comm`).

## Later-quantum mode: the compile lemma

`PqxdhDeploymentLaterCompile.compileLater setup codec route bounds mode A₁ A₂` is an ordinary source14 program in three parts.

- Run part: the CE-3 compiler applied to the wrapped `A₁`, with one changed case (`compileSnapImpl`). Before a `finish` on owner `c` it issues the source14 field reads `(c, prekey)` and `(c, oneTime)` and captures them in its own snapshot; then it runs the unchanged compiled finish. These reads are local reads that change no state and record no pool entry.
- Terminal part: for every owner its own log counts, the field reads `identity`, `prekey` and `oneTime`, turned into the reveal with the snapshot.
- Post part: `A₂` on the run's output and that reveal, with its coins, HMAC and BLAKE2b queries forwarded to source14 by the unchanged compiler.

The finish pre-read is a wrapper around `compileImpl`, not a change to it. The design expected the finish case of the compiler itself to change and warned that `PqxdhDeploymentCompileStep`, `PqxdhDeploymentCompileInvariant` and `PqxdhDeploymentCompileBudget` would then need re-checking. With the wrapper they are unchanged; they were re-checked anyway, and their artifacts are byte-identical to the unit A ones.

The proof. `merge_fields` shows that merging the compiled program's local copies changes no identity, KEM, prekey or one-time field of any owner, because `merge` replaces only peer and established-owner kernels, counters and produced frames. Hence the pre-read captures exactly what the native snapshot handler captures (`snapshot_merge`) and the terminal reads give exactly the reveal of the merged final state (`reveal_merge`, `terminal_merge`). `snap_step` is the finish pre-read case of the compile step: under the CE-3 step invariant, merging after a compiled step with the snapshot is the snapshot-handler step from the merged state; the CE-3 invariant `Good` is preserved (`snap_good`). `compile_snap_run` lifts this to the run part. `compile_post` is the post-phase commutation: forwarding `A₂`'s queries through the unchanged compiler, from a state with the CE-3 invariant, is the native post phase on the merged state. `compile_later_native` combines them, using that `Good` holds at the end of every run part.

The theorems. `compile_later_game`: under `Phase1ReadBack` and `Phase2ReadBack`, the later game with a generated Server seed is exactly the initialized source14 native execution of `compileLater A₁ A₂` with the merged final state, jointly over the Server's public data, `A₂`'s output, the ledger, the snapshot, the complete final deployment state and the runtime state. `compile_later_source` transfers this to the annotated initialized execution that T4, the KEM hop and T6 are stated for. No other premise is used; `FrameReadBack` and `DecoderAgreement` stay unused.

Budget transport. `compile_later_bound`: if `A₁` respects a run budget and `A₂` respects a post-run budget on every input, `compileLater` makes at most `∑ core, laterCost kind core * runCap core + readCost kind * runCap 1 + ∑ post, cost kind (postCore post) * post.cap post` source14 queries of each kind. `runCap` is the native cap transported through the secrecy layer, `laterCost` is the CE-3 cost plus one prekey and one one-time read per finish, `readCost` is one identity, prekey and one-time read, and `runCap 1 = qCreate` and `runCap 5 = qFinish` (`runCap_create`, `runCap_finish`). The terminal reads are bounded through the number of created owners the log counts (`owners_bound`), which is a property of every run, not a per-command cost. `compile_later_reads` gives the design's read caps: at most `qCreate` identity reads, `qFinish + qCreate` prekey reads and `qFinish + qCreate` one-time reads, and no KEM read. It assumes only that `A₁` respects its run budget and holds for every `A₂`, with no post-run budget, because the post part forwards only coin, HMAC and BLAKE2b commands, which issue no field read. `compile_later_no_kem` states the KEM part for every pair of adversaries without any budget, which keeps the KEM read cap of the approved GoodKem argument at 0 for LQ-3. `continuation_no_accept` shows that the terminal reads and the post part issue no raw accept, for every run-part result and every `A₂` without a budget, so every raw accept of `compileLater` is issued by its run part.

## Later-quantum mode: rules for later stages

- Never cite A2 or T5 on `compileLater`; cite them on the classical compiled program of `A₁`. This is a scoping rule that follows from the owner's profile, not a failed premise. Authentication is not claimed in this mode (plan section 19), and authentication is a property of the run: by `snap_erase` the run phase of the later game is exactly the classical game of `A₁`, so the run-phase authentication terms that later stages keep, such as `ε_A2` in the symbolic-eligibility corollaries, are classical terms of `A₁`: they bound events in the classical game, and `later_classical_event` carries such an event to the end of the later game when it is an event of the Server's public data, the ledger and the final deployment state that ignores the caches. `compileLater` is a different program: it adds the finish pre-reads, the terminal reads and `A₂`. A2 is planned for the classical compiled program of a deployment adversary (plan section 10, CE-A2). T5 holds for every program, and its premises `certified` and `capacity` hold for `compileLater` with the caps of `compile_later_bound` (an instantiation was checked in the fix pass), but its reductions are built from the whole program: its KEM adversary from `work`, and its signature reductions from the selected prefix, which is the whole program, `A₂` included, when the selected accept is never reached. On `compileLater` its terms would therefore not be terms of `A₁` alone. The terminal identity reads falsify no premise and no event of either result: they are reveal requests to the identity pool, but every raw accept of `compileLater` is issued before them (`continuation_no_accept`), T5 reads protection at the cut just before the selected accept (`PqxdhRegistrationJointAcceptOrigin.Protected`), and A2, as planned, reads freshness at each accept. What they rule out is whole-run unrevealedness: `kernel_reads_unrevealed` follows from a zero identity-read cap, which the classical compiled program has and `compileLater` does not, so it is not available for `compileLater`. `approved_goodkem` can still be re-proved for `compileLater` with `compile_later_no_kem` (LQ-3).
- Never project the R1 cache, the ghost touches or the family history into the reveal. `Revealed` cannot hold them, and later stages must not widen it with values that depend on the KEM output.
- No component whose secrecy is keyed by DH may be imported into a later-quantum claim (the design's new constraint for I-5): not `PqxdhJointDhExtractFamily.Protected`, the correlated DH Extract family or Gap-DH, which the reveal voids.
- The post-run queries are classical. This is a classical adversary with a post-run disclosure, not a quantum adversary and not the QROM; the real threat also needs ML-KEM, HMAC, Extract and the AEAD to be quantum-secure, which is a remark, not a Lean premise.
- Authentication is not claimed in this mode: run-phase authentication events are decided before the reveal and are the classical claims.

The experiment. `PqxdhDeploymentSecrecy.game … bounds mode A` constructs the Server from a generated seed and runs the adversary of mode `mode` against the CE handler from an empty ledger. The CE handler is the trial's native handler behind the secrecy layer. The layer forwards every coin and command unchanged and records it with its mode O reply. `test handle left right` requires equal nonzero lengths. The first admitted test draws the hidden bit with one experiment coin and fixes the test handle. A later test is admitted only on the same handle or on a handle with the same public designation, computed on the transcript so far. An admitted test is one send of `left` or `right` by the bit. `fresh handle length` requires `min ≤ length ≤ max`, draws a uniform message of that many bytes with one coin per byte when the command is issued, keeps it private and sends it. A rejected secrecy command changes nothing but the transcript, and the experiment's own draws never enter the transcript. Mode P is mode O behind `observeFull`, whose replies are the mode P projections of the mode O replies (`observeFull_project`). Secrecy claims (left-or-right and fresh-message secrecy) are stated only for mode P, as plan section 3.6 and owner input 4 (accepted on 2026-10-06) require: in mode O a raw receive returns the actual plaintext, so forwarding a test or fresh ciphertext to the partner's raw receive reveals the hidden message, and the secrecy commands are just sends there. Authentication claims may use either mode. `game_wrap` shows that the experiment is the trial's native game run on the wrapped adversary, with the ledger moved into the final state. Every record seal handed to the frame writer is logged with the record handle of its command, including seals whose writer then fails, and `logged_forget` shows that the log changes no result.

Logs. Both components of `Logs` are analysis logs, not public views. The transcript stores the mode O reply of every query in both modes, so in mode P it contains the plaintexts of raw receives, including those of test or fresh ciphertexts that the adversary forwarded; the adversary's view of an entry is `Entry.view mode`. The produced-frame log contains frames whose writer failed and that were never published, each tagged with a `FrameTag`: the peer key ID of a Server send, the owner handle of every Beacon record command, and `none` for a Server raw receive, which names no handle before routing. The tag never contains a plaintext, so the hidden messages of `test` and `fresh` never enter `Logs.produced`; together with the frame's sequence number and sender it gives the plan's (side, handle, sequence) tuple. Events meant to be public must be built from `Entry.view` and from the frames and tags only.

The compile lemma. `compile_full_game` and `compile_full_source` state that the experiment in either mode equals the merged initialized execution of `compileFull A` (the trial compiler applied to the wrapped adversary) jointly over the Server's public data, the adversary's output, the whole ledger (transcript, test session, fresh messages), the whole deployment state with the produced frames, and the runtime state. They use exactly the trial's two codec contracts, `Phase1ReadBack` and `Phase2ReadBack`. Because the wrapped adversary draws the bit and the fresh messages at the same positions as the experiment, no sampling-swap lemma is needed.

Budget transport. `wrap_bound` and `compile_full_bound` transport per-class caps through the secrecy layer and the compiler; `PqxdhDeploymentCompileCaps.transported` gives the closed form. The compiled program and its tagged form at any raw-accept ordinal make at most `qCoin + qTest + qFreshBytes` coins with `qFreshBytes = ℓmax · qFresh`, the registration and HMAC caps unchanged, `qHash + S + R + qTest + qFresh` BLAKE2b queries, `qSS + qSR + qTest + qFresh` Server kernel reveals, `qBS + qBR + qTest + qFresh` established-kernel reads and no identity, KEM, prekey or one-time read. `tag_certified` is the `certified` premise of T4 at these caps, and `transported_room` its `room` premise for `count + 1 = qCreate + 1`. The coin and BLAKE2b caps are looser than the plan; this is listed below as a plan change for the owner to confirm.

Selection (CE-4). For a run with outcome space `Ω` and a public `designate : Ω → Option G`, `split` writes the probability of an event on eligible outcomes as the exact sum over targets of the probability of the event with that target designated; `guess` writes it as `card G` times the probability that a uniform guess drawn before the run is the designated target; `advantage` is the split form for a left-or-right bit with the eligibility-weighted half subtracted. `sum_eq_card_mul` and `signed` turn a sum of per-target probabilities or of signed per-target differences into `card G` times the probability or signed difference of the run with a uniformly guessed target; with signed per-target hops this gives the owner's `N · Adv(B_guess)` wording. All statements are exact and use the measure form `𝒟[f <$> run] {true}` of the KEM theorems.

Publicity (CE-5). `agree_game` shows that every outcome of the experiment, in either mode, satisfies `Agree`: the transcript summary counts exactly the native owners, the public phase of every handle is the class of its native phase, every created binding is the owner's pinned Server identity and key ID, every successful bundle in the transcript is the Phase 1 writer output of the candidate the owner signed with its own identity key and the KEM public key it holds until finish, and every successful build response is the Phase 2 writer output of fields carrying the Server identity, which never changes. `phase_public`, `owner_public` and `failure_public` are its readings for `phase`, `owner` and `NoBundleFailure`: a rejected bundle sets an owner's failure flag exactly when the owner is natively Fresh. `owner_kemIndex` shows that in the annotated execution of any program the owner created `k`-th holds KEM creation index `k` and the KEM pool has one key per owner. The transcript functions read only queries and the replies of create, bundle, accept, build and finish commands, never a raw-receive reply. `summarize_view`, `phase_view` and `designate_view` prove it: two transcripts with the same mode P view (`SameView`) have the same summary, public phases, owner numbering, `NoBundleFailure`, designation and budgeted designation. So these functions are public in mode P although the transcript stores mode O replies.

Designation and key match (CE-5). The designation compares keys, as plan section 7 says, not signed fields. On the Server side, the accept bytes of the session that built the peer are read into a raw candidate, and `acceptedKeys` applies to it the source attached verification and parsing of the setup's crypto (`PqxdhJointPhase1Reports.sourceAccept`), which yields the same identity and keys as the native verification prefix `RawSignatures.verified` whenever that succeeds (`verified_keys`); only accepts that returned a session handle are looked up. The designated owner is the smallest created owner whose published bundle carries the candidate's identity field and whose published PQ field, split and parsed without a signature check (`publishedPq`), is the verified PQ key. On the Beacon side, the session must also verify to the PQ key read from the Beacon's published bundle. An accept that carries an honest owner's identity and published PQ key under a different valid signature is therefore designated like the owner's own bytes, and `designate_peer_complete` and `designate_owner_complete` show that the designation is made whenever its conditions hold. `designate_keymatch` (with `Phase1ReadBack`): for a Server peer designated `(i, k)`, every verification of the accept bytes of session `i` by the native verification prefix `RawSignatures.verified` yields owner `k`'s identity key and the PQ key owner `k` signed in its honest published bundle (`PublishedKey`). `owner_link` (with `Phase1ReadBack` and `Phase2ReadBack`): an owner designated `(i, c)` is natively Established and pinned to the protected key ID and to the Server's own identity; the response of session `i` is the Phase 2 writer output of fields carrying the Server identity; the ciphertext read from the owner's accepted finish input is the KEM ciphertext of those fields; and the PQ key verified at accept `i` is the one the owner published. `keymatch_game` and `link_game` state both on every outcome of the experiment. Both proofs read the verified key through `verified_keys` (the candidate and source attached verification inside `RawSignatures.verified`) and the published key through `publishedPq_candidate`; they use no signature-scheme property and no wiring law.

What `PublishedKey` does not give. It ties owner `k`'s published key to the owner's native KEM pair only while the owner is not finished: `kemPublic` is `none` for Established and Aborted owners, so in the designated case, where owner `k` has usually finished, `designate_keymatch` says nothing about KEM creation index `k` of the pool. Plan section 9 step 9.1 expected CE-5's `designate_keymatch` to yield `KeyMatchFinal k`, which compares with the final KEM pool of the annotated execution. The existing ownership invariant `PqxdhRegistrationJointOwnership.Owned` does not close this gap, because it constrains only the live KEM pair, which finish also erases. The step needs a new invariant on the pool-carrying annotated execution of `tag (compileFull A) i`, together with a relation that carries the compiled program's transcript into that execution: every bundle of owner `k` in the transcript carries pool key `k`, which holds when the bundle is produced (ownership and `owner_kemIndex`) and persists because the pool only appends. Unit A does not prove it. Strengthening `BundleShaped` with a ghost of the published key is not available within unit A: the native deployment state keeps no KEM key after finish, and a ghost added to it would have to be reproduced by `merge` from the source14 state, which does not keep it either. The step is re-estimated below as part of CE-9.

Freshness (CE-5). `approved_goodkem`: in the exact execution that T4 is stated for, the tagged compiled program of a complete-interface adversary, in either mode and at any raw-accept ordinal, ends every run with `GoodKem` for every KEM creation index. `kernel_reads_unrevealed`: in the same execution no identity index is ever revealed (`revealedAt` is false). Both follow from `quiet_initialized`: every annotated step other than an identity or KEM field read records only creation, signing, static DH and decapsulation observations, and the compiled program makes no such read. The forms named in the plan carry a budget that the adversary respects, which T4's `certified` premise needs anyway; the plan states them without one. `approved_goodkem_unbudgeted` and `kernel_reads_unrevealed_unbudgeted` are the plan's unconditional statements: they hold for every adversary, because no compiled command issues an identity or KEM read (`compile_unread`, `compile_full_unread`, via the generic `simulate_zero`).

CE-A2 (`PqxdhDeploymentProvenance.a2_bound`). For an adversary that respects `budget` and with the attached-signature format rule `shortRejects` (the existing premise, with `setup.wiring`):

```lean
letI := Classical.propDecidable
𝒟[(fun final => decide (NativeForgery setup codec checks ensureInit none (budget.create + 1)
    (compileFull setup codec route bounds mode adversary) runtime final)) <$>
  PqxdhJointPhase1Reports.run setup.joint (budget.create + 1)
    (PqxdhRegistrationJointReportCompiler.initialized setup codec checks ensureInit none (budget.create + 1)
      (compileFull setup codec route bounds mode adversary) runtime)] {true} ≤
  ∑ target : Fin (budget.create + 1), PqxdhJointIdentity.advantage setup.joint
    (reduction setup codec checks route ensureInit bounds mode adversary budget.create runtime fallback
      ordinaryFallback target)
```

The probability space is the report-instrumented initialized execution of the compiled program with a generated Server seed. The bound itself uses no codec law. Reading it as a statement about the deployment experiment uses `report_game`, which shows, under the approved codec laws `Phase1ReadBack` and `Phase2ReadBack` (needed through `compile_full_source`), that the projection of this execution to the constructed Server's public data, the adversary's output and the whole ledger is exactly the deployment experiment with the Server's identity index 0: `compile_full_source` gives the deployment game the identity index equal to the number of seeds in the pool at which the instrumented execution starts, and that pool is empty. `NativeForgery` (`PqxdhDeploymentAcceptDetection`) holds for a final outcome when the run passes through a successful raw accept at some position, the accept's raw bytes pass the native verification prefix `RawSignatures.verified` with the identity key of a generated owner of the owner registry, that owner is unrevealed, and the verified key tuple is not among the owner's chronological signing attempts, failed publications included, all read in the state reached when the accept returned. The bound is one ordinary joint-use weak-EUF term per generated identity position, summed over the `qCreate + 1` positions (the Beacons and the generated Server seed), with coefficient one: no accept-position, owner, field or report-position factor and no collision term. `fallback` and `ordinaryFallback` are the arbitrary default forgeries of `fieldOrigin_advantage_le_sum`. The per-ordinal fallback of the plan was not needed.

The unrevealed conjunct of `NativeForgery` holds on every run of the compiled program, so CE-A2 holds for every generated owner (`PqxdhDeploymentProvenance.a2_generated_bound`). Stopped right after its raw accept at any position, the compiled program issues no identity-field, KEM-field, prekey or one-time read (`upto_unread`: the scan keeps the zero caps of `compile_full_unread` and the stopping step issues only the accept). By `PqxdhDeploymentQuiet.quiet_initialized`, the source execution of such a program records no reveal observation, so `revealedAt` is false for every identity index on every stopped run (`stopped_unrevealed`). Hence `NativeForgery` of the compiled program is the same set of final outcomes as `GeneratedForgery`, the event without the unrevealed conjunct (`generated_forgery_iff`), and `a2_generated_bound` bounds `GeneratedForgery` by the same sum, with the same premises; since `GeneratedForgery` contains `NativeForgery` for every program, it is at least as strong as `a2_bound`. So no identity is revealed during any run of the compiled program; unit A's `kernel_reads_unrevealed_unbudgeted` shows the same at the end of every run of its tagged form. The owner's post-run reveal mode, which discloses honest Ed25519 identity secrets after the run, does not change this event, which is about accepts during the run.

Query bills of the A2 reductions (`PqxdhDeploymentProvenance.a2_bills`). These are the reductions of `a2_bound`, `a2_generated_bound`, CE-A2pub and CE-R1', and the bills have the form of the accept/KEM join's T5b. For an adversary that respects `budget`, every reduction at every generated position, for every challenger public identity, makes at most `3 * budget.bundle` signing requests and at most `budget.finish + budget.accept` converted-DH requests (`a2_service_bound`). With T5b's uniform-bill premises (`initBound`, which bounds `ensureInit` by `qInit` queries, and `KemBound setup caps`), the A2 client pays at most the uniform bill `PqxdhRegistrationJointIdentityUniform.total caps qInit (PqxdhDeploymentCompileCaps.transported bounds budget)` (`a2_client_uniform`), every reduction makes at most `32 * budget.create` more uniform requests for the other reserved seeds (`a2_reduction_uniform`), and every endpoint game `PqxdhJointIdentity.game setup.joint (reduction … target)` makes at most `32 * (budget.create + 1)` queries plus the client bill in total (`a2_game_uniform`). The proofs transport the compiled program's caps (`compile_full_certified`) through the report compiler and the terminal batches, which issue no request of any source class (`client_class_bound`), and apply `PqxdhJointPhase1Reports.fieldReduction_query_bound` and `fieldReductionGame_uniform_bound`. The four per-reduction lemmas hold for every reduction count; `a2_bills` collects them at the count `budget.create` of the bounds.

The `NoBundleFailure` signing-history lemma (`PqxdhDeploymentSigningHistory.signing_history`). On every outcome of the initialized source execution of the compiled program from empty pools, for every owner of the registry with `NoBundleFailureAt T owner`, either the owner published no bundle and its whole signing history is empty, or its first published bundle is `codec.write1` of the candidate it signed with its own identity key over one key tuple `keys`, and its whole signing history is exactly the three messages of `keys`. It is proved with the invariant `Signed` along the stacked execution of the secrecy layer, the compiler and the annotated Server schedule (`execution`); no codec law and no assumption is used.

CE-A2pub (`PqxdhDeploymentPublishedTuple.a2pub_owner_bound` and its corollary `a2pub_bound`), with `shortRejects`, the approved codec laws `Phase1ReadBack` and `Phase2ReadBack` and the budget: `𝒟[(fun outcome => decide (OwnerEvent setup codec outcome)) <$> (PqxdhDeploymentSecrecy.game setup codec checks route ensureInit 0 bounds mode adversary).run runtime] {true}` is at most the same sum as CE-A2, over the same reductions. `OwnerEvent` holds when the outcome constructed a Server and, for some created owner that made no rejected bundle call in Fresh (`NoBundleFailureAt`), some successful accept carries a raw candidate that the source attached verification of `setup.source.crypto` accepts with that owner's identity key and a key tuple other than the tuple of that owner's published bundle, read from public bytes without a signature check (`publishedTuple`), or that owner published none (`OwnerForgery`). ## Unit 3: decisions and deviations

- CE-A2 is detected mid-run, not by a selection argument. `upto` stops the program right after its raw accept at a chosen position, so the report run of the stopped program ends exactly after that accept and its own public report batch; `upto_detects` shows that the stopped run's final snapshot is the one at which that batch was evaluated, and `violation_detects` turns a native violation there into a detected original-field failure through `AttemptReports.owner_origin`, the report-run form of `raw_origin`'s argument. The report flag is sticky (`continuation_sticky`), so every final outcome reachable through a violating accept has the flag raised (`forgery_detected`).
- `NativeForgery` is a reachability event on final outcomes: an outcome belongs to it when some execution path through a violating accept reaches it. It contains every outcome of a path that actually passes through a violating accept, so the bound covers the path event and can only be larger than it. The violation is read in the state reached when the accept returned; the accept changes no Beacon owner's signing history, reveal history or identity handle.
- CE-A2 is stated on the report-instrumented execution, not on the deployment game's state, because its event refers to the private signing log, reveal history and identity handles, which exist only there; `report_game` identifies the public projection with the deployment game under the approved codec laws `Phase1ReadBack` and `Phase2ReadBack`, which it needs through `compile_full_source`. CE-A2pub and CE-R1' are the public-transcript corollaries and are stated on the deployment game itself.
- `NativeForgery` keeps its unrevealed conjunct because `PqxdhDeploymentAcceptDetection` is stated for every source14 program, some of which reveal identities. For the compiled program the conjunct is proved to hold (`stopped_unrevealed`), so CE-A2 is also stated without it (`a2_generated_bound`).
- The A2 client (`PqxdhDeploymentProvenance.client`) is the instrumented execution followed by one terminal public batch for the raw candidate of every successful accept of the final transcript (`announceAll`). The batches add no identity request (`client_creates`), so CE-A2, CE-A2pub and CE-R1' share one family of reductions and one sum, and the published-tuple corollaries need only final-state facts.
- CE-A2pub and CE-R1' are stated for the Server's identity index 0. The reason is the proof route: `compile_full_source` identifies the compiled program's initialized execution with the deployment game at the identity index equal to the number of identity seeds in the starting pool, and the report-instrumented execution starts from empty pools. In the deployment game the index enters only through `PqxdhLiveServerConstruction.initialized`, which stores it in the constructed Server's metadata next to its key ID, but no lemma shows that the probabilities of the CE-A2pub and CE-R1' events do not depend on it, so other indices are not claimed. CE-R1 and CE-C3 hold for every identity index.
- CE-A2pub and CE-R1' are proved per owner (`a2pub_owner_bound`, `r1prime_owner_bound`): the forged or doubly accepted owner must have made no rejected bundle call in Fresh, and other owners are unrestricted. This is stronger than the plan's events, which require `NoBundleFailure` for every owner; those planned forms (`a2pub_bound`, `r1prime_bound`) keep their statements and are corollaries.
- CE-A2pub compares key tuples, never signature bytes: the verified tuple of the accept against the tuple parsed from the published bundle. No SUF-CMA or signature-uniqueness assumption is used.
- CE-R1' needs no reduction of its own: its event is contained in the CE-A2pub event on every outcome (`replay_published`), so its bound is the CE-A2pub bound, not twice it.
- CE-C3 is proved with the consumption relation of `RawCtxReceiveConsumption` (`ConsumedRefines`, `raw_spent`, `send_spent`, `initialized_spent`) rather than HB-105's private history monitor: the deployment handler runs owners and peers directly, so the consumed positions are read from the transcript. The owner side includes the finish's acceptance of sequence one, so the registration record cannot be accepted again by a raw receive; this is stronger than the plan's raw-receive-only reading. Peers are separated by the key ID the decrypted record names, which is the key ID the Server routed to (`rawGame_success`).
- No planned statement was found false or unprovable, and none was weakened.

### Plan changes recorded

- Read caps. The plan's section 8 table bounds Server reveals by `qBuild` and established-kernel reads by `min(qCreate, qFinish)`. `compile_bound` gives looser caps: reveals at most the budget of Server send and raw-receive commands, and kernel reads at most the budget of Beacon send and raw-receive commands. `peerKernel` and `ownerKernel` read whenever no local copy exists, including for key IDs that are not installed and Beacons that are not established, and an empty answer is not kept, so such reads repeat. Soundness is unaffected: T4 `actual_le_real` instantiates on `compile A` with `compile_bound` as its budget premise, and its creation-count premise uses only the create cap. Later bills that count reveals or kernel reads use the record-command budgets. Gating the reads on the public log would need an amortized whole-run count in place of the per-command `weighted_bound` argument and changes to several checked modules, so it was not done.
- The local Server metadata placeholder (plan section 8 b) is unnecessary: Server metadata is `Unit`, and the invariant proves that the sender ID equals `setup.serverKeyId`.
- A peer's identity needs only the identity parse of the accept bytes, not the full signature check.

### Open points

- F1, decided by the owner on 2026-10-06: option (a), recorded as deviation D5. The experiment's adversary takes no input; it learns the Server identity key through the protocol, for example by registering one of its own Beacons and reading the build response, which costs registration queries and shifts session ordinals and key IDs, so it is not an exact reduction from an adversary that receives the key as input. Background: The plan gives the adversary the Server's public identity key as input, but T4-T6, the report lines and `InitializedSchedule.source` run a fixed program with no input after the Server is generated, and no source14 command returns the Server key. In the trial the adversary therefore has no input and can learn the Server key only by parsing build responses. Learning it by registering first also shifts session ordinals and key IDs, so this is not an exact reduction from the plan's adversary. Options: (a) accept the input-free adversary as a recorded deviation, at no proof cost; (b) generalize the T4-T6 and report lines to programs that depend on the generated public identity; (c) add a Server-identity getter to source14 and re-prove the line over the extended interface. With the key as input only `Phase1ReadBack` would be needed; the trial needs `Phase2ReadBack` because it reads the Server identity from a build response.
- Post-run reveal mode. On 2026-10-06 the owner chose a post-run "later quantum" mode: after the run, every honest X25519 secret, every DH output and every honest Ed25519 identity secret is revealed, and only confidentiality is claimed. The interface stays open to it. Because `compile_game` equates the whole final deployment state, the mode can be added as a phase after the run that is a function of the final state, without changing `Command` or the compile cases. Open: on the compiled side the secrets are reachable only through source14's identity, prekey and one-time field reads, which `compile_bound` caps at zero, which interact with `revealedAt` and `GoodKem`, and which follow native erasure; the Server identity seed, ephemeral scalars and DH outputs have no read. Its cost is to be designed and confirmed before it is built.
- Not done: the `test` and `fresh` commands with the sampling swap, `CE.Logs`, mode P beyond the wrapper, the public functions `phase`, `owner`, `NoBundleFailure` and `designate`, the comparison of the transported caps with T4's ledgers, and the step from `compile A` to `tag work index`.
