# Related-DH Extract outputs at the pinned-server boundary

Three modules define one explicit additional related-input Extract game, connect its real replies to the production 32-byte root, and check adaptive query accounting. They contain 29 guarded statements. The endpoint does not assume its advantage is small and does not establish pinned-server authentication. It is stronger than the existing ordinary Gap-DH recovery game and the existing single-sampler Extract game. No primitive implementation, snapshot or persistence behavior is proved.

## Why the output service is necessary

Beacon's accepted Phase-2 root contains two values unavailable to a reduction holding neither the pinned Server identity seed nor the selected Beacon prekey scalar: the static Server/Beacon DH value in the first coordinate and that same Beacon prekey's DH with the response ephemeral in the third coordinate. The prior source package checks exact optional callback order, conversion and raw Ed25519 pinning, and recognizes the actual extracted 192-byte input using two anchored Gap-DH decisions. Recognition alone cannot answer root-derived record queries.

The same unavailable Server seed also services other registrations. Their Beacon prekeys need not have known discrete logarithms. A service restricted to only the selected Beacon prekey cannot simulate those outputs. Replacing every such output by random values would instead give an immediate known-scalar distinguisher: an attacker can choose another prekey with known scalar, calculate its DH with the published Server key, supply all remaining coordinates, and evaluate fixed public Extract. The single endpoint below therefore retains real related outputs outside the protected actual-DH class.

## Exact ordinary game

`PqxdhJointDhExtractFamily` samples the existing uniform 32-byte Ed25519 identity seed and then the existing uniform 32-byte X25519 prekey scalar. It publishes the correlated Ed25519/converted-X25519 identity and the prekey public encoding. The same-seed signing service always evaluates the actual joint primitive. The challenger retains both selected secrets. This endpoint sampling order is explicit; embedding it into interleaved source generation still requires the complete continuation law and target-selection argument. Equality of keypair marginals is not used.

An adaptive derivation message contains an arbitrary static-DH peer encoding, a descriptor for the third coordinate, and supplied 32-byte second, fourth and KEM coordinates. The third descriptor either contains a known 32-byte result or requests the selected Beacon prekey's DH with an arbitrary peer encoding. The challenger first evaluates static DH at the supplied static peer. If it succeeds, it evaluates the third descriptor. The actual optional failure is identical in both worlds. Success builds exactly FF32 || DH1 || DH2 || DH3 || DH4 || KEM, of length 192. Neither selected secret is a request field. Supplied local values are not presumed independent of the public challenge, other replies or each other.

The real service returns full 64-byte fixed-zero-salt HMAC-SHA-512 Extract at that input. The ideal changes only successful inputs whose actual first DH coordinate equals the selected Server/Beacon cross-DH value. Those inputs share one private table indexed by the entire actual 192 bytes. A new input gets one uniform 64-byte block; a repeated input reuses the whole block. Inputs outside that class keep the fixed real Extract value. The private table is retained as analysis instrumentation in the real service as well. Its key is never a request label, peer encoding or symbolic constructor.

Protection is defined from actual input bytes. `input_protected_iff` proves that it is exactly equality of the successful static-DH replies. Hence different public encodings, different request constructors, and known versus selected third-coordinate descriptions coalesce whenever their real 192 bytes coalesce. No DH, public-key or cross-key injectivity is assumed. `side_real` proves identical complete service behavior for an unrelated actual DH1 value. `protected_hit`, `protected_miss` and `derive_hit` check complete table reuse and state updates. `input_some_iff` and `input_length` check actual assembly, and `real_derive` and `rejected` retain the original optional reply and truthful request history.

A separate public-HMAC request takes an arbitrary 64-byte key and arbitrary bytes. It always evaluates the fixed real HMAC in both worlds, including zero-salt guesses of any full input. It neither consults nor programs the private table. `public_evaluation` checks this equality. Public algorithms may also be used in local client computations; their computational cost must be included in the caller's ordinary running-time contract. Table lookup, input assembly, comparisons, parser work and primitive evaluation are not assigned zero cost by the random-query bounds.

The winning event is only the final distinguishing bit. There is no authentication predicate, protocol-acceptance requirement, input-recovery premise or hidden freshness premise in the endpoint. No selected-secret or raw selected-DH reveal service is supplied. The consuming protocol reduction must prove that its fresh branch does not need such a service, and must stop or consistently switch at selected compromise. Absence of a reveal oracle does not prove the source freshness condition. Recovering an actual protected input reveals its first DH coordinate, but this observation is not a reduction to the existing Gap-DH game: that game cannot simulate these additional derived-output side queries.

## Source-shaped requests and the real root reduction

`PqxdhJointDhExtractRoot.beaconMessage` uses the public selected prekey, actual response ephemeral and actual locally held Beacon identity-DH, one-time-DH and KEM replies. `beacon_input` identifies it with the prior two-coordinate source address. `beacon_source` consumes the checked source-reference/conversion and extracted builder laws to obtain exactly the production 192-byte input. Those premises are ordinary source occurrence and functional builder facts; they are not root secrecy or authentication assumptions. The prior source package supplies their derivation from reached preparation and exact pinning.

`serverMessage` uses the actual admitted Beacon prekey and the Server's locally generated ephemeral-DH results, with the actual encapsulated KEM shared secret. `server_input` checks its assembly without requiring a scalar for the admitted Beacon prekey. Connecting every such descriptor to the full Server-side optional callback trace remains a consuming source compiler task; this module does not claim that a descriptor definition alone proves all Server scheduling or field provenance.

The executable root reduction receives a full PRK through the family service, makes one explicitly counted real HMAC query at PRK and INFO_PQ || 01, and returns only its first 32 bytes to the root caller. A failed input returns None without expansion. It holds neither challenge seed nor scalar. Internal family/Expand observations and the full cache remain private interpreter instrumentation, not additional network observations.

`root_real` uses the existing ordinary functional source-HKDF contract and proves equality with the actual typed source root, including optional rejection and the complete history/cache. `reduction_step` retains real same-seed signing and public evaluations alongside roots. `reduction_complete` proves equality for an arbitrary adaptive root-valued client and its entire final state. `game_real` additionally retains the exact endpoint sampler and final bit. `advantage_exact` gives coefficient one: the real source-root service versus its protected-family ideal has exactly the advantage of the constructed ordinary family distinguisher. This is a concrete interface reduction, not an assertion of small advantage, a uniform-root conclusion, or a final authentication theorem. The ideal still expands the table PRK with the fixed real HMAC; a later ordinary uniform-secret-key HMAC hybrid and its alias/freshness consumer remain necessary.

## Resource ledger

`PqxdhJointDhExtractBounds` partitions requests into uniform sampling, signing, public HMAC and derivation. Let their complete adaptive root-client caps be qU, qSign, qHmac and qRoot. The executable reduction has caps qU, qSign, qHmac + qRoot and qRoot respectively. Every attempted root counts, including rejected and repeated inputs. At most qRoot of the HMAC calls are the explicit Expand calls, and at most qRoot fixed Extract calls occur in the real family service. Thus real primitive HMAC evaluations from these services total at most qHmac + 2*qRoot. Signing calls remain at most qSign. Each family request evaluates at most one static DH and one selected-prekey DH, so its functional input work is at most 2*qRoot DH evaluations; the fixed protected cross-DH comparison value can additionally be evaluated once per challenger. These functional call counts do not prove primitive implementation running time.

`extract_uniform`, `real_step`, `ideal_step`, `real_run` and `ideal_run` prove all adaptive random-query bounds while retaining full service state. `game_uniform` pays both challenge samplers: the real endpoint uses at most 64 + qU uniform queries; the ideal uses at most 64 + qU + 64*qRoot. The 64 initial draws and each 64-draw table block are byte samplers. General client uniform requests retain their original finite ranges and ordinary running-time costs. `root_bills` counts one derivation and at most one expansion per request. `reduction_step`, `reduction_weighted` and `reduction_bills` prove the four caps across every optional reply. `root_game_uniform` combines the source-root equality with both complete endpoint ledgers.

These are service bounds. Actual source preparation still pays all KEM, conversion, parsing, local DH, allocation and continuation work, including attempts rejected after DH/decapsulation. In particular the prior Beacon prefix retains its twelve callbacks, split into two selected effects and ten auxiliary effects with bound 10*qAux + 2*qVisit. The family endpoint does not make that work disappear or grant a free opaque ambient oracle.

## Remaining computational obligation

The additional advantage must remain explicit unless independently justified for the exact fixed HKDF-SHA-512 and joint Ed25519/X25519 input family. Ordinary EUF-CMA does not simulate converted-DH use. Ordinary Gap-DH recovery, collision resistance, HMAC PRF under a uniform secret key, or a claim of input entropy does not imply this related-input fixed-Extract property. The same-seed signing, real related-output side interface, actual optional validation and full-input aliases are essential parts of its statement. Independent interface review found no immediate known-scalar or request-alias distinguisher under these exact rules; that scrutiny is not a proof of security of the endpoint.

The global consuming proof must still embed the actual source generator order, every unavailable-seed use, dynamic target/session selection, selected compromise stopping, later full-output KDF/record effects and the exact symbolic event. No smallness hypothesis is introduced in these modules. Their guarded axiom reports contain only the standard Lean axioms; no custom security axiom or placeholder is present.
