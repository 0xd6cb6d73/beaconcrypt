The game. `PqxdhDeploymentLater.laterGame setup codec checks route ensureInit identityIndex bounds mode A₁ A₂` constructs the Server from a generated seed, never a supplied one, as the classical game does, and then runs `laterExec` from the initial deployment state. First `A₁ : OracleComp (ModeSpec mode) X` runs against `laterHandler`, the CE handler with one ghost change. Then the reveal `revealOf owners snap` is computed from the final native owners and the snapshot. Then `A₂ : X → Reveal → OracleComp PostSpec Out` runs on `A₁`'s output and the reveal, under `postImpl`, from the final deployment state. The game returns the Server's public data, `A₂`'s output, the ledger, the snapshot and the deployment state after the post phase. It is defined for both observation modes; as in the classical game, secrecy claims are to be stated in mode P, and the adversary takes no input (D5).

The ghost change. `snapImpl` runs every command with the unchanged native handler; before a `finish c raw` it captures owner `c`'s current prekey and one-time fields in the snapshot. A capture keeps an earlier captured value where the current field is absent (`capture_absent`), so a later finish on a terminal owner erases nothing from the snapshot. `capture_initSent` shows that a finish on an InitSent owner records exactly its prekey scalar and one-time scalar, which the native finish then erases on both success and abort. `snap_erase_run` shows that forgetting the snapshot gives back the native run, and `snap_erase` that the run phase of the later game, with the snapshot forgotten, is exactly the classical game `PqxdhDeploymentSecrecy.game`, jointly over the Server's public data, `A₁`'s output, the ledger, the deployment state and the runtime state.

The post phase. `PostSpec` has coins, the public HMAC and the BLAKE2b oracle, and no protocol, `test` or `fresh` command. `postImpl` answers them with the native handler's own coin, HMAC and BLAKE2b commands on the final caches (`post_embed`), so the HMAC is the same R1 slice table with real HMAC elsewhere, and the hash is the same BLAKE2b cache. The post-run budgets `qCoin₂`, `qHmac₂` and `qHash₂` are a `PostBudget`, separate from the run budget. `post_frame` shows that a whole post phase changes at most the Extract family, the BLAKE2b cache and the ghost touch list: no owner, Server peer, pending token, counter, other ghost field or produced frame changes. `later_frame` adds that the later game keeps the run's ledger and snapshot. `later_event` and `later_classical_event` turn this into the design's run-phase transfer: an event of the Server's public data, the ledger and the deployment state that ignores the caches has the same distribution at the end of the later game as at the end of the classical game. Run-phase terms such as the planned symbolic-eligibility terms `ε_A1` and `ε_A2` therefore carry over unchanged as classical terms of `A₁`.

## Later-quantum mode: what is revealed

`revealOf` holds one entry for every Beacon created through `create`, which is every owner of the native state, AnyPin Beacons included, in creation order (`revealOf_eq`, `revealOf_length`). The entry holds:

- the Beacon's Ed25519 identity seed, which stays live after finish;
- the Beacon's X25519 prekey scalar, drawn at `create`;
- the X25519 one-time scalar of the Beacon's successful bundle, if it has one.

Each scalar is the current field if the owner's phase still holds it, otherwise the value captured before finish or abort erased it. The Beacon's X25519 identity secret is not listed because it is the production conversion of the revealed seed. DH outputs are not listed either: every Beacon-side DH output is a public function of revealed scalars and public points, and so is the Server-side output of a session with an honest Beacon whose response was published, because the X25519 function commutes (`Pqxdh.Crypto.dh_comm`).

Not revealed:

- Deviation D6: no Server secret. Neither the Server's Ed25519 identity seed (nor its X25519 conversion) nor any Server ephemeral scalar is revealed. Server-side DH outputs against points whose discrete logarithm the adversary does not know, and DH values of sessions whose ephemeral public key was never published, therefore stay unrevealed. The owner's full profile (plan section 19) also reveals these; LQ-S would add the Server identity seed and LQ-F the Server ephemeral scalars.
- The one-time scalars of failed bundle attempts. They are dropped in Rust and in Lean and their public keys are never output (owner decision 2 of the design).
- ML-KEM secret keys and shared secrets. The mode assumes that ML-KEM stays secure against the later attacker; revealing a Beacon's KEM secret key would let `A₂` decapsulate its ciphertext and recompute its roots, so no confidentiality claim could hold. The stage request listed KEM secrets among the revealed values; excluding them matches the owner's profile in plan section 19, which reveals X25519 secrets, DH outputs and Ed25519 identity secrets and no ML-KEM secret, and the design's list of values that are never revealed (design section 1). It is also what the design's T7 condition needs: with a Beacon's KEM secret key revealed, the KEM output `u` of each of its sessions would be determined by the reveal and the public ciphertext, while T7 needs `u` to be independent of everything else, including the revealed values.
- The Extract family and the R1 cache, the ghost touches and the family history (they contain the KEM output and roots), roots, chains, kernels, skipped keys, record keys and plaintexts, the hidden bit and the fresh messages.

The type `Revealed` has only an identity seed and two optional scalars, so nothing else can enter the reveal. The snapshot stores only the scalars of prekey and one-time field values (`scalarOf`).

## Later-quantum mode: the compile lemma

`PqxdhDeploymentLaterCompile.compileLater setup codec route bounds mode A₁ A₂` is an ordinary source14 program in three parts.

- Run part: the CE-3 compiler applied to the wrapped `A₁`, with one changed case (`compileSnapImpl`). Before a `finish` on owner `c` it issues the source14 field reads `(c, prekey)` and `(c, oneTime)` and captures them in its own snapshot; then it runs the unchanged compiled finish. These reads are local reads that change no state and record no pool entry.
- Terminal part: for every owner its own log counts, the field reads `identity`, `prekey` and `oneTime`, turned into the reveal with the snapshot.
- Post part: `A₂` on the run's output and that reveal, with its coins, HMAC and BLAKE2b queries forwarded to source14 by the unchanged compiler.

The finish pre-read is a wrapper around `compileImpl`, not a change to it. The design expected the finish case of the compiler itself to change and warned that `PqxdhDeploymentCompileStep`, `PqxdhDeploymentCompileInvariant` and `PqxdhDeploymentCompileBudget` would then need re-checking. With the wrapper they are unchanged; they were re-checked anyway, and their artifacts are byte-identical to the unit A ones.

The proof. `merge_fields` shows that merging the compiled program's local copies changes no identity, KEM, prekey or one-time field of any owner, because `merge` replaces only peer and established-owner kernels, counters and produced frames. Hence the pre-read captures exactly what the native snapshot handler captures (`snapshot_merge`) and the terminal reads give exactly the reveal of the merged final state (`reveal_merge`, `terminal_merge`). `snap_step` is the finish pre-read case of the compile step: under the CE-3 step invariant, merging after a compiled step with the snapshot is the snapshot-handler step from the merged state; the CE-3 invariant `Good` is preserved (`snap_good`). `compile_snap_run` lifts this to the run part. `compile_post` is the post-phase commutation: forwarding `A₂`'s queries through the unchanged compiler, from a state with the CE-3 invariant, is the native post phase on the merged state. `compile_later_native` combines them, using that `Good` holds at the end of every run part.

The theorems. `compile_later_game`: under `Phase1ReadBack` and `Phase2ReadBack`, the later game with a generated Server seed is exactly the initialized source14 native execution of `compileLater A₁ A₂` with the merged final state, jointly over the Server's public data, `A₂`'s output, the ledger, the snapshot, the complete final deployment state and the runtime state. `compile_later_source` transfers this to the annotated initialized execution that T4, the KEM hop and T6 are stated for. No other premise is used; `FrameReadBack` and `DecoderAgreement` stay unused.

Budget transport. `compile_later_bound`: if `A₁` respects a run budget and `A₂` respects a post-run budget on every input, `compileLater` makes at most `∑ core, laterCost kind core * runCap core + readCost kind * runCap 1 + ∑ post, cost kind (postCore post) * post.cap post` source14 queries of each kind. `runCap` is the native cap transported through the secrecy layer, `laterCost` is the CE-3 cost plus one prekey and one one-time read per finish, `readCost` is one identity, prekey and one-time read, and `runCap 1 = qCreate` and `runCap 5 = qFinish` (`runCap_create`, `runCap_finish`). The terminal reads are bounded through the number of created owners the log counts (`owners_bound`), which is a property of every run, not a per-command cost. `compile_later_reads` gives the design's read caps: at most `qCreate` identity reads, `qFinish + qCreate` prekey reads and `qFinish + qCreate` one-time reads, and no KEM read. It assumes only that `A₁` respects its run budget and holds for every `A₂`, with no post-run budget, because the post part forwards only coin, HMAC and BLAKE2b commands, which issue no field read. `compile_later_no_kem` states the KEM part for every pair of adversaries without any budget, which keeps the KEM read cap of the approved GoodKem argument at 0 for LQ-3. `continuation_no_accept` shows that the terminal reads and the post part issue no raw accept, for every run-part result and every `A₂` without a budget, so every raw accept of `compileLater` is issued by its run part.

## Later-quantum mode: rules for later stages

- Never cite A2 or T5 on `compileLater`; cite them on the classical compiled program of `A₁`. This is a scoping rule that follows from the owner's profile, not a failed premise. Authentication is not claimed in this mode (plan section 19), and authentication is a property of the run: by `snap_erase` the run phase of the later game is exactly the classical game of `A₁`, so the run-phase authentication terms that later stages keep, such as `ε_A2` in the symbolic-eligibility corollaries, are classical terms of `A₁`: they bound events in the classical game, and `later_classical_event` carries such an event to the end of the later game when it is an event of the Server's public data, the ledger and the final deployment state that ignores the caches. `compileLater` is a different program: it adds the finish pre-reads, the terminal reads and `A₂`. A2 is planned for the classical compiled program of a deployment adversary (plan section 10, CE-A2). T5 holds for every program, and its premises `certified` and `capacity` hold for `compileLater` with the caps of `compile_later_bound` (an instantiation was checked in the fix pass), but its reductions are built from the whole program: its KEM adversary from `work`, and its signature reductions from the selected prefix, which is the whole program, `A₂` included, when the selected accept is never reached. On `compileLater` its terms would therefore not be terms of `A₁` alone. The terminal identity reads falsify no premise and no event of either result: they are reveal requests to the identity pool, but every raw accept of `compileLater` is issued before them (`continuation_no_accept`), T5 reads protection at the cut just before the selected accept (`PqxdhRegistrationJointAcceptOrigin.Protected`), and A2, as planned, reads freshness at each accept. What they rule out is whole-run unrevealedness: `kernel_reads_unrevealed` follows from a zero identity-read cap, which the classical compiled program has and `compileLater` does not, so it is not available for `compileLater`. `approved_goodkem` can still be re-proved for `compileLater` with `compile_later_no_kem` (LQ-3).
- Never project the R1 cache, the ghost touches or the family history into the reveal. `Revealed` cannot hold them, and later stages must not widen it with values that depend on the KEM output.
- No component whose secrecy is keyed by DH may be imported into a later-quantum claim (the design's new constraint for I-5): not `PqxdhJointDhExtractFamily.Protected`, the correlated DH Extract family or Gap-DH, which the reveal voids.
- The post-run queries are classical. This is a classical adversary with a post-run disclosure, not a quantum adversary and not the QROM; the real threat also needs ML-KEM, HMAC, Extract and the AEAD to be quantum-secure, which is a remark, not a Lean premise.
- Authentication is not claimed in this mode: run-phase authentication events are decided before the reveal and are the classical claims.

Names for consumers. Game: `PqxdhDeploymentLater.laterGame`, `laterExec`, `laterRun`, `LaterState`, `PostSpec`, `PostBudget`, `postImpl`. Reveal: the entry type `Revealed`, the list type `Reveal`, the reveal function `revealOf` and its description `revealOf_eq` (with `revealOf_length`); LQ-4's T7 condition and the LQ-7 headlines should name the reveal through these. Run-phase transfer: `snap_erase`, `later_event`, `later_classical_event`, `post_frame`, `later_frame`. The invariance premise of `later_event` and `later_classical_event` is stated with the frame relation `Caches`, defined as `result = withCaches state …`; a proof of it unfolds `Caches` and rewrites with that equation. Compile: `PqxdhDeploymentLaterCompile.compileLater`, `mergeLater`, `compile_later_game`, `compile_later_source`, `compile_later_bound`, `compile_later_reads`, `compile_later_no_kem`, `continuation_no_accept`.

The layer forwards every coin and command unchanged and records it with its mode O reply. `test handle left right` requires equal nonzero lengths. The first admitted test draws the hidden bit with one experiment coin and fixes the test handle. A later test is admitted only on the same handle or on a handle with the same public designation, computed on the transcript so far. An admitted test is one send of `left` or `right` by the bit. `fresh handle length` requires `min ≤ length ≤ max`, draws a uniform message of that many bytes with one coin per byte when the command is issued, keeps it private and sends it. A rejected secrecy command changes nothing but the transcript, and the experiment's own draws never enter the transcript. Mode P is mode O behind `observeFull`, whose replies are the mode P projections of the mode O replies (`observeFull_project`). Secrecy claims (left-or-right and fresh-message secrecy) are stated only for mode P, as plan section 3.6 and owner input 4 (accepted on 2026-10-06) require: in mode O a raw receive returns the actual plaintext, so forwarding a test or fresh ciphertext to the partner's raw receive reveals the hidden message, and the secrecy commands are just sends there. Authentication claims may use either mode. `game_wrap` shows that the experiment is the trial's native game run on the wrapped adversary, with the ledger moved into the final state. Every record seal handed to the frame writer is logged with the record handle of its command, including seals whose writer then fails, and `logged_forget` shows that the log changes no result.

Logs. Both components of `Logs` are analysis logs, not public views. The transcript stores the mode O reply of every query in both modes, so in mode P it contains the plaintexts of raw receives, including those of test or fresh ciphertexts that the adversary forwarded; the adversary's view of an entry is `Entry.view mode`. The produced-frame log contains frames whose writer failed and that were never published, each tagged with a `FrameTag`: the peer key ID of a Server send, the owner handle of every Beacon record command, and `none` for a Server raw receive, which names no handle before routing. The tag never contains a plaintext, so the hidden messages of `test` and `fresh` never enter `Logs.produced`; together with the frame's sequence number and sender it gives the plan's (side, handle, sequence) tuple. Events meant to be public must be built from `Entry.view` and from the frames and tags only.

The compile lemma. `compile_full_game` and `compile_full_source` state that the experiment in either mode equals the merged initialized execution of `compileFull A` (the trial compiler applied to the wrapped adversary) jointly over the Server's public data, the adversary's output, the whole ledger (transcript, test session, fresh messages), the whole deployment state with the produced frames, and the runtime state. They use exactly the trial's two codec contracts, `Phase1ReadBack` and `Phase2ReadBack`. Because the wrapped adversary draws the bit and the fresh messages at the same positions as the experiment, no sampling-swap lemma is needed.

Budget transport. `wrap_bound` and `compile_full_bound` transport per-class caps through the secrecy layer and the compiler; `PqxdhDeploymentCompileCaps.transported` gives the closed form. The compiled program and its tagged form at any raw-accept ordinal make at most `qCoin + qTest + qFreshBytes` coins with `qFreshBytes = ℓmax · qFresh`, the registration and HMAC caps unchanged, `qHash + S + R + qTest + qFresh` BLAKE2b queries, `qSS + qSR + qTest + qFresh` Server kernel reveals, `qBS + qBR + qTest + qFresh` established-kernel reads and no identity, KEM, prekey or one-time read. `tag_certified` is the `certified` premise of T4 at these caps, and `transported_room` its `room` premise for `count + 1 = qCreate + 1`. The coin and BLAKE2b caps are looser than the plan; this is listed below as a plan change for the owner to confirm.

Selection (CE-4). For a run with outcome space `Ω` and a public `designate : Ω → Option G`, `split` writes the probability of an event on eligible outcomes as the exact sum over targets of the probability of the event with that target designated; `guess` writes it as `card G` times the probability that a uniform guess drawn before the run is the designated target; `advantage` is the split form for a left-or-right bit with the eligibility-weighted half subtracted. `sum_eq_card_mul` and `signed` turn a sum of per-target probabilities or of signed per-target differences into `card G` times the probability or signed difference of the run with a uniformly guessed target; with signed per-target hops this gives the owner's `N · Adv(B_guess)` wording. All statements are exact and use the measure form `𝒟[f <$> run] {true}` of the KEM theorems.

Publicity (CE-5). `agree_game` shows that every outcome of the experiment, in either mode, satisfies `Agree`: the transcript summary counts exactly the native owners, the public phase of every handle is the class of its native phase, every created binding is the owner's pinned Server identity and key ID, every successful bundle in the transcript is the Phase 1 writer output of the candidate the owner signed with its own identity key and the KEM public key it holds until finish, and every successful build response is the Phase 2 writer output of fields carrying the Server identity, which never changes. `phase_public`, `owner_public` and `failure_public` are its readings for `phase`, `owner` and `NoBundleFailure`: a rejected bundle sets an owner's failure flag exactly when the owner is natively Fresh. `owner_kemIndex` shows that in the annotated execution of any program the owner created `k`-th holds KEM creation index `k` and the KEM pool has one key per owner. The transcript functions read only queries and the replies of create, bundle, accept, build and finish commands, never a raw-receive reply. `summarize_view`, `phase_view` and `designate_view` prove it: two transcripts with the same mode P view (`SameView`) have the same summary, public phases, owner numbering, `NoBundleFailure`, designation and budgeted designation. So these functions are public in mode P although the transcript stores mode O replies.

Designation and key match (CE-5). The designation compares keys, as plan section 7 says, not signed fields. On the Server side, the accept bytes of the session that built the peer are read into a raw candidate, and `acceptedKeys` applies to it the source attached verification and parsing of the setup's crypto (`PqxdhJointPhase1Reports.sourceAccept`), which yields the same identity and keys as the native verification prefix `RawSignatures.verified` whenever that succeeds (`verified_keys`); only accepts that returned a session handle are looked up. The designated owner is the smallest created owner whose published bundle carries the candidate's identity field and whose published PQ field, split and parsed without a signature check (`publishedPq`), is the verified PQ key. On the Beacon side, the session must also verify to the PQ key read from the Beacon's published bundle. An accept that carries an honest owner's identity and published PQ key under a different valid signature is therefore designated like the owner's own bytes, and `designate_peer_complete` and `designate_owner_complete` show that the designation is made whenever its conditions hold. `designate_keymatch` (with `Phase1ReadBack`): for a Server peer designated `(i, k)`, every verification of the accept bytes of session `i` by the native verification prefix `RawSignatures.verified` yields owner `k`'s identity key and the PQ key owner `k` signed in its honest published bundle (`PublishedKey`). `owner_link` (with `Phase1ReadBack` and `Phase2ReadBack`): an owner designated `(i, c)` is natively Established and pinned to the protected key ID and to the Server's own identity; the response of session `i` is the Phase 2 writer output of fields carrying the Server identity; the ciphertext read from the owner's accepted finish input is the KEM ciphertext of those fields; and the PQ key verified at accept `i` is the one the owner published. `keymatch_game` and `link_game` state both on every outcome of the experiment. Both proofs read the verified key through `verified_keys` (the candidate and source attached verification inside `RawSignatures.verified`) and the published key through `publishedPq_candidate`; they use no signature-scheme property and no wiring law.

What `PublishedKey` does not give. It ties owner `k`'s published key to the owner's native KEM pair only while the owner is not finished: `kemPublic` is `none` for Established and Aborted owners, so in the designated case, where owner `k` has usually finished, `designate_keymatch` says nothing about KEM creation index `k` of the pool. Plan section 9 step 9.1 expected CE-5's `designate_keymatch` to yield `KeyMatchFinal k`, which compares with the final KEM pool of the annotated execution. The existing ownership invariant `PqxdhRegistrationJointOwnership.Owned` does not close this gap, because it constrains only the live KEM pair, which finish also erases. The step needs a new invariant on the pool-carrying annotated execution of `tag (compileFull A) i`, together with a relation that carries the compiled program's transcript into that execution: every bundle of owner `k` in the transcript carries pool key `k`, which holds when the bundle is produced (ownership and `owner_kemIndex`) and persists because the pool only appends. Unit A does not prove it. Strengthening `BundleShaped` with a ghost of the published key is not available within unit A: the native deployment state keeps no KEM key after finish, and a ghost added to it would have to be reproduced by `merge` from the source14 state, which does not keep it either. The step is re-estimated below as part of CE-9.

Freshness (CE-5). `approved_goodkem`: in the exact execution that T4 is stated for, the tagged compiled program of a complete-interface adversary, in either mode and at any raw-accept ordinal, ends every run with `GoodKem` for every KEM creation index. `kernel_reads_unrevealed`: in the same execution no identity index is ever revealed (`revealedAt` is false). Both follow from `quiet_initialized`: every annotated step other than an identity or KEM field read records only creation, signing, static DH and decapsulation observations, and the compiled program makes no such read. The forms named in the plan carry a budget that the adversary respects, which T4's `certified` premise needs anyway; the plan states them without one. `approved_goodkem_unbudgeted` and `kernel_reads_unrevealed_unbudgeted` are the plan's unconditional statements: they hold for every adversary, because no compiled command issues an identity or KEM read (`compile_unread`, `compile_full_unread`, via the generic `simulate_zero`).

The probability space is the report-instrumented initialized execution of the compiled program with a generated Server seed. The bound itself uses no codec law. Reading it as a statement about the deployment experiment uses `report_game`, which shows, under the approved codec laws `Phase1ReadBack` and `Phase2ReadBack` (needed through `compile_full_source`), that the projection of this execution to the constructed Server's public data, the adversary's output and the whole ledger is exactly the deployment experiment with the Server's identity index 0: `compile_full_source` gives the deployment game the identity index equal to the number of seeds in the pool at which the instrumented execution starts, and that pool is empty. `NativeForgery` (`PqxdhDeploymentAcceptDetection`) holds for a final outcome when the run passes through a successful raw accept at some position, the accept's raw bytes pass the native verification prefix `RawSignatures.verified` with the identity key of a generated owner of the owner registry, that owner is unrevealed, and the verified key tuple is not among the owner's chronological signing attempts, failed publications included, all read in the state reached when the accept returned. The bound is one ordinary joint-use weak-EUF term per generated identity position, summed over the `qCreate + 1` positions (the Beacons and the generated Server seed), with coefficient one: no accept-position, owner, field or report-position factor and no collision term. `fallback` and `ordinaryFallback` are the arbitrary default forgeries of `fieldOrigin_advantage_le_sum`. The per-ordinal fallback of the plan was not needed.

The unrevealed conjunct of `NativeForgery` holds on every run of the compiled program, so CE-A2 holds for every generated owner (`PqxdhDeploymentProvenance.a2_generated_bound`). Stopped right after its raw accept at any position, the compiled program issues no identity-field, KEM-field, prekey or one-time read (`upto_unread`: the scan keeps the zero caps of `compile_full_unread` and the stopping step issues only the accept). By `PqxdhDeploymentQuiet.quiet_initialized`, the source execution of such a program records no reveal observation, so `revealedAt` is false for every identity index on every stopped run (`stopped_unrevealed`). Hence `NativeForgery` of the compiled program is the same set of final outcomes as `GeneratedForgery`, the event without the unrevealed conjunct (`generated_forgery_iff`), and `a2_generated_bound` bounds `GeneratedForgery` by the same sum, with the same premises; since `GeneratedForgery` contains `NativeForgery` for every program, it is at least as strong as `a2_bound`. So no identity is revealed during any run of the compiled program; unit A's `kernel_reads_unrevealed_unbudgeted` shows the same at the end of every run of its tagged form. The owner's post-run reveal mode, which discloses honest Ed25519 identity secrets after the run, does not change this event, which is about accepts during the run.

Query bills of the A2 reductions (`PqxdhDeploymentProvenance.a2_bills`). ## Unit 3: decisions and deviations

- CE-A2 is detected mid-run, not by a selection argument. `upto` stops the program right after its raw accept at a chosen position, so the report run of the stopped program ends exactly after that accept and its own public report batch; `upto_detects` shows that the stopped run's final snapshot is the one at which that batch was evaluated, and `violation_detects` turns a native violation there into a detected original-field failure through `AttemptReports.owner_origin`, the report-run form of `raw_origin`'s argument. The report flag is sticky (`continuation_sticky`), so every final outcome reachable through a violating accept has the flag raised (`forgery_detected`).
- `NativeForgery` is a reachability event on final outcomes: an outcome belongs to it when some execution path through a violating accept reaches it. It contains every outcome of a path that actually passes through a violating accept, so the bound covers the path event and can only be larger than it. The violation is read in the state reached when the accept returned; the accept changes no Beacon owner's signing history, reveal history or identity handle.
- CE-A2 is stated on the report-instrumented execution, not on the deployment game's state, because its event refers to the private signing log, reveal history and identity handles, which exist only there; `report_game` identifies the public projection with the deployment game under the approved codec laws `Phase1ReadBack` and `Phase2ReadBack`, which it needs through `compile_full_source`. CE-A2pub and CE-R1' are the public-transcript corollaries and are stated on the deployment game itself.
- `NativeForgery` keeps its unrevealed conjunct because `PqxdhDeploymentAcceptDetection` is stated for every source14 program, some of which reveal identities. For the compiled program the conjunct is proved to hold (`stopped_unrevealed`), so CE-A2 is also stated without it (`a2_generated_bound`).
- The A2 client (`PqxdhDeploymentProvenance.client`) is the instrumented execution followed by one terminal public batch for the raw candidate of every successful accept of the final transcript (`announceAll`). The batches add no identity request (`client_creates`), so CE-A2, CE-A2pub and CE-R1' share one family of reductions and one sum, and the published-tuple corollaries need only final-state facts.
- CE-A2pub and CE-R1' are stated for the Server's identity index 0. The reason is the proof route: `compile_full_source` identifies the compiled program's initialized execution with the deployment game at the identity index equal to the number of identity seeds in the starting pool, and the report-instrumented execution starts from empty pools. In the deployment game the index enters only through `PqxdhLiveServerConstruction.initialized`, which stores it in the constructed Server's metadata next to its key ID, but no lemma shows that the probabilities of the CE-A2pub and CE-R1' events do not depend on it, so other indices are not claimed. CE-R1 and CE-C3 hold for every identity index.
- CE-A2pub and CE-R1' are proved per owner (`a2pub_owner_bound`, `r1prime_owner_bound`): the forged or doubly accepted owner must have made no rejected bundle call in Fresh, and other owners are unrestricted. This is stronger than the plan's events, which require `NoBundleFailure` for every owner; those planned forms (`a2pub_bound`, `r1prime_bound`) keep their statements and are corollaries.
- CE-A2pub compares key tuples, never signature bytes: the verified tuple of the accept against the tuple parsed from the published bundle. No SUF-CMA or signature-uniqueness assumption is used.
- CE-R1' needs no reduction of its own: its event is contained in the CE-A2pub event on every outcome (`replay_published`), so its bound is the CE-A2pub bound, not twice it.
- CE-C3 is proved with the consumption relation of `RawCtxReceiveConsumption` (`ConsumedRefines`, `raw_spent`, `send_spent`, `initialized_spent`) rather than HB-105's private history monitor: the deployment handler runs owners and peers directly, so the consumed positions are read from the transcript. The owner side includes the finish's acceptance of sequence one, so the registration record cannot be accepted again by a raw receive; this is stronger than the plan's raw-receive-only reading. Peers are separated by the key ID the decrypted record names, which is the key ID the Server routed to (`rawGame_success`).
- No planned statement was found false or unprovable, and none was weakened.

### Plan changes recorded

- Read caps. The plan's section 8 table bounds Server reveals by `qBuild` and established-kernel reads by `min(qCreate, qFinish)`. `compile_bound` gives looser caps: reveals at most the budget of Server send and raw-receive commands, and kernel reads at most the budget of Beacon send and raw-receive commands. `peerKernel` and `ownerKernel` read whenever no local copy exists, including for key IDs that are not installed and Beacons that are not established, and an empty answer is not kept, so such reads repeat. Soundness is unaffected: T4 `actual_le_real` instantiates on `compile A` with `compile_bound` as its budget premise, and its creation-count premise uses only the create cap. Later bills that count reveals or kernel reads use the record-command budgets. Gating the reads on the public log would need an amortized whole-run count in place of the per-command `weighted_bound` argument and changes to several checked modules, so it was not done.
- The local Server metadata placeholder (plan section 8 b) is unnecessary: Server metadata is `Unit`, and the invariant proves that the sender ID equals `setup.serverKeyId`.
- A peer's identity needs only the identity parse of the accept bytes, not the full signature check.

### Open points

- F1, decided by the owner on 2026-10-06: option (a), recorded as deviation D5. The experiment's adversary takes no input; it learns the Server identity key through the protocol, for example by registering one of its own Beacons and reading the build response, which costs registration queries and shifts session ordinals and key IDs, so it is not an exact reduction from an adversary that receives the key as input. Background: The plan gives the adversary the Server's public identity key as input, but T4-T6, the report lines and `InitializedSchedule.source` run a fixed program with no input after the Server is generated, and no source14 command returns the Server key. In the trial the adversary therefore has no input and can learn the Server key only by parsing build responses. Learning it by registering first also shifts session ordinals and key IDs, so this is not an exact reduction from the plan's adversary. Options: (a) accept the input-free adversary as a recorded deviation, at no proof cost; (b) generalize the T4-T6 and report lines to programs that depend on the generated public identity; (c) add a Server-identity getter to source14 and re-prove the line over the extended interface. With the key as input only `Phase1ReadBack` would be needed; the trial needs `Phase2ReadBack` because it reads the Server identity from a build response.
- Post-run reveal mode. On 2026-10-06 the owner chose a post-run "later quantum" mode: after the run, every honest X25519 secret, every DH output and every honest Ed25519 identity secret is revealed, and only confidentiality is claimed. The interface stays open to it. Because `compile_game` equates the whole final deployment state, the mode can be added as a phase after the run that is a function of the final state, without changing `Command` or the compile cases. Open: on the compiled side the secrets are reachable only through source14's identity, prekey and one-time field reads, which `compile_bound` caps at zero, which interact with `revealedAt` and `GoodKem`, and which follow native erasure; the Server identity seed, ephemeral scalars and DH outputs have no read. Its cost is to be designed and confirmed before it is built.
- Not done: the `test` and `fresh` commands with the sampling swap, `CE.Logs`, mode P beyond the wrapper, the public functions `phase`, `owner`, `NoBundleFailure` and `designate`, the comparison of the transported caps with T4's ledgers, and the step from `compile A` to `tag work index`.
