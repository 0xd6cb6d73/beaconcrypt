# Repeated source initialization from one root table

`PqxdhRootTableInitialization` factors repeated actual ratchet initialization through the [consistent uniform-root service](correlated-root-expand.md). Every initialization uses its retained root to execute the extracted Server or Beacon start/request/resume path and the supplied fixed HKDF source at 64 bytes. Owner and role labels do not create new root-table addresses. The complete execution preserves kernel replies, private initialization history, prior root-cache entries and arbitrary adaptive continuations.

## Actual source initialization

`initialResponse` converts the supplied source function's exact requested 64-byte output to the extracted response array. `initialResponse_bytes` and `initialResponse_law` derive its representation and actual fixed label. `rootArray_bytes` preserves all 32 bytes of the retained root. This constructs an interpreter for the existing functional source contract; it is not a proof of native libsodium, ABI, error, allocation or timing behavior.

`initialKernelRun` runs the existing extracted `initializeServer` or `initializeBeacon` program. It retains the complete `RustM ConcreteRatchetKernel` result, rather than substituting a pair of independently sampled chains. `initialize_refines` derives successful completion, the actual source byte origins, zero send/receive counters and the empty skipped-key refinement for either role. The concrete ratchet crypto parameter is explicit and need not assume cryptographic security.

`initialResponse_prefix` identifies the actual 64-byte response with the prefix of the same 76-byte ratchet stream at the retained root and `INFO_R`. `initialize_stream_refines` identifies the two chain origins with its first and second projections. The Server sends from the first half and receives from the second; the Beacon uses the opposite orientation. `complementary_kernels` preserves the complete initial kernels and their equal opposite material streams under the same supplied ratchet crypto. It is a deterministic correspondence statement, not a claim that either chain is uniform or independent.

## Root dictionary and complete continuation

The private `InitRequest` carries an owner label, role orientation and the original 128-byte coordinates. `InitSpec` also allows explicit finite uniform requests and the existing public fixed-HKDF projection interface. These are a private protocol capability and its surrounding public-service forwarding, not a new network API that exposes complete kernels or roots. The owner label is bookkeeping; no native owner allocation, uniqueness, authorization or registration installation is inferred from it.

`initCompile` forwards exactly one root request for each initialization, using only its unchanged coordinates as the root-table key. It executes the actual role initializer on the returned root and appends the original request and root to private analysis history. Explicit coins remain in source order. Public projections evaluate the original fixed source function and preserve that complete history. No public HKDF random table is introduced.

`sourceImpl` independently spells out the direct dictionary execution. A new coordinate samples one 32-byte root and installs it. A hit reuses the stored root. Both branches run the source initializer again and record that call. Thus repeated initialization keeps its real HKDF and kernel work even when it samples no new root. Public projections remain evaluations of the same production stream, including the ordinary 64/76 prefix correlations at a guessed or otherwise known root.

`source_query` and `source_complete` prove exact complete program equalities between the interpreted compiler and direct source service, retaining the actual kernel reply, every prior initialization and the same root cache. Arbitrary complete client results can include the caller's entire private state. `source_uniform_game` erases only private instrumentation and identifies the resulting client output with the published uniform-root interpreter on the compiled initializer client. This is the scoped uniform-family observation; instantiating the preceding authenticated source's `Protocol` continuation with actual global role publication remains separate.

## Ownership aliases and cache persistence

`source_cached` and `source_fresh` retain the exact actual initializer result and cache update. `source_preserves_cached` and its full-run lift show that later initializations, other owners and public calls never overwrite an installed coordinate. `source_initial_result` records the actual root used on every reached initialization. `Aligned` relates every private history entry to that same cache, and its step/run proofs derive the relation from actual empty-state execution.

`source_history_same_coordinates` therefore proves that repeated coordinate events share the same retained root regardless of owner or orientation labels. Distinct coordinates may also sample equal roots. `equal_roots_kernel` preserves their identical source initialization for the same orientation; opposite orientations remain complementary. No injectivity or collision exclusion is assumed for root values, PRKs, chain outputs, public keys or owner labels. `source_initial_kernel` combines the actual supported call with its source initialization refinement, without a caller-supplied successful-opening or honest-owner premise.

The returned concrete kernel has the same type used by `RawCtxServerRouting.Peer.kernel` and `RawCtxBeaconLifecycle.Phase.established` in the existing finite role scheduler. Actual identity fields, assigned handles, control phase, stored 153-byte associated data and peer metadata must still come from registration publication. This result does not construct those fields, prove native map installation, or erase privileged API plaintext into a network observation policy. Repeated-root ownership must remain visible when those initial states are composed with the evolving source and record scheduler.

## Query and computation ledger

`compile_step` and `compile_bound` preserve every selected root/coin class through arbitrary possible replies and the complete stateful continuation. If the original client has `U` explicit uniform requests and at most `I` initialization requests, `source_uniform_bound` proves a complete uniform-request cap of `U+32*I`. A miss draws 32 byte-valued values; a cache hit draws none. Every arbitrary finite client uniform request counts once.

`source_initial_count` increments the private history once per actual initialization. `source_run_initial_count` bounds all recorded calls by the original `I`, including cache-hit retries and repeated owner labels. If the original public-projection count is `P`, `source_hkdf_calls` proves the combined logical source HKDF cap `I+P`: each initializer evaluates its 64-byte source response and each public projection evaluates a complete 76-byte stream. These deterministic calls, conversion, splitting, cache lookup, history copies and full kernel construction remain real local work. A zero uniform-query cost does not make them free, and the inherited functional cache representation does not establish native runtime complexity.

The existing ordinary HMAC/Extract-family and authenticated-source sampling ledgers remain unchanged. No additional primitive security assumption or advantage term is introduced by this exact structural factorization. The explicit unreduced Extract-family obligation, actual registration publication, evolving secret-input replacement, multiple-family/reveal policies, pinned-Server Phase2 authentication and global computational protocol theorem remain open.
