# Failure deletion for the bounded Beacon-to-Server process

This argument transfers exactly two bounded symbolic correspondences, `b2s-C2-chosen-fs` and `b2s-C4`, from `fs-records-b2s-kr3-failstop.pvl` to `fs-records-b2s-kr3.pvl`. Both use the unchanged real window hooks and chosen-message send process, with three receive attempts per peer. C2 retains its honest-pin main process; C4 retains AnyPin. It neither changes those pins nor introduces another source schedule. The checked ProVerif results and their recorded inputs remain the evidence for the fail-stop correspondences.

The argument concerns finite symbolic traces projected onto honest public outputs, adversary knowledge and all events except `FsReceiveRejected`. This projection omits input-consumption actions and call labels: an adversary offer can remain even when the corresponding consuming worker step is deleted. A receive call in these two processes publishes neither an optional-result bit nor plaintext. Their pure term destructors have no externally visible evaluation history. Events are instrumentation, not inputs to a process. There is no fairness, elapsed-time or exact-call-count observation. These facts are essential; the active strong-secrecy result-bit interface and the computational raw receive interface require their own simulations.

Write the complete receive-worker parameters as `W = (server_identity, beacon_identity, assigned_key_id, root, associated_data, receive_material_1, receive_material_2, far_anchor, r, cached_1)`. The only differences between the two bound files are the failed-open continuations in attempts one and two: the ordinary file calls the next attempt and the fail-stop file calls `FsB2sRecvStop`. Both use the same third attempt, whose every continuation stops. The attempt bodies themselves are the same macro, and the numeric attempt index is neither a term, an event field, nor a test. It only determines how many copies of that macro remain.

| Receive branch | State and effects before the continuation | Transformation |
| --- | --- | --- |
| Decode or sender-routing failure | The complete `W` is unchanged; no event or public output | Keep the attempt and its next continuation |
| Rejected old or uncached target | The complete `W` is unchanged; only `FsReceiveRejected` | Keep the attempt and its next continuation |
| Failed cached open of sequence 1 | The first eight fields are passed literally; `fs_b2s_failed_r(r,1) = r` and `fs_b2s_failed_cached_1(r,1,cached_1) = cached_1`; only `FsReceiveRejected` | Delete this worker's attempt |
| Failed future open of sequence 1 or 2 | The same two hook identities hold at the selected target; all other fields pass literally; only `FsReceiveRejected` | Delete this worker's attempt |
| Failed far open | The complete `W` passes literally; no event or public output | Delete this worker's attempt |
| Successful cached or future open | Preserve the exact counter/cache update, both acceptance events, their full fields and the next continuation | Keep the attempt |
| Successful far open | Preserve `FsFarAccepted` and worker termination | Keep the attempt |

The identities in the table are the three definitions of `fs-records-b2s-window.pvl`, together with the four `Failed` calls in `FS_B2S_RECV_STEP`. The stale-state and retained-cache control libraries are not loaded by either target. A failed receive allocates no fresh name, changes no table, sends no message and changes none of the worker parameters. No send action is deleted: in particular, this argument says nothing about the source send state advancing before a failed seal.

For a finite ordinary trace, delete only the failed-open steps from each receive worker and consecutively number its retained attempts. Keep every other role's steps, public outputs, chosen-message inputs and fresh names. Public messages offered to a deleted input can remain on the public channel; consuming a public message is not a destructive change to the adversary's knowledge. There is no private synchronization or shared write in a deleted attempt. Thus steps of other processes interleaved with its pure tests can stay in their original relative order. A finite trace can stop at the last event of interest, so a partially evaluated trailing request imposes no extra progress obligation.

An induction over the retained actions constructs a trace of the fail-stop process. At a retained receive input its ten worker parameters equal the ordinary trace's parameters at the corresponding input: deleted predecessors return the same `W`, while retained predecessors perform the same updates. The offered term is still derivable, because every prior public output and fresh-name scope is unchanged. The same pure tests therefore choose the same retained branch. That branch never calls `Failed`; a failed branch was deleted. It either calls the next identical macro or terminates at the same successful far event. At most three inputs remain for each worker, so renumbering never exceeds the bound. Workers with no retained input need not be scheduled. This construction preserves all non-rejection event occurrences, their order, arguments and multiplicity, and the adversary's derivable terms at every retained point.

For C2, any violating collection of `FsReceived` occurrences and all candidate `FsSent` matches survives with the same event arguments and order. Their occurrence identifiers have a bijection, so an injective matching exists in one trace exactly when it exists in the other. The alternative `attacker(k)` is unchanged: no public output is removed or added by deleting these pure receiver steps. Hence a C2 violation in the ordinary process produces a C2 violation in the fail-stop process. For C4, retain the offending `FsFarAccepted` occurrence and the unchanged inability to derive its identity term `k`; this is a violation of the same implication in the fail-stop trace. Taking contrapositives transfers the two checked TRUE correspondences.

The opposite trace inclusion, after this event projection, follows by scheduling the ordinary process identically through any failed open and leaving its remaining input continuation unscheduled. It is not needed to transfer the TRUE results. The construction does not transfer queries about rejection events, exact attempt counts, timing or the final residual process. It gives no observational equivalence for an interface that returns a failure bit, and no probability or computational reduction bound.

The existing source-fidelity checks pin the real window hooks, macro continuations, admitted target roster and the two query files. The free-schedule checker admits fail-stop only for these two chosen-message security targets at `K_r = 3`, and rejects a query mentioning `FsReceiveRejected`. Their exact `FsReceived`/`FsSent` or `FsFarAccepted` implications are the formulas used above; absence of the rejection event by itself would not justify arbitrary formulas or a different observation interface. Reviewed source hashes accompany this argument. No query, target bound, model equation, runtime primitive contract or ProVerif verdict changes.

This discharges the local E21 trace-deletion argument. A claim about the Rust API still requires L3's source-to-model failure-neutrality and observation projection, the pending routing/lifecycle/registration abstractions, and the appropriate computational component simulations. E3 pin independence, L1 pending-token movement, direction splitting and the global common experiment are independent obligations. Snapshot and persistence behavior remain excluded.
