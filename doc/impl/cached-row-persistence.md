# Cached row persistence and network database validation

This extension starts from the completed row implementation at `b1d297d13a42cdd1bb78befac655822e468a4b5a` on `codex/row-persistence`, itself based on `codex/mldsa65-transcript`. The owner requested a hybrid that retains protocol state in memory, preserves the existing uncached row API, and measures SQLite and localhost TCP PostgreSQL. Correctness and safety take precedence over performance. Proof work remains outside the explicitly authorized scope.

## Storage and ownership contract

`CachedRowServer<S>` retains a bounded set of decoded peers and their exact committed row bytes. `RowServer<S>` remains uncached and keeps its existing behavior. Both use `RowStore` and the same row format; applications choose and implement their database adapter. PostgreSQL and SQLite dependencies remain confined to development/example code.

The compatible `RowTransaction::expect(key, expected)` method requires exact-value or absence validation in the same atomic transaction as the operation's other reads and writes. Its default implementation loads and compares, so existing adapters remain correct. An optimistic adapter can instead buffer the expected bytes and validate them at commit, avoiding a separate fetch on a warm peer. The complete row comparison includes the independent storage generation, lineage, key binding, and peer payload. Protocol sequence numbers alone are insufficient because consuming a skipped receive key changes state without advancing the receive frontier.

The library removes a cached peer before doing tentative work. It installs the resulting peer only after the outer transaction confirms durable success. Callback failure, storage conflict, invalid row, and unknown commit outcome discard tentative state and clear the cache. An application can recover an exact committed response from its own receipt after a lost acknowledgement. Neither the library nor an adapter may automatically rerun the one-use callback. Read-only operations, rejected native receives, and cached application results must still validate every mutable record on which their result depends. A state-independent malformed-input rejection can still finish before storage access.

Capacity zero disables caching; capacities do not cause eager allocations. The initial bounded policy evicts the smallest resident peer ID when insertion requires space, using logarithmic map operations. This is a deterministic size bound, not an LRU promise. A host can explicitly clear the cache. Registration retains its existing uncached acceptance and completion transactions, preserving consumed-marker durability and non-resumable pending-token semantics. No new allocator cache or registration recovery mechanism is introduced.

Application authorization, revocation, request identity, receipts, and retention remain application-owned. The peer cache does not automatically cache those records. Their reads, including absence checks, must be covered by the same atomic commit. One warm-peer commit exchange is possible only when the adapter has all other necessary values or can express the required conditions in that commit request.

## Mythic provider compatibility

The local [Mythic provider repository](https://github.com/0xd6cb6d73/mythic-beaconcrypt) was reviewed at commit `6f39a757e490ff5147e389b70f5463a4ce79dce2`, which was not available from GitHub when checked. Source paths below identify files in that checkout; Go paths are relative to `Payload_Type/mythic_beaconcrypt/`. Its `ROW_PERSISTENCE.md` describes a future migration; the provider still runs the aggregate checkpoint implementation. The native adapter (`internal/native/native.go`) pins Beaconcrypt v0.6.1 at `0c629b1c0af4139b77551da30d39e18b0e77698d`, restores version-2 checkpoints, and exposes whole-state export. Adopting this branch requires coordinated native provisioning, registration parsing, agent/wire compatibility, and explicit state migration. `CachedRowServer` does not convert those checkpoints.

The provider's engine (`internal/engine/engine.go`) currently runs native work privately, exports a checkpoint, and commits it with metadata and the exact response. Replacing its `Native.Encrypt` or `Native.Decrypt` implementation with cached convenience methods would commit cryptographic state before that existing outer commit. The integration must instead use the Go cached server's `Transaction` callback for authorization and receipt preflight, at most one `RowSession` native transition, authenticated peer-ID validation, response encoding, and application writes. Return the encoded response only after this call succeeds. The existing `Native`/`Export` abstraction therefore needs an orchestration change, not merely a different factory implementation.

The storage contract (`internal/wire/state_types.go`) still commits one aggregate `StateBlob`, `ProviderJSON`, and result under a global revision. It cannot implement independent peer and application-row commits by issuing several existing RPCs. The proposed Mythic service capability must atomically validate all read/expect conditions and apply their writes, preserving exact bytes versus absence and reporting failures without publishing output. A provider adapter can implement `CachedRowStore.Expect` by buffering conditions for that capability; an adapter with only the default load/compare path remains correct but saves no peer-fetch RPC. Retaining the engine's current aggregate `Load` and separate `LookupResult` calls retains those RPC costs as well. SQL and service authorization remain outside Beaconcrypt.

The current campaign mutex and per-message global revision also serialize peers independently of the cache. A migration seeking concurrent peers must split changing session/request metadata appropriately and choose an explicit provider ownership model. The activation path (`internal/engine/owner.go`) acquires a new owner epoch, fencing prior owners; it cannot be run independently for every handle in a concurrent cache pool. A provider-controlled owner group could share a stable epoch checked in each transaction while independent peer rows progress, but ownership transfer, revocation, and pool lifecycle remain provider decisions. A cached peer is never evidence of current authorization or ownership.

Preserve stable request IDs and immutable input digests, the saved response's original request-ID check before correlation remapping, current authorization before receipt replay, and exact response recovery after uncertain commit. Clearing the peer cache permits an authoritative reload; it does not authorize repeating a request whose outcome remains unknown. Registration still needs two commits and an incomplete-receipt policy because its accepted native token is not resumable. Request admission, tombstones, result expiry, and any application-row caching remain Mythic responsibilities. These requirements are unchanged by decoded-peer caching, and neither the SQLite nor PostgreSQL component benchmark establishes a provider-wide speedup.

## Validation

Focused native tests cover warm/cold access paths, exact expectations, present empty values versus absence, capacity bounds and zero capacity, eviction, explicit clearing, reopen, independent peers, stale workers, skipped receive keys, authentication rejection, replay, generation exhaustion, malformed stored rows, callback misuse, rollback, uncertain commit, and registration phase failures. File-backed tests check that competing cached workers publish one successor and that application receipts and peer state remain atomic.

Property tests use the repository's existing `proptest` infrastructure and persisted regression seeds. Generated histories compare the cached implementation with the uncached path under arbitrary message payloads, reordered and repeated receives, authentication damage, multiple peers, competing external writers, cache eviction, explicit clearing, and reopen. A larger case count is run separately from the ordinary suite. Focused tests provide explicit coverage for failure modes that must not depend on random generation.

Both example adapters require contract tests for full read-set validation, absent-row races, read-only conflicts, atomic multirow writes, and a single winner under concurrent conditional commits. PostgreSQL tests use a dedicated local cluster over TCP. The PostgreSQL commit function must obtain sorted transaction-level locks for every read or written key before checking expected values, including absent keys, and perform no writes until every expectation succeeds. Its validation queries must see changes committed by prior lock holders. These are adapter obligations; Beaconcrypt does not embed SQL or depend on a PostgreSQL server.

All supported native bindings receive cache constructors, expectation callbacks with a safe default, cache controls, and focused tests. The existing WASM row-API unsupported behavior remains explicit. Runtime validation includes the complete configured native and WASI mutation suites; viable misses and timeouts must be resolved before completion. An independent review checks the ownership and commit boundary and the database adapters before any performance result is accepted.

The native runtime run passed 435 tests, including eight cached file-backed integration tests and 17 existing row integration tests. Both new generated properties also passed a separate `PROPTEST_CASES=128` run. The native Go race suite, no-CGO unsupported-path check, two C composition bridge tests, and all 97 Python tests passed. The WASI runner passed 27 ordinary tests plus its isolated allocation probe; its fresh mutation campaign accounted for 159 selected cases as 147 caught and 12 genuine compiler failures, with no misses or timeouts. Three previously documented equivalent WASI cases remain excluded. Formatting, all-feature/all-target Clippy, server-only and beacon-only builds, and workspace doctests passed. The fresh native mutation campaign covered all 1,672 current cases: 1,206 caught and 466 verified source compilation failures, with no misses, timeouts, duplicate outcomes, or uncovered cases. The current source catalog was regenerated and matched the audited catalog exactly. Eleven initially unclassified compiler diagnostics were manually reviewed as unavailable `Vec`/`vec!` in `no_std` crates, constant subtraction underflow, and cast/comparison parsing errors; none were infrastructure failures.

All 18 database example tests passed against file-backed SQLite and a dedicated PostgreSQL 16.15 instance over `127.0.0.1` TCP. These include seven contracts per backend, a deterministic advisory-lock wait test, native stale-cache and lost-acknowledgement recovery, a competing-request receipt race, and an actual immediate PostgreSQL crash/restart. The crash test checks committed receipt recovery, continued ratchet sequencing, disappearance of an uncommitted row, and cache invalidation on the broken connection. PostgreSQL tests are explicitly ignored by default, so missing database configuration cannot silently count as an exercised backend. The first example run rejected 11 PostgreSQL cases during the loopback check because PostgreSQL rendered its address as `127.0.0.1/32`; changing that check to `host(inet_server_addr())` resolved the representation mismatch. The archived original failure log and the subsequent complete 18-test passing run are both retained.

To reproduce the non-crash database tests, point both `BEACONCRYPT_BENCH_POSTGRES` and `BC_PERSISTENCE_PG_DSN` at the same dedicated durable loopback database, then run `cargo test -p beaconcrypt --example persistence_bench -- --include-ignored --skip postgres_crash_restart`. The crash test additionally requires `BC_PG_TEST_OWNED_DATA`, `BC_PG_TEST_PG_CTL`, and a `BC_TEST_CLUSTER_ONLY` marker inside that disposable cluster's data directory. It checks the connected server's actual data directory before invoking immediate shutdown and restart. Run the complete example suite with those variables and `-- --include-ignored --test-threads=1`; do not target an application database. The collection guards and these correctness tests are separate: no benchmark measurement is part of database validation.

## Benchmark collection plan

The expanded experiment compares full snapshots, uncached rows, and cached rows on SQLite and localhost TCP PostgreSQL. It retains the existing 1/100/1,000-peer axes, three trials, small/larger/mixed streams, and identical 512,000-byte bursts of 64/256/512 messages. Each arm uses the same protocol revision and durably commits each successful message operation. Registration, fixture creation, client cryptography, and exact-output validation remain outside message timing.

The cached arm warms every eligible peer outside timing, and the report records cache warmup and subsequent probe counters. Results therefore describe a resident working set; misses and conflicts are correctness-tested and must not be silently counted as cache hits. Three-arm ordering rotates across trials so each arm runs first once per case. Counter names distinguish library load/expect/store calls, logical value bytes, database commands, and client/server exchanges. Prepared PostgreSQL statements are established outside timing so hidden preparation exchanges do not distort the intended comparison.

Both database benchmarks run only after implementation, correctness testing, mutation audits, review, and release compilation have completed. `/tmp/bc-coord` governs resource use. Each retained report requires a monitored quiet interval with no competing active leases, occupied Lean slots, or detected heavy jobs. PostgreSQL processes belonging to the benchmark are part of the measured workload. The owner confirmed that no other worker remains on the VM, while the physical host has an active Kubernetes cluster. The collection records that unavoidable host noise and separately accounts for its exact Codex controller process as instrumentation; it does not claim host isolation. Interrupted or contaminated complete-axis attempts are discarded and rerun under a rule fixed before inspecting their timings. Source, binary, configuration, server version, raw trials, and quiet-window evidence are archived with the results.

All six configurations completed and passed validation. The [SQLite and PostgreSQL results](cached-row-persistence-results.md) include 324,864 measured operations, all 72 comparison groups, and the full correctness/build/collection evidence. Warm cached PostgreSQL operations used one query exchange instead of two, but localhost timings did not show a consistent advantage over uncached rows; the strong scaling improvement was row persistence versus full snapshots. The report records trial variability and unavoidable physical-host noise.
