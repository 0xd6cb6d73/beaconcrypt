### What is proved

**Tag (M0).** `AcceptCutTag.tag work index` is `AcceptCut.scan work index >>= tagFinish` (`tag_split`, by definition). `tagFinish` resumes a pending cut exactly as `AcceptCut.finish` does, issuing the same raw accept and passing its reply to the original continuation, and additionally returns `some (raw, reply)`; a complete cut returns `none`. `finish_erase` and `tag_erase` show that forgetting the record gives `AcceptCut.finish` and the original program `work`, so the tag adds no request and changes no reply. `tag_bound` and `decision_bound` carry every `IsQueryBoundP` cap of `work` to `tag work index` and to `decisionClient decision work index`, the Boolean client `decision result && accepted tag` that later stages run. `accept_lt` shows that a reached pending cut has `index < cap` for any all-reply cap on raw accepts, and `accept_source` instantiates it at `qAccept = budget (.inl 3)`. Rejected earlier accepts are counted, so this bounds the raw-accept ordinal, not the encapsulation ordinal of `PqxdhRegistrationJointKemCut`; the two are different handles.

**Report split and naturality (M1).** `resume` restarts the reported command compiler from a recorded initialized outcome with the same Server, owner registry and native state, and `continuation` runs that resumption under the same identity reduction, from the reached local KEM/runtime state and source registry, and under the same report interpreter, from the reached monitor and reporting state. `commands_initialized_bind`, `initialized_bind` and `run_bind` show that the reported commands, the initialized report compiler and the report run of `program >>= next` are those of `program` followed by this resumption; the identity-reduction step is `TerminalReports.compiler_bind`. `cut_split` instantiates `run_bind` with `AcceptCut.scan_finish`: the report run of `work` is the report run of the raw-accept scan followed by `continuation … AcceptCut.finish`. `split` couples the two runs of the tagged program: it draws the reached outcome `r₁` of the scan and then the final outcome `r₂ ← continuation … tagFinish r₁`. `split_snd` is the program equality `Prod.snd <$> split … = RR (tag work index)`, so the final component is exactly the report run of the tagged program. `ReportSource.initialized_source` already identifies the source projection of that run with the actual initialized source execution of the tagged program, which by `tag_erase` issues exactly the requests of `work` and receives the same replies. `split_fst` shows that every countable observation of the cut component has the same distribution as under `RR (scan work index)`; the continuation is an ordinary probabilistic computation and cannot fail. `commands_initialized_map`, `reduction_map`, `initialized_map` and `run_map` are naturality in the program result, and `selected_run` gives `RR (AcceptCut.selected work index owner fallback) = mapChoice owner fallback <$> RR (scan work index)`, where `mapChoice` replaces only the program-result component by `AcceptCut.choice` and keeps local state, registry, monitor, snapshot and reporting state. `sourceResult_map` and `raw_eq` push the map through the source projection: a pending cut with raw bytes `raw` maps to the final choice `(owner, raw)` with the same Server and encoded state.

**EUF instantiation (M2).** `selected_certified` discharges the fourteen source caps of `AcceptCut.selected work index owner fallback` from `certified`. `selected_report_bound` is the address-free half of `native_origin_bound` at that program: under `capacity : (if supplied.isNone then 1 else 0) + qCreate ≤ count + 1`, the probability in `RR (selected …)` of `PqxdhRegistrationJointFinalReportEvent.Failure setup.joint codec` is at most `∑ target : Fin (count + 1), advantage setup.joint (NativeOriginBound.reduction … (selected …) … target)`. The proof is `FinalReportEvent.transport`, `FinalCandidate.reported_bound` with `ReportCosts.initialized_creates`, then `PqxdhJointPhase1Reports.fieldOrigin_advantage_le_sum`, the same chain as `native_origin_bound` after its first step. The five bills are `selected_service_bound` (at most `3 * qBundle` signing and `qFinish + qAccept` converted-DH requests per reduction), `selected_reports_bound` (at most `(count + 1) * (qAccept + 1)` public candidate reports), `selected_client_uniform` (the complete client uniform bill `total caps qInit budget`), `selected_reduction_uniform` (`32 * count + total caps qInit budget` per reduction) and `selected_game_uniform` (`32 * (count + 1) + total caps qInit budget` for the endpoint game); the uniform bills take the existing `qInit`, `initBound`, `caps` and `KemBound setup caps` premises of `NativeOriginUniform`. Each is a direct instantiation of the existing theorem with `certified` from `selected_certified`.

**Protection, classification and authentication bound (M3).** `ProtectedAt kemIndex r₁ encoded raw next value address owner target publicKey` says that the reached outcome is a pending raw cut on `raw`, that `RawSignatures.verified setup codec checks raw = some value`, that `address` locates `owner` in the public owner registry `encoded.2.2.owners`, that `owner.2.1 = kemIndex.val` (the public KEM creation index), that the owner's identity index routes to `generated target`, that the source identity key of that index is `publicKey`, that `value.identity = publicKey.ed25519`, and that `revealedAt owner.1` is false in the transcript reached at the cut. `Protected kemIndex r₁` is its existential closure. `KeyMatchCut kemIndex r₁` says that the verified PQ key of the pending candidate is the public key at index `kemIndex` of the native KEM pool at the cut; `HonestTuple` adds to protection that the verified tuple occurs in the witness owner's chronological signing history. `attached_detached` is the attached-to-detached step: from `RawSignatures.verified … raw = some value`, `RawSignatures.verified_origin` gives `candidate codec raw = some value.candidate` and `RawSignatures.verified_detached` gives `acceptPhase1Candidate setup.joint.verify value.candidate = some (value.identity, value.keys)`; the latter uses the inherited `shortRejects` premise and `setup.wiring` through `PqxdhJointPhase1Reports.source_attached_adapter`. `protected_origin` applies `AttemptReports.owner_origin` to the program `scan work index`, to the reached outcome `r₁` itself and to the witness address, with `accepted` from `attached_detached` rewritten by `value.identity = publicKey.ed25519`: either the verified tuple occurs in the owner's history and `KeyMatchCut kemIndex r₁` holds, through the owner's fixed receipt and `owner.2.1 = kemIndex.val`, or `FieldOriginFailure setup.joint ⟨target, value.candidate⟩` holds in the snapshot reached at the cut. `chosen_mapped` shows that `FinalCandidate.selected` of the mapped outcome is `some value.candidate`, by `raw_eq`, `NativeKemOrigin.selected_source` and `verified_origin`. `protected_report_failure` combines them: `Protected ∧ ¬KeyMatchCut` implies `FinalReportEvent.Failure` of `mapChoice owner fallback r₁`, whose snapshot is the one reached at the cut. `classify` (T1) shows that every supported `r₁` satisfies at least one of `CutComplete` (constructor failure, or fewer than `index + 1` raw accepts), `VerifyRejected` (attached verification `none`), `VerifiedSome ∧ ¬Protected` (attacker-owned, imported, revealed, missing owner, other identity or other KEM index, or a generated owner outside the report range (impossible under capacity)), `Protected ∧ HonestTuple ∧ KeyMatchCut` (honest unchanged or honestly re-issued tuple) and `Protected ∧ FinalReportEvent.Failure (mapChoice owner fallback r₁)` (honest identity, changed tuple). The cases are not exclusive: two generated owners with equal identity public keys can place one cut in the honest case through one owner and in the failure case through the other, and the failure case is address-free. `classify` does not separate rejection by the Server after a successful attached verification: such a cut lands in case 3, 4 or 5, as explained under "What stays open". `protected_bound` (T2) states that the probability in `RR (scan work index)` at `count + 1` positions of `Protected kemIndex ∧ ¬KeyMatchCut kemIndex` is at most `∑ target : Fin (count + 1), advantage setup.joint (NativeOriginBound.reduction … (AcceptCut.selected work index owner fallback) … target)`, by `protected_report_failure`, `selected_run` and `selected_report_bound`. There is no honest-target premise.

### Target designation and freshness reading

The target is designated by the public pair `(index, kemIndex)`: the zero-based raw-accept ordinal and the KEM creation index. The owner is located existentially in the public owner registry by address, and every comparison in `ProtectedAt` and `KeyMatchCut` is between public values: the verified identity against the owner's public identity key, the owner's public KEM index against `kemIndex`, and the verified PQ key against the public half of the native KEM pool entry. The source key lookup `sourceKeys … seeds` is an analysis projection, exactly as in `NativeKemOrigin.key_or_failure`, and is never evaluated by a reduction. No secret key is compared.

This is an intentional deviation from the recipe in the [raw-accept cut guide](registration-joint-accept-cut.md), which suggested passing a designated owner address as the owner argument of `AcceptCut.selected` and using `key_or_failure`, whose `found` premise is tied to the address `encoded.2.1.1` returned by the program. Stage A instead uses `AttemptReports.owner_origin` at the witness address and the address-free `FinalReportEvent.Failure`. `FinalCandidate.selected` reads only the raw bytes of the choice, the terminal report batch goes to all `count + 1` positions, and `FinalReportEvent.Failure` has no address, so the owner constant of `AcceptCut.selected` is never read and no owner-selection factor arises. The plan fixes that constant to `0`; the statements here are stated for an arbitrary constant `chosenOwner`, of which `0` is an instance. The fixed public `(index, kemIndex)` designation itself is owner decision 3, which the owner took on 2026-10-06 (see below). The existential owner address and the unread owner constant are owner decision 6 of the plan, which still needs the owner's confirmation.

`Protected` reads the identity freshness of the owner at the cut, in the report state reached immediately before the selected raw accept is issued (option (a) of owner decision 1 in the plan, which the owner chose on 2026-10-06). The definitions `ProtectedAt` and `Protected` are isolated in the section `CutProtection` of `PqxdhRegistrationJointAcceptOrigin`. A whole-run reading (option (b)) or a public cut-time observable recorded by the tag (option (c)) would be new predicates with their own theorems; the statements proved here would not change. The plan's stage C combines this cut-time horizon with the whole-run KEM freshness `GoodKem` (no disclosure of KEM key `kemIndex` over the whole run). The two horizons differ by design, and the planned main theorem is an event of the `split` coupling, whose final component is the report run of the tagged program; nothing in stage A states that theorem.

### Assumptions and accounting

No primitive game, contract, axiom or premise is added. The only inherited contracts are the functional attached-format premise `shortRejects` and the `setup.wiring` contract, which owner decision 4 allows in the top-level statement, both used through `RawSignatures.verified_detached`, as `KemOrigin.raw_selected` and `AttemptOrigin.raw_origin` already do. The bounds additionally take the existing creation-capacity premise `capacity` and the existing uniform-bill premises. The loss is one sum `∑ target : Fin (count + 1)` of ordinary joint-use weak-EUF advantages with coefficient one; there is no factor for the owner address, for a field or report position, or for the raw-accept ordinal, which is designated. `scan`, `selected`, `tag` and `decisionClient` forward every query exactly once, and every all-reply cap of `work` carries over; omitted continuation work is neither charged nor used to offset earlier work. A reached raw cut has `index < qAccept`, so an adversary-chosen raw ordinal would range over a family of at most `qAccept` handles; no such selection is made or charged here. ### Deviations from the plan

Five helper statements are added and guarded: `finish_erase` (M0), `run_bind`, `commands_initialized_map` and `reduction_map` (M1, the last two from the scratch probe), and `selected_certified` (M2). `PqxdhRegistrationJointAcceptOrigin` imports `PqxdhRegistrationJointNativeKemOrigin` directly, because that module is outside the import closure of `PqxdhRegistrationJointAcceptCut`. ### What is proved

**Key-list monotonicity (M4).** In the report run the private KEM pool is the pool component of the local state of the identity compiler (`IdentityCompiler.Local`), below the public-report extension `ReportLift.extend`, the identity router and the report interpreter, and `(sourceResult r).2.1.2` is exactly that local pool. `pool_keys` shows that one step of `PqxdhLiveKemBirth.poolImpl` keeps the key list as a prefix: creation appends one pair, and decapsulation and reveal only extend the transcript. `impl_keys` shows the same for one step of `IdentityCompiler.impl`: identity, coin and import requests are forwarded with the local state unchanged, runtime initialization changes only the runtime, and KEM requests run the pool step. `extend_keys` and `program_keys` extend this to one reported step and to every adaptive program, and `reduction_keys` and `continuation_keys` carry it through the identity router and the report interpreter, which can only keep results of the inner run (VCVio `support_simulateQ_run'_subset`; `simulate_result` is the same fact for a plain oracle interpretation). `resume_keys_prefix` concludes that in every execution of the coupling `AcceptCutReports.split` the key list reached at the cut is a prefix of the final key list. `reported_result` shows that every program result of the reported command compiler is a result of the program, and `resume_tag` concludes that a pending cut on `raw` ends with a final source outcome whose tag is `some (raw, answer)`, where `answer` is the public reply of the selected accept. The step was proved directly from `poolImpl`; no lifting of `PqxdhLiveKemReservation.noncreate_keys` was needed, and the plan's fallback R3 (whole-run identity freshness) is not used.

**Tagged and decision programs (M9a).** `commands_map`, `program_map` and `hide_map` show that the exposed command compiler, the actual command program and hiding are natural in the client result, and `decision_program` instantiates this: the actual command program of `decisionClient decision work index` is the `mapOutcome (decideTag decision)` image of the actual command program of `tag work index`. `exposeAt_map` shows that composing the observation of `AcceptKemCut.exposeAt` maps its outcome on every path, and `exposeAt_tag` that, with the identity observation, `exposeAt` interprets under the actual encapsulator to the actual command program of the tagged client itself. `scan_map` shows that the KEM scan is natural in the program result, including the saved continuation of a pending cut, and `rawScan_map` concludes that the scanned program of the raw-ordinal prechallenge (`KemRawChallenge.rawScan`, which uses `observe := decideTag decision`) is the `cutMap (mapOutcome (decideTag decision))` image of the KEM scan of the identity-observation exposure: the KEM games scan the decision program at the same cut, with the same request and with the mapped saved continuation. `initialization_map` and `selectedFirst_map` state the same naturality for `KemInitialization.commands` and `selectedFirst`; the proof of T4 does not use them. The router facts hold for every optional stateful router `QueryImpl spec (OptionT (StateT σ ProbComp))`: `router_split` is the router-run split (the run of a bind is the run of its prefix followed, from the reached state, by the run of the continuation, and a stop stays a stop), `router_map` is naturality, and `router_support` says that every completed result is a result of the program. `coins_stopped` is the random-coins lemma: under `PqxdhDynamicKemJointRouter.stopped`, `PqxdhLiveKemBirth.coins work` samples exactly `work` and leaves the router state unchanged, by induction over `work` from the definition of `combine`; nothing is assumed. `finish_stopped` follows: finishing a pending KEM cut on request `(raw, key)` under the stopped router is the ambient-interpreted `setup.kem.encaps key`, followed by the stopped run of the saved continuation at `KemResume.reply` of the sample, from the same router state, because the source encapsulator is the reply map of `kem.encaps` (`simulateQ_map`).

**Bridge from the actual run to the KEM real game (M9).** The final-state predicates are those of plan section 2.1 and read only the final source result. `Decided decision final` says that the final initialized outcome exists, the decision holds on its original result and the tag of the selected accept is accepted (the accept returned a session). Here and below, "returned a session" means that the selected `get_shared_secret` attempt returned its pending registration output (session index): the public reply of the raw accept is the session index under which `nativeAccept` publishes the pending token, the model's counterpart of the `RegistrationOutput` that `Server::get_shared_secret` (`beaconcrypt/src/server.rs`) returns. Failures of `build_registration_response`, which the model runs as a separate request, are not excluded from the event. `GoodKem kemIndex final` says that the final private KEM transcript has no successful reveal of creation index `kemIndex`. `KeyMatchFinal setup codec checks kemIndex final` says that the recorded raw bytes of the selected accept verify (`RawSignatures.verified`) and that the verified PQ key is the public key at index `kemIndex` of the final KEM pool. Theorem T4 is (binder types abridged and the `PqxdhRegistrationJoint` prefix dropped; the exact statements are in the module and in the receipt):

```lean
theorem actual_le_real (setup) (codec) (checks) (ensureInit) (supplied) (decision : X → Bool)
    (work : OracleComp (SourceSpec KemSK) X) (runtime : A) (budget) (certified)
    (count : Nat) (selected : Fin (count + 1)) (index : Nat) (room : budget (.inl 1) ≤ count + 1) :
    letI := Classical.propDecidable
    𝒟[(fun final => decide (Decided decision final ∧ GoodKem selected final ∧
        KeyMatchFinal setup codec checks selected final)) <$>
      ((fun result => (result.1.map (InitializedSchedule.encodeOutcome setup), result.2)) <$>
        (InitializedSchedule.source setup codec checks ensureInit supplied (tag work index)).run
          ((PqxdhDynamicIdentityPool.initialState, PqxdhLiveKemBirth.empty), runtime))] {true} ≤
    𝒟[KemRawGame.sourceReal setup codec checks ensureInit supplied decision work runtime count selected index] {true}
```

The left side is the literal actual initialized execution of the tagged program from the initial state with the empty KEM pool. The first step is the existing source-order equality `KemInitialization.actual_source_first` for the client `tag work index`, with `certified` carried to the tagged program by `AcceptCutTag.tag_bound` and with `room`; it is an equality of `𝒮` distributions, and every later step is a probability inequality or an unconditional program identity inside the selected-first game and the KEM real game; no program is rewritten across the distributional equality. `probOutput_bind_mono` then descends through the selected key pair, the actual constructor (a failed constructor has no outcome and contributes nothing) and the other reserved pairs to `commands_le_real`. There, the final pool of the selected-first game is `pairs.take created` and its transcript is the router history, so the event implies the router-run event `RunEvent` together with the absence of a successful reveal of `selected` in the history, on the ordinary-router run of the actual command program of the tagged client; the existing `PqxdhDynamicKemJointStopping.history_event`, started from the actual empty pool whose monitor is tracked by definition, turns this into `RunEvent ∧ Good` on the stopped-router run, and `Good` is then dropped. `run_le_real` handles the stopped run: by `exposeAt_tag` and `KemCut.scan_finish`, the tagged program is the KEM scan at occurrence zero of the identity-observation exposure followed by `KemCut.finish`, `router_split` splits the stopped run at that cut, and `rawScan_map` with `router_map` writes the prephase of the KEM real game as the same stopped scan with the cut mapped. For each reached cut, a stop contributes nothing, and a completed cut contributes nothing because its tag is not accepted (`AcceptKemCut.accepted_reached`). A pending cut whose requested key is not the selected key contributes nothing by `active_raw`: by `rawCut_shape` and `rawResume_tag` the recorded raw bytes are the raw bytes of the cut, so the verified PQ key is the requested key, and the run event equates that key with the reserved key at the selected index (`prefix_lookup`, `selected_lookup`). An active cut is finished by `finish_stopped`, that is, by the challenger's ordinary encapsulation to the selected key followed by the saved continuation, which after removing the lossless ghost draw is exactly the continuation `KemResume.sourcePost` of the decision program in `KemRawGame.sourceReal`; the event implies the game's decision because `decideTag decision` of the final tagged result is `decision result && accepted tag`. `good_source` states the monitor invariant on its own (the monitor bit is clear exactly when the projected transcript has no successful reveal of the selected index, from `schedule_tracked`); the proof of T4 uses `history_event`, which contains it. `program_tag` and `client_tag` show that, in the actual command program and in the actual initialized source client of the tagged program, an accepted selected accept records raw bytes whose attached verification succeeded; `classify_final` uses them.

**Main theorem, bills and final classification (M10).** Theorem T5 is (abridged in the same way):


### What is proved

`scan_opaque` shows that the KEM scan of `AcceptKemCut.exposeAt` at occurrence zero is, as a program, the image under `toCut` of `opaqueScan`. That scan runs the actual source prefix up to the selected raw accept, then the Server's attached verification and its steps before encapsulation, exactly as the KEM scan does. A run that completes before the selected accept, a rejected verification and a rejection before encapsulation complete the whole run; otherwise it saves the raw bytes, the verified record, the ephemeral value, the consumed set after the steps before encapsulation, the native state and the owner list at the accept, and the adversary's continuation after the accept.
