# Pre-seal reveal control on the same joint witness

`PqxdhServerAuthJointPresealWitness` completes the separate pre-seal-chain reveal control on the exact `PqxdhServerAuthJointWitness.setup` and `codec` already used by the functional-contract consistency, Server-seed reveal and honest-relay controls. It introduces no new primitive implementation and makes no claim that this deliberately insecure toy provides cryptographic security. The same setup satisfies the approved peer-class law, the scalar-fiber bound, nonzero honest agreement, the actual root/full HKDF equations, the joint Ed25519/X25519 wiring and zero KEM correctness error. Those facts are the previously checked joint-witness results, not additional assumptions of this control.

The concrete adversary requests the one-byte payload `[1]` from one actual Server accept/build, reveals a copy of the installed kernel whose send chain is replaced by the actual recorded pre-seal KDF input, and reseals the distinct one-byte payload `[2]`. The added request history is private until that separate control reveal. The original builder and installed state are unchanged, and the attack uses the original Beacon finish. This tests the reveal boundary in the intentionally altered control experiment; it is not an attack on the unchanged headline experiment's current-chain reveal.

`actual_control_laws` supplies the existing `NegativeControl.ControlLaws` at the concrete public size limit `100`, using the same joint witness. No new functional-law record or desired-event premise is introduced. The source provenance, admission/publication and resealing arguments come from the reviewed `PresealControl` theorem. Nonempty distinct payloads, their length bounds, the actual allocation bound, the nonexhausted Server ID, functional KEM decapsulation and zero KEM correctness error are all discharged for this concrete instance.

`success_lower` applies the complete pre-seal reveal theorem to this instance and obtains a lower bound of one for its separate Boolean authentication decision. `success` uses the probability upper bound to conclude exact probability one. `wrong_payload` separately applies the original `W2` theorem and concludes that the actual wrong-payload event has probability exactly one on the same run. Thus the success statement is attached to the intended authentication failure, rather than only to an unspecified disjunction of winning events. All new probability statements use the current measure interface.

`query_budget` instantiates the original authentication interface budget with one accept, zero public HMAC requests and one public commitment-hash request. `query_classes` retains the finer all-reply-path ledger: at most one accept, build, altered reveal, hash and finish, and zero explicit adversary coin or public HMAC calls. `query_total` proves at most five API queries in total. These are upper bounds through every optional rejection branch; they do not erase the source constructor's randomness, KEM work, local real HKDF/AEAD computation, root-Extract calls or component interpretation costs. The private request instrumentation retains the existing complete source query equivalence proved by `PresealControl.program_queries`.

The functional witness remains an abstract consistency and regression check, not a proof of the actual primitive algorithms. Both the original programmable root-Extract ROM and shared CTX/BLAKE2b ROM interpretations remain explicit. The abstract message writer/read-back and bounded-writer laws are witnessed by the existing codec; no serialization implementation theorem is claimed. Snapshot restoration and persistence remain outside the approved proof. The original headline authentication experiment, its reveal policy and its pending final computational bound are unchanged.
