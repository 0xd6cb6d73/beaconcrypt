# Saved-monitor classification of generated later-record cuts

The five modules `PqxdhLaterChallengeSavedMonitor`, `PqxdhLaterChallengeBuilderContinuation`, `PqxdhLaterChallengePreparedContinuation`, `PqxdhLaterChallengeGeneratedContinuation` and `PqxdhLaterChallengeSavedClassification` connect each saved cut of the actual generated later-record sampler to the private challenge monitor. Their 33 guarded statements use the source-generated selection the sampler already carries, the literal initial Builder and the exact captured wrapper callback. They add no premise, contract, sampler branch or loss term, and they do not state a confidentiality bound.

## Saved callback and outside program

`SavedMonitor.complete_append` splits a saved callback from its appended outside program as an exact `OracleComp` equality, keeping record, finish and Builder effects, both writers, optional refusal and the complete component state. `resume` runs the captured callback once and then the request's carried `next` continuation under the monitor. `resume_erase` and `resume_budget` hold for every value of its private marker.

For the initial Builder, `builderOnly` keeps every field, the trace and the origin of the saved Builder, and replaces only its outside continuation by `pure`. `builder_append` proves that appending the saved Builder's own outside continuation gives back the exact descriptor, and `builder_fits` derives the callback allowance from the descriptor's own certificate. `builderResume` runs the callback-only Builder once through the unchanged saved compiler, then the monitored adversary from the wrapper's `initial` state with an unset marker. When the saved outside continuation is the literal wrapper from `initial`, `builder_erase` proves that erasing the marker gives the complete saved program, including Builder effects, writer failures and outer refusal. `builder_budget` preserves every weighted query budget. `builder_pre` gives the two-world twin relation up to the monitor's explicit private events by `PqxdhLaterChallengeMonitor.program_pre`. Its target-versus-parent address inequality is the existing explicit alias event of `program_pre` and `random_client`, charged by the published same-sampler alias allowance; it is not a new premise.

## Source continuations

`BuilderContinuation.Continuation` requires the literal Builder outside continuation when request metadata is absent, and the existing exact `Joined` request/callback composition when it is present. `captured_continuation` and `shared_continuation` derive it from the actual complete Builder, adaptive Post and shared scanner, including diagnostics, failed writers and admission branches. `PreparedContinuation.prefix_continuation` and `run_continuation` carry it through the native prepared prefix and the original collector's pending branch; completed and cached Booleans are unchanged.

`GeneratedContinuation` carries only the generated selection beside the existing sampler carrier: a pending packet carries `prefixOutput.context.selection.1` and a completed packet carries `none`. `run_erase`, `run_budget` and `continued` show that this changes no program, budget or state-dependent continuation. `prepared_capture` proves the source continuation property for every supported normalized prepared pending packet: the completed case is impossible by constructor disjointness, and the pending case transports the literal packet equalities to `run_continuation`. `run_capture` and `evaluated_capture` give, for the same carried selection that supplies the stored Post, the descriptor property `Continuation owner number bit (adversary selection) (pending.1, result.1.2)`. When `result.1.2 = none` (a Builder cut) this binds the selection to the saved Builder's literal outside wrapper. When `result.1.2 = some details`, `Continuation` ignores its adversary argument and is only the selection-independent `Joined` composition of the actual `details.callback` and `details.request.next`, so these two theorems bind the selection to the stored Post alone; the request chronology of the same packet is `GeneratedChronology.run_reaches`, discussed under Remaining obligations. The evaluated form projects support only.

## Classification

`phase` reads only carried metadata. Absent metadata is the initial Builder. A request whose pre-query wrapper state already holds a pair is `used`. An ordinary or unequal-length request from an unused wrapper is `before`, and an equal-length challenge from an unused wrapper is `inside`. `phase_used` states that the used phase is exactly an already chosen pair.

`before_record` shows that the monitor's own `record` function leaves the marker unset at a before-phase request for every instrumented state. `inside_record` shows that inside the admitted challenge the marker is the selected-input condition of the instrumented state immediately before that callback. A cut inside the callback does not carry that state, so the inside phase stays an explicit obligation.

`generated_builder` instantiates the Builder phase with the actual generated sampler. The carried selection supplies the stored Post, the saved Builder's literal outside wrapper, and the equation between the complete saved program and the erased `builderResume (adversary selection)` on `builderOnly`. `generated_request` instantiates the request phases with the actual captured callback `details.callback` and the request's carried continuation `details.request.next`: the stored descriptor satisfies `Joined`, the callback allowance is derived from the descriptor's own certificate rather than assumed, and the complete saved program equals the erased monitored `resume` for any marker. In this theorem the carried selection fixes only the stored Post; `Joined` does not mention it. `evaluated_not_used` reads `GeneratedCache.run_not_used` from the 64-statement captured-chronology checkpoint ([guide](later-record-captured-chronology.md), called Chronology64 below) through `run_erase`. At position `depth + 2`, when the frame-level saved continuation returns the original true output with the marked target publication, the phase is not `used`. This is an event exclusion, not a probability bound.

## Private selection and adversary interface

The selection is source-produced private metadata. The adversary receives `adversary selection` and the Builder reply exactly as in the original wrapper; no identity, KEM or service secret enters its interface. The selection in each conclusion is pinned by `result.2 = some selection`, and the saved Builder is taken from the descriptor's literal equation `pending.1.original = .inr saved`. No function is recovered by existential choice or descriptor inversion, and equal or correlated bytes are not ruled out.

## Remaining obligations

The [compiler-support checkpoint](later-challenge-compiler-support.md) now restates the original evaluated chronology for the carried selection and proves compiler-level all-reply support for the literal saved callback. It derives the before-phase unused-wrapper certificate from the actual generated execution and applies `program_pre` to the monitored resume with marker `none`. Transporting the monitor through the whole historical prefix, so that its actual marker at the cut is proved to be `none`, remains open. The inside phase still needs the actual pre-send counter and historical directional path at the same callback cache; it must not be replaced by an address-separation or fresh-cut premise. The used-phase exclusion remains stated for the frame-level resume under the original true marked-publication event at `depth + 2`; its publication-trace join to the compiler remains open.

The two-world join of the generated prefix, the real/raw primitive hop, the actual Fresh/event implication, selected finish and refusal accounting, the alias allowance `(8 + 67 * postCap) / 2^256`, owner/session/position selection factors and the complete reduction ledger remain open. Support lemmas here transfer no probability, budget or independence.
