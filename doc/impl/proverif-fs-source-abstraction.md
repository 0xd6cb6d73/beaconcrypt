# Source obligations for the bounded free-schedule models

This is a paper argument and source audit against `codex/full-proof-composition` at `0220835d1148afcd695fd0d1429339ca89538bb4`. The Rust and ProVerif sources at that revision are unchanged from the published P3 result basis. The existing 49 exact results are statements about the bounded fs processes. This document establishes several local source facts, supplies two model-level simulation arguments, and distinguishes them from the global source-to-fs trace relation that remains unproved. No new primitive assumption, protocol change or ProVerif restriction is introduced. Serialization remains the approved abstract message contract; persistence and restored states are outside this proof.

The phrase “preserves state” below names the state it preserves. Native allocation capacity, random-generator state, primitive-oracle histories, query counters and private caches are not silently deleted. A symbolic trace argument about unobservable restricted names is not a computational distribution or cost argument. The actual Rust APIs return optional replies; the current fs receive processes do not expose those replies to the network. Consequently the model-only deletion arguments below do not establish an adaptive raw-receive API theorem.

## Status of the obligations

| Obligation | Result established here | Remaining global obligation |
| --- | --- | --- |
| L1, Server decomposition and accept/build scheduling | Exact state footprints; complete builder independence from consumed context, checked in Lean; source counterexamples to an event-preserving adjacency or object-renaming argument | An explicit pending-token scheduler or a claim-specific violation-preserving simulation covering arbitrary accept/build order and cross-object token transfer |
| L2, per-peer state and routing | Exact routing to the claimed sender's installed peer, same-peer AD, and preservation of all other peer entries, already checked in Lean | A term/trace relation for many peers collapsed to `fs_kid(1)`, including reflected query matches and binding bytes |
| L3, receive relation | Exact cached/future failure rollback and successful publication at the source boundary; bounded state relation described below | A material-preserving simulation of the model-only far branch and a global induction from reached states |
| L4, send relation | Allocation, chain publication and failed-seal behavior at the actual source interface | Composition with the fs material interpretation, application inputs and the global trace relation |
| L5, Beacon lifecycle | At most one returned bundle and one active finish; failure is terminal; silent pre-bundle key operations cannot create a second successful bundle | Computational accounting for failed/pre-generated draws and signing, and any API observation or reveal beyond the current no-reveal symbolic scope |
| L6, later event fields | `FsReceivedFrame` and the rejected-frame field have a precise source occurrence interpretation | This is an event projection, not a byte-to-free-term injection or global trace compiler |
| E20, early Server names | Paper proof of equality of symbolic labeled traces at one attempt per object | No computational generator-order interchange follows |
| E21, fail-stop | Paper proof for C2 and C4 in the current model with hidden failure replies | Does not apply to a receive oracle returning optional plaintext or recording primitive calls |
| E19, direction split; E3, arbitrary pins | The exact state-separation premise and remaining proof obligations are identified | A deduction-preserving simulation is still required; the previous prose is not a checked cryptographic-origin argument |

These statements require independent review before their status is used elsewhere. In particular, writing a local paper proof does not remove the existing “pending abstraction” qualifier from an fs security result.

## L1: exact footprints and the accept/build distinction

Write a live Server's logical state as `(binding, C, n, P)`, where `C` is its consumed registration set, `n` is its allocation counter, and `P` is its map of installed peers. The application separately owns opaque pending tokens. This is the projection of [`Server`](../../beaconcrypt/src/server.rs), not an assertion that its complete native or cryptographic state has only four components.

`get_shared_secret` reads the current binding and checks the verified `(Beacon identity, one-time public key)` pair against `C`. Before `server.rs:415`, a refusal leaves `C`, `n` and `P` unchanged; reservation and primitive effects may already have occurred. At success it inserts precisely that pair and returns the root and pending context in a token. It never installs a peer or advances `n`. `build_registration_response` consumes its token by value on both success and failure. It reads the building Server's current binding, counter and occupancy, and leaves `C` unchanged. It installs a peer and advances the counter only after first-record and outer response serialization succeed (`server.rs:424-502`). The checked statements `PqxdhRegistrationAdmission.accept_consumed`, `.build_consumed`, `PqxdhRegistrationResponse.accept_control`, `.build_publication` and `.build_counter` cover these logical footprints in the original source-shaped handlers. They do not assert that the associated primitive work commutes.

The new module [`PqxdhRegistrationBuildContext`](../../beaconcrypt-core/proofs/lean/BeaconcryptCore/Computational/PqxdhRegistrationBuildContext.lean) proves a stronger local fact than a footprint observation. For every function `f : Consumed → Other`, the original complete builder applied to a state whose consumed context is `f(C)` is the original builder followed by applying `f` to the returned consumed context. The same pending token, root, binding, peer map, counter, source KDF, application input and peer metadata are retained. `publish_map` proves the publication case; `after_map` preserves seal, erasure and outer writing; `candidate_map` also preserves identity parsing, reservation, initialization and binding; `build_map` includes allocation, occupancy and binding rejection. `build_interpreted` quantifies over an arbitrary stateful probabilistic implementation, retaining its whole final private state. `build_continuation` quantifies over the complete subsequent continuation. `build_queries` preserves every selective logical callback bound. No callback is deleted and no sampling is declared free; any interpreted base or uniform query count remains that of the identical program through the same interpreter.

This theorem explains why the consumed set at build time need not contain the token's registration ID. The builder never consults that set. It does **not** move the original acceptance event to the building object, copy the token, or allow reuse after a build. The exact current binding is still checked by `server_prepare_commit` (`pqxdh.rs:847-858`), and allocation still uses the building object's current counter. A claimed proof that the token must have originated on that object would contradict these source facts.

### Cases (i) and (ii): adjacency is not an event-preserving commutation

Let one object accept distinct bundles `x` and `y`, producing opaque tokens `tx` and `ty`, then build `ty` before `tx`. A successful source trace has the event order `Accepted(x), Accepted(y), Committed(y,k+1), Committed(x,k+2)`. The fs registration step must decide build or drop before its next acceptance. Keeping the two acceptance events in order forces `x` to be built first or dropped; keeping both commits in order forces `y` to be accepted first. Therefore no mapping preserves this event order, both token associations and the assigned IDs. This is a counterexample to full event-trace equality, not a violation of A1 or another advertised security property.

A claim-specific permutation may still be possible, but it must say which event order it forgets, preserve the attacker's next-input recipes, and reflect every match in the target query. Delaying a replay rejection along with an acceptance changes a source `None` reply and the time of the witness event. The fact that the refusal leaves the logical state unchanged does not by itself justify that permutation for an adaptive caller. Likewise, equality of marginal fresh-key distributions is insufficient to exchange source generation across adaptive calls.

### Case (iii): unused and failed tokens

A token that is never built has no public response; an attempted build that returns `None` consumes the token and leaves allocation/peers unchanged. At the fs network-event projection both can be represented by the drop choice, provided the pending-token identity and the previous consumed-set update are retained. This local projection does not simulate the API caller's optional build result or the failed build's primitive/private effects. The same distinction applies to deleting an early failed acceptance in case (v).

### Case (iv): tokens can move between live objects

Choose two live objects `A` and `B` with the same identity public key and `server_kid`, and two valid distinct honest bundles `x` and `y`. Execute `A.accept(x)`, `B.accept(y)`, `B.build(tx)`, `A.build(ty)`, with both builders' counters initially equal. Both builds pass the actual binding check. The committed root on `B` is the one accepted by `A`, and vice versa. Each consumed set still contains only the pair accepted by that object. The fs process has the stronger invariant that every committed root was accepted on that same object. Swapping the two object labels does not repair the mismatch: either labeling still relates each commit to the other object's acceptance. Identifying the objects loses the two separate consumed sets and their per-object replay events. OD2 identifies the identity key, not these live states, so it does not exclude this trace.

An exact symbolic extension needs a finite pool of opaque linear pending tokens, indexed by creation occurrence, containing the accepting object, binding, verified fields, root and public response inputs. An accept inserts a token only after inserting its registration pair in its own consumed set. A build chooses a token and a live building object, removes the token on every outcome, checks the binding, and allocates from that object's current counter. Commit events label the building object and retain the accepting occurrence separately as ghost provenance. Tokens must not be put on a public channel: that would disclose their root. Bound accounting must separately count accept attempts, build attempts and installed peers per object; a builder can receive several imported tokens without accepting any bundle itself. This describes the required correction, not an implemented or verified new process.

### What this means for individual claims

R1 is already a source-local no-reacceptance fact for the same live object's consumed set (`PqxdhRegistrationAdmission.no_reacceptance` and its whole-history forms). It does not need to identify a building object. R1' additionally needs the one-returned-bundle property and an authentication argument for the verified identity/one-time pair. A2 needs bundle origin but not a same-object build. A1 and S3-server concern successful builds, so importing a valid token does not immediately falsify them; their lift must retain the original root/token provenance and the current builder's assigned ID. The two traces above disprove the proposed unrestricted trace equality while leaving these claim-specific security arguments open. No global claim is marked false merely because that equality is false.

## L2: exact peer selection, before any ID collapse

The native routing equation is exact. `Server::decrypt_message_transition` first decodes the frame's claimed sender `k`, computes AD from the Server identity and the identity stored in `P[k]`, selects that same `P[k]` ratchet and calls the raw receiver with expected sender `k` (`server.rs:229-249`). Missing decoding or a missing peer refuses before any ratchet operation. A full decoder that accepts a frame must agree with the header decoder on its sender; complete-input behavior remains the explicit message contract. There is no separate trusted association from the network channel to a peer.

The checked `RawCtxServerRouting.rawGame_cases` exposes precisely this routing path. `.rawGame_success` ties the returned plaintext to the actual primitive-produced optional plaintext under the selected peer's AD, sender and sequence. `.putPeer_other` preserves every other peer entry; `.rawGame_failure_server` restores the entire logical peer map on refusal while retaining actual primitive effects; `.rawGame_peer_fields` prevents a receive from rebinding an identity. Induction over the actual serial schedule therefore gives per-peer logical state independence: to know one peer's next logical kernel, retain its own routed operations and the real outcomes they received. This induction does **not** erase other peers' calls from a common primitive interpreter, whose state and query accounting may be shared.

There is a direct routing-selection map for the restricted class with one locally accepted-and-built peer per object, represented by `fs_kid(1)`, the existing application restrictions, and the stated bounds. On each source receive choose that object's worker; unknown IDs refuse, and known IDs select its sole peer. This is a statement about which peer is selected, not an exact relation on arbitrary raw bytes or cryptographic terms. The remaining material, far-branch and cryptographic theory obligations are unchanged. This local correspondence does not establish the proposed many-peer collapse.

The many-peer map `server_kid+i ↦ fs_kid(1)` is not a renaming: it is non-injective. Preserving successful equality tests is necessary but insufficient for a trace simulation. A source failed equality can become true and choose a different branch. Moreover the ID occurs inside the authenticated eight-byte registration prefix, ciphertext context and query session fields, not just in a routing lookup. An A1 counterexample based on unequal IDs could disappear if both IDs collapse, because a previously absent matching commit may become a match. The source binding theorem can discharge exact ID agreement separately, but the decomposition and its query-reflection proof have to be stated, not inferred from “merging only adds traces.”

A sound many-peer lift must specify a translation on messages and attacker recipes, show closure under every public constructor/destructor used, simulate successful **and rejected** control paths, and reflect unmatched/injective events of each query. Alternatively the pending-token scheduler can retain distinct public IDs and an explicit peer map and avoid this collapse. Neither a global map nor a new distinct-ID scenario is claimed in this checkpoint.

## L3 and L4: the local ratchet relations

For a materialized bound `T`, relate a source receive kernel to `(r,C)` by its exact receive counter `r`, the set `C` of cached sequence numbers and the material/chain associated with each position by the fixed source KDF. `C` has no duplicate sequence and contains only positions below or equal to `r` that have not been consumed. Under that relation, a cached success removes precisely its sequence; an old uncached target refuses; a future success at `t` adds the skipped positions `r+1,…,t−1`, consumes `t`, and advances the live chain/counter to `t`; an unsuccessful attempt preserves the entry kernel. The representation forgets cache array order, so swapping the last occupied slot into a consumed slot implements set deletion without changing any remaining sequence's material. This is the local state relation represented by the fs window flags.

The source equations are `concrete.rs:261-299`, `:425-454`, `refined.rs:700-778`; checked boundaries include `RatchetReceiveStructural.receiveRun_exists_classified`, `RatchetReceiveRollback.receiveNext_failure_entry` and the whole-owner/raw routing results above. At the current bounds, starting from the registration poststate, s2b materializes only positions through 3 and b2s through 2, so an all-materialized trace cannot fill the source cache capacity of 50. Failure neutrality means the kernel is restored, not that its attempted KDF, commitment or AEAD calls disappear. Events carrying the actual failed frame can be erased only for queries which do not inspect them and only under the stated observation model.

The far branch is a separate unresolved material relation. Replacing a real sequence of public HKDF applications by `fs_far_chain(chain,t)` changes a term. C4 proves a property of that replacement; it does not prove that an arbitrary real far acceptance maps to it. The required argument must translate both honest-secret and attacker-known chain cases and preserve public KDF evaluations and frame recipes until the first far success. Merely dropping the cache bound broadens admission but does not justify replacing the cryptographic material. OD4 approves the intended abstraction; the source simulation remains to be supplied.

For sends, `SendKdf::resume` installs the next send chain and counter before sealing, and `SendSeal::finish(None)` returns that advanced kernel (`concrete.rs:133-209`). Receive fields are unchanged. Empty application data and exhaustion refuse before this allocation. Thus `FsSent` correctly denotes a source allocation occurrence, not a successful API return. For the current network-only symbolic projection a failed post-allocation seal/write may be represented by allocating and outputting the corresponding ideal frame, which the attacker withholds; this adds attacker knowledge and no receive is forced. The source's subsequent sequence number remains the same. Bounds count allocation attempts including failed seals, not only returned frames. This argument supplies the local send footprint, not a computational coupling with free extra oracle outputs or a simulation of the API's optional result.

## L5: the actual Beacon lifecycle

The phase transitions establish the following property by induction on calls to the public methods, without persistence or direct memory access. A Beacon constructed in `Fresh` can move to `FreshWithCoins` and back before its first successful bundle. `new_onetime_keypair` can replace pre-generated coins only in those fresh phases; `delete_onetime_keypair` aborts an `InitSent` owner; `delete_pq_keypair` aborts any active registration phase (`beacon.rs:222-295`). None of these methods takes `InitSent`, `Established` or `Aborted` back to a fresh phase.

`get_registration_bundle` accepts only `Fresh`/`FreshWithCoins`. Every failure before publication leaves the entry phase; once all three signatures and the writer succeed it installs `InitSent` before returning `Some(buffer)` (`beacon.rs:300-398`). It can therefore return at most one bundle per live Beacon object. Failed attempts may generate different one-time keys and produce private signatures; the proof is about returned bundles, not a bound of three signatures for an API permitting retries. No failed attempt's bundle is returned, and the current symbolic scope has no reveal interface. An application observing prekey/one-time secret accessors or private primitive logs is outside that scope and must not be erased into one successful symbolic draw.

`finish_registration` called outside `InitSent` returns `None` unchanged. The first call in `InitSent` executes the real parser, preparation, KEM/DH/root, initialization and raw opening; then it either publishes `Established` or installs `Aborted`. Any later finish is inactive (`beacon.rs:402-509`). `PqxdhRegistrationBeacon.no_retry` and `.active_failure` prove this for the complete source-shaped owner while retaining callback poststates. A finish at any decoded sequence other than 1 aborts after the actual raw execution; `.wrong_target_continuation` proves that its final decision can be replaced by rejection for an arbitrary complete continuation while keeping that raw execution. Only the network/event projection may omit the otherwise unobserved work. The original sequence-one response property is preserved.

This establishes the lifecycle premises used by the single-bundle and one-finish symbolic process. It does not prove that independent Beacon objects cannot collide in computational identity bytes, that unsuccessful signing/draw work is free, or that R1' follows without authentication. Those are separate computational obligations.

## L6: frame-valued events added after the original review

`FsReceivedFrame(dir,S,B,kid,root,t,f)` records the same successful call as `FsReceived`, with the actual raw frame argument `f` instead of its returned plaintext. It is emitted only after opening succeeds and before continuing with the committed kernel. Its source meaning is the input argument to that occurrence, whose full decode and sequence are supplied by `RawCtxOwnerProvenance.raw_success_metadata` and `RawCtxServerRouting.rawGame_success`; it asserts neither uniqueness of serialization nor that equal raw bytes identify a unique execution. At the Beacon finish, it records the inner application frame, not the outer response envelope.

The added `f` field of `FsReceiveRejected` records the actual input of a parsed expected-sender receive that returned `None`, at the same entry state described by that event. It excludes outer parser failure and wrong-sender/missing-peer rejection, which do not emit this witness event. The replay witness can therefore compare the exact previously accepted input against the exact later refused input. It does not infer replay from two independently existential frame values. Both frame events are ghost instrumentation; neither exposes plaintext or a new API return to the attacker.

## E20: symbolic early-name extrusion

For one attempted registration per object, compare the original symbolic prefix in which `new e; new coins` occurs after parsing/status tests with the v2 prefix in which those restrictions surround the input and tests. Alpha-rename both restricted names fresh for the whole configuration. Before their original binding point no test, event, output, public recipe or prior state contains them. Each successful input/test transition of either process is therefore enabled in the other with the same label and substitution, and the new names remain unavailable in both. At the original binding point pair the late names with the already-restricted early names and continue identically. On a prefix refusal, the early unused restrictions disappear with the stopped process; neither trace emits their values. Induction over interleavings with other objects preserves all event and output labels up to this alpha-renaming. This is equality of symbolic labeled traces at the one-attempt scope; replication creates fresh names independently for each object.

The old sentence “both forms draw exactly one pair” is too broad for a refused Rust prefix: Rust may draw neither value whereas v2 binds unused names. The proof above relies on unused symbolic restriction being unobservable. A computational version must retain the full continuation and actual distributions, state and costs of failed/delayed generation. No such computational reordering is inferred here, and this argument does not move a single pair across several attempts on one live object.

## E21: deletion in the current symbolic receive process

Take a finite trace of the failure-interleaving b2s process through a chosen violating event. Delete every failed-open receive step of each worker and retain every other process step in its original order. Each deleted step receives an attacker-derivable term, introduces no restricted name, outputs nothing, emits only the ignored rejection event if any, and continues at exactly the entry `(r,cached_1)` state. Therefore deletion removes no term from the attacker's knowledge and changes no local state read by a remaining step. Renumber the remaining receive macro instances consecutively; their bodies differ only in the next/failed continuation. There are no more than the original three instances. By induction on the retained global trace, each retained input recipe remains derivable and every success executes with the same material, events and next state. The resulting finite trace has no failed open and is a prefix of the fail-stop process. A worker that has unused attempts can simply be left unscheduled; no fairness premise is needed.

The retained events are in bijection with the original events except the deleted rejection events. Event order and equality of occurrence times among retained events are preserved. Consequently an injective C2 violation keeps its lack of an injective matching send, and a C4 violation keeps the same far event and attacker-knowledge condition. These are exactly the two maintained fail-stop targets. This proof uses the current no-output failure interface; it does not prove a lift for C5 failure witnesses, strong secrecy with observable replies, or the computational raw receiver. At that receiver every deleted attempt still costs queries, can populate a shared cache/ROM log, and returns an optional result to its caller. Those effects must remain in the computational reduction.

## E19 and E3: remaining deduction arguments

The native send/receive field separation is exact, and the T0 symbolic theory gives different initial chain projections in the two directions. This alone is not a proof that deleting the other direction preserves attacker deductions: its ciphertexts are still output terms, may be copied into later attacker-controlled fields, and include decryptable records for attacker-owned sessions. A full direction-split proof needs a relation on adversary frames/recipes, replacing opaque omitted outputs consistently while preserving their public tests and any readable plaintext. It must also preserve query matching and account for visible receive replies if the interface is extended. Until supplied, E19 remains a paper argument requiring completion, not a consequence of product state alone.

Similarly, the current arbitrary-pin argument for C2/C3 uses an unproved origin claim: every successful other-pin Beacon finish implies that the attacker knew its root before the finish. Constructor one-wayness alone does not prove that claim; it requires an induction over all ways an opening key/frame can enter attacker knowledge, including previously emitted frames and other sessions. The PIN diagnostic's “cannot be proved” result is not that induction and is not a counterexample either. This checkpoint does not cite pin independence for C2/C3; their maintained ProVerif evidence remains the honest-pin process. A direct bounded AnyPin result or a complete deduction/origin simulation would remove this remaining dependency. The already pin-free A1, A2, S2, UKSr and C4 results retain their existing scope.
