# Raw-accept source cut and native KEM origin

Status: four modules and nine statements pass direct single-module Lean 4.34 checks with exact `#print axioms` guards that permit only `propext`, `Classical.choice` and `Quot.sound`. The root module also checks against the retained artifacts. These modules were independently reviewed on 2026-10-06 (semantic and hygiene lenses, APPROVE_WITH_NITS) at commit 5f712e7a, and the nits were fixed in the follow-up commit "Record accept-cut review and clarify join step". They are source-correspondence components; they do not join the authenticated root theorem and give no probability bound of their own.

## Modules and statements

| Module | Statements | Content |

## What is proved

`AcceptCut.scan work index` walks the adversary program over `PqxdhRegistrationJointRevealSchedule.Spec`. It forwards every query once and passes each reply to the original continuation. It counts only raw `.accept raw` requests, and it suspends before the zero-based `index`th one, keeping the raw bytes and the original optional-answer continuation. The scan never reads a reply to decide whether to count, so rejected attempts are counted as well. `scan_finish` is the program equality `scan work index >>= finish = work`; because it is an equality of oracle programs, it holds under every later interpreter, including the native state and private histories. `scan_bound` and `selected_bound` carry every `IsQueryBoundP` cap of `work` to the scan and to `selected`, which packages the caller-supplied public owner address with the suspended raw bytes. If the program completes before the selected request, `selected` returns a fixed public fallback without examining any state. No query is added, and continuation work that the scan omits is neither charged nor used to offset earlier calls.

`AcceptCutSource` states the cut on `PqxdhRegistrationJointKemEncapsulation.commands`, which is the actual source14 command compiler with only its encapsulation operation exposed. `commands_bind` shows that this compiler respects program composition and passes on the complete owner registry and native state. `commands_resume` shows that compiling the scan and then compiling the resumed remainder from the resulting state gives the original compiled execution. `pending_command` shows that, at a pending cut, the next computation is the exposed `KemEncapsulation.accept` on the same raw bytes and native state. The original continuation then receives the actual optional reply, and the owner registry is unchanged.

`CutVerification.verified_pure` uses the exposed prefix handler, which is the encapsulation-exposing `prefixImpl` composed with the Server prefix compiler. From any consumed-registration list, simulating `PqxdhServerRootPreparation.verifyInput raw` equals `pure (PqxdhRegistrationJointRawSignatures.verified setup codec checks raw, consumed)`. The verification therefore makes no oracle query, leaves the consumed list unchanged and does not touch pools, signing logs or reveal state. The equality holds before any interpreter is chosen for the exposed encapsulation hook or for a KEM challenger.

`NativeKemOrigin.selected_source` shows that, when the initialized report source finishes with outcome `encoded`, the candidate that `PqxdhRegistrationJointFinalCandidate.selected` reads from the adversary's output equals the candidate parsed from the outcome's original raw bytes. Reattaching private pools does not change it. `key_or_failure` covers every result in the support of `PqxdhJointPhase1Reports.run` over `PqxdhRegistrationJointReportCompiler.initialized`. Its premises are that the addressed owner is generated and unrevealed, that the owner has a source identity key, and that the detached typed verifier accepts the selected candidate under that key, that is, `acceptPhase1Candidate setup.joint.verify candidate = some (publicKey.ed25519, decoded)`. This is a different interface from the attached source verification of `verified_pure`. It concludes one of two cases. In the first, the decoded tuple occurs in the owner's literal chronological signing transcript, and the owner's native KEM slot holds the decoded PQ public key. In the second, `PqxdhRegistrationJointNativeOriginEvent.Failure` holds. The integrated `NativeOriginEvent.transport` already bounds that event by the ordinary final-report detector with coefficient one, and `PqxdhRegistrationJointNativeOriginBound.native_origin_bound`, under its creation-capacity condition, charges that detector to an explicit sum of ordinary joint weak-EUF advantages over the generated targets. No premise requires an honest incoming tuple.

## What is not proved

The next join is still open. It is to instantiate this cut inside the initialized report compiler, so that `AcceptCut.selected work index owner fallback` becomes the `program` argument of `key_or_failure` and of the existing `PqxdhRegistrationJointFinalCandidate` machinery. The raw-accept ordinal must stay distinct from the encapsulation ordinal of `PqxdhRegistrationJointKemCut`. A request rejected before encapsulation makes the two ordinals differ, and no theorem here relates them. The owner must be selected by a public source handle or index, never by comparing a secret key. The join must use `verified_pure`, the step from attached to detached verification described in the next paragraph, `key_or_failure` and the native-origin coefficient-one transport, and it must keep all source and private state and every source query class. None of the modules here proves that the pending raw accept reaches encapsulation, that its verified PQ field equals the selected challenge key, or any selection or freshness loss.

The step from `verified_pure` to `key_or_failure` is the next obligation and is not proved here. `verified_pure` ends in `PqxdhRegistrationJointRawSignatures.verified setup codec checks raw`, which is the source attached verification: it parses the identity field, applies `checks.identityPoint`, and opens each signed field with `setup.source.crypto.verify`. The `accepted` premise of `key_or_failure` is instead the detached typed interface `acceptPhase1Candidate setup.joint.verify candidate = some (publicKey.ed25519, decoded)`. The existing bridge is `PqxdhRegistrationJointRawSignatures.verified_detached`: from `RawSignatures.verified setup codec checks raw = some value` it gives `acceptPhase1Candidate setup.joint.verify value.candidate = some (value.identity, value.keys)`, and `RawSignatures.verified_origin` gives `RawSignatures.candidate codec raw = some value.candidate` from the same hypothesis. `verified_detached` takes the existing attached-format premise `shortRejects`, which says that the source verifier rejects every input shorter than a 64-byte signature, and it goes through `PqxdhJointPhase1Reports.source_attached_adapter`, which also uses the existing `setup.wiring` contract. The join must then show that, when the scan suspends, the outcome's raw bytes `encoded.2.1.2` are the suspended `raw`, so that `selected_source` turns the candidate equation into the `chosen` premise with `candidate := value.candidate`. The `accepted` premise then follows, with `decoded := value.keys`, only when `value.identity = publicKey.ed25519`, that is, when the candidate's own identity field is the addressed owner's source identity key. A `none` verification result and a verified candidate under another identity key are outside `key_or_failure`, and the final event of the join must treat them separately. `PqxdhRegistrationJointKemOrigin.raw_selected` and `PqxdhRegistrationJointAttemptOrigin.raw_origin` already carry `shortRejects` for the same reason, so the join inherits that existing contract rather than adding a new one.

Handoff item 1 also remains open. The authenticated root theorem still needs the actual source14 accept/report execution to be joined to the retained Phase-1 EUF reduction and the selected one-key ML-KEM challenge. Its final event must cover honest unchanged candidates, honest changed candidates, attacker-owned candidates and rejection, without an honest-target premise. The candidate/KEM value must also stay out of the KDF distinguisher's public context. These modules add no KDF, Extract or root-input statement.

Handoff item 7 also remains open. The production/source boundary still lacks its acceptance, root, record, rollback/replay, publication and associated-data joins. These modules are statements about the existing Lean source14 model, not new Rust correspondence. Compiler correctness, storage, physical erasure, codec internals and native primitive internals remain external contracts. Persistence, snapshots and attacker access to running code remain outside the experiment.

## Assumptions and accounting

No primitive game, contract, axiom or premise is added, and none of the nine statements takes `shortRejects`. The join will use two existing primitive-facing items, and both are cited, not re-proved or strengthened. The first is the ordinary joint Ed25519/X25519 weak-EUF family, to which `native_origin_bound` charges the final-report detector that bounds the native tuple-origin failure. The second is the functional attached-format premise `shortRejects` together with the `setup.wiring` contract, which `RawSignatures.verified_detached` needs for the step from attached to detached verification. Symbolic constructor injectivity is not used. `scan` forwards each query exactly once and keeps every cap of the original program, so the existing source query classes and the all-reply resource bills of the native-origin and KEM-cut cohorts are unchanged.

## Names for consumers

`PqxdhRegistrationJointAcceptCut` reuses short names that other namespaces already declare. `Cut`, `scan`, `finish` and `scan_finish` also exist in `PqxdhRegistrationJointKemCut`, `scan_bound` also exists in `PqxdhRegistrationJointKemCutBounds`, and `selected` also exists in `PqxdhRegistrationJointFinalCandidate`. When `AcceptCut` and one of these namespaces are both opened in full, Lean reports an ambiguity error wherever both readings of such a name elaborate; a scratch check reproduced that error for all six names. The next join needs the raw-accept cut, the KEM encapsulation cut and the final-candidate machinery side by side, so consumers must qualify these names, for example `PqxdhRegistrationJointAcceptCut.Cut` and `PqxdhRegistrationJointKemCut.Cut`, or open names selectively, as `NativeKemOrigin` already does with `open PqxdhRegistrationJointFinalCandidate (Choice selected)`. This is a naming matter only and changes no statement.
