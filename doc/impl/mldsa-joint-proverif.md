# Joint ML-DSA registration and record model

## Status and scope

This work starts after the property-test merge `64ab17dd`. The bounded profile in `mldsa-joint-session.pvl` and `mldsa-joint-session.pv` passes its strict focused checker: eight security queries are true, six reachability queries are false with reconstructed traces, and five verifier-bypass controls reconstruct attacks. These are conditional symbolic results under the explicit primitive assumptions below. Heavy jobs were coordinated through `/tmp/bc-coord`; no full Lean build or `verify-in-shell` ran for this extension.

The first exploratory run produced eight true security rows and six unknown witness rows. It was rejected: a synchronous private token output preceded the parallel spawn of its receivers, blocking every process. Those security rows supply no evidence. Two finite private-reply service encodings then timed out without an accepted receipt. A corrected table/token version proved the eight security rows and reconstructed five witnesses, but left replay rejection unknown; a separate precise-action probe did not reconstruct it either. Those versions were not accepted as complete receipts. The final profile retains the corrected table/token protocol and adds the passive causal witness monitor described below, without the unsuccessful precision setting or annotations. Its accepted receipt reconstructs all six witnesses as well as proving the security rows; unknown, missing or unreconstructed rows remain failures.

The earlier `mldsa-registration-auth` profile checks 12 authentication queries and two verifier-bypass controls. Its response body/tag/commitment and finite AD test use separately chosen values, so those results do not connect authentication to an actual PQXDH root, first CTX record and later directional traffic. The new profile models that connection while reusing the existing ideal primitive boundary and the explicitly assumed ML-DSA verifier. Its execution has one protected honest beacon, two generic registration attempts at one server owner, the initial sequence-one server record, one further server-to-beacon record at sequence two, and one beacon-to-server record at sequence one. Each directional application receiver makes one attempt. It does not model an arbitrary ratchet/cache schedule.

## Execution being modeled

The bounded model performs all four X25519 contributions, ML-KEM encapsulation/decapsulation, the existing root-input ordering and HKDF projections, initial CTX sealing/opening, and a bounded continuation of directional records. ML-DSA contributes authentication; it adds no secret input to the key schedule. Record secrecy therefore relies on the modeled KEX, KDF and authenticated encryption. Signatures are not secret containers.

Requests carry the mandatory self-presented beacon ML public key and ML signature. Verification uses the beacon role and fixed context before classical signature checks, replay admission or DH/KEM work. The Init digest binds the pinned server identifier, both server keys and the original decoded request fields, including their classical Ed25519 signature bytes; only the ML signature field is excluded. Accepted private state retains that digest and the two ordered ML public-key hashes. Cross-owner pending-result retargeting is a separate source requirement; the first joint trace has one server owner and does not execute that API case.

Responses carry the mandatory server signature over the retained Init digest, exact decoded identity/ephemeral/KEM fields, raw application `C || T || U` and assigned identifier. The beacon verifies it with the pinned server ML key before DH/KEM or CTX opening. Registration decoding restores sequence one and the pinned server identifier; those values are implicit metadata, rather than extra signed wire fields. Both ordered ML hashes enter the same logical AD value used for initial and subsequent CTX records. The old extracted classical AD constructor is wrapped by `mldsa_ad` to interpret the current AD281/CTX357 layout; this is not a migration or byte-refinement proof of the historical global AD153 extraction. The current exact core AD-slot refinement remains a separate result.

The two server invocations have distinct public assigned-ID labels. Their scheduling can reverse their admission order, so those labels abstract routing identity rather than the source's monotonic allocation order. Counter exhaustion, wrapping, collisions and allocation failure are not modeled. Pure private root calculations are also moved across the replay check and root-input construction is grouped before the beacon's pinned-Ed gate. No primitive-call order, timing, failure or resource theorem follows from this abstraction.

## Principals and replay state

The beacon pins both server public keys. The server accepts a beacon's ML key from its request and has no enrollment pin binding that key to the claimed Ed25519 identity. Attacker-owned beacon keys and registrations remain admissible. The positive request-origin query therefore selects the exact unrevealed honest ML key after admission, without adding an enrollment or authorization check to the protocol.

An attacker who recovers a classical Ed25519 secret may present that identity with an attacker-owned ML key; the owned-registration witness reconstructs this case. A session with that self-presented ML key is not an authenticated session of the protected honest ML principal, even when its Ed25519 identity bytes are the same. Honest-recipient secrecy challenges and correspondence events retain this distinction explicitly; neither an Ed-only application routing guarantee nor an enrollment binding follows from the extra signature.

The replay identifier stays exactly the Ed25519 identity and one-time X25519 public key, as in `VerifiedInitKex::registration_id`. ML keys, transcript hashes, prekeys and ML-KEM keys do not become new identifier fields. Different ML keys attached to the same classical identity/one-time pair therefore share the same consumed identifier. A monotone table retains the consumed identifiers for the one server owner. The two callers acquire a single token on a private channel before checking membership; an absent identifier is inserted before releasing the token, while a present identifier takes the rejection branch. No failing crypto calculation occurs while the token is held. Initial token delivery runs in parallel with the callers, and release runs in parallel with acceptance/publication or rejection, so the final invocation can complete even when no later caller receives the token. The network attacker never learns the private channel and cannot forge admission or release. Source acceptance consumes the identifier irreversibly, including when response construction later fails; failed builds are outside this trace, so it does not establish that failure property. No broader injective-registration or record-replay theorem should be inferred from a bounded rejection witness or from the signature algebra.

The replay witness uses a passive private monitor to distinguish the two actual invocations during trace reconstruction. The real post-insertion branch sends its assigned invocation label and actual registration ID on one private observation channel; the real table-present branch sends that pair and the acquired token on another. Each token release carries a nonrecursive pair of the releasing invocation's label and actual ID. Every lock input accepts any token value; its contents affect only witness bookkeeping. The monitor emits `JointReplayRejected` only after matching equal actual IDs, different invocation labels and the token released by the observed accepting invocation. It therefore witnesses one real consumption and token handoff followed by the other invocation's rejection, rather than accepting a Horn derivation that reuses one input. All observation sends run in parallel with token release and the unchanged protocol continuation. The monitor cannot forge admission, change the replay identifier, block publication or reject an otherwise admissible registration. Erasing the monitor, observations and witness event, and mapping token payloads to one token, preserves the protocol's public behavior and security-query events. It reuses the existing assigned-ID label and adds no field to signed transcripts or encrypted plaintexts. No additional security axiom or solver-precision declaration is used.

## Primitive and attacker assumptions

ML-DSA verification is an explicit ideal unforgeability assumption for unrevealed signing keys. No ML-DSA algorithm or primitive-security theorem is being proved, and no unfinished VCVio theorem is used. Signatures, public keys, contexts and transcript digests are public; they must not carry proof-only roots, session secrets or record plaintexts.

The existing primitive theory also idealizes Ed25519 verification, DH correctness, HKDF, collision-free symbolic BLAKE2b and authenticated encryption/CTX. Its free `mlkem_shared_secret(public_key, coins)` constructor assumes public-key binding, or strong shared-secret collision resistance across different ML-KEM keys, beyond generic IND-CCA. A joint result using that theory inherits this existing assumption; adding ML-DSA does not remove it or turn it into a derived fact.

The classical-key-recovery scenario exposes secrets behind Ed25519 and X25519 public keys while leaving independent protected ML-DSA and ML-KEM secrets opaque. Recovery functions are public throughout the active network execution, rather than available only after traffic capture. These symbolic operations represent a threat interface, not a quantum machine, QPT reduction or QROM theorem. The earlier authentication profile's signing-key compromise witnesses remain separate. The joint profile makes no secrecy or origin claim after recovery of a relevant protected ML secret.

## Checked claims and controls

The primary roster has three challenge-secrecy queries, five correspondences and six reachability witnesses. The correspondences concern request provenance under the exact protected beacon ML key; response provenance under the pinned server ML key and retained Init digest; agreement on the unsigned response, AD, assigned identifier, initial plaintext and independently derived root at completion; and the two directional application records with their root, AD, sequence, sender, receiver and plaintext. All five are noninjective correspondences. The three secrecy rows ask whether the attacker can deduce fixed private canaries used as the initial payload and the two application payloads; they are not strong-secrecy or observational-equivalence claims.

The six reachability rows reconstruct honest completion and both record directions, attacker-owned registration, bounded registration replay rejection, and the classical-key recovery capability. Each has its own reconstructed execution; they need not all occur in the same two-attempt schedule. They are execution witnesses, rather than security correspondences. Honest ML-key selection affects query instrumentation and challenge payload choice after generic admission; it is not a registration acceptance guard.

The 19 new metadata rows distinguish eight security results, four witness results, two limitation results and five negative controls. Honest completion, both record directions and the two-invocation replay are witness rows. Allowed owned-ML/recovered-Ed registration and classical-key recovery are limitation rows; their reachable traces are not counted as additional security guarantees.

The five negative controls execute modified models, not synthetic expected-output fixtures. Bypassing request ML verification reconstructs both a protected-key request-origin failure and disclosure of the initial canary: the attacker can attach the protected public ML key to classical/KEM fields it controls. Bypassing response ML verification reconstructs a pinned-server response-origin failure, a completion-agreement failure and disclosure of the beacon-to-server canary: with the already enabled classical-recovery capability, the attacker supplies an otherwise valid response under a known root. Each control changes one verifier binding and retains the original query, KEX, CTX checks and attacker theory.

The earlier focused authentication profile's role/context/request-digest and AD-hash separation controls remain separate results, not additional joint queries. The joint trace excludes cross-owner token transfer, failed builds, arbitrary record replay/scheduling, cache capacity, rollback, forward-secrecy and post-compromise guarantees.

## Source and validation boundary

The checked deterministic transcript extraction and its 14 refinement facts identify the core byte constructors, their literals, parts order and AD overwrite. They do not constitute a semantic Rust-to-ProVerif compiler or a complete adapter proof. Logical decoded constructors abstract CBOR bytes; parser correctness, hash streaming, native primitive behavior and failures, actual signing histories and the correspondence of source execution to model traces remain separate obligations.

This bounded profile does not migrate every historical ProVerif scenario or the approximately 115 handwritten Lean modules and global extraction that retain AD153/CTX229. Existing legacy source-security and inventory pins remain visible. No global proof gate is claimed.

The broader source-fidelity target passes 30 of 31 tests; the remaining failure is the preserved legacy `beacon.rs` provenance digest. The reviewed inventory retains the same 33 historical source/proof digest mismatches and still fails on the first of those pins. Only reviewed files changed by this increment and its five new proof/validation files receive updated inventory entries; those updates do not close the older migration obligations.
