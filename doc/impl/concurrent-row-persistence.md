# Concurrent persistence validation and measurement

This extension builds on `codex/row-persistence` at `ad3382627df2f3fbebe1954393ad80cf7e60027c`. The existing full-state, row and cached-row APIs remain available. Beaconcrypt remains independent of any particular database. The work adds concurrent workload measurement and limited integration acceptance against Mythic's custom crypto provider feature; it does not change protocol proofs.

Correctness takes precedence over performance. Every offered callback has an immutable identity, original arrival time, peer, direction and payload size. Successful runs must account for every callback, preserve each peer's order, authenticate every output, and verify exact plaintext and sequence numbers. Errors, panics, storage conflicts, incomplete work or expiration of the drain budget fail the run. Native operations are never automatically retried, and a latency deadline does not imply that a durable mutation was cancelled.

## Ownership and workload

The full-state arm uses one resident server owner and one database connection because opening independent snapshot owners would fence earlier owners. Row and cached-row arms use stable peer ownership across up to eight workers, each with its own connection to the same database. All arms use the same logical feeder lanes and aggregate queue limits: 256 waiting callbacks and 16 MiB of waiting plaintext. Queued capacity excludes work already in service. Row queues partition that budget by owner; the snapshot owner shares its budget among feeder lanes. This ownership difference is part of the API comparison and must accompany any performance claim.

Schedules are fixed before execution and use absolute arrivals, with no catch-up rescheduling. A blocked feeder retains the original arrival times of its remaining callbacks. Measurements separate scheduling lag, admission backpressure, queue waiting, native service and completed response latency. Pre-generation and client verification are excluded from the measured phase, with a completion barrier preventing verification on one lane from interfering with another lane's measured operations. The retained request/output allocation has a separate bound from the queue budget.

Queue waiting includes waiting for the serial owner. The field `owner_wait_ns` measures dispatch overhead between dequeue and the native call; it is not an owner-mutex contention measurement. Report checkpoints are flushed and synchronized to storage before the next trial is prepared, so dirty report pages are not deliberately carried into the next measured trial.

The planned primary matrix uses SQLite WAL with FULL synchronization and PostgreSQL over localhost TCP, registered populations of 1, 100 and 1,000, up to 32 active peers, three balanced trials and all three persistence arms. Each periodic schedule offers work for two seconds; per-peer periods are 1,000, 100, 10 and 5 ms. Each period has small-message and mixed-message cases. Additional cases cover 64 KiB messages at a one-second period, simultaneous heterogeneous peer cadences, and bursts of 64, 256 and 512 messages of exactly 512,000 bytes (32.768, 131.072 and 262.144 decimal MB). Mixed workloads make every sixteenth send/receive pair large; short slow-rate cases may contain only small messages, so the separate regular-large case ensures larger periodic traffic is exercised. The completion deadline is one second; the finite drain allowance is ten minutes. No timings will be selected on the basis of favorable results.

The raw report records actual worker and database-client-call overlap. Overlapping calls include lock, network and commit waiting; they do not demonstrate simultaneous database CPU execution or physical writes. Logical bytes and query exchanges are not physical disk or network traffic. Saturated runs must report deadline misses, queue backlog and response latency alongside throughput rather than describing native service time alone as application latency.

The first concurrent SQLite collection exposed writer starvation beyond its original five-second busy timeout. The follow-up uses a 600-second SQLite busy timeout for all three arms, matching the collection's drain allowance. Lock waiting remains inside measured response latency; the one-second completion deadline, offered workload and native no-retry policy are unchanged. The failed attempt is preserved separately. PostgreSQL settings and implementation are unchanged, so its already completed measurements are retained with their original source and binary provenance.

## Correctness evidence

Validation covers checked schedule arithmetic and allocation limits, property-based schedule and timing invariants, queue byte/job bounds, concurrent feeder accounting and peer order, failure and cancellation paths, duplex native ratchets on every arm, and malformed report rejection. Existing native, binding and database persistence checks remain relevant to the unchanged library implementation. Required mutation testing must identify its exact source catalog; example-only code is not implicitly covered by a library-only mutation run.

The limited Mythic acceptance uses the pinned `crypto-shim` source at `1c66dacec77fe2262fcb3f22eb0260534239562b` and a fresh-campaign fixture adapted explicitly to the current Beaconcrypt registration format, ML-DSA verification key and snapshot version. It exercises real HTTP, AMQP, provider and PostgreSQL paths, concurrent clients, checkpoint output gating, atomic state/result rollback, request replay, provider restart and exact output recovery. This fixture uses the provider's existing full-state storage contract. It is not evidence of a production Mythic migration to row persistence, nor an implicit conversion of existing campaigns.

## Collection and publication

Implementation, tests and review finish before the benchmark executable and collection plan are frozen. Collection begins only after all other coordination leases and owned test services have ended, followed by a quiet-VM observation window and an exclusive benchmark reservation. Host scheduling noise from the physical machine's Kubernetes workloads is recorded rather than assumed absent. All attempts, interference decisions, source and binary pins, environment settings, raw reports and analysis inputs are retained. The existing sequential results remain historical evidence and are not overwritten.

The user's empty Forgejo repositories are seeded with the corresponding upstream history and reviewed branches without force pushes. Every new commit includes `Co-authored-by: Codex <codex@openai.com>`. Beaconcrypt work remains on the separate `codex/concurrent-persistence` worktree branch; the owner checkout is untouched.
