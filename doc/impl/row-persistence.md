# Database-independent row persistence

This implementation starts from `codex/mldsa65-transcript` at `278204b921ae31a3e900cf21f690184173e531f5` and lives on `codex/row-persistence`. The library exposes an application-owned transaction interface over opaque keys and values. It neither selects a database nor includes a database driver in its normal dependency graph.

`RowServer` retains only immutable server identity material between calls. Ordinary sends and receives load one peer, run the existing protocol implementation, and replace that peer only when its state changes. Each peer contains both ratchet directions, the bounded skipped-key cache, and the authenticated peer identities. The independent row generation also advances when a cached receive consumes a key without moving the receive frontier. Handles opened by different workers coordinate through the application's authoritative database.

Registration first commits a permanent consumed-registration marker, then commits the allocator and new peer together. Failure during response construction or the second transaction retains the marker. All operation output remains confined until the final durable transaction succeeds. An uncertain commit suppresses output and discards tentative state; the next call reads current database state.

The Rust API has corresponding C, native Go and Python bindings. The SQLite adapter is example code, with a development-only dependency and file-backed integration tests. The Go WASM backend reports row persistence as unsupported. Existing snapshot APIs remain available; automatic snapshot migration is not implemented. The maintained contract and examples are in [the persistence reference](../persistence.md).

Application transaction composition adds callback-scoped sessions for opaque application rows and zero or one native transition. Applications can check authorization and request identity, recover a stored response, or commit a newly encoded response with the peer update. Registration composition preserves separate acceptance and completion commits, with application-owned incomplete receipts and private pending native material. The library defines no request IDs, response formats, inbox/outbox schema, retention policy, or database driver. The [integration design](row-delivery-design.md) documents the implemented boundary and the atomic batch storage capability a future Mythic provider migration needs.

## Validation

All 418 runtime library and integration tests passed, including 17 file-backed row tests and the composition unit tests. This covers row access counts, restart, independent peer records, cached receives, malformed rows, authentication rejection, replay, concurrent workers and registrations, transaction rollback, uncertain commit, callback misuse, and output suppression. Concurrent duplicate requests recover one exact durable receipt with one native receive, and an authenticated peer mismatch rolls back application and ratchet changes before a valid retry. Two additional C bridge tests verify sticky recursion and argument failures before native access. All 93 Python tests passed, including SQLite-backed composition and recovery tests. The complete Go race suite and the no-CGO unsupported-path test passed. Server-only and beacon-only feature checks, workspace Clippy with all targets and features, doctests, formatting, and release benchmark compilation also passed. The SQLite example was exercised against a persistent file during the initial draft.

Binding validation caught and fixed missing callback declarations in the generated C header and a Go buffer-copy helper that converted present empty values into absent `nil` slices. The final C declarations use explicit callback function pointers, and the shared Go copier preserves empty values. C and Go session bridges reject recursive calls and prevent subsequent I/O after a latched misuse error.

Validation exposed an unrelated repeated-build cost: the build script rewrote `bindings.h` even when its final content was unchanged. It now renders and deduplicates the header in memory and writes only changed bytes. The generated header's bytes and modification time remained unchanged across Clippy and the subsequent test build. All 404 runtime tests also passed under nextest, with none skipped; mutation runs use its fail-fast execution to reduce wasted work on the shared host.

The owner explicitly excluded proof work. No Lean, ProVerif, extraction, or proof inventory artifacts were changed. The shared immutable identity refactor changes source spellings expected by five existing proof source-fidelity checks: `endpoint_frame_context_mutation_matrix_is_complete_and_rejected`, `free_schedule_rust_fidelity_annotations_are_exact`, `mldsa_transcript_source_and_model_mutations_are_rejected`, `production_manifest_symbolic_model_and_adapters_are_exact`, and `proverif_verdict_classes_cover_every_checker_and_profile`. Consequently, an unfiltered `cargo test --workspace --locked` does not pass those proof checks. Runtime and mutation validation exclude the two proof-only integration binaries, `proverif_transcript_fidelity` and `mldsa_joint_fidelity`; this is not a claim of refreshed proof correspondence.

The actual WASI guest suite passed all 28 tests, including its isolated allocation-failure probe. Its complete configured mutation suite passed: 159 mutants, 147 caught and 12 unviable, with no missed cases or timeouts.

Native mutation validation is being completed under `/tmp/bc-coord` resource leases. The command includes the complete configured native runtime mutation catalog, with all runtime library and integration tests; feature-gated C/Python adapters retain the repository's binding-test treatment. Cold-build timeouts from an interrupted, overloaded run are rerun, not treated as killed mutants. Final native counts and the coordinated benchmark results will be recorded after completion.
