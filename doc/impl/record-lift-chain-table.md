# Persistent source-coordinate table

`PqxdhRecordLiftChainTable` constructs the operational interpretation that the preceding `PqxdhRecordLiftChainState` module left open for individual derivation callbacks. Its twenty-two guarded theorems use the existing generic `PqxdhRecordLiftLazyTable` with one complete 76-byte reply per request coordinate. This is a component of R3, not the evolving-chain security theorem or a replacement of publicly evaluable HKDF by a random function. No primitive or deployment contract is added or assumed.

A coordinate is the slot, direction and source's last derived sequence. False means Server-to-Beacon and starts at one, because the registration response has already consumed sequence one; true means Beacon-to-Server and starts at zero. A table entry at position `p` supplies the derivation for record `p + 1`. `Seeds` is an arbitrary fixed interpretation of each slot's two seed values during a callback; the module neither samples those seeds nor asserts their distribution or permits the environment to inspect them. The dynamic world must still instantiate this interpretation from its actual lazy installations.

`Available table coordinate` holds at a directional seed or above that seed when the predecessor reply is present. `Closed table` requires every stored request coordinate to be available. `chain` reads the appropriate seed at the directional start and the predecessor reply's second 32 bytes at later coordinates. Its explicit zero fallback only makes the function total; availability excludes that fallback at every reference covered by the theorems. Neither predicate assumes fresh bytes, distinct keys, a source-origin security conclusion or an injective interpretation. `Available` is separate from the counter-alignment and admitted-window invariants proved in `PqxdhRecordLiftChainState` and `PqxdhFirstRecordReplay`.

The interpretation lemmas `chain_mono`, `available_mono`, `previous_advance`, `successor_available` and `successor_chain` establish stability under cache growth and identify each successor with the second-32 projection of the same stored full76 reply. `closed_empty`, `closed_record` and `closed_lookup` prove closure from the empty table and through the actual lazy hit and miss branches. A repeated lookup retains its entire old reply. Different coordinates may interpret to the same bytes; no theorem assumes away or bounds those aliases.

`pending_mono` and `send_pending_mono` preserve the complete existing native KDF request when the table grows, including both original chains, rollback entry, source control, context and staged slots. `receive_lookup` and `send_lookup` then identify the actual source continuation on the decoded full76 reply with the coordinate continuation under the enlarged interpretation. The successor chain, message key and nonce all come from that one reply through `RawCtxFreshChainCut.decoded_parts`: second32, first32 and final12 respectively. `receive_continuation` and `send_continuation` preserve the complete reply, table, counters and every continuation as equal computations, so their evaluated distributions are equal too. These equations realize a supplied table callback; they do not claim that real deterministic HKDF returns independent values at byte-aliasing coordinates.

The operational availability predicates are generic in cached payload type. `begin_available` follows every actual receive admission branch. `resume_available` follows every skip, target and rejection branch with its supplied successor; `receive_lookup_available` discharges that successor premise using the supported table lookup and preserves the closed table and complete effect. `send_begin_available` obtains its request from actual source admission, and `send_lookup_available` preserves closure and both available chains in the advanced kernel before sealing. `seeds_available` initializes both source kernels, and `seeds_erasure` discharges the former functional seed bindings against the complete production seed kernels. Source counter exhaustion and validation decisions are inherited unchanged; coordinates do not control those decisions.

`rollback_lookup` combines actual failed-opening rollback with the persistent table. After any supported first lookup and arbitrary adaptive table work, restoring the source entry kernel and querying the same coordinate returns the original full76 reply, preserves the final table, increments logical lookups once and performs no fresh draw. This concerns failed operations within one execution. The existing source retry-admission theorem supplies identical admission after rollback; this module does not yet identify the complete raw retry trace with a dynamic-world execution.

Accounting uses the existing `PqxdhRecordLiftLazyTable.step_facts`: each lookup increments `lookups` once and increments `draws` exactly when the old cache lacks that coordinate. A draw denotes one complete full76 sampling operation, not a byte-coin bill or a free primitive call. The complete state is retained in the continuation equalities and rollback theorem. The source/global derivation bound, uniform-byte and base costs, Extract and HMAC bills and all reduction losses remain to be composed; no ambient work is declared free.

The remaining join must place this private table outside operation rollback in the dynamic record world, establish its reachable-state invariant through successful publication and subsequent commands, prove handle-to-slot provenance with ghost erasure, and add coordinate attribution and interpretation for skipped material. This module retains the actual cached material payloads in its callback equations; it does not yet prove their table provenance. Public HKDF evaluations remain real. The full private table contains predecessor outputs and therefore target-chain bytes, so it cannot simply be passed as the public context of a secret-input reduction. Selected-cut input distributions, masked interpreter simulation, alias/collision/refusal terms, the ordered Extract/HMAC hybrids, `chain_lift` and the CTX/AEAD lift remain separate obligations. Registration erasure stays in the CE lane.
