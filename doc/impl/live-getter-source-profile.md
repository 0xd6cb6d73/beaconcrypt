# Live getters, erasure and the approved observation profile

This audit connects the actual public Rust secret getters to the existing computational current-field projections. Its source basis is `34122c10635ce334fe6260ab05cd315ac1aa6a7e`, including the initial sequence-one fix. It adds no adversarial capability, primitive assumption, ProVerif restriction, solver verdict or computational security bound. The maintained checker compares every getter/phase case and pins the complete reviewed source files. The lifetime argument below is a reviewed source argument; the checker does not compile Rust or mechanize that argument.

The later owner decisions in [the October5 handoff, section 2](handover/pause-2026-10-05/README.md) govern the advertised deployment profile: attacker access to running code is excluded, the ideal Server has independent uniform keys and never discloses keys or secret state, and the optional P7 logical-compromise extension has no owner approval. Public Rust methods are host capabilities; they are not automatically network attacker oracles. The original broad proof brief and richer reusable component interfaces do not override this scope. Codec internals, snapshots, persistence, restoration, physical erasure and native primitive internals remain external or excluded as previously agreed.

`Server::identity_sk` always returns its current identity secret-key reference. These five complete method bodies are in [beacon.rs](../../beaconcrypt/src/beacon.rs) and [server.rs](../../beaconcrypt/src/server.rs). `get_shared_secret` returns an opaque `RegistrationOutput`, not the bytes of the root secret. The C and Python adapters expose no corresponding direct secret-getter entry point; this statement is limited to those direct getters and does not characterize excluded state-export interfaces. The identity row is a field-availability correspondence, not an equality between a 32-byte seed and a 64-byte secret-key representation. Rust returns the primitive's `crypto_sign::SecretKey`; `PqxdhRegistrationJointLiveRead.Value.identity` carries `PqxdhJointIdentity.IdentitySeed`. The existing `PqxdhJointIdentity.SourceWiring` relates a supplied `secretOfSeed` representation to public conversion, signing, verification and converted DH. It does not assert literal byte equality or furnish an inverse secret-key-to-seed reveal simulator. This stage supplies neither. No such adversary reveal is enabled in the approved deployment experiment. The KEM secret type is likewise supplied by the existing primitive implementation contract; the phase table does not prove its representation internals.

## Why terminal reads cannot recover the registration secrets

`BeaconState` stores the prekey and KEM pair only in `Fresh`, `FreshWithCoins` and `InitSent`; it stores the one-time pair only in the last two of these. `Established` contains the verified control, associated data and ratchet. `Aborted` contains only the aborted control. Identity is outside the phase enum, so changing phase intentionally leaves it live.

For an active `InitSent` call, `finish_registration` stages the complete operation and then either assigns `Established`, or calls `abort_registration` on a failed stage or binding comparison. Both replace the phase and remove all three registration secret fields. A finish attempted from any other phase returns without changing it; in particular a call from `Fresh` is not an erasure operation. The successful response contains the application suffix, never a saved root or these secret fields. The existing `PqxdhRegistrationJointOwnership.finish_fields` and `owner_fields` prove the corresponding native identity/KEM behavior, including the complete supported callback state. `JointLiveRead.entry_value`, `read_source`, `read_projection` and `erased_client` connect current native fields to the exact service reply/poststate and prove that erased KEM reads perform no historical private-pool lookup.

The remaining Beacon host methods do not turn an existing terminal object back into a fresh object. `new_onetime_keypair` can replace a coin in `FreshWithCoins` or add it to `Fresh`; it generates before rejecting other phases, so a rejected call can still incur primitive work. `delete_onetime_keypair` maps `FreshWithCoins` to `Fresh`, `InitSent` to `Aborted`, and preserves every other phase. `delete_pq_keypair` aborts fresh/active registration phases and leaves terminal phases unchanged. Bundle publication accepts only the two fresh phases. Record operations require `Established` and operate on its ratchet. Constructing a new Beacon creates a different object and fresh identity. This argument concerns returned states of sequential host calls; it makes no claim about concurrent unsafe memory access or interruption inside a method.

Therefore every later direct prekey, one-time and KEM getter on the same terminal object returns `None`. This is logical field unavailability, not forward secrecy by itself. A value copied by an authorized caller before deletion or replacement is still known to that caller. No proof deletes prior observations, claims physical memory erasure, or derives a security advantage from these getter equations. Identity compromise after establishment is not proved safe here.

## Roots, chains and skipped keys have different availability

| Material | Actual source location and lifetime | Host/network boundary | Existing proof meaning |
| --- | --- | --- | --- |
| Server root | `RegistrationOutput.derived_secret`, private to the crate, after successful accept until the by-value token is built or dropped | No public root getter; build consumes its token even on failure | Private pending data can appear in source correspondence. A ghost old root is not a live reveal oracle. |
| Beacon root | Local `derived_secret` inside the staged finish, before constructing the initial ratchet | No between-call getter and no established root field | Internal KDF input at its actual point of use, not an after-finish reveal |
| Current send/receive chains | Installed `RatchetManager` kernel, selected by the actual Server peer or established Beacon | Native adapter accessors are internal; public `ratchet_status` returns only counters/cache length | `RawCtxProtocolReveals` defines an explicit richer logical current-field read, not a network API |
| Skipped key/nonce material | Actual present cache slot, until consumption/removal | No direct public adapter getter in this profile | `RawCtxProtocolReveals.skipped_exact` is the exact total extracted guarded lookup; missing or invalid slots return `None` |
| Historical primitive pools | Private proof interpreter histories | Not a source field read | Ownership/projection theorems do not expose an erased slot merely because the interpreter retains it |
| Plaintext | Actual successful finish/receive reply to the trusted application | Public in the stronger origin comparison; private in the approved application-secrecy comparison | Origin with public optional plaintext does not imply confidentiality of that plaintext |

An established Server peer contains its public identity and ratchet, not the old root. `KexDerivedSecret` is a 32-byte typed secret object, but that type's byte-view methods do not make the private `RegistrationOutput` field public. The public opaque pending token can be delayed or moved as already modeled. A root in a private theorem event or retained analysis transcript does not create a source endpoint. Conversely, the token still contains its real root before consumption; describing all roots as erased immediately after accept would be false.

State-update and snapshot APIs are excluded by the owner. They must not be used to infer that a current-chain or root reveal is admitted here, nor may this table be cited as an audit of their security. The complete files are pinned because they also contain the in-scope getters; no theorem about excluded methods follows from those pins.

These last three component rows are available for consuming proofs; their existence does not add compromise actions to the first four profiles. In particular, no P7 result or post-compromise recovery claim is advertised. `RawCtxSelectedMessageReveals.source_admitted` preserves the actual optional reply. Its separate `source_stopped` comparison stops only after the existing source freshness event has become false; it does not substitute a fake `None` and keep serving the attacker.

If current-chain disclosure is studied in a separately authorized experiment, the public actual KDF computes every descendant. Retained skipped material and prior copies remain relevant. Failed receive attempts preserve their entry state, while failed sends can advance allocation without publication, so timing must count attempts rather than successful events. The existing reveal history counts all attempts and `known_length` charges at most one known 32-byte candidate per optional read, plus prior candidates. Identity and KEM reads are accounted separately in the existing service ledgers. This audit introduces no global query cap and treats no ambient sampler, public evaluation, failed call or copied observation as free.

## Maintained finite check and remaining boundary

`beaconcrypt-core/proofs/source/getter-profile.py` reads all five complete Rust getter bodies, accepts only their reviewed read-only projection grammar, and compares the 20 Beacon presence cases against the complete existing Lean `value`, `localValue` and `activeKey` definitions. It separately checks the live Server identity projection. Exact hashes bind seven production adapter files and seven existing Lean interface/contract files, covering the surrounding lifetime, visibility and freshness argument. Nine regression tests reject wrong fields, changed phases, mutable or duplicate getters, extra effects, changed Lean projections and drift in every pinned file. The check runs from the trust-boundary inventory gate; it adds no ProVerif target or verdict-class entry.

The established result is finite field availability and the reviewed adapter/lifetime mapping under existing contracts. Compiler correctness, primitive secret representations and physical storage remain external; source secrecy still requires the computational reductions and common experiment. Existing source-lifted secrecy remains within the trusted-application bounded profile. The public optional-plaintext computational challenge/freshness interface and global computational composition remain separate open consumers. These facts do not require or justify expanding the approved symbolic threat model.
