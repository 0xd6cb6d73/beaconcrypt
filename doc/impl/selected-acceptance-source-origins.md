# Actual acceptance and earlier source production

`RawCtxSelectedAcceptanceOrigins` classifies an actual accepted raw record using the concrete receive compiler and the complete adaptive production audit. It no longer takes `SelectedFresh` as a premise. The resulting classification is an operational step toward the global authentication reduction; it does not claim that matching key bytes or ciphertext fields identifies a cryptographic session.

`raw_cases` starts with support in the monitored, actual mixed-owner raw call and an actual successful optional plaintext reply. The existing raw and receive consumers recover the exact decoded frame, validation result, reached cached/future opening continuation, and material returned by the actual getter. The conclusion has three alternatives: the getter returned known material; the ordinary selected-key integrity observer has won; or the actual selected opening matched a prior successful CTX seal in the attempt-time history. The known-material branch remains explicit and permits byte aliases with selected material. The code neither substitutes a recovered plaintext into an adversarial target nor assumes that an accepted record is a fresh tuple.

In the selected branch, the observer's target is packed from the exact reached nonce, retained AD, sequence, decoded sender and ciphertext payload. The actual challenger-produced plaintext remains the opening reply. If no full-tuple match exists in the saved history, that exact accepted attempt supplies the ordinary observer's witness. Otherwise `Matching` retains the exact raw bytes, decoder result, validation, reached getter, returned plaintext and observer update, together with a matching entry. This classification makes no claim that a matched entry has been successfully serialized, returned by an API, or published by the required peer.

`family_beacon_cases` and `family_server_cases` consume the existing concrete role receipt theorems. The Beacon conclusion retains its actual established phase and exact reinstallation; the Server conclusion retains raw routing, the AD lookup, the repeated peer lookup and the exact peer publication. Both preserve the original indexed family update. They give the same exhaustive classification at the reached owner, without a selected-slot assumption and without equating claimed routing IDs with server-assigned IDs.

The classification also consumes an actual complete adaptive schedule, rather than an assumed source history. `current_record` starts from support in `RawCtxSelectedProductionAudit.client` and an exact position in its generated record list. The production-audit theorem supplies that position's actual source-call support. It also proves that every seal available before this call belongs to the retained initial prefix or was produced by a strictly earlier source query. This chronology is by list position, so duplicate queries and repeated equal outputs do not collapse into a single occurrence.

`trace_won` preserves an ordinary integrity winner through all later actual source-query records. It uses the histories saved at the original attempts; later sealing cannot retroactively turn a fresh earlier attempt into a replay. `audited_beacon_cases` and `audited_server_cases` combine these facts: an actual accepted indexed role query has either reached known material, yielded the final ordinary observer winner, or matched an entry whose earlier source production is established by the same execution. They retain the complete original role publication and actual decrypted result.

The module adds no oracle call, random sample, or new reduction budget. The audit's exact query equivalence and source-position bound remain those proved in `RawCtxSelectedProductionAudit`. The ordinary authentication observer already accounts for every adaptive raw attempt, including failures and repeated targets. Consequently this attribution does not introduce another raw-attempt selection factor. Finite key/session selection and any required record-origin selection still need actual constructed reductions. Private KDF derivations, known-key work, setup and initializer costs retain their separate bounds.

The distinction between inner production and protocol origin remains material. A source production witness retains the actual optional writer result, including `None`. The normal-return Vec serializer audit in [the seal receipt guide](selected-seal-production-receipts.md) identifies a precise native functional contract that may discharge that branch for the production adapter, but the generic writer theorem remains conditional. Matching full CTX tuples does not identify installation, session, direction, API target, receiver, or the corrected eleven-field registration session. The source installation/lineage consumers, same-key aliases and permitted disclosures must establish those additional coordinates. An arbitrary nonempty initial receipt prefix also requires its actual setup provenance.

The maintained auxiliary `PS1PrimitiveOpen ⇒ PS1PrimitiveSeal OR PS1PrimitiveReveal` query asks only for inner production under the actual key and is deliberately noninjective. Its endpoint-origin strengthening is a false control. The main `MessageReceived ⇒ MessageSent` and corrected registration record correspondences require successful publication and their particular protocol-origin fields, followed by the separate source consumption argument for injectivity. The present classification is compatible with those scopes; it does not identify them. Current initial registration still requires sequence one, and the independent claimed/assigned labels in the general projected queries remain independent.

The selected-key uniform distribution in the complete context, the retained private KDF-table to real fixed-HKDF hop, exact known-key probe/alias and disclosure accounting, source nonce-risk term and global selection reductions remain explicit consuming obligations. Public fixed HKDF evaluations remain real. No primitive implementation proof, custom axiom, snapshot or persistence premise is introduced.
