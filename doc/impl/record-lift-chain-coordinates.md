# Record-lift source coordinate invariants

`PqxdhRecordLiftChainCoordinates` proves that the complete local source drivers preserve the private coordinates attached to live chains and skipped record material. It starts from the actual post-registration Server and Beacon seed constructors. Every supported receive and send execution retains a certificate consisting of valid source replay/cache control, equality between both chain positions and the source counters, and the exact slot, direction and source sequence attached to every retained skipped material. These are operational source invariants, not a secrecy or independence claim.

The module uses the actual `PqxdhRecordLiftChainCompiler.receive` and `.send` drivers. Their lookup, opening and sealing callbacks may carry arbitrary primitive state and return arbitrary supported typed responses. The theorems retain the complete result and primitive/table poststate in their support premises. They place no functional, distributional, freshness or security requirement on these callbacks. The lookup table's growth and byte interpretation are handled by the companion compiler and table modules; this module neither resets the table on failure nor replaces callback results.

## Coordinate origins and source advancement

`ReceiveCoordinates` says that the send coordinate is unchanged and the receive coordinate is the original receive coordinate advanced by a number between zero and 51. `finish_coordinates` derives this from actual cached publication, future publication and failed-opening rollback. The future bound follows from the source cache capacity and the admitted skipped window: at most 50 skipped steps followed by one target step. Cached consumption and failed opening advance neither coordinate. `receive_coordinates` lifts this through the complete decreasing-rank source driver, and `admitted_receive_coordinates` supplies its tracking and admission facts from actual admission for an arbitrary requested sequence.

`SendCoordinates` says that the receive coordinate and complete skipped-material array are unchanged, while the send coordinate advances by zero or one. `send_coordinates` derives this from the actual exhausted/requested source branches and the complete sealing continuation. Exhaustion leaves the kernel unchanged. A requested send advances before sealing, so a sealing callback that returns no ciphertext retains that advancement. `admitted_send_coordinates` starts at actual source admission. `receive_origins` and `send_origins` project the exact installed slot and direction preservation needed by the dynamic compiler; these origins are never recovered by comparing key bytes.

## Counter alignment and skipped materials

`Aligned` is the existing source invariant equating each live chain position with its actual source counter. `resume_future_send` reads the actual source future-opening validator, which checks that the committed sender counter equals the entry sender counter. `begin_future_send` proves that admission itself emits no future opening before a derivation. `finish_aligned` combines that check with existing cached-consumption and future-publication results. Cached consumption preserves both counters, a successful future opening installs its actual advanced receive counter, and failed opening restores the complete original kernel. Natural coordinate positions are tied to bounded source counters; no modular wraparound is introduced.

A skipped material is `Attributed` when its slot and direction agree with the receive origin and its recorded source sequence is its own position plus one. A cache entry retains its earlier position as the live receive chain advances. `receive_invariants` propagates this through the actual recursive driver using the source request-counter alignment and exact staged-slot writes. At publication it reuses the complete cached-array and future-array property theorems; consumed entries disappear without changing the attribution of retained entries. `attributed_reanchor` shows that the unchanged slot and direction allow the final live receive coordinate to act as the cache anchor. `admitted_receive_invariants` therefore returns both aligned counters and attributed skipped material at the resulting kernel. `send_invariants` and `admitted_send_invariants` prove the same properties through actual sends, whose receive array and receive coordinate remain unchanged.

## Certificate and seed boundary

`Certified` joins the existing `control.ValidControl` predicate with aligned live chains and attributed skipped material. The control predicate records cache capacity, positive cached sequences, cached sequences at or below the receive counter, and uniqueness. `receive_certified` reuses the existing source rejection, acceptance and replay-consumption theorem to preserve this certificate after every supported local receive. Rejection restores the entry kernel; acceptance retains valid control and the coordinate invariants above. `send_certified` uses actual source advancement to show that the receive counter and cache control stay unchanged, and consequently preserves the same certificate.

`seeds_certified` establishes the certificate for the complete actual labeled seed constructors in both orientations. Server starts with the Server-to-Beacon coordinate at position one and Beacon-to-Server at position zero; Beacon has those same coordinates in its opposite kernel fields. Both caches are empty. This reuses the extracted `from_counters` structural validity theorem and the already proved material-table seed correspondence. It does not create a new independently sampled seed family or assert that a supplied kernel was installed by a particular dynamic handle.

## Contracts, accounting and remaining join

No cryptographic contract or new assumption is used. The only logical axioms are the three permitted Lean built-ins, checked by 18 exact guards. The theorem premises are ordinary local source invariants, supplied at both seed constructors and preserved by the actual send and receive drivers. The receiving theorems apply to the local receive operation after a caller supplies the target and context; raw parsing, peer lookup, owner routing and dynamic installation remain in the global compiler.

The 51 bound counts coordinate advancement along one admitted receive, including its target. It does not claim a new global oracle bound or make callback work free. The existing companion driver bounds and WorldBudget accounting remain responsible for the actual KDF, hash, uniform, AEAD and outer-query bills. Failed openings can leave newly queried persistent table entries while restoring the source kernel; repeating the receive starts at the same source coordinates, as established by the earlier complete rollback theorem.

The next join must connect these local certified kernels to actual dynamically installed and routed World objects, retain the same partial seed cache, and instantiate native opening and sealing callbacks with the existing source adapters. That join must preserve complete raw replies, source state and primitive effects. This module proves no global handle attribution, target-free observer property, alias probability, independent record-key distribution, hybrid advantage, CTX security or whole-protocol secrecy. Seed/table erasure and actual native KDF realization remain the checked companion operational results, not security assumptions.
