# Selected fresh-record secrecy with trusted application plaintext

Status: proposed next source projection after L2 and S2b near-origin. No new maintained model, verdict or security claim. The origin interfaces intentionally publish actual plaintext and cannot support unrestricted secrecy. This experiment instead keeps receive plaintext inside the trusted application while allowing the caller to observe the exact Some/None result bit and frame/call association. It matches the existing S1/S2 trusted-application observation premise, strengthened by explicit result bits and the reviewed actual-ID/delayed-build interface. It does not add a target-decryption rejection or presume authentication as freshness.

## Exact candidate processes

Derive each process from the corresponding reviewed record-origin/tasking-origin inputs. Retain all source generation order, selected Beacon private slots, AnyPin, protected Server identity, literal own/assigned IDs, candidate verification, source root input, replicated accepts, delayed single-use pending contexts, single active Beacon finish, allocation gaps on failed seal, two near send allocations and three receives. Keep the exact stronger observations already proved admissible in the direction: opposite chain and chain after the near prefix, and roots only at other exact signing identities. Retain actual primitive opening of the adversary's original frame. Change only its public reply from Some(plaintext) to Some(result_marker), preserving None, per-call label, original frame correlation and every private state transition. The plaintext remains available to the private application, which has no echo or secret-dependent subsequent public action in this stated profile.

At each existing fresh-application send branch, mark its independently sampled plaintext with a new ghost event carrying full direction, Server identity, Beacon identity, assigned ID, root, sequence and plaintext. The attacker-chosen branch remains available, but does not emit this event. Both fresh and chosen branches retain real seal results and allocation gaps. If the fresh draw is never published because sealing fails, its secrecy is trivial but still a truthful event; optionally place the target marker at successful publication to keep the advertised statement nonvacuous and match current publication-origin events. Prefer the latter.

The query selects the one fresh Beacon, fixes the exact protected Server signing identity and asks whether that fresh-successful-publication event can coexist with attacker knowledge of its plaintext. Positions are b2s1/2 or s2b2/3, respectively. In b2s a different AnyPin identity is not silently equated to the protected Server. In s2b accepted candidates remain arbitrary; the exact signature-origin classification supplies source provenance where needed, not an honest-selected-KEM premise.

## Source and knowledge obligations

For a source counterexample whose target application draw is independent and privately owned until its selected successful publication, preserve that fresh name throughout the retained trace. Other independent application values can be exposed in the comparison when needed, but the target must never be renamed to an attacker-known value. Caller-chosen inputs remain their actual recipes. Prior origin papers already give the appropriate event/knowledge ledger for delayed builds and omitted directions; their public-plaintext observation is stronger than this private-plaintext result-bit view, but a secrecy transfer still needs its own target-name preservation argument, not an authentication conclusion used as an assumption.

Opposite/far omitted openings are public-computable from the exact disclosed chains. Their true/false outcome and any public output remain reproducible at the original cuts. Target-direction plaintext remains private even on successful delivery; the result bit may be public. The application must not later echo the target, place it in a chosen plaintext under an attacker-owned key, or use it in a publicly observable branch. Such behavior would deliberately release it and is excluded by the same trusted-application profile underlying fresh-name S1/S2, not by a cryptographic primitive assumption. This profile must be stated in source terms and retained as an explicit application/deployment premise.

The model result would be ordinary symbolic message secrecy only, with exact bounded source projection. It would not imply active strong secrecy, arbitrary secret-dependent application behavior, adaptive target-release freshness, compromise-forward secrecy or a computational IND$ theorem. P5 and the common computational experiment remain separate until their exact observation/reveal rules are joined.

## Controls and scope preservation

For each direction use the same secrecy formula with one explicit plaintext disclosure after the selected fresh publication; require a confirmed FALSE trace. This both tests the query and witnesses an eligible selected fresh publication. Preserve Kr3 for both positive and negative results. If output-name resolution needs precision hints, keep them as analysis-only changes with an exact finite allowlist and independent review; no receive/send-bound or schedule reduction. Existing origin, primitive, strong-secrecy and legacy queries remain unchanged.
