# HB-85 constructive validation nonce

The conventional CTX secret-prefix reduction now uses an executable bounded search for its validation nonce. This replaces the earlier extensional `Classical.choose` selector while retaining the existing ordinary nonce-AEAD IND$ winning event, advantage inequality, `qE + 1` seal bound, and `qH / 2^128` random-validation term. The source protocol, wire format and primitives are unchanged.

`CtxConstructiveNonce.nonceOfIndex` converts a counter below `256^12` to twelve little-endian bytes using base-256 digits padded with zeros. `nonceOfIndex_decode` reconstructs the exact counter from those bytes, and `nonceOfIndex_injective` proves that distinct counters give distinct nonce bytes. This is an encoding theorem for reduction bookkeeping, not a cryptographic primitive proof.

`candidates` constructs exactly `used.length + 1` such counters under the existing strict nonce-space bound. `candidates_nodup` proves distinctness of that list. If every candidate were used, a list containing that many distinct values would have length at least `used.length + 1`, a contradiction; `candidates_have_fresh` proves that one candidate is unused even when the used list contains duplicates. `chooseNonce` performs an ordinary first-match list search and returns that candidate. `chooseNonce_not_mem` proves that its fallback cannot occur under the strict length bound.

`candidates_length_le_of_seal_bound` bounds the generated list by `qE + 1` when the actual history has length at most `qE`. `chooseNonce_not_mem_of_seal_bound` connects freshness directly to the existing `qE < 2^96` condition. The search enumerates no nonce universe: it creates at most `qE + 1` fixed twelve-byte encodings and tests each against a list of length at most `qE`. Thus the direct list implementation needs at most `(qE + 1) * qE` nonce comparisons and linear candidate storage; each nonce comparison is on twelve bytes. Counter encoding uses at most twelve base-256 digits. These bounds describe the executable algorithm using the proved candidate-length and encoding facts; they are not a compiler-level cost semantics for Lean's runtime.

`CtxNonceAeadIndDollarValidation.chooseFreshCtxNonce` now calls this algorithm. Its helper theorem takes the strict used-list length bound, and its sole caller already derives that bound from the checked source sealing counter and `qE < 2^96`. The ordinary validation reduction and all its final advantage/query statements are unchanged. The selected nonce may differ from the former unspecified choice, but it satisfies the same freshness property wherever the reduction uses it.

`chooseNonce_no_queries` proves that the scan makes zero primitive or uniform-oracle requests. This does not make its local search work free. The complete validation reduction still performs the extra challenger seal and at most `qH` local candidate-key encryptions/tag comparisons, together with its complete source simulation and cache/history work. Existing source uniform and primitive-query caps remain separate from runtime. No nonce inequality across unrelated keys or extra primitive guarantee is assumed.

The adaptive log/reject-to-conventional-IND$ simulation, repeated private-cache alias guessing, production raw decoder/ratchet correspondence, correlated evolving keys, reveals/freshness, session/record selection and common computational/symbolic experiment remain open. This focused algorithmic correction does not discharge those protocol composition obligations or strengthen the permanent primitive, compiler, storage and deployment contracts.
