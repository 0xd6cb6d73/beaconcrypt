# LQ-F spike: the exact later-quantum profile over a logged source

Status: time-boxed spike (3-5 agent-days budgeted) for the exact later-quantum profile LQ-F, on branch `codex/deployment-lqf-spike` over central `c29cea81`, with seven Lean commits and one documentation commit. It adds nine modules with 109 guarded statements under `beaconcrypt-core/proofs/lean/BeaconcryptCore/Computational/`; no existing module changed. It has not been reviewed and is not merged. The design is the later-quantum reveal-mode design (`/tmp/bc-arc-scratch/common-experiment/reveal-mode-design.md`, sections 1, 4 and 5) and the plan sections 9, 14 and 19-22 (`/tmp/bc-arc-scratch/common-experiment/plan.md`). The Beacon-side mode LQ (stages LQ-1 and LQ-2, deviation D6) is described in the [common deployment experiment guide](common-deployment-experiment.md).

## What the spike tests

The owner's profile (plan section 19) reveals after the run every honest X25519 secret, every Diffie-Hellman output and every honest Ed25519 identity secret. LQ reveals only the Beacon side (deviation D6). LQ-F adds the Server's Ed25519 identity seed (and so its X25519 conversion) and the Server's per-registration ephemeral scalars. Neither is reachable by a source14 program: the Server seed is read by no source14 command, and the ephemeral scalar is generated inside the Server's accept and dropped after the DH steps. The design therefore proposed a logged source, source14 with a logged accept and a terminal Server read, and named the re-proofs whose feasibility the spike was to test: the selected-first KEM reservation, the selected-disclosure monitor, the KEM cut carrying the selected accept's ephemeral as an explicit value, T4, the KEM hop, T6 and their bills, all over `SourceSpec + LaterRead`.

## Result in one paragraph

Every listed re-proof was completed and is checked and guarded: the logged source with its projection back to source14 and its terminal read, the logged command compiler, the KEM cut with the explicit ephemeral, the selected-first reservation with a creation cap derived from the program, the monitor, the correspondence between the logged source and its compiled form, T4, the KEM hop, T6, the composed KEM transfer and the bills of the KEM adversary. No assumption, contract or premise was added; the only contract used is `FunctionalDecapsulation`, exactly where the existing KEM hop uses it, and the bills use the existing uniform-bill premises. No re-proof failed; every one was a copy of the corresponding existing proof with the logged definitions, and several existing results turned out to be generic and were reused without change.

## The logged source

`LaterRead` has one query, the terminal Server read, whose reply is `Reveal = Option IdentitySeed × Log`. `Log = List (Option ScalarBytes)` has one entry per raw accept, in raw-accept order: the Server's ephemeral scalar when the accept reached its encapsulation, and `none` when its attached verification or a step before encapsulation rejected. The logged collector `collectLogged` is the actual collector `PqxdhServerRootPreparation.collect`, split at the encapsulation as in `KemCollected.collect_split`, which also returns the generated ephemeral's secret; forgetting it gives `collect` back as an oracle program, before any interpretation (`collectLogged_fst`), and a successful collection logs exactly the secret recorded in its collected input, the scalar of its DH2 to DH4 steps (`collectLogged_some`). `acceptSource` is the literal annotated Server accept of `ServerAccept.source` with the logged collector, and returns the logged entry beside the reply (`acceptSource_fst`).

The handler `source` runs a raw accept by `acceptSource` and appends its entry to the log, runs every other source14 request by the unchanged `ServerSchedule.source`, and answers the terminal read by the ordinary identity-pool reveal request at the Server's slot, returning the revealed seed with the current log. The log is ghost state beside the source state; no source14 command reads it. For every source14 program, the logged execution from any log projects to the source14 execution with the same result and complete source state (`program_projection`), and the logged initialized source projects to `InitializedSchedule.source` (`initialized_projection`). At a state whose Server slot holds `seed`, the terminal read returns `(some seed, log)`, keeps the log and changes no seed, KEM key, owner or shared state (`later_read`); every logged step keeps the Server-slot and owner invariant of source14 (`query_owned`, `program_owned`), which the constructor establishes for the constructed Server's seed (`ServerBirth.source_owned`), so every terminal read of a reached state returns the Server's actual seed.

What the reveal contains, against the owner's profile: the Server's Ed25519 identity seed (its X25519 identity secret is the production conversion of the seed) and the ephemeral scalar of every accept that reached its encapsulation; together with LQ's Beacon-side reveal this is every honest X25519 secret and every honest Ed25519 identity secret. Diffie-Hellman outputs are not listed: each is a production function of revealed scalars and public points (design section 1, recommendation 3). Not logged: the ephemeral of an accept that generated its ephemeral and then failed the PQ-key parse, the only step between generation and encapsulation; its public key is never output, so a harvesting attacker could not recover it. This is a semantic choice for owner confirmation (open point 5); logging it too would need one more split of `beforeEncapsulation`. Never revealed, as in LQ: ML-KEM secret keys and shared secrets, the R1 table, the Extract family, the ghost touches, roots, chains and record keys; the reveal type holds only a seed and scalars.

## The KEM chain over the logged source

The logged command compiler (`LaterServerCommands.impl`) keeps the owner list and the log beside the native state of `KemEncapsulation.Client`. A raw accept runs the exposed logged accept and appends its entry; every other source14 request runs the unchanged exposed backend `KemEncapsulation.impl` on the unchanged level-2 client `RevealSchedule.client`; the terminal read issues the identity-pool reveal of the Server's slot. `commands` returns the source outcome type `KemCommands.Outcome` of the existing chain, so every consumer generic in that type applies, and for every source14 program it is `KemEncapsulation.commands` from any log (`commands_embed`).

The KEM cut. The logged `exposeAt` runs the logged compiler up to the raw accept at the designated raw-accept ordinal with every encapsulation interpreted in place, then the exposed logged accept, then the rest of the tagged logged program from the log extended by that accept's entry. An active KEM cut of it comes from a reached pending raw-accept cut, the attached verification of its raw bytes succeeds, the request is the raw bytes with the verified PQ key, and the saved continuation is `rawResume`: the literal suffix after the encapsulation reply, the unchanged accept tail, and the rest of the tagged program from the log at the cut extended by `some ephemeral.secret`, where `ephemeral` is the explicit value fixed before the encapsulation (`ordered_cut`, `accept_scan`, `exposeAt_scan`, `rawCut_shape`). A completed cut has a non-accepted tag (`accepted_reached`), and interpreting the exposed encapsulation gives the logged command program of the tagged program (`exposeAt_actual`).

The selected-first reservation and the monitor. `PqxdhDynamicKemJointSource.selected_source` and `PqxdhDynamicKemJointStopping.history_event` are stated for any program over the joint identity, coin and KEM pool interface, and apply to the hidden logged program unchanged (`selected_first`, `monitor`). The only new fact is the creation cap: the hidden logged program has at most as many KEM creations as the logged program has Beacon creations (`LaterServerReserve.creations`), because each source14 request issues the creations of the same request in the existing compiler and the terminal read issues none.

The correspondence with the source. Under the actual encapsulator and the actual pools, the logged compiler has the same result, encoded final state and final log as the logged annotated source, for every logged program from a state satisfying the Server-slot invariant (`LaterServerInitialized.program_source`); the accept case uses the existing generic program lemmas `KemEncapsulation.prefix_program`, `OpenBackend.prefix_program` and `ServerPrefix.program_source` on the logged collector, and every other source14 request uses the existing `ServerClient.query_source`, `OpenBackend.program_run` and `KemEncapsulation.program_actual`. With the reservation and the constructor-order swap this gives `actual_source_first`, the logged counterpart of `KemInitialization.actual_source_first`: the logged initialized source, with the log forgotten and the outcome encoded, has the distribution of the selected-first game of the logged source.

T4 (`LaterServerBridge.actual_le_real`). In the logged initialized execution of the tagged logged program, with the log forgotten, the probability that the selected raw accept returned a session, the decision holds, KEM key `selected` was never disclosed and the verified PQ key of the recorded raw bytes is the final pool key at creation index `selected` is at most the probability that the raw-ordinal KEM real game at the logged exposure returns `true`. The event is the existing `KemRawBridge.Decided ∧ GoodKem ∧ KeyMatchFinal` on the final state with the log forgotten; the decision reads the program result, which may contain the terminal Server reveal. The premise is a cap `count + 1` on the Beacon creations of the program; there is no honest-target premise, and the raw-accept ordinal and the KEM creation index are public handles.

The KEM hop. `KemRawGame` and `KemRawCertified` never look inside the scanned program: their proofs use only `PqxdhDynamicKemJointRouter.pre_program`, `KemResume.post_source` and the one-key IND-CCA branch lemmas. `LaterServerKemHop` states them for every scanned program, and the existing raw-ordinal definitions are its instances by `rfl`; the logged exposure is the instance `LaterServerCut.scanned` (`kem_hop`). The loss is one ordinary one-key ML-KEM IND-CCA advantage of the proof-carrying adversary and one ordinary ML-KEM correctness error, each with coefficient one.

T6 (`LaterServerOpaque.branch_opaque`). The branch of the KEM hop at the logged exposure equals the logged opaque branch, for both values of the branch bit. The opaque cut saves the log at the cut beside the existing fields; every saved field is fixed before the selected encapsulation. The existing `KemOpaqueResume.resume_reply` and `resume_post` take the rest of the run as an argument, so they apply with the logged rest, which appends the explicit ephemeral and depends on neither the ciphertext nor the candidate (`LaterServerCut.rawResume_opaque`, `post_opaque`). `transfer` composes T4, the hop and T6, abridged:

```lean
theorem transfer (setup) (functional : FunctionalDecapsulation setup.kem) (codec) (checks) (ensureInit) (supplied)
    (decision : X → Bool) (work : OracleComp (LaterServerSource.Spec KemSK) X) (runtime) (count)
    (selected : Fin (count + 1)) (index : Nat)
    (bounded : work.IsQueryBoundP (fun query => laterKind query = some (.inl 1)) (count + 1)) :
    (letI := Classical.propDecidable
    𝒟[(fun final => decide (Decided decision final ∧ GoodKem selected final ∧ KeyMatchFinal setup codec checks selected final)) <$>
      ((fun result => (result.1.map fun outcome => encodeOutcome setup outcome.1, result.2)) <$>
        (LaterServerSource.initialized setup codec checks ensureInit supplied (LaterServerCommands.tag work index)).run
          ((PqxdhDynamicIdentityPool.initialState, PqxdhLiveKemBirth.empty), runtime))] {true}) ≤
    𝒟[opaqueBranch setup codec checks ensureInit supplied decision work runtime count selected index false] {true} +
      ENNReal.ofReal (setup.kem.IND_CCA_Advantage (runtimeOfImpl (kemAmbientImpl setup.baseImpl))
        (LaterServerKemHop.certified setup ensureInit supplied (LaterServerCut.scanned setup codec checks decision work index)
          runtime count selected).toINDCCA + KemRawGame.correctnessError setup)
```

The bills (`LaterServerBills.adversary_bound`). The proof-carrying adversary at the logged exposure has exactly the caps of `KemRawBills.adversary_bound` (and so of `KemReductionBills.adversary_bound`) for the Beacon-side budget of the program, for any number of terminal reads: each source14 request has the four bills of the same request in the existing compiler, and the terminal read is one identity-pool reveal, which counts as no generated identity, no decapsulation, no uniform work and no exposed encapsulation. The composition uses `FinitePartitionQueryBounds.weighted_bound` over the request kinds of the logged source and the linearity of the native uniform allowance (`total_single`).

## Open points (LQ-F is not finished)

1. The CE level. The common deployment experiment's native game must reveal the Server seed and log the ephemerals (a logged native accept, as `nativeAccept` with `collectLogged`; the native and annotated prefixes agree on the logged collector by the existing `ServerPrefix.program_projection`), and the compile lemma of LQ-2 must be extended to the logged source: the compiled program issues the terminal Server read after its Beacon reads, and the compile simulation must carry "native log equals source log" through the accept case. Not built; estimated 3-6 agent-days.
2. CE-9 over the logged execution. `GoodKem` and `KeyMatchFinal` are read on the projected final state, but the compiled LQ-F program is not a source14 program, so the bundle-to-pool invariant that CE-9 needs (unit A note) must be carried over the logged execution; the terminal read only appends to the identity-pool transcript (`later_read`), so a frame lemma suffices. Estimated 1-3 agent-days on top of CE-9.
3. Item 2 (T7, T8, the R1 split) is not built. If it is stated over the opaque branch for an arbitrary scanned program, as the KEM hop now is, the logged instance costs little (1-3 agent-days); retrofitted, 5-10. The design's T7 condition holds: the reveal is not a function of the ML-KEM output `u` (the log holds ephemeral scalars generated before the selected encapsulation, and the seed).
4. The terminal read is an identity-pool reveal of the Server's slot, so `revealedAt` holds for the Server identity in LQ-F executions: T5 and A2 must not be cited on LQ-F programs, as for `compileLater`.
5. Owner confirmation: the ephemeral of an accept that fails the PQ-key parse after generating it is not logged (its public key is never output); the read returns `Option IdentitySeed`, which is `some` of the actual seed by the slot invariant.
6. Not reviewed; the guards, root import check and focused inventory pass for every commit.

## Re-estimate and recommendation

Spent: the spike built all nine modules in one working session, well inside the 3-5 day time box, because every re-proof was a copy of an existing proof with the logged definitions and the generic results above needed no change. The design's LQ-F figure (+20-40 agent-days, including the spike) was dominated by these re-proofs and their bills, which are now done. Remaining LQ-F-specific work, in agent-days: the CE-level logged game and compile extension 3-6, CE-9 over the logged execution 1-3 (after CE-9), item 2 over the generic opaque branch 1-3 if designed in (5-10 retrofitted), headlines, guide, analysis and review 2-4; about 7-16 in total, on top of LQ's remaining 7-16. LQ-S through the design's route (supplied seed, averaging, a decision-11 exception, losses as an expectation over the seed or signed hops) keeps its +4-8; through the logged source it would cost almost the same as LQ-F (the ephemeral log is already built), about 6-14.

Recommendation: LQ-F. It meets the owner's exact profile with no new contract and no exception to decision 11, its KEM chain and bills are already proved with the same losses as the classical chain, and the remaining work is CE-level plumbing of the kind LQ-1 and LQ-2 needed. LQ-S would need the decision-11 exception and weaker loss forms while saving little.
