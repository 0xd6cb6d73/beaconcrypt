# Signature-origin lifting for the source-shaped registration interface

This claim-specific symbolic argument has independent semantic review of the exact T0 theory, source ledger, target-key reflection and six development probes. Its maintained process/checker integration and final source-bound validation are recorded separately. It concerns the exact T0 theory in `crypto.pvl` and the abstract decodable-message contract used by the maintained models. It is not a computational signature reduction, a statement about curve encodings, or a full protocol trace equivalence.

The proved symbolic conclusion is A2's projection: if a successful Server accept has verified tuple `init` and registration identifier `rid`, with identity `ed_public(k)`, then that exact tuple and identifier occurred at a returned Beacon registration bundle, or the attacker can derive `k`. Server object identity, the accepting Server key, root, pending handle and assigned ID are not conclusion fields. They can remain arbitrary in the source trace. This projection therefore does not require immediate build, same-object build, any particular accepting Server key, or assigned-ID equality. In particular it cannot transfer A1, record agreement or secrecy by implication.

## Exact theory and selected source interface

The loaded theory consists of `production-transcript-interface.pvl`, `crypto.pvl`, `extraction/lib.pvl`, `fs-common.pvl` and `registration-set-admission.pvl`. The probe adds only public request/reply constructors, three ghost events and processes. Its observer calls the existing `registration_set_verify` helper without modification. That helper parses the identity tag, verifies PQ/prekey/one-time signatures in source order, checks the three exact purpose tags, and constructs the same `VerifiedInitKex` and registration ID. The source `Server::get_shared_secret` performs those checks before all consumed-set, DH, KDF and returned-token conditions. Consequently each successful source accept implies one observer verification success. Omitting the later checks is one-way admission overapproximation, not an equality of private state or returned values.

An honest abstract owner samples one hidden identity and one opaque owner name. It publishes its public identity, exposes both role-tagged converted-DH operations with exact T0 success/failure behavior, and accepts at most one publication request. That request supplies arbitrary known prekey, one-time and KEM public terms. The owner signs their three distinct source tags and emits `ProvPublished` only with the actual returned bundle. No separate signing endpoint exists. A second publication under the same identity appears only in the explicit negative control.

Giving the adversary the unsigned triple is deliberate. Native prekey and KEM getters are available before publication, and `new_onetime_keypair` can replace a previously readable one-time key in `FreshWithCoins`. In a selected finite source trace, every nonidentity generation can be assigned an injectively distinct attacker-generated name at its source creation point. This preserves all term equalities, inequalities and creation-before-use dependencies, while exposing material sooner. It does not compare computational distributions or rearrange a sampler and its continuation.

The source-shaped interface under consideration includes actual Beacon/Server construction, identity/public/material getters, one-time preparation/deletion, arbitrary registration accepts and builds, pending-token moves between objects, finishes, established sends/receives, and reads of current root/chain/skipped material when explicitly modeled as reveals. It excludes snapshots, persistence and serialization/update wrappers that return saved state. Honest generated identity/material names are fresh as in T0. For the honest Server this uses the existing October 5 handoff OD2 premise: uniform independent keys and correct key management (`doc/impl/handover/pause-2026-10-05/README.md`, owner-decision row dated October 3). That premise is external to API validation; exposing nonselected keys in the comparison is an analysis overapproximation, not a new advertised honest-Server reveal capability. A caller-supplied Server seed is either an attacker-known recipe or an independently supplied fresh private identity name; a trusted host that derives an undisclosed new Server seed from the selected Beacon seed is not represented by this source profile. The actual API accepts caller bytes, so this input-distribution boundary must remain explicit rather than becoming an asserted API validation. Application terms are the existing independent fresh application names or attacker-supplied recipes, with reuse allowed. A trusted application that secretly inserts an identity seed into plaintext or another returned value is outside this interface; proving secrecy for such a key-dependent application is not assumed. Primitive results and parsing follow the declared T0/abstract-message contracts, not arbitrary auxiliary callbacks.

Identity revelation requires care rather than a blanket no-compromise assumption. For an A2 counterexample, the selected `k` is not derivable at its finite violation cut. If `k` is an honest identity name, returning that identity through `identity_sk` or an identity-reveal oracle before the cut is therefore impossible in that counterexample. Other identities may be revealed and can be exposed from the start in the target-specific comparison. A later reveal after the chosen cut does not occur in that finite prefix. The theorem below never claims a temporal secrecy property after compromise.

## Protected names and the exact reduction audit

Fix one honest identity atom `a`. Call a term protected when every occurrence of `a` lies below at least one of these argument positions: argument 1 of `ed_public`; argument 1 of `x25519_public`; either argument of the private `x25519_shared`; or argument 2 of `sign`. There are no barriers at signature messages, HKDF/hash inputs, AEAD plaintexts, tuple fields, encodings or cached material. Thus protection cannot silently assume that decrypting a ciphertext preserves an identity hidden directly inside its plaintext.

For a term pattern `p`, let `U(p)` be its variables occurring at an unprotected position. For every constructor ground substitution `sigma`, `p sigma` is protected exactly when each `sigma(x)` for `x` in `U(p)` is protected, provided the pattern itself contains no literal `a`. This is a structural induction on `p`: a protected argument position contributes no condition; all other children contribute their conjunction. Pattern constants differ from the fresh name `a`.

The finite audit parses all 28 explicit reduction rules in the exact five libraries. For each rule `l = r`, it checks `U(r)` is a subset of `U(l)`, with a nonbarrier destructor at the root of `l`. Therefore a reduction at an unprotected position in a protected term has a protected result by the substitution lemma. A reduction below a barrier cannot expose a name outside that barrier. The audit separately checks that none of the four barrier constructors has `[data]`, and lists all 38 data constructors in the five base libraries, plus six public request/reply data constructors in the projection: their implicit projections expose only an already unprotected argument and satisfy the same condition. Tuple projections have that identical argument. Type-converter erasure introduces no barrier and preserves the predicate. Arithmetic and boolean operations do not construct bitstring identity names. No equational theory is loaded, and unsupported rule/declaration syntax is rejected by the audit.

Public constructor application to protected known arguments remains protected. Public destructors either fail or preserve protection by the preceding result. Public tests create no identity occurrence. An induction on attacker recipes therefore shows that protected initial knowledge and protected subsequent outputs never derive the atom `a` itself. This is a syntactic fact about T0, not an ordinary EUF-CMA or related-DH assumption.

The honest identity-DH service is an additional output rule, not an invocation of a public destructor with a secret argument the attacker supposedly knows. A successful reply is `x25519_shared` with the hidden identity in its role-correct argument; both arguments lie below barriers. A refusal is public `None`. Both preserve protection for arbitrary peer recipes. This explicitly handles Ed25519/X25519 related use at the symbolic interface. Any computational realization still needs the existing exact joint-use contract.

The source output ledger below shows that all extra revelations used by the comparison are protected. This supplies the necessary direction for A2's corruption disjunct: the stronger abstract attacker still cannot derive the selected identity. A simple assertion that more knowledge only helps the attacker would not suffice.

## Signature-key classification, including non-atomic keys

Take the first successful source verification used by the selected accept and write its ground signature as `sign(message,k)`. T0 has exactly the stated verification rule; public-key conversion, KEM, HKDF, AEAD, frame opening and structural accessors do not create a `sign` constructor. The audit checks that no explicit reduction right-hand side contains `sign`. Implicit data/tuple projections return existing subterms, and `sign` is not a data constructor.

Trace a signature occurrence backwards through the finite recipe and source-output history. A public construction of this occurrence with `sign` requires a recipe for `k` at that earlier point; monotonic knowledge then gives `attacker(k)` at the violation cut. A destructor or non-signing constructor can only carry an occurrence already present in one of its inputs. Fresh atomic generation contains no signature. An honest protocol output can introduce new signatures only when `get_registration_bundle` returns its bundle: all three signature keys are that Beacon's fresh identity atom. Privately computed signatures from failed calls are not returned, stored in a public field, or exposed by another getter. Their occurrence is not part of the public history being traced.

This induction classifies an accepted signature key without assuming it is an honest key: it is either already derivable or is an honest Beacon identity atom that signed a returned bundle. It applies when the candidate `k` is a compound or attacker-owned term, and when the signature was nested inside a field, hash, ciphertext or previously returned plaintext. Releasing other material can reveal an old signature occurrence but cannot change its constructor key. A hidden Server identity has no signing call in the production roles, so it cannot be the second case. An attacker-known imported identity or already revealed identity falls in the known-key case at the considered cut. An independently supplied hidden private Server identity has no signing output and therefore cannot supply the unknown-key origin case. No ability to recover an arbitrary signing key from its public key is used.

For completeness, this occurrence induction is over the allowed source interface, not over arbitrary honest code with access to private state. It would fail for a new API that signs arbitrary hidden messages or returns privately failed signatures. The finite source ledger and source hashes are therefore part of the argument's scope.

## Deduction-preserving and violation-reflecting construction

Suppose a finite source-shaped T0 trace violates A2. Its accepted candidate key `k` is not derivable. Signature-key classification gives a specific unrevealed honest Beacon identity atom `a = k`, even if the attacker originally offered a compound candidate term. Keep `a` restricted in one abstract owner. Map every other fresh identity, nonidentity value, payload atom and opaque handle injectively to fresh attacker names, retaining its original creation-before-use point. The comparing attacker may generate those names privately and later use them as needed; no symbol is identified with another. The selected identity's public and converted-DH terms are obtained from its abstract owner/service. No equality of the selected source T0 terms under this profile is changed by the injective renaming; no assertion about equality or parsing of native byte strings follows.

Induct over the finite source outputs and chosen input recipes using the ledger. At the selected owner's sole returned registration bundle, invoke its single publication with the mapped actual public triple and matching public label. Other signatures have known keys in the comparison and are public constructor recipes. Non-signing outputs are reconstructible from known nonidentity values, prior recipes, public T0 constructors/destructors and selected-owner DH replies. A source failure can simply contribute its public failure term to the comparing attacker's knowledge; it need not consume an abstract signing request. Every source input at a later step consequently has a mapped abstract recipe. Additional abstract DH/refusal information and known nonselected keys remain protected by the earlier induction, so the selected `a` is still not derivable.

At the selected successful accept, submit its mapped raw bundle to the observer. Exact validation produces the mapped same `init` and `rid` and emits `ProvAccepted(ed_public(a), init, rid)`. The checked unrestricted A2 query gives either a matching `ProvPublished` or `attacker(a)`. Protection rules out the second alternative. An abstract `ProvPublished` for `ed_public(a)` can only come from that one restricted owner: the term theory gives no constructor collision with another identity, and no abstract publication was scheduled without the corresponding source returned bundle. Its event therefore reflects to exactly a source returned bundle with the same `init` and `rid`, contradicting the chosen violation.

This is a target-specific finite symbolic counterexample transformation. It requires neither an honest-target premise in the original query nor a source-to-model equality of full distributions. It introduces no session-selection probability factor because no probabilistic reduction is asserted. Computational selection, related-key reductions, query bills and exact joint input distributions remain the separate common-experiment obligations. In particular, this argument does not transfer the proved A2 projection into cryptographic security solely from the names Ed25519, X25519 or ML-KEM.

## Probe evidence and boundaries

The six new known-material probes use ProVerif 2.05 with the exact five-library theory, per-target shared lock, 180-second cap and 10-GiB address-space cap. The unrestricted A2 query, allocated Beacon identity secrecy and the hidden no-sign Server identity secrecy each returned TRUE. A joint publication/acceptance reachability query returned FALSE with a reconstructed trace. A one-time-purpose parser mutation and a two-publication mutation each returned FALSE with a trace for allocated-identity provenance. The control formulas are deliberately scoped to allocated identities; the unrestricted A2 positive query retains its attacker-key disjunct. Earlier sampled-material probes remain archived separately and are not substituted for this interface.

The positive abstract owner allows arbitrary unsigned terms, whereas source honest material follows actual typed generation. That overapproximation is safe only with the source-output and target-key arguments above. The theorem remains within T0's explicit constructor/destructor idealizations, including its existing KEM binding and perfect public-key/tag distinctions. Native high-bit aliases, invalid-point checks and implicit-rejection behavior belong to the separate encoding profile; ordinary computational EUF-CMA does not imply this idealized trace theorem. The abstract codec contract, actual primitive reductions and their joint-use context must still be connected by the final common experiment.

The reviewed source-profile argument therefore lifts A2's signature-origin projection beyond the old adjacent accept/build schedule within the stated T0 interface. A1's response/root origin, L2 routing, general source observations, raw optional plaintext, global reveal/freshness rules and all quantitative cryptographic composition remain distinct obligations. No snapshot or persistence property is involved.
