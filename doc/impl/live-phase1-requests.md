# Live Phase-1 state controls and registration requests

These two modules connect repeated live Beacon operations to the maintained full native Phase-1 publication boundary. They contain 23 guarded statements and introduce no cryptographic security assumption. The source reference is `beaconcrypt/src/beacon.rs`: `new_onetime_keypair`, `delete_onetime_keypair`, `delete_pq_keypair`, and `get_registration_bundle`. The computational owner retains the complete private state and exposes only the actual optional API reply. Snapshots, restoration and persistence are excluded.

## Explicit one-time generation and deletion

`PqxdhLivePhase1State` has nine statements. The explicit regeneration helper calls its generator before inspecting the role phase. A successful generation replaces the one-time pair in `FreshWithCoins` or changes `Fresh` to `FreshWithCoins`; an inactive role still incurs the generator attempt and then rejects. A failed generation leaves the original role unchanged. This differs from a bundle request, which draws only while `Fresh`.

`abort_controls` identifies the exact extracted abort operations and their retained pinned identity identifier. `newOneTime_complete` preserves the generator's actual optional reply, full auxiliary poststate and arbitrary complete continuation. `newCoins_privateKeys` retains both the original prekey and KEM pair during regeneration. `newCoins_fields` retains the identity, identity identifier, pinned server and raw-attempt instrumentation. `newOneTime_bound` charges exactly one generator-service attempt even on an inactive role; it does not claim that implementing this generator is free.

Deleting one-time material changes `FreshWithCoins` back to `Fresh`, changes `InitSent` to `Aborted`, and otherwise leaves the original role untouched. Deleting the KEM pair aborts each pre-registration active phase. `deleteKem_privateKeys` proves that no prekey/KEM payload remains in the result, including inactive phases. `newCoins_map`, `deleteOneTime_map` and `deleteKem_map` commute with the complete identity/KEM interpreter-handle map without inspecting either secret. The resulting phase transitions and untouched fields are part of the executable definitions, not a premise about a final security event.

## Full source bundle request

`PqxdhLivePhase1Bundle` has fourteen statements. Its client receives public projections for the owner index, Ed25519 identity, X25519 key pairs and ML-KEM pair. It receives no identity seed or KEM secret. A `Fresh` request draws its one-time pair at the source position; `FreshWithCoins` uses the explicitly retained pair without a draw. Every other phase rejects. The exact existing signing program signs the purpose-framed prekey, one-time and KEM messages in source order. The existing optional unpacked Cap'n Proto writer then publishes the complete `InitSent` state only after success.

`signing_interpretation` and `writing_interpretation` route the original callbacks without changing their replies or auxiliary state. `afterGenerated_complete` retains every earlier signature-service result and the exact optional writer result before an arbitrary complete continuation. `bundle_complete` adds the actual generator position and all inactive/rejection branches. No generator-order interchange is assumed.

`signing_bound` counts at most three calls in the routed identity-service block; the actual program in this block issues only those three signature requests. `writing_bound` counts one writer attempt, including failure. `afterGenerated_bound` and `bundle_bound` combine these with preparation and generation. The per-request caps are one generator attempt, three signature-service attempts and one writer attempt. `schedule_bound` proves caps of `qBundle`, `3*qBundle` and `qBundle` for an arbitrary adaptive client with at most `qBundle` requests, across every optional callback reply. Underlying generator, signing and writer implementations still require their ordinary resource contracts; these service counts do not declare their random sampling or deterministic work free.

`writing_map`, `afterGenerated_map` and `bundle_map` preserve the whole optional computation when private identity/KEM payloads are replaced by interpreter handles with the same public projections. The maps need not be injective. `bundle_map_run` evaluates that equation while preserving the full primitive/signing/cache state. `owner_complete` places the role state inside the API interpreter, so a caller receives optional serialized bytes and not the private role state.

A successful publication consumes the fresh phase. Nevertheless the generic optional-callback model allows earlier signing or writer failures, with the original fresh role retained and previous signing events still present in the auxiliary state. It therefore does not justify reusing the older exact single-bundle three-entry signing-log premise for every repeated live schedule. The global authentication consumer must retain the complete joint signing history and these adaptive query caps, or separately derive the narrower normal-return behavior under the ordinary functional primitive/writer contracts. This checkpoint supplies neither a new EUF assumption nor a completed dynamic-identity authentication reduction.

All 23 guarded dependencies use only the standard Lean axioms; the signing-routing equality uses only propositional extensionality and quotient soundness. The native fixed-size public projections, primitive call behavior, optional serializer and compiler boundary remain explicit functional contracts. No primitive algorithm, physical erasure, allocator availability or persistence security is proved.
