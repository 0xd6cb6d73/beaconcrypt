# The generated PQXDH code refines the handwritten ideal model

This note indexes the refinement proof that connects the extracted Rust code in
`BeaconcryptCore/Extraction/` to the handwritten ideal model in
`BeaconcryptCore/Model/Pqxdh/` (described in `PQXDH_IDEAL_MODEL.md`).

Everything below is machine-checked; the whole project builds with no `sorry`
and the results depend only on Lean's standard axioms
(`propext`, `Classical.choice`, `Quot.sound`).

## What "refines" means here

The extracted PQXDH layer is *cryptography free*: the primitives live outside the
extracted core, so the generated transitions are driven by the values the caller
obtained from them — the four X25519 contributions and the ML-KEM shared secret
(`pqxdh.PqxdhSharedSecrets`), the replay verdict (`pqxdh.RegistrationStatus`), the
key-identifier availability verdict (`pqxdh.KeyIdAvailability`), the authenticated
sender identifier and the authenticated key-identifier binding recovered from the
first record.

A refinement theorem therefore reads: *if the generated inputs abstract to the values
the ideal model computes with the abstract interface `Pqxdh.Crypto`, then the
generated transition returns exactly the ideal outcome* — the same acceptance or the
same rejection, and on acceptance the same identifier, the same published data and
the same surviving state.

The abstraction from generated bytes to ideal bytes is `absBytes` (from
`BeaconcryptCore/Refinement/PqxdhBytes.lean`), lifted to protocol data by
`absBinding`, `absVerified` and `absDHs`.

## Byte level — `BeaconcryptCore/Refinement/PqxdhBytes.lean`, `PqxdhEncoding.lean`, `PqxdhCore.lean`

The tagging and parsing of public keys (`tag_*_abs`, `untag_*_abs`), the associated
data (`build_associated_data_abs`), the PQXDH transcript (`build_root_key_input_abs`,
including the all-zero rejection), the registration identifier (`registration_id_abs`)
and the key-identifier binding (`registration_key_id_binding_abs`).

## Transition level — `BeaconcryptCore/Refinement/PqxdhProtocol.lean`

| Spec | Generated | Ideal | Theorem |
| --- | --- | --- | --- |
| §5 | `pqxdh.beacon_start` | `Pqxdh.beaconInit` | `beacon_start_refines` |
| §6 | `pqxdh.validate_init_kex` | `Pqxdh.validateInit` | `validate_init_kex_refines`, `honest_bundle_validates` |
| §6–§14 | `serverRegister` (`server_accept` → `server_prepare_commit` → `server_commit`) | `Pqxdh.serverRespond` | `serverRegister_refines` |
| §11 | `pqxdh.server_abort_candidate` | transactional rollback | `server_abort_candidate_refines` |
| §15–§18 | `beaconFinishDriver` (`beacon_prepare_finish` → `authenticate_registration_key_id_binding` → `beacon_commit`) | `Pqxdh.beaconFinish` | `beaconFinishDriver_refines` |
| §17 | `pqxdh.beacon_abort_init` | ideal abort | `beacon_abort_init_refines` |

`serverRegister_refines` covers all five outcomes of the ideal server transition that
the extracted core can express (replay, all-zero contribution, exhausted counter,
identifier collision, success) and `beaconFinishDriver_refines` all five outcomes of
the ideal beacon transition (pinned-identity mismatch, all-zero contribution, wrong
authenticated sender, key-identifier mismatch, success).  The rejections the extracted
core cannot express are exactly the ones its callers detect (a failed signature
verification, a failed decapsulation or key conversion, an empty application message,
an inadmissible record, a malformed plaintext); they are listed in `genServerError`
and `genBeaconError`.

## Session level — `BeaconcryptCore/Refinement/PqxdhSession.lean`

`GenHonestRun h` bundles the generated data of one honest registration together with
the assumption that it abstracts to the ideal honest run `h : Pqxdh.HonestRun`.
`honest_run_refines` then composes the four transition results: on this data the
generated pipeline runs to completion without a rejection and produces the identifier,
the published peer (identity key and associated data) and the pinned binding of the
ideal run, while the ideal run itself takes the two steps `Pqxdh.HonestRun.serverStep`
and `Pqxdh.HonestRun.beaconStep`.

## The record layer

Sealing and admitting the first server record is not part of the extracted PQXDH
module: it is the symmetric ratchet, whose own refinement lives in
`BeaconcryptCore/Refinement/RatchetRefinement.lean`,
`RatchetControl.lean`, `RatchetControlRestore.lean`, `RatchetEffect.lean` and
`RatchetEffectRefinement.lean`.  In the PQXDH refinement it appears through the
plaintext and the receive state the caller feeds back into the beacon transition.
