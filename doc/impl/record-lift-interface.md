# Record-lift interface proposal

This revised R1 proposal follows Claude's answers 26 and 30 and the owner direction recorded in decision 17. It is based on central `4cc974c049a3d542fdec728982bf80594ce443d2`, with the successful seed constructors and dynamic ordinary-record correspondence integrated. The implementation is `PqxdhRecordLiftInterface.lean`. The proposed freeze is the provisional typed surface of answer 26 §6.1 as refined by answer 30 §3, with a later revision expected once CE-11 exists. A concrete private interpreter, its installation invariants and source simulation are still required before `RecordLift.game env A` exists as a probabilistic experiment. This component is not a completed executable R1 world or a security theorem.

## Interface and import direction

CE-11 will import this interface. No record-lift module imports `PqxdhDeploymentIdealKeys`, `PqxdhDeploymentHeadlines` or a later CE module. The proposal reuses the existing CE command, reply, mode, handle, transcript, log and budget types. `RecordQuery` is the sum of the source Server query domain and an owner index paired with the source Beacon query domain. `recordQuery` embeds those requests in CE without changing their fields. `RecordSpec` obtains its replies from CE's existing mode-specific specification. The guarded `server_reply` and `beacon_reply` statements establish the complete source reply types in mode O; mode P uses CE's existing success-bit projection.

The registration environment answers `EnvSpec`: create, bundle, accept, build, finish and public HMAC. Public BLAKE2b bypasses the environment and invokes the shared-hash capability directly. The environment handler is a program over `EnvEffects`, consisting of coins and restricted capabilities, and receives only its own state. Its effects contain no ordinary record command, initialization request, hidden-state or cache read, or secrecy-ledger read. Caller-known kernels can be supplied to installation; hidden kernels are named only by a slot. The installation operation chooses the role, so the caller cannot supply an opposite-role hidden reference. There is no environment-private send or transient-receive capability.

`Environment.start` is a uniform-oracle program returning an optional pair of the existing Server constructor result and the initial environment state. Constructor failure ends the open program. On success, `program` hands that same constructor result to the private world before running any command. The CE instantiation must prove that this startup is its actual generated-seed constructor at the chosen initial runtime. `program` takes an explicit `serverKid` and passes it unchanged to the canonical secrecy wrapper, matching CE's `setup.serverKeyId`. No new generator distribution is assumed by the interface.

`native` partitions the unchanged CE native interface: all coins, public hashes and the four record branches bypass the environment. `program` runs the exact existing `PqxdhDeploymentSecrecy.wrap` and `asModeO` against that partition. The test bit, fresh message and actual mode-O receive plaintexts retained by the ledger are not arguments to the registration environment. `program` returns the ledger for analysis. The future world interpreter must execute the existing source record handlers, shared primitives and production logging; `PqxdhRecordLiftRoles` supplies the ordinary-record projection and native put-back equalities, without yet supplying this interpreter.

## Successful installed kernels

The module imports `PqxdhRecordLiftSeed`. Its hidden seed is `(next32, right32)`. `KernelRef.hidden` contains only a slot. `hiddenKernel` maps `.server` and `.beacon` to the corresponding existing seed constructors, while `resolveKernel role seeds` preserves `.known kernel` and resolves `.hidden slot` through `hiddenKernel role (seeds slot)`. Server installation must use `resolveKernel .server`; Beacon installation must use `resolveKernel .beacon`. Three guarded equations record the known branch and both role-directed hidden branches. The seed assignment is an argument to this pure semantic definition, never an environment input or capability result. This definition performs no allocation, sampling or installation and makes no eager-sampling claim.

The seed constructors abbreviate the extracted `ConcreteRatchetKernel.from_counters`. The Server has send/receive counters `(1, 0)`, chains `next32`/`right32`, and empty receive cache and material slots. The Beacon has counters `(0, 1)`, chains `right32`/`next32`, and empty receive cache and material slots. `PqxdhRecordLiftSeed.serverKernel_total` and `beaconKernel_total` already prove normal return for every seed, while its sequence-one source equations give the exact successful transition shapes. The `RustM` result remains explicit. Kernel-constructor refusal adds no probability term and cannot cause seed-dependent installation acceptance. The future interpreter must make its installation `Bool` depend only on the permitted vacancy, phase and role-use checks; this is still an implementation obligation. The outer Beacon sender ID remains separate from the control's assigned ID.

The brief's former `kernelOf`-then-first-step wording is superseded by answer 26 §1: `kernelOf` alone has zero counters, and using `next32` as an initial chain before a real first step would advance it twice. CE proves its labelled installed forms resolve to these same seed kernels. The real-HKDF relations `Live`, `Finished` and `Tracked` are not imposed on hidden uniform installs; their real-origin witnesses are not supplied as assumptions.

The first Server-to-Beacon position remains item 2/CE-A1 material. The first-record `key32` and `nonce12` remain inside CE-11's environment state; there is no separate `FirstMaterial` interface type. Neither value is an input to `resolveKernel` or to any hidden-install capability. The future world draws a slot seed once at its first hidden install of either role and reuses that draw for the other role. Evolving hybrids start at `step(next32)` for Server-to-Beacon position two and `step(right32)` for Beacon-to-Server position one. They never re-randomize the first material or either seed coordinate. The slot count `n` is a parameter.

## Outstanding CE erasure equality

Production `Beacon::finish_registration` initializes the kernel, runs the full raw receive and only then checks sequence one (`beaconcrypt/src/beacon.rs:459-470`). The central model has the same order in `PqxdhBeaconPhase2Publication.afterRoot` and `afterOpening` (`PqxdhBeaconPhase2Publication.lean:72-103`). A valid later initial sequence can derive additional chain values and query the shared commitment hash before registration rejects. Dropping the staged kernel does not remove those primitive effects.

Following decision 17, answer 26 §2.3 and answer 30 §4.3, this work stays in the CE/registration lane as obligation C7. CE must prove the exact equality `CE.idealGame g = CE.idealGame° g` on the analysis projection described below. In the proposed erased game, a hidden-entry finish whose raw input does not decode to sequence one rejects without derivation or a hash query. The proposed proof removes an unused shared-ROM query while preserving the entire later observable computation; the final hidden cache is not part of the projection. The erasure equality and its accounting are outstanding proof obligations, not established facts, axioms, additional cryptographic assumptions or hypotheses of any record-lift theorem. If CE cannot discharge this equality, the interface requires another cross-lane review before being used as a source endpoint.

After that equality is proved on the CE side, its environment opens sequence one with its own first-record material, performs binding and pin checks, and requests the agreed hidden Beacon install. The interface contains no candidate object, ticket, commit/discard operation or transient-receive budget. It makes no claim to model the removed work directly. Claude proves the erased-game connection and composes it with C7, giving C1 for the original `CE.idealGame`. Neither step is a record-lift hypothesis.

## F1–F6 and resource accounting

The compiled `Frame` remains a resource predicate: it bounds startup uniform calls and each actual environment handler, including rejection paths, for coins, shared hashes and administrative capabilities. Its `allowance : Fin 14 → EffectKind → Nat` is indexed by the existing `queryClass (.inl (.inr query.val))`. Thus one fixed allowance applies to every query payload in a class, preventing arbitrarily long raw bytes from silently increasing the per-call allowance. It assumes no secrecy, authentication, independence, noninterference, alias probability or game-distance conclusion. The following F1–F6 specify the full interface obligations; the open program alone does not discharge the future interpreter obligations.

| Condition | Required boundary and current status |
| --- | --- |
| F1 | Environment record-state changes are limited to Server installation at an unoccupied ID with `.known kernel` or `.hidden slot` resolved at `.server`, legal Beacon append/phase advance/install with `.known kernel` or `.hidden slot` resolved at `.beacon`, and shared-cache hashes. Sequence-one seal/open is environment-local with its own first material. The capability types expose these requests; vacancy, role-use and phase checks remain interpreter work. |
| F2 | No seed or hidden kernel, chain, skipped-key, lazy-table or cache read is a capability. The restricted effect types provide this access boundary; this is not an assertion that adaptive public replies are statistically independent of hidden data. |
| F3 | At most one installation per `(slot, role)`. The interpreter must enforce and prove this schedule restriction; phase advance must not reset an established kernel. CE proves its environment satisfies the corresponding source schedule. |
| F4 | One unconditional uniform seed draw per slot at its first hidden install, shared by both roles. The interpreter must implement persistent lazy allocation; `resolveKernel` fixes only the resulting kernel semantics. |
| F5 | The environment issues no record command. Neither ordinary record queries nor private-send effects occur in `EnvEffects`; the exact ledger sends bypass the environment through `native`. |
| F6 | The later post handler and reveal take only environment state and public parameters. Their hashes use the world's shared cache, their coins use the world's sampler, and HMAC uses the environment's R1 table. No seed, kernel, lazy-table entry, ledger or record state is an input. This structural post boundary remains to be implemented in R6 after LQ-F integration; it is not probabilistic independence. |

`Caps` contains the unchanged CE `Budget` and a parameter `sharedHash`. `Caps.envTotal caps allowance kind` is the finite sum over the fourteen classes of `caps.outer.cap class * allowance class kind`. It describes the environment-effect allowance induced by the outer budget; startup coins are separate. The theorem that composes `Frame` with a budget-respecting client to obtain this cap remains to be proved. Its derivation expression is exactly `Budget.sends + 51 * Budget.receives`. This is a definition awaiting the ordinary-record transport theorem, not a proved cap for arbitrary programs. `Budget.sends` already includes `test` and `fresh`. Failed finish-time work and the cap comparison for erasure belong to CE; neither a transient term nor an environment-private-send term occurs in the record-lift bill.

CE-11 must establish the shared-hash parameter from `qHash + S + R + qBuild + qFinish`, with the post-phase hash cap added for R6: adversary hashes, record seals/opens, one sequence-one seal per build and at most one open per finish. This planned CE transport is not assumed or proved here, and no fixed slot count is imposed. Every logical sample and primitive evaluation must still be charged in the eventual reduction budgets.

## Analysis and public projections

The C1 and C7 analysis projection retains the transcript, CE `Logs` including `produced` with the existing `FrameTag`s, `Ledger.test`, `Ledger.fresh`, and output. CE-LOR and CE-APP inspect the chosen bit and fresh message in that private ledger. The future game result must expose `produced : List (FrameTag × PqxdhDeploymentNative.Frame)`, logged exactly by `produce`, `serverTag` and `beaconTag`. Ordinary record frames handed to the writer are retained even if the writer fails; registration seals are not added to this log. It must also expose the raw-attempt counters needed by integrity statements. Then CE's `PqxdhDeploymentKemTransfer.Observed X := X × Ledger × List (FrameTag × Frame)` can be projected from the result. Keeping `program`'s ledger result alone is insufficient. This component does not yet define the game result/projection or prove its equality.

The whole analysis record is never passed to the environment, a post handler or a reveal. Public transcript entries use `Entry.view mode`, and ordinary public replies retain the chosen observation mode. The ledger, private world state and private environment state are not thereby public outputs. Registration may depend on permitted public observations, but receives no final analysis-log or ledger read. Equality of a public view alone would be too weak for C1 because it would omit the ledger observations used by CE's application events.

## Remaining implementation and proof

This revision requests provisional typed freeze under answer 26 §6.1 with answer 30's required refinements. The optional `InactivePhase` and full-`Created` startup shapes are retained; no post or reveal currently reads that private startup request. The real interpreter must still own the dynamic record state, persistent hidden-seed table, role flags, shared BLAKE2b cache, production logs and refusal instrumentation, and satisfy F1–F6 at the stages indicated above. The existing `PqxdhRecordLiftRoles` equalities cover ordinary record commands, not complete registration interleavings or the generic game. The persistent lazy table and successful seed constructors are proved components, not completed chain or CTX lifts.

The evolving-chain hybrids, both-direction source compiler, alias/collision/refusal bounds, selected-key CTX compiler, event and Boolean two-sided bounds, and appropriate ideal-world facts remain open. Five elementary interface lemmas establish only kernel-resolution branches and reply types. No primitive contract or assumption is added. The eventual allowed component contracts remain modified nonce-AEAD IND$ and INT-CTXT, functional AEAD correctness, BLAKE2b ROM, HMAC PRF, Extract on uniform 32-byte inputs, `SourceFullCorrect`, `FrameReadBack` and `DecoderAgreement`; use in a CE headline remains a separate scope decision. No production Rust, snapshot, persistence or restoration behavior is changed or proved.
