# Mandatory ML-DSA-65 transcript authentication sketch

This sketch was initially built from a local snapshot of the in-progress Lean 4.35 port (`17c62b95`) and was subsequently rebased onto the merged `vcvio` state (`248953c9`). The original port worktree is unchanged. This implementation changes Rust and the binding surfaces required by its constructor and wire-format changes. Proof files and generated proof artifacts remain unchanged; their source-fidelity checks require a subsequent proof update.

Both parties now have independent Ed25519 and RustCrypto `ml-dsa` 0.1.1 ML-DSA-65 identities. `Server::new` and `try_new` take separate optional Ed25519 and ML-DSA seeds; each supplied seed must be 32 uniformly generated secret bytes. `None` generates an independent identity. Beacon construction requires the server's Ed25519 and ML-DSA public keys. Unsigned registration and legacy snapshots are rejected. ML-DSA seeds are persisted in snapshot version three with zeroizing decoding buffers, and peer signing-key hashes survive restore.

InitKex authentication hashes a fixed Beaconcrypt/ML-DSA-65/version domain, server key ID in LE64, pinned server Ed25519 key, agent ML-DSA key, server ML-DSA key, then the decoded identity/prekey/one-time/PQ fields in their existing order. Each variable field is prefixed with its LE64 byte length. The response hash uses a distinct domain, the InitKex hash, all decoded response byte fields including appCipherText, and assigned key ID in LE64. BLAKE2b uses a 512-bit output. Hashing uses deterministic concatenation, independently of CBOR encoding.

Each signature covers 64 space bytes, a distinct Beaconcrypt agent/server context label, a zero byte, and the transcript hash, following the CertificateVerify input pattern. ML-DSA additionally uses its fixed nonempty Beaconcrypt signing context. The signature itself is excluded from the transcript. Signing is deterministic ML-DSA over that message, rather than HashML-DSA. Verification precedes key agreement and replay consumption on the server, and precedes decapsulation and registration publication on the beacon. Existing terminal-abort semantics for a failed beacon registration response are retained.

The prototype wire envelope is `"beaconcrypt/ml-dsa-65/v1\0" || kind || [agent ML public key] || signature || existing CBOR registration payload`, with kind zero for InitKex and one for KexResponse. The public key occurs only in InitKex; the response key is pinned. Fixed ML-DSA-65 widths are 1,952 public-key bytes and 3,309 signature bytes. Complete-message limits include the envelope. This avoids changing or regenerating the CBOR codec during the sketch; there is no unsigned fallback or negotiation path.

AD is the previous 153-byte prefix followed by `BLAKE2b-512(server ML public key) || BLAKE2b-512(agent ML public key)`, totaling 281 bytes. AEAD and CTX both receive the complete AD. CTX inputs consequently grow from 229 to 357 bytes. The commitment and zero-padded RFC AEAD known answers were recalculated, and the multi-opening fixture was derived again for the new AD width; Python and Go implementations independently validate those reviewed changes. Existing Ed25519 signatures and PQXDH key agreement remain in place.

The C/Python APIs, Go backends, and WASM ABI carry the mandatory second server key. WASM ABI version two includes seed-presence flags for independent identity generation. Authentication establishes possession of the private key corresponding to the presented agent key; enrollment and authorization of that key remain application responsibilities.

Validation completed with 366 production Rust tests across every library and integration target except `proverif_transcript_fidelity`, plus 76 Python tests in the worktree's isolated environment. The unchanged proof-fidelity target still fails against the new Rust layout; no Lean build, proof regeneration, or `verify-in-shell` gate was run. Rust formatting, workspace/all-target/all-feature Clippy, and separate beacon-only/server-only feature checks passed. Clippy retains existing style warnings and the enlarged allocation-free beacon-state enum warning.

Release C and WASM builds, CGO and Wazero tests with race checks, mixed native/WASM interoperability, the Go example, strict C-example syntax checking, and 19 WASI tests plus the allocation-failure probe passed. The reviewed BLAKE2b/AEAD fixture outputs agree exactly between Python and Go generators.

The final mutation catalogs contain 1,428 native identities and 159 guest identities. All 1,023 viable native mutations and all 147 viable guest mutations are caught. The initial sweeps exposed nine native coverage gaps and one guest gap; focused runtime tests caught each survivor on rerun. Three new test-fixture mutations were also checked, and the final catalog audit has no unresolved identity. All 405 native and 12 guest unviable mutations were reviewed as genuine compiler rejections. There were no timeouts or new mutation exclusions.
