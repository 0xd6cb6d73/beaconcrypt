## Lean extraction

`beaconcrypt-core` supports extraction to Lean through Hax's **new Lean backend**:

```text
Rust
  → Charon
  → LLBC
  → Aeneas
  → Lean
```

This is the Aeneas/Charon-backed `lean` target. Do not use Hax's `legacy-lean` backend.

### Prerequisites

Run Lean extraction inside the repository's proof environment so the pinned Hax, Charon, Aeneas, Lean, and Lake versions are used.

From `beaconcrypt-core`:

```bash
nix --extra-experimental-features 'nix-command flakes' \
  develop --no-update-lock-file 'path:..#proofs'
```

The generated Lean project lives under:

```text
proofs/lean/
├── BeaconcryptCore.lean
├── lakefile.toml
├── lean-toolchain
├── BeaconcryptCore/
│   └── Extraction/
│       ├── Types.lean
│       ├── Funs.lean
│       ├── TypesExternal_Template.lean   # when required
│       ├── TypesExternal.lean            # maintained, when required
│       ├── FunsExternal_Template.lean
│       └── FunsExternal.lean             # maintained
└── llbc/
    └── beaconcrypt_core.llbc
```

`Funs.lean`, `Types.lean`, and the `*_Template.lean` files are generated by Aeneas.

`FunsExternal.lean` and `TypesExternal.lean`, when present, are maintained files. Do not delete them during regeneration.

### Extract the Lean model

The current Lean proof boundary deliberately excludes code containing function pointers and higher-order ratchet machinery:

```bash
cargo hax -C --locked ';' into lean --lakefile \
  --charon-args="\
--exclude=beaconcrypt_core::ratchet::concrete::* \
--exclude=beaconcrypt_core::ratchet::refined::* \
--exclude=beaconcrypt_core::pqxdh::concrete::*"
```

The excluded modules contain production executor plumbing:

```text
ratchet::concrete
    KDF function pointers
    concrete ratchet kernel
    concrete seal/open adapters
    restore adapter

ratchet::refined
    higher-order generic ratchet machinery

pqxdh::concrete
    initial KDF executor
    concrete ratchet-kernel construction
```

The extracted model retains the first-order protocol logic, including PQXDH state transitions, validation, transcript construction, initial ratchet-chain interpretation, ratchet data types, and ratchet control logic.

### Build the generated Lean project

After extraction:

```bash
cd proofs/lean
lake build
```

A successful build verifies that the generated Aeneas model is accepted by the pinned Lean toolchain.

### Clean rebuild

To check that the extraction is reproducible from generated state:

```bash
rm -rf proofs/lean/llbc
rm -rf proofs/lean/.lake/build

cargo hax -C --locked ';' into lean --lakefile \
  --charon-args="\
--exclude=beaconcrypt_core::ratchet::concrete::* \
--exclude=beaconcrypt_core::ratchet::refined::* \
--exclude=beaconcrypt_core::pqxdh::concrete::*"

cd proofs/lean
lake build
```

Do **not** remove the entire `proofs/lean/BeaconcryptCore/Extraction/`
directory, because it may contain maintained `FunsExternal.lean` or
`TypesExternal.lean` files.

### Makefile targets

The extraction can be exposed through separate Lean verification targets:

```make
LEAN_DIR := proofs/lean

LEAN_CHARON_ARGS := \
	--exclude=beaconcrypt_core::ratchet::concrete::* \
	--exclude=beaconcrypt_core::ratchet::refined::* \
	--exclude=beaconcrypt_core::pqxdh::concrete::*

.PHONY: extract-lean check-lean verify-lean verify-lean-in-shell

extract-lean:
	rm -rf $(LEAN_DIR)/llbc
	cargo hax -C --locked ';' into lean --lakefile \
		--charon-args="$(LEAN_CHARON_ARGS)"

check-lean:
	cd $(LEAN_DIR) && lake build

verify-lean:
	$(NIX) --extra-experimental-features 'nix-command flakes' \
		develop --no-update-lock-file '$(PROOF_SHELL)' -c \
		$(MAKE) verify-lean-in-shell

verify-lean-in-shell:
	$(MAKE) check-toolchain
	$(MAKE) extract-lean
	$(MAKE) check-lean
```

Keep Lean verification separate from the existing F*/ProVerif verification
target until changes to the Lean proof boundary are intentional.

## Writing Aeneas-compatible Rust

The Aeneas Lean backend currently supports a smaller Rust surface than normal
Rust or the existing F* extraction. Code inside the Lean-visible boundary
should follow the conventions below.

### Construct fixed arrays functionally

Avoid mutation through array or slice indexing:

```rust
let mut bytes = [0; N];
bytes[a..b].copy_from_slice(source);
```

Prefer `core::array::from_fn`:

```rust
let bytes: [u8; N] = core::array::from_fn(|i| {
	if i < FIRST_END {
		first[i]
	} else {
		second[i - FIRST_END]
	}
});
```

This avoids generated references to unsupported operations such as:

```text
core.Array.Insts.CoreOpsIndexIndexMut.index_mut
core.slice.Slice.copy_from_slice
core.array.Array.as_mut_slice
```

Padding or unused output ranges should also be represented functionally:

```rust
let bytes: [u8; ROOT_KEY_INPUT_SIZE] = core::array::from_fn(|i| {
	if i < PQXDH_PADDING_SIZE {
		0xff
	} else if i < PQXDH_PADDING_SIZE + DH_SECRET_SIZE {
		secrets.dh1[i - PQXDH_PADDING_SIZE]
	} else {
		// ...
	}
});
```

### Avoid `!=` in Lean-visible code

The generated Lean core model supports the equality path used by `==`, but the
current extraction produces unsupported `PartialEq::ne` references for `!=`.

Write:

```rust
if !(lhs == rhs) {
	// ...
}
```

instead of:

```rust
if lhs != rhs {
	// ...
}
```

This applies to scalar and array comparisons, including compile-time
assertions.

### Gate implementation-only derives during Hax compilation

Some derives generate implementations that Aeneas does not need and cannot
currently translate.

In particular, derive `Debug` only outside the Hax compilation:

```rust
#[derive(Clone, Copy, Eq, PartialEq)]
#[cfg_attr(not(hax_compilation), derive(Debug))]
pub struct Example {
	// ...
}
```

Charon invokes rustc with:

```text
--cfg=hax_compilation
```

so the `Debug` implementation is absent from the extracted crate while normal
Rust builds retain it.

The same pattern can be used for implementation-only traits such as
`Zeroize` and `ZeroizeOnDrop` when those implementations are not part of the
proof model:

```rust
#[cfg_attr(
	not(hax_compilation),
	derive(Zeroize, ZeroizeOnDrop)
)]
pub struct RatchetChain {
	// ...
}
```

Normal Rust builds must continue to retain the zeroization behavior.

If `rustc` warns about the custom configuration name, declare it in
`Cargo.toml`:

```toml
[lints.rust]
unexpected_cfgs = { level = "warn", check-cfg = ['cfg(hax_compilation)'] }
```

Merge this with an existing `[lints.rust]` table rather than creating a
duplicate table.

### Avoid higher-order values in the proof-visible boundary

Aeneas currently rejects function-pointer and higher-order signatures such as:

```rust
fn(&Request) -> Output
```

and callback-bearing generic APIs.

Keep those values behind first-order module boundaries. `beaconcrypt-core`
uses:

```text
ratchet::concrete
pqxdh::concrete
```

for executor binding and production adapter logic.

The proof-visible side should instead expose first-order operations such as:

```text
construct request
        ↓
external primitive
        ↓
fixed-width output
        ↓
interpret/split output
```

For example, `split_initial_ratchet_kdf_output` and
`split_ratchet_kdf_output` remain proof-visible, while invocation of the KDF
executor remains in the excluded concrete module.

### Avoid `?` if `Try::branch` appears

If generated Lean reports missing identifiers such as:

```text
core.result.Result.Insts.CoreOpsTry_traitTry.branch
core.option.Option.Insts.CoreOpsTry_traitTry.branch
```

rewrite `?` explicitly.

Instead of:

```rust
let value = operation()?;
```

use:

```rust
let value = match operation() {
	Ok(value) => value,
	Err(error) => return Err(error),
};
```

For `Option`:

```rust
let value = match operation() {
	Some(value) => value,
	None => return None,
};
```

Only perform this rewrite when the affected code is inside the Lean-visible
boundary.

## Generated external files

Aeneas may generate:

```text
FunsExternal_Template.lean
TypesExternal_Template.lean
```

When the generated Lean imports the corresponding non-template module, create
the maintained file once:

```bash
cp BeaconcryptCore/Extraction/FunsExternal_Template.lean \
   BeaconcryptCore/Extraction/FunsExternal.lean
```

and, when required:

```bash
cp BeaconcryptCore/Extraction/TypesExternal_Template.lean \
   BeaconcryptCore/Extraction/TypesExternal.lean
```

Subsequent extraction should preserve these files.

Do not add arbitrary missing core-model definitions to the external files.
They are intended for external definitions explicitly requested by Aeneas,
not for patching unsupported generated Rust/core operations.

## Known non-fatal Charon warning

The current toolchain may print a warning similar to:

```text
cargo miri setup failed ...
unknown `-Z` flag specified: json-target-spec
```

Charon currently falls back to rustc's default sysroot after this warning.
If the crate compiles and Aeneas subsequently runs, this warning is not the
cause of Lean extraction failures.

## Verification boundary

The current successfully built Lean boundary is:

```text
beaconcrypt-core
├── commitment                 extracted
├── pqxdh                      extracted
│   └── concrete               excluded
└── ratchet
    ├── control                extracted
    ├── concrete               excluded
    └── refined                excluded
```

Any change that moves higher-order executor plumbing back into an extracted
module, or introduces unsupported mutable array operations, should be expected
to require either a source-level normalization or an intentional change to
the Charon exclusion boundary.
