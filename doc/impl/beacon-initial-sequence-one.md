# HB-95: require sequence one for Beacon registration

This focused topic implements the user's 7 September 2026 requirement that Beacon registration accept only the initial record at sequence 1. It starts from `codex/full-proof-composition` at `666867e30c6d6bf61437f8c9ae99f7dbdf168153`. The separate computational-symbolic proof effort remains paused; this change addresses the registration admission policy and the models and validation affected by it.

## Production behavior

`Beacon::finish_registration` checks `decrypted.seq != 1` immediately after the existing authenticated decrypt returns and before reading the sender, splitting the plaintext binding or publishing the assigned identity and ratchet. The sequence comes from the successful open request, whose commitment binds that sequence. Failure returns from the staged closure and follows the existing terminal abort path, dropping the private registration material and uncommitted candidate ratchet. A valid original response still consumes only sequence 1 and establishes an empty receive cache.

The Server already emits its registration response as its first send. A genuine later same-session application record is now rejected even when it contains the correct eight-byte binding, or a binding matching a changed outer routing ID. This closes the previous later-record substitution path. The generic receive ratchet and its 50-skipped-key capacity are unchanged: after successful registration, receiving sequence 3 before sequence 2 still works, consumed keys reject replay, and later future traffic remains possible.

The wire format, cryptographic primitives, KDF labels, authenticated binding format and public function signatures are unchanged. All language bindings use the same Beacon registration implementation. The separate X25519 alternative-encoding witness can still preserve a genuine sequence-one record, so raw response-byte equality is not claimed by this policy change. The full computational-symbolic bridge remains incomplete.

## Tests and model scope

Production regressions replace the former successful later-completion cases with terminal rejection for every sequence from 2 through 51, plus the cache-bound and malformed-input cases. They check that the assigned ID, operational ratchet and private pending keys are not published after failure, and the valid original response cannot revive the aborted Beacon. The former later-record relabel witness is now a rejection test. Positive original-response and established-session out-of-order/replay tests remain.

A native unit fixture uses the actual accepted root, initial sender chain and associated data to seal sequence-one plaintexts of lengths 1 through 8, a wrong binding, and a valid binding plus application byte. The valid case succeeds, so the malformed cases exercise the original plaintext/binding checks rather than failing only because of a later sequence.

The ProVerif transition applies the policy after successful opening. Later registration commit is unreachable, while a deliberately omitted-check process retains the substitution witness as a negative control. An authenticated sequence-three opening before the gate remains reachable, distinguishing the new policy from decryption failure. The post-registration process now starts with actual sequence-one completion and continues through ordinary sequence three, cached sequence two, replay rejection and future sequence four. Underlying raw-receiver 1–51 admission lemmas remain valid but do not describe registration completion at those later targets.

The Lean model adds the same post-opening decision. `Pqxdh.beaconRecordAdmitted_sequence` proves that every accepted or subsequent plaintext-format outcome has sequence one for arbitrary modeled states and cryptographic operations. `CtxTransitionReduction.beaconWrongSequenceAdvantage_eq_zero` proves exact zero for the existing wrong-sequence registration event, without an honest-run correctness or collision premise. Its scope is registration admission, not general raw decryption. `completeBeacon_refines` connects the updated composed driver to the ideal transition, including the new rejection branch and the retained sequence-one established state. The narrower extracted-core driver does not receive a sequence field, so `beaconFinishDriver_refines` explicitly requires the adapter to have established sequence one. The general raw-receiver proofs retain their existing statements and exact poststates. Earlier model-level sender and nonzero prechecks retain their existing abstraction; this focused update does not establish a new equality of every native primitive effect and its evaluation order.

These changes add no primitive security assumption, reduction loss or primitive oracle call. A rejected later candidate still executes the existing receive and cryptographic operations before the new decision; that work is not removed from source accounting. The two new guarded dependency reports contain only standard Lean classical and quotient axioms.
