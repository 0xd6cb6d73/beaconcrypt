## The experiment a composition theorem must cover

A protocol adversary must be able to create and schedule sessions, register attacker-owned identities, deliver arbitrary wire bytes, request honest records, observe public transcripts and permitted outputs, and reveal explicitly chosen identity, root, current-chain or skipped-key state. Session identifiers used only in a proof are not extra KDF domain bytes. The production KDF uses exactly two public labels; directional separation comes from opposite selections of the initial split, and every later key, nonce and next chain is derived together from the current chain.

A freshness rule must exclude disclosures that reveal or derive the target message key at any point before the adversary’s final decision, including after the challenge. It must separately record permitted later chain disclosures that cannot recover already erased past material. Revealing the current chain compromises its descendants: there is no post-compromise recovery. A retained live skipped key can expose a past target. Integrity of state ownership and replay history is an execution premise, not a consequence of key secrecy.

For a justified finite hybrid chain, the triangle inequality sums the adjacent distinguishing distances; it does not bound any distance by itself. If a reduction guesses one of `s` eligible sessions or `q` target records, the corresponding guessing loss is at most `s` or `q` only after proving that selection distribution and simulation. Adaptive stopping, compromise filtering, and multiple accepted attempts can change the counting. We therefore do not publish a numeric network-forgery bound obtained by multiplying existing component advantages by informal session counts.

Similarly, random-table collision bounds count distinct canonical `(domain, input, projection)` identities. Repeated observations and the intentional initial/step prefix alias at the same input are not independent samples. Distinct 32-byte coordinates yield the usual pair-count term divided by `2^256`, while distinct 12-byte nonce coordinates yield a pair-count term divided by `2^96` in that ideal experiment. Transferring those bounds to fixed production HKDF is precisely where the unsupported public-table hop must not be used. Nonce uniqueness across unrelated keys is also different from the per-key nonce discipline required by AEAD.

## Primitive guarantees, additional assumptions and idealizations

ML-KEM IND-CCA concerns hiding an honestly encapsulated secret under a target public key despite permitted decapsulation queries. The symbolic equation `mlkem_shared_secret(public_key, coins)` additionally treats that constructor as injective in the public key: equality of secrets forces equality of selected public keys. This is a stronger cross-key statement. To see why generic IND-CCA cannot imply it, append an ignored public tag to an IND-CCA KEM's public key and leave the encapsulation algorithm unchanged. The independent tag adds no information about the challenge secret, yet two differently tagged public keys with the same underlying key and coins produce the same secret. This separation is mathematical reasoning, not a machine-checked security reduction for ML-KEM. The repository's strong/weak re-encapsulation controls expose reliance on the stronger equation. A concrete ML-KEM binding analysis must state how keys and coins are chosen, account for invalid keys and implicit rejection, and bound cross-key collisions in that interface.

Ordinary Ed25519 EUF-CMA gives the adversary signatures but does not automatically give it DH computations using the X25519 scalar derived from the same identity seed. A protocol authentication reduction must simulate that extra interface while retaining the signing challenge. Conversely, an X25519 assumption must tolerate the correlated signing public key and signature transcript. The maintained `PqxdhJointIdentity` family exposes the exact correlated public-key, signature and converted-DH interface and its ordinary fresh-valid forgery event. The current actual-source authentication reductions use that explicit joint-use contract; the earlier stopped one-session reduction alone does not simulate every related use. The KEM reduction generates the identity locally, and the source server computes DH with its own seed/ephemeral and public conversion of the beacon identity. Replicated related uses and compromises still require the same joint interface throughout the common experiment. The global proof must supply a matching joint-use interface or a reduction that avoids every unavailable secret; see the reviewed [deployment contract](deployment-boundary.md).

ProVerif free constructors and destructors supply perfect opacity, constructor injectivity and exact equalities. BLAKE2b collision resistance is a concrete additional assumption for collision-witness bounds; treating its outputs as a programmable classical random oracle is a stronger modeling idealization for privacy/authentication hops. Neither collision resistance nor a standard AEAD primitive name alone supplies that random-oracle behavior. The HB-111 and HB-112 games use this idealization, with one lazily sampled cache shared by the CTX commitment, the KDF callbacks and the adversary's direct queries, and the HB-126 and HB-127 CTX games use the same shared-cache random oracle. None of these classical experiments proves quantum-random-oracle or post-quantum authentication security.

The HB-111 and HB-112 bounds contain the advantage of an explicitly constructed reduction against the correlated Extract family `PqxdhCorrelatedExtractFamily`. That family is a generic adaptive game over an arbitrary client, not a game tied to the protocol adversary. It samples one hidden uniform 32-byte string `s` once; `s` occupies the ML-KEM shared-secret position of the root input. Each client query `m` of 128 bytes is answered with zero-salt HMAC-SHA-512 of `FF^32 || m || s` in the real game and by a lazily sampled random function in the ideal game. This is an additional, non-standard split-key PRF assumption in the dual-PRF style, which keys HMAC through its message input. It is not implied by the HMAC PRF assumption, which places the secret key in the key position, or by extractor results for high-entropy inputs. As a plausibility note, not a proof: `s` lies in the last SHA-512 block of the inner hash, after 160 adversary-chosen bytes, and the best known generic attacks cost about `2^256` work. Backendal, Bellare, Günther and Scarlata, ["When Messages are Keys: Is HMAC a dual-PRF?"](https://eprint.iacr.org/2023/861) (CRYPTO 2023), analyse this kind of use of HMAC and show that its security depends on how the key-carrying message is positioned; no published result covers this exact 192-byte input shape. Every term of the HB-111 and HB-112 bounds is stated as the advantage of a constructed reduction, so bounding this term for that reduction does not make the family game adversary-specific.

The Server-authentication proof (Milestone B, route R1, in progress) adds one hardness assumption, one idealization and three functional contracts. The hardness assumption is the advantage of a constructed reduction against the existing game `PqxdhJointGapDh.game` (named `PqxdhServerAuthAssumptions.serverGapDhAdvantage`): anchored two-sided strong CDH on X25519, where the adversary sees the Server's identity public key and the Beacon's prekey and gets decision services that answer whether a candidate is the X25519 output of one of the two hidden secrets with a chosen peer, on every 32-byte input the function accepts, including points of the quadratic twist. It strengthens textbook Gap-DH (Okamoto and Pointcheval, PKC 2001) rather than following from it; each service is a strong-DH oracle in the sense of Abdalla, Bellare and Rogaway (CT-RSA 2001), Signal's PQXDH specification assumes Gap-DH on Curve25519, and the twist-inclusive form is plausible because Curve25519's twist is secure (Bernstein, PKC 2006; RFC 7748). The idealization models zero-salt HKDF-Extract on 192-byte inputs, the width of the PQXDH root input, as a programmable random oracle, next to the existing BLAKE2b random oracle; it is implied by modelling the whole zero-key HMAC-SHA-512 as a random oracle, and every other HMAC use stays real (`PqxdhExtractRomSeparation`, `PqxdhExtractRomFamily`). The functional contracts, stated as explicit premises like `dh_comm`, are the X25519 class law (equal outputs under one scalar imply equal outputs under every scalar), the X25519 scalar-spread law (for a fixed peer, a nonzero output comes from at most 64 scalar strings), and nonzero honest DH (X25519 with an honest public key is never all-zero, used only by the negative controls); all three are facts about clamped X25519 on Curve25519 and its twist (RFC 7748).
