## Lean extraction

`beaconcrypt-core` supports extraction to Lean through Hax's **new Lean backend**:

```text
Rust
  → Charon
  → LLBC
  → Aeneas
  → Lean
```

This is the Aeneas/Charon-backed `lean` target. Do not use Hax's `legacy-lean` backend.

### Prerequisites

Run Lean extraction inside the repository's proof environment so the pinned Hax, Charon, Aeneas, Lean, and Lake versions are used.

From `beaconcrypt-core`:

```bash
nix --extra-experimental-features 'nix-command flakes' \
  develop --no-update-lock-file 'path:..#proofs'
```

### Extract the Lean model

The default production core is first-order at its cryptographic boundary and is translated without Charon module exclusions:

```bash
cargo hax -C --locked ';' into lean
```

This includes `ratchet::control`, `ratchet::refined`, the production `ratchet::concrete` effect phases, deterministic PQXDH logic, and the `pqxdh::concrete` initial-KDF phases. Translation coverage is not theorem coverage: successful extraction shows that Charon and Aeneas accepted the Rust source, while `lake build` checks the generated definitions and imported handwritten files. A refinement theorem is still needed before a newly translated transition can be called verified against the handwritten ideal model.

### Build the generated Lean project

After extraction:

```bash
cd proofs/lean
lake build
```

A successful build verifies that the generated Aeneas model is accepted by the pinned Lean toolchain.

The imported `Computational/PqxdhJointKdf.lean` module models the production HKDF-SHA-512/no-salt wrapper as one canonical 76-byte stream for each exact `(info, input)` address. The typed public projection surface has only the source constants `INFO_PQ` and `INFO_R`: the PQXDH root is `first32` under `INFO_PQ`, the initial ratchet output is `first64` under `INFO_R` split into `first32` and `second32`, and a ratchet step at the same `INFO_R` address is `first32`, `second32`, and `final12`. It proves exact output widths, domain/address separation, same-address cache consistency, initial/step projection equality, and exact 64/76-byte prefix consistency without inventing phase, role, direction, sequence, session, peer, or output-length tags. `ProductionHkdfPrefixConsistent` is an explicit functional/source contract relating the fixed production wrapper calls, not a cryptographic-security theorem or an axiom strengthening `Pqxdh.Crypto`.

The imported `Computational/PqxdhJointKdfGame.lean` module exposes all three public projections under exactly those two typed domains while backing them with one shared lazy 76-byte answer per address. Cache hits reuse the stored stream with no sampling; misses draw and install exactly 76 uniform bytes. The named primitive source accepts raw `(info, input)` stream addresses, but the constructed forwarding reduction has a checked invariant showing that it emits only the two typed production-domain images. The reduction preserves a `qU` adversary-uniform bound and a `qKdf` logical projection/complete-stream bound with factor one, and exact experiment equalities end at the deliberately named fixed BeaconCrypt HKDF-SHA-512/no-salt joint-stream real-or-random advantage. This endpoint is not presented as an ordinary secret-key PRF game because the inputs and public domains vary and no hidden PRF key is modeled; the proof does not analyze HKDF, HMAC, or SHA-512 internals or propose a substitute KDF.

The imported `Computational/PqxdhHiddenRoot.lean` module begins after the final 32-byte coordinate of the source input `FF^32 ‖ DH1 ‖ DH2 ‖ DH3 ‖ DH4 ‖ hidden32` is independently uniform. It proves the exact 192-byte layout and injectivity, forwards every adversarial root- or symmetric-domain projection, and compares the shared lazy stream with an independent honest root by programming one complete 76-byte stream so later projections remain consistent. The candidate vector allocates one optional slot per logical adversarial root-domain query, on both cache hits and misses, and the sticky bad event fires when such a query's exact-layout candidate equals the hidden coordinate. Symmetric-domain queries, the reduction-owned honest lookup, and handler-internal miss sampling allocate no candidate slot, giving the bound `qRoot / 2^256`. A checked whole-reduction invariant covers the hidden-coordinate sampler, the honest `INFO_PQ` lookup, and the forwarded computation and proves that the packaged reduction emits no stream address outside the exact `INFO_PQ` and `INFO_R` images. The capstone is `Adv(root real, independent root) ≤ Adv_fixed-HKDF-SHA-512-joint-stream(reduction) + qRoot / 2^256`; the reduction uses at most `qU + 32` uniform-byte queries, `qRoot + 1` root-domain queries, `qSym` symmetric-domain queries, and `qRoot + qSym + 1` stream queries total. It makes no ML-KEM IND-CCA or public-key-binding claim, adds no output-collision term, and does not by itself compose the complete ProVerif protocol into a computational theorem.

The imported `Computational/PqxdhProjectionCollisions.lean` module proves the computational noncollision property needed for source-observed fixed-HKDF projections. A canonical 32-byte identity is an exact stream address paired with `first32` or `second32`, while a canonical 12-byte identity is an exact address paired with `final12`; repeats and the required initial/step aliases at the same identity are cache equality rather than bad events, but `first32 = second32` at one address and every other equality across distinct same-width identities are covered. The checked stream equivalence splits one uniform 76-byte answer exactly into independent 32-byte, 32-byte, and 12-byte coordinates, and an adaptive distributional normalization preserves the adversary result plus exactly the projections returned to source calls while removing unobserved latent coordinates. For source-call caps `r`, `i`, `s`, `pF`, `pS`, and `pN`, the theorem derives `qF = r + i + s + pF`, `qS = i + s + pS`, `qN = s + pN`, and one challenger stream call per logical source call, then proves `Pr[collision] ≤ ofReal(Adv_fixed-HKDF-SHA-512-joint-stream(reduction)) + choose(qF + qS, 2) / 2^256 + choose(qN, 2) / 2^96`. The named primitive advantage is charged once; the reduction separately preserves the `qU` uniform-query cap, makes at most `r + i + s + pF + pS + pN` complete-stream queries, and emits no raw address outside the exact `INFO_PQ` and `INFO_R` images. The `qU` samples and challenger-internal lazy-cache randomness are absent from both birthday terms. This proves noncollision only among source-observed same-width HKDF outputs; arbitrary attacker-chosen raw-value equality, cross-width encodings, preimage resistance, end-to-end constructor soundness, and HKDF/HMAC/SHA-512 internals remain separate obligations.

The imported `Computational/PqxdhKemIndCca.lean` module gives one honest source-shaped ML-KEM-768 leg an exact generic IND-CCA endpoint while leaving the KEM opaque. Its untagged primitive public-key, ciphertext, and shared-secret types have the production widths 1184, 1088, and 32 bytes; the separate one-byte wire algorithm marker and parser remain outside this theorem, and the decapsulation-key type remains abstract. The two fixed branches share one key generation and unrestricted pre-challenge phase, run one honest encapsulation, always draw one ghost uniform 32-byte secret, and pass either the encapsulated or ghost secret privately to the same post-challenge continuation. The public challenge transcript contains only the selected public key, exact challenge ciphertext, and opaque caller context. After the challenge, the exact challenge ciphertext returns `none` without a primitive decapsulation call, while every unequal ciphertext is forwarded exactly once. Under the runtime's pure, bind, lifted-sampling, and totality laws, `oneKey_indCCAAdvantage_eq_branchDist` proves that the real-versus-uniform branch distance equals one `KEMScheme.IND_CCA_Advantage` with coefficient one and no factor two. Separate pre/post client caps `qUPre/qUPost`, `qBPre/qBPost`, and `qDPre/qDPost` are preserved exactly by packaging; their raw structural sums are `qUPre + qUPost`, `qBPre + qBPost`, and `qDPre + qDPost`, and the post-phase primitive-forwardable decapsulation count is at most `qDPost`. These caps exclude ambient-oracle work internal to opaque KEM operations; the hidden bit and ghost sample are runtime draws rather than adversary uniform queries. The source branch uses the encapsulator's `kReal` directly, and a separate probability-one generic KEM-correctness theorem identifies any supported direct honest `decaps sk cStar` result with `some kReal`. The module proves no ML-KEM internals, deterministic-coins bridge, public-key injectivity or cross-key binding, cross-key shared-secret uniqueness, multi-user composition, QPT lifting, or end-to-end protocol theorem.

The imported `Computational/PqxdhEd25519EufCma.lean` module gives the sole successfully returned Phase-1 bundle for one target honest Beacon identity a coefficient-one weak EUF-CMA endpoint while leaving Ed25519 opaque. It fixes the raw public-key and signature widths at 32 and 64 bytes, uses the exact tagged identity, prekey, one-time, and 1184-byte ML-KEM public-key encodings, and represents an attached field as the exact 64-byte signature prefix followed by its message. The honest client signs prekey, one-time, then PQ; the source-shaped acceptance view verifies PQ, prekey, then one-time and parses the core tuple in identity, prekey, one-time, PQ order. General acceptance still permits attacker-owned self-signed identities: the bad event separately filters for the honest target public key and a decoded key tuple different from the one honest tuple. The reduction deterministically selects the first changed field in server verification order, proves its canonical raw message was absent from all three signing queries, and obtains `Phase1FieldSubstitutionAdvantage ≤ SignatureAlg.unforgeableAdv.advantage` with coefficient one, no factor three, and no additive collision term. The wrapper makes at most three logical signing-interface calls and every successfully returned path has exactly the ordered message log `[prekey, one-time, PQ]`; material and adversary base caps compose as `qMaterial + qAdversary`. Those counts exclude ambient work inside opaque key generation, signing, and verification. Honest attached opening is a separate consequence of generic `SignatureAlg.PerfectlyComplete`, deterministic detached verification, explicit runtime pure/bind evaluation laws, and a named source-adapter premise equating production attached verification with exact splitting plus detached verification. Protocol use is scoped by HB-62's one-successful-`Some` lifecycle, while the Lean theorem itself assumes one successful transcript and makes no coherence claim for multiple successful bundles. It proves no Ed25519 internals, libsodium/FFI/Cap'n Proto/compiler refinement, signature uniqueness or strong EUF, public-key uniqueness, multi-user lifting, attacker-owned-registration exclusion, reveal safety, QPT claim, or end-to-end theorem; in particular it stops before production's related-key Ed25519-to-X25519 conversion.

The imported `Computational/CtxReduction.lean` theorem defines the modified-CTX misattribution event over the handwritten ideal PQXDH record model and reduces its probability losslessly to VCVio's standard collision-resistance advantage for the same `Crypto.blake2b` function. The adversary supplies one arbitrary raw payload and two well-formed explanations, and the reduction returns the exact unequal CTX preimages built from the shared parsed tag. Honest-seal specializations expose concrete collisions for wrong-sequence, wrong-sender, and cross-session acceptance. The proof assumes no AEAD security and makes no random-oracle replacement. It does not prove BLAKE2b collision resistance, track PPT cost, or connect the ideal transcript and hash call to the extracted production builder and adapter; see [`../../../doc/impl/vcvio-feasibility.md`](../../../doc/impl/vcvio-feasibility.md).

The imported `Computational/CtxSplitCache.lean` module gives the canonical lazy-ROM cache an exact split representation. Non-prefix inputs remain complete in a public cache, while inputs beginning with the hidden 32-byte key are stored by the key-free suffix after that prefix. `merge_splitCtxCache` proves that merging a canonical projection returns the original cache extensionally, and `splitCtxCache_merge` proves the converse for normalized split caches. The module also proves that an honest modified-CTX outer input projects to exactly `N ‖ AD ‖ T ‖ LE64(seq) ‖ LE64(sid)`, whose retained-tag instance has 197 bytes.

The imported `Computational/CtxIndependentTags.lean` module lifts that representation through every public and sealing query and through the complete adaptive adversary run. In the routed split handler, public secret-prefix queries and honest seals address the suffix cache; in the key-free independent-tag handler, every adversary ROM query uses only the complete-input public cache while honest seals use only the suffix cache. The handlers agree until the exact sticky public-prefix event, and the uniform-key capstone proves `Δ(ctxSplitBeforeVerifyGame, ctxIndependentTagGame) ≤ Pr[public ROM query with hidden-key prefix]`, charging that event exactly once.

The imported `Computational/CtxHonestTagSampling.lean` module proves that the first 12 bytes of an honest suffix determine its nonce and maintains an adaptive split-state invariant covering marked nonces, pairwise-unique successful-seal nonces, and suffix-cache provenance. An unused nonce therefore forces a suffix-cache miss. `ctxIndependentTagImpl_run_eq_directSample` replaces the complete lazy-suffix execution exactly by a handler that draws one fresh uniform `CtxDigest` after each successful base-AEAD seal; repeated nonces return `none` without sampling. The uniform-key games are equal, so this hop adds no statistical term and the previous secret-prefix event remains charged exactly once.

The imported `Computational/CtxNonceAeadIntCtxt.lean` module defines a nonce-rejecting modified nonce-AEAD INT-CTXT game with complete `(nonce, AD, ciphertext)` freshness and constructs the retained-base forger. The reduction simulates public ROM calls using only private uniform samples, maps each fresh CTX seal to exactly one primitive seal call followed by one independent 512-bit outer-tag draw, and rejects repeated nonces before the primitive call. Exact per-query state projections lift through the adaptive run and uniform-key games, so `ctxFreshAcceptedRetainedBaseProbability_le_intCtxtAdvantage` charges every fresh retained-base acceptance to the constructed primitive advantage with factor one. `ctxRetainedBaseReduction_seal_query_bound` additionally proves that every source `qE` seal-query bound is preserved by the primitive forger. Exact uniform-byte accounting is composed in `CtxComputationalSecurity.lean`; asymptotic PPT preservation remains external.

The imported `Computational/CtxNonceAeadIndDollar.lean` module turns each of at most `qH` public ROM inputs into one optional candidate for the hidden 256-bit key. It proves that the canonical secret-prefix probability is exactly the real key-probe experiment for a modified nonce-AEAD IND$ reduction. In the nonce-rejecting random world, length-matched ciphertext bodies and 16-byte tags are sampled independently and a ghost key is sampled only after the adversary finishes, so the candidate-hit probability is at most `qH / 2^256`. The resulting bound is one key-probe IND$ advantage plus that explicit upper-bound term. The reduction preserves the source `qE` primitive-seal bound, and the source has total public/seal query bound `qH + qE`. This deliberately named key-probe notion is retained as a tighter specialized alternative; the next module supplies the conventional Boolean IND$ bridge.

The imported `Computational/CtxNonceAeadIndDollarValidation.lean` module bridges those returned key candidates to a conventional Boolean modified nonce-AEAD IND$ game. When `qE < 2^96`, it selects a nonce absent from the complete source seal history, makes one extra empty-message validation encryption, and compares the returned 128-bit tag with locally recomputed tags under all `qH` candidates. A true key hit always validates in the real world, while the fresh random-world tag matches with probability at most `qH / 2^128`. Thus `Pr[secret prefix] ≤ ofReal(Adv_IND$) + qH / 2^128`; the conventional reduction makes at most `qE + 1` primitive seals. The exact fresh-nonce choice and structural query bounds are checked, but asymptotic efficiency is not encoded.

The imported `Computational/CtxComputationalSecurity.lean` module defines the actual typed full-fresh one-key modified-CTX game on the exact canonical split-cache surface. A new reachable-state invariant proves that every honest commitment remains installed at its exact key-free suffix, allowing every accepted full-fresh target to be classified as either a fresh retained-base forgery or a context-alias replay. The canonical-to-direct hop charges the secret-prefix event exactly once and the direct alias branch costs one fresh 512-bit digest guess. The conventional capstone, under `qE < 2^96`, proves `Pr[typed CTX forgery] ≤ Adv_INT-CTXT + ofReal(Adv_IND$) + qH / 2^128 + 2^-512`; a second theorem retains the stronger specialized key-probe bound with `qH / 2^256`. The accounting record proves a source bound of `qH + qE`, preserves `qE` primitive seals for the factor-one and key-probe reductions, gives the conventional validation reduction `qE + 1` seals, bounds private uniform randomness by `64(qH + qE)` byte queries, bounds the conventional reduction's complete primitive interface by `64qH + 65qE + 1` calls, accounts for 32 key-sampling queries in the real primitive games, and bounds the complete direct CTX game including final verification by `96 + 64(qH + qE)` uniform-byte queries. The conventional interface count does not include the random challenger's plaintext-length-dependent ciphertext sampling; a complete conventional-game coin bound additionally needs a total plaintext-length budget. The theorem remains a typed single-key classical-ROM result; raw-payload normalization, multi-key composition, production correspondence, and asymptotic PPT preservation remain outside this capstone.

The imported `Computational/CtxComputationalPrivacy.lean` module proves component-level confidentiality preservation for the same modified-CTX sealing surface. A bounded Boolean adversary receives adaptive access to the consistent public lazy ROM and a nonce-rejecting chosen-plaintext seal oracle, then returns one decision bit. The real game samples one hidden 256-bit key and returns the actual `C || T || T*` record; the ideal game preserves plaintext length and nonce-reuse leakage while sampling each fresh body, 16-byte base tag, and 64-byte outer commitment independently, without conditioning away natural collisions. Split-cache isolation charges the public hidden-key-prefix event exactly once, honest outer commitments become one exact independent `CtxDigest` sample per successful fresh seal with zero loss, and a Boolean view reduction has exact real and random primitive-game equalities. The structural bound is `ofReal(Adv_CTX-privacy) ≤ ofReal(Adv_IND$(R_view)) + Pr[prefix]`; substitution gives the specialized `ofReal(Adv_CTX-privacy) ≤ ofReal(Adv_IND$(R_view)) + ofReal(Adv_IND$-probe(R_prefix)) + qH / 2^256` and, for `qE < 2^96`, the conventional `ofReal(Adv_CTX-privacy) ≤ ofReal(Adv_IND$(R_view)) + ofReal(Adv_IND$(R_validate)) + qH / 2^128`. These are two distinct primitive reductions. There is no INT-CTXT, collision-resistance, birthday, `2^-512`, or commitment-guessing term in the privacy theorem. Accounting proves source total `qH + qE`, `qE` primitive seals for the view and probe reductions, `qE + 1` for validation, `64(qH + qE)` reduction-side uniform-byte calls, and primitive-interface totals `64qH + 65qE` or `64qH + 65qE + 1`. Those fixed counts deliberately exclude challenger-private length-matched bodies and 16-byte tags; a complete ideal-world coin bound needs a total plaintext-byte budget. This result justifies the confidentiality half of ProVerif's ideal `seal_frame`/`open_frame` component under the stated primitive assumptions, but it does not mechanically turn the complete ProVerif analysis into an end-to-end computational theorem.

The imported `Computational/VCVioFeasibility.lean` pilot uses the immutable VCVio v4.31.0 commit recorded in `lakefile.toml` and the manifest. It specializes VCVio's tight and looser collision-resistance-chain bounded adaptive random-oracle binding theorems to the Aeneas-extracted 229-byte commitment-transcript type and a 512-bit digest, and it checks exact one- and two-call behavior for a linked private consuming-key store. It is feasibility evidence, not a checked embedding of beaconcrypt's CTX game, a complete state-separated composition, or a production security theorem; see [`../../../doc/impl/vcvio-feasibility.md`](../../../doc/impl/vcvio-feasibility.md).

The imported `RatchetEffect.lean` layer proves structural laws directly against generated phase definitions: exact initial requests and role starts, core-owned response partitioning, exact send/receive requests, context preservation, entry-state recovery on cancellation/rejection/failed open, advanced-state return on either seal result, and publication of the same successful plaintext.

The imported and checked `RatchetEffectRefinement.lean` adds a precise `KernelRefines` relation tying control, both counters/chains, and the live concrete cache bidirectionally to ideal send/receive states; `ResponseRefines` isolates the assumed law that a typed KDF response realizes the ideal chain and message-material step. It proves the non-exhausted send path from `begin_send` through response resume and successful `SendSeal::finish`, plus cancellation; receive KDF cancellation, open rejection, and failed open preserve refinement; and any supplied finite `ReceiveFailureTrace` witness returns the exact entry kernel. No theorem yet constructs such a witness from every `begin_receive` execution. `OpenReplyRefines` conditionally relates a successful reply to the phase-selected material and `cr.dec`. Given `KernelRefines`, the target/index equality, and an ideal skipped-key lookup, `begin_receive_cached_refines` proves that generated `begin_receive` returns the exact cached open satisfying `CachedOpenRefines`. That phase exposes the exact ideal skipped material and matches the cached branch of `Ratchet.recvStep`; concrete finish returns the same plaintext. `ratchet.control.Refines.finish_receive_with_removal_consumed_refines` proves the control-plane filtered-cache post-state, while preservation of the full `KernelRefines` relation remains conditional on the separately stated `CachedPublicationRefines` material-array publication relation. Separately, `RatchetRefinement.lean` proves that the generated control-plane receive driver refines `Ratchet.recvStep` directly, including success with exactly 50 retained skipped keys because the target is consumed without entering the cache.

The canonical transcript-fidelity checker adds a deterministic source boundary around the two production message helpers. It locks normal-return `RatchetKernelSlot::take`/`put`, exact `pending.request()` → typed `ratchet_hkdf` → the same pending continuation's `resume`, send exhaustion, exact seal/open capability arguments, `finish`, returned-kernel reinstatement, all receive gates before take, receive KDF arms without slot publication, and receive terminal restoration before `opened?`. It also checks that the ProVerif record model keeps these steps atomic and that the named structural declarations and conditional `ResponseRefines`/`OpenReplyRefines` relation anchors still exist. This is source-text synchronization only; it neither proves the adapter satisfies the Lean relations nor composes Rust execution with the extracted core.

HB-60 adds a separate deterministic comparison between current core receive planning/publication source and the existing finite ProVerif state-neutral fixtures. It checks the shared bound of 50 retained skipped keys, the separately consumed target, exact entry-state restoration on failed open, successful future publication, replay through a missing cached target, whole-entry cached removal, capacity release, and the complete finite query tuples. The Rust cache array is oldest first and the ProVerif constructor is nested newest first, so the comparison asserts membership and length rather than representation equality. It is not a new Lean theorem, does not establish `CachedPublicationRefines` or future-receive refinement, and does not turn the finite symbolic schedule into an arbitrary execution theorem.

HB-62 adds deterministic source and finite-ProVerif synchronization for registration lifecycle and replay-key scope. It checks that the core replay identifier is the exact 64-byte identity-plus-one-time concatenation, excluding prekey and ML-KEM key; that the adapter returns at most one successful `Some` from `get_registration_bundle` per live Beacon object; that Server consumption follows successful root derivation and precedes any later response-building failure; and that the finite honest replay owner, malicious fresh overapproximation, and unsupported HB-49 rotation fixture retain those meanings. This is not a new Lean theorem or a semantic Rust-to-ProVerif refinement, does not prove key uniqueness or primitive security, and does not cover caller-constructed bundles made through public secret-key accessors, persistence, rollback, crash behavior, or multiple owners.

The remaining proof boundary is explicit: complete `CachedPublicationRefines` by proving that concrete material-array swap-removal preserves the bidirectional slot relation and empty suffix; prove the future-receive KDF staging induction and publication; compose initial role directions and restoration; semantically refine the synchronously source-checked adapter driver; and add an ideal send-exhaustion result. These gaps prevent a claim that the complete production effect lifecycle refines the ideal ratchet, but they do not erase the direct bound-50 control refinement or the checked non-exhausted send, supplied failed-trace, conditional open-reply, cached-open construction, control-plane cached consumption, and conditional cached-success results.

### Clean rebuild

To check that the extraction is reproducible from generated state:

```bash
rm -rf proofs/lean/llbc
rm -rf proofs/lean/.lake/build

cargo hax -C --locked ';' into lean

cd proofs/lean
lake build
```

Do **not** remove the entire `proofs/lean/BeaconcryptCore/` directory because it contains the maintained `Assumptions/`, `Model/`, `Refinement/`, and `Verification/` trees.

### Makefile targets

The Makefile exposes separate Lean verification targets:

```make
LEAN_DIR := proofs/lean

.PHONY: extract-lean check-lean verify-lean verify-lean-in-shell

extract-lean:
	rm -rf $(LEAN_DIR)/llbc
	cargo hax -C --locked ';' into lean

check-lean:
	cd $(LEAN_DIR) && lake build

verify-lean:
	$(NIX) --extra-experimental-features 'nix-command flakes' \
		develop --no-update-lock-file '$(PROOF_SHELL)' -c \
		$(MAKE) verify-lean-in-shell

verify-lean-in-shell:
	$(MAKE) check-toolchain
	$(MAKE) extract-lean
	$(MAKE) check-lean
```

The canonical `make verify` path regenerates and checks Lean after F* and ProVerif. `verify-lean` remains useful for an isolated pinned run, and `check-generated-lean` adds generated-drift checking for CI.

## Writing Aeneas-compatible Rust

The Aeneas Lean backend currently supports a smaller Rust surface than normal
Rust or the existing F* extraction. Code inside the Lean-visible boundary
should follow the conventions below.

### Construct fixed arrays functionally

Avoid mutation through array or slice indexing:

```rust
let mut bytes = [0; N];
bytes[a..b].copy_from_slice(source);
```

Prefer `core::array::from_fn`:

```rust
let bytes: [u8; N] = core::array::from_fn(|i| {
	if i < FIRST_END {
		first[i]
	} else {
		second[i - FIRST_END]
	}
});
```

This avoids generated references to unsupported operations such as:

```text
core.Array.Insts.CoreOpsIndexIndexMut.index_mut
core.slice.Slice.copy_from_slice
core.array.Array.as_mut_slice
```

Padding or unused output ranges should also be represented functionally:

```rust
let bytes: [u8; ROOT_KEY_INPUT_SIZE] = core::array::from_fn(|i| {
	if i < PQXDH_PADDING_SIZE {
		0xff
	} else if i < PQXDH_PADDING_SIZE + DH_SECRET_SIZE {
		secrets.dh1[i - PQXDH_PADDING_SIZE]
	} else {
		// ...
	}
});
```

### Avoid `!=` in Lean-visible code

The generated Lean core model supports the equality path used by `==`, but the
current extraction produces unsupported `PartialEq::ne` references for `!=`.

Write:

```rust
if !(lhs == rhs) {
	// ...
}
```

instead of:

```rust
if lhs != rhs {
	// ...
}
```

This applies to scalar and array comparisons, including compile-time
assertions.

### Gate implementation-only derives during Hax compilation

Some derives generate implementations that Aeneas does not need and cannot
currently translate.

In particular, derive `Debug` only outside the Hax compilation:

```rust
#[derive(Clone, Copy, Eq, PartialEq)]
#[cfg_attr(not(hax_compilation), derive(Debug))]
pub struct Example {
	// ...
}
```

Charon invokes rustc with:

```text
--cfg=hax_compilation
```

so the `Debug` implementation is absent from the extracted crate while normal
Rust builds retain it.

The same pattern can be used for implementation-only traits such as
`Zeroize` and `ZeroizeOnDrop` when those implementations are not part of the
proof model:

```rust
#[cfg_attr(
	not(hax_compilation),
	derive(Zeroize, ZeroizeOnDrop)
)]
pub struct RatchetChain {
	// ...
}
```

Normal Rust builds must continue to retain the zeroization behavior.

If `rustc` warns about the custom configuration name, declare it in
`Cargo.toml`:

```toml
[lints.rust]
unexpected_cfgs = { level = "warn", check-cfg = ['cfg(hax_compilation)'] }
```

Merge this with an existing `[lints.rust]` table rather than creating a
duplicate table.

### Defunctionalize higher-order values at the proof boundary

Lean can model functions, but the pinned Rust-to-Lean translation path does not support Rust function-pointer and callback signatures such as:

```rust
fn(&Request) -> Output
```

and callback-bearing generic APIs. Keep those values out of `beaconcrypt-core` rather than excluding the production modules that contain them. The current core uses affine request/response continuations:

```text
begin operation and construct exact request
        ↓
adapter interprets external HKDF or AEAD effect
        ↓
typed fixed-width response or `Option` result
        ↓
consume continuation and resume/finish
```

`InitialRatchetKdfPending` accepts only an `InitialRatchetKdfResponse`; ratchet steps accept only `RatchetKdfResponse`; `SendSeal` and `ReceiveOpen` expose the core-selected material, sequence, and opaque context before consuming a seal/open result. No executor is stored in `ConcreteRatchetKernel`, and no callback crosses the extraction boundary. This is defunctionalization: the finite protocol of possible calls is represented by data constructors and consuming resume methods instead of higher-order Rust values.

Do not infer semantic verification from this representation alone. The imported refinement files supply the checked direct bound-50 control refinement and `KernelRefines` invariant and cover non-exhausted send begin/resume/ideal success plus cancellation, rollback for supplied finite failed-trace witnesses, conditional open-reply consistency, generated cached-open construction from an ideal skipped-key lookup, the control-plane half of cached consumption, and conditional cached success. Structural equations separately cover exhaustion and either seal result. The proof still needs the cached material-array publication theorem, the future-receive staged invariant and publication, initial role composition, restoration, semantic refinement of the synchronously source-checked adapter driver, and ideal send exhaustion, while HKDF/AEAD correctness remains an assumption about the external effect interpreter.

### Avoid `?` if `Try::branch` appears

If generated Lean reports missing identifiers such as:

```text
core.result.Result.Insts.CoreOpsTry_traitTry.branch
core.option.Option.Insts.CoreOpsTry_traitTry.branch
```

rewrite `?` explicitly.

Instead of:

```rust
let value = operation()?;
```

use:

```rust
let value = match operation() {
	Ok(value) => value,
	Err(error) => return Err(error),
};
```

For `Option`:

```rust
let value = match operation() {
	Some(value) => value,
	None => return None,
};
```

Only perform this rewrite when the affected code is inside the Lean-visible
boundary.

## Generated external files

Aeneas may generate:

```text
FunsExternal_Template.lean
TypesExternal_Template.lean
```

Hax seeds the maintained `BeaconcryptCore/Assumptions/FunsExternal.lean` from the function template when first needed and generates `BeaconcryptCore/Extraction/FunsExternal.lean` as a forwarding import. Fill only the maintained assumptions copy; subsequent extraction preserves it so template drift can be reviewed explicitly.

Do not add arbitrary missing core-model definitions to the external assumptions. They are intended for external definitions explicitly requested by Aeneas, not for patching unsupported generated Rust/core operations.

## Known non-fatal Charon warning

The current toolchain may print a warning similar to:

```text
cargo miri setup failed ...
unknown `-Z` flag specified: json-target-spec
```

Charon currently falls back to rustc's default sysroot after this warning.
If the crate compiles and Aeneas subsequently runs, this warning is not the
cause of Lean extraction failures.

## Verification boundary

The no-exclusion Lean translation boundary is:

```text
beaconcrypt-core
├── commitment                 extracted
├── pqxdh                      extracted
│   └── concrete               extracted
└── ratchet
    ├── control                extracted
    ├── concrete               extracted
    └── refined                extracted
```

“Extracted” here means translated by Charon/Aeneas. `RatchetRefinement.lean` proves that the generated control-plane receive driver refines `Ratchet.recvStep` directly at its 50-skipped-key bound. `RatchetEffect.lean` proves exact structural laws for generated production phases, and imported `RatchetEffectRefinement.lean` checks non-exhausted send begin/resume/ideal success plus cancellation, rollback for supplied finite failed-receive traces, conditional open-reply consistency relative to `cr.dec`, generated cached-open construction from `KernelRefines` plus an ideal lookup, the control-plane half of cached consumption, and cached success directly against `recvStep` under its publication premise. Full verification still requires the cached material-array publication theorem, future-receive staging/publication, initial role composition, restoration, semantic refinement of the source-checked adapter interpreter, and an ideal send-exhaustion result.

Any change that reintroduces higher-order executor plumbing or unsupported mutable-array operations should be expected to require source-level normalization. Reintroducing exclusions would reduce production coverage and must be documented as a trust-boundary regression rather than treated as a routine extractor workaround.
