# Authentication with arbitrary KEM replies

The nine authentication correspondences from the maintained fourteen-query main model also hold in a separate model with no ML-KEM constructor, correctness equation or decapsulation destructor. A public controller chooses every generated KEM public key, encapsulation ciphertext and shared secret, and every decapsulation result. It can return failures, give different creation origins the same public key, reuse a secret across unrelated keys, or return a secret unrelated to a ciphertext. This result removes dependence on the symbolic KEM algebra for these nine authentication queries. It is a symbolic result at the original main process's scope; it does not establish a computational simulation of its remaining cryptographic operations or a secrecy result under KEM disclosure.

The new model is generated by `generate-kem-controller-auth.py` from the maintained `crypto.pvl`, `environment.pvl`, `queries.pvl` and `baseline.pv`. Those files remain unchanged. The generator removes only the exact reviewed KEM declaration block, replaces its three public-key, three encapsulation and two decapsulation call sites, and copies the original nine authentication query bodies. It rejects an unexpected KEM equation, call site or event roster. All original event emissions, signature checks, replay services, root/associated-data builders, registration binding checks, sequence-one admission, ratchet code and source network continuations remain present. There is no coin-only quotient equating publicly distinguishable evaluations at different keys, and no newly assumed KEM binding game.

## Controller interface and concrete interpretation

`kem-controller-interface.pvl` exposes requests for generation at a public creation handle, encapsulation at a public key, and decapsulation at a handle/public-key/ciphertext triple. Successful replies contain a public key, a ciphertext/32-byte-secret pair, or a 32-byte secret respectively; `kem_failure()` represents optional failure. Symbolic bitstrings deliberately allow more lengths and values than the typed native interfaces. Every request and reply is recorded before the continuation. A failure records `KemControllerRejected` and terminates that local path; no later target event is emitted on it. Scheduling and replies are controlled on a public channel, so the controller may block forever, mix requests or answer inconsistently. Such freedom is appropriate only for this authentication analysis.

The fresh handle is an origin token, not a KEM secret encoded as a public value. Its computational counterpart is the stable native creation index. The concrete interpreter samples and retains the real generated keypair locally, publishes only the returned public key and creation index, and evaluates the exact actual KEM callbacks. It can therefore expose their actual optional results without obtaining an unavailable identity seed or DH scalar. In particular, this interpretation must keep every original private-state update and callback query; exposing a reply does not erase the work that produced it. The authentication controller's public secret replies are additional observations, not part of BeaconCrypt's production network API.

The native coordinate controller/source lemmas separately establish the complete encapsulation/decapsulation interpretation and retain their optional failures. The creation-controller source consumer establishes the corresponding indexed constructor equation. These operational equalities support choosing the concrete source interpreter inside the stronger controller interface; they do not themselves translate arbitrary native byte equality and all remaining public cryptographic evaluations into applied-pi terms. That final trace/event interpretation must still be established by the common experiment.

The generated Beacon decapsulation request appears after response destructuring and before the original identity pin and four DH calls. This permits extra requests even when native point admission would reject; the original pin and source checks still guard every target event. Thus an invalid-point rejection is not modeled as an attacker obtaining a secret point. Correct point admission and primitive implementation behavior remain the user's functional contracts. For length-correct ML-KEM ciphertexts, the controller can supply the actual implicit-rejection fallback. It never infers a public rejection flag from a ciphertext's failure to match an honest encapsulation. The distinction between input validation and the internal fallback is specified in [FIPS 203, sections 6.3 and 7.3](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.203.pdf).

`set preciseActions = true` and the explicit controller `[precise]` inputs ask ProVerif to retain one reply per execution of an input in its Horn-clause approximation. They do not restrict the process traces or add a security axiom. Without the annotations, the arbitrary public-key input produced false candidate derivations by instantiating one input twice. The exact checker rejects those inconclusive results. The setting's semantics are documented in [the ProVerif manual, sections 6.2 and 6.7.2](https://bblanche.gitlabpages.inria.fr/proverif/manual.pdf).

## Exact event map

The family keeps the replicated main process, including arbitrary network scheduling, attacker-owned registrations and their known-state task canary. Each honest role instance still has its original finite record prefix; replication does not turn that prefix into an arbitrary evolving-session proof. Honest identity and prekey secrets stay private in the positive authentication run, while every KEM result is controller-known. Root, current-chain and skipped-key disclosures are not added by this family. Their target-relative conditions belong to the later live common experiment.

The following are the nine original injective correspondences, in original query order. Their complete field lists remain in `queries.pvl` and are copied verbatim; the checker independently fixes both event names and ordered arguments.

| Accepted event | Required earlier event | Exact scope |
| --- | --- | --- |
| `ServerAccepted` | `BeaconInitiated` | Same ordered signed InitKex, registration identifier, both identities and honest origin. The accepted event additionally records its actual root input and root; no initiating event claims either value. |
| `ServerBundleAccepted` | `BeaconBundleInitiated` | Same authenticated bundle, including the three selected public keys and honest origin. An attacker-owned self-signed bundle is permitted but does not become an honest-origin event. |
| `ServerAccepted` | `RegistrationConsumed` | Same signed registration and origin; response computation does not bypass the live single-owner replay guard. |
| `RegistrationConsumed` | `BeaconInitiated` | One successful live replay-consumption event per honest initiation. There is no storage, crash or restoration premise in this scope. |
| `ServerResponseAborted` | `RegistrationConsumed` | The modeled response failure retains prior registration consumption. It does not prove atomic durable publication. |
| `BeaconAuthenticatedRegistrationCompleted` at sequence one | `AuthenticatedRegistrationRecordSent` at sequence one | Same projected session, accepted plaintext and decoded frame, and the same claimed/assigned ID authenticated by the initial eight-byte binding. |
| `MessageReceived` | `MessageSent` | Same root-based session label, direction, positive sequence, sender, receiver and plaintext within the original bounded record prefix. This is decoded field agreement, not equality of Cap'n Proto encodings. |
| `BeaconAuthenticatedRegistrationCompleted` | `ServerAuthenticatedSessionCommitted` | Same projected cryptographic session, with the claimed and server-assigned routing IDs kept as distinct query variables. |
| `BeaconAuthenticatedRegistrationCompleted` | `AuthenticatedRegistrationRecordSent` | Same projected session, sequence, complete accepted plaintext and decoded frame. This general query likewise does not assert equality of the claimed and originally assigned IDs. |

The projected session is the existing eleven-field `establishment_authenticated_session`: both identities, signed Phase-1 InitKex, registration ID, three signed public keys, actual root bytes, exact associated data, pinned server ID and registration origin. It excludes the raw response ephemeral encoding, KEM ciphertext, pre-Extract input, complete response and routing ID. The accepted-record event carries the actual decoded frame separately. Equality of roots is not used to assert an inverse of Extract; raw X25519 encoding aliases and the old later-record assigned-ID countercontrols retain their documented scope. Current initial Beacon admission remains sequence one only.

The five main secrecy queries are deliberately absent from this auxiliary gate. Their maintained original checks remain unchanged, as do the original eight reachability controls, legacy registration gates, generated admission family and post-registration gates. A successful canonical secrecy query still requires the separate computational target-root/evolving-key reductions and a checked public-observation projection; the free KEM constructor is not justified by ordinary IND-CCA merely because a different authentication model passes.

Generic IND-CCA does not imply the former shared-secret constructor's cross-public-key injectivity: one can append an ignored public tag to a KEM's public key while preserving its challenge-secret game. Known-secret reencapsulation alone leaves honest constructor injectivity and unmatched decapsulation unresolved. The prior coin-only quotient changes public equality branches and is not a global simulation. The new controller therefore avoids both routes for these authentication events. This is an interface change in the proof, not a change to ML-KEM-768 or its implementation.

## Query and validation accounting

There are three generated-public-key call sites, three encapsulation call sites and two decapsulation call sites in the complete library; only the original replicated roles called by `baseline.pv` execute. Each individual generated role instance reaches at most one call of each relevant kind. With actual executed counts G, E and D, the controller has exactly G + E + D requests and at most that many replies. Aborted, malformed and repeated attempts count when reached. A concrete implementation pays G native key generations, E native encapsulations and D native decapsulations, plus all unchanged non-KEM source work and controller bookkeeping; no ambient work is declared free. The recovered native prefix bounds separately pay at most one encapsulation plus twenty-one other Server callbacks and one decapsulation plus twelve other Beacon callbacks. Whole-program generation, continuation and global adaptive counts remain the consuming computational ledgers.

`check-kem-controller-auth.py` runs four independent focused ProVerif groups and rejects missing, duplicated, reordered, changed or inconclusive results and mismatched final summaries. Each intentional FALSE result must have its own confirmed trace. The positive group contains all nine original authentication queries. The controls contain the eight unchanged original reachability queries, six explicit controller failures/aliases/inconsistent-result witnesses, and four original response/record correspondences under a deliberate public Server-identity-secret disclosure. That final control establishes the need for the remaining uncompromised DH/identity interface; it is not a production attack against the positive scope.

The focused gate passed all 27 classifications with locked ProVerif 2.05: nine TRUE authentication results and eighteen FALSE results with confirmed traces. The independent Python controls reject result substitution, changed fields/IDs/sequences, wrong polarity, absent summaries or traces, unrecognized KEM sites/equations and dropped original queries. Existing production files and old gates remain unchanged. No Rust changes or mutation campaign are involved. The exact generated input and log hashes are recorded by the gate's `receipt.json`; final integration also records the reviewed inventory and maintained Make/CI invocation.

This closes the KEM-algebra dependency of these nine symbolic correspondences at their stated schedule and compromise scope. It leaves the actual replicated computational-to-applied-pi trace/event projection, remaining DH/KDF/CTX hybrid consumers, full live scheduling and global losses to the common experiment. No final computational protocol theorem follows from this auxiliary family alone.
