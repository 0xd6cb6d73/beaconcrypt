# Record-lift interface proposal

This is the initial R1 proposal for handoff items 4 and 5, based on central `e90d54d934387bd08bfadff345449b84ebd1be2d`. The owner authorized starting against the CE-11 interface before CE-10 on 2026-10-07. The implementation is `PqxdhRecordLiftInterface.lean`. This proposal is not yet frozen and is not a computational security theorem. It fixes a restricted command interface and an open program; the private capability interpreter, its installation invariants and its source simulation are still required before `RecordLift.game env A` exists as a probabilistic experiment. No missing capability is implemented as a rejection or an arbitrary callback with access to hidden state.

## Interface and import direction

CE-11 will import this interface. No record-lift module imports `PqxdhDeploymentIdealKeys`, `PqxdhDeploymentHeadlines` or a later CE module. The proposal reuses the existing CE command, reply, mode, handle, transcript, log and budget types. `RecordQuery` is exactly the sum of the source Server query domain and an owner index paired with the source Beacon query domain. `recordQuery` embeds these requests in CE without changing their fields. `RecordSpec` obtains its replies from CE's existing mode-specific specification. The guarded `server_reply` and `beacon_reply` statements establish the complete source reply types in mode O; mode P uses CE's existing success-bit projection.

The registration environment answers the restriction `EnvSpec` of CE commands: create, bundle, accept, build, finish and public HMAC. Public BLAKE2b bypasses the environment and directly invokes the shared-hash capability. Its handler is a program over `EnvEffects`, consisting of coins and a restricted capability specification. It receives only its own state. It cannot call the ordinary raw receive interface internally, read a world-state lens, obtain a kernel or skipped key, inspect the shared hash cache, or inspect the secrecy ledger. Caller-known kernels can be supplied to installation; hidden kernels are named only by a slot and role.

`Environment.start` is a uniform-oracle program returning an optional pair of the existing Server constructor result and the initial environment state. Constructor failure ends the program. On success, `program` hands that same constructor result to the private world before running any command; the CE instantiation must prove this startup is the actual generated-seed constructor. No new generator distribution is assumed by the interface.

`native` partitions the unchanged CE native interface: all coins, public hashes and the four record branches bypass the environment. `program` runs the exact existing `PqxdhDeploymentSecrecy.wrap` and `asModeO` against that partition. Thus the chosen test bit, chosen fresh message and actual mode-O receive plaintexts in the ledger are not passed to the registration environment. The program returns its ledger for analysis; it must not be exposed through a public game projection or post-run reveal. Public transcript observations use `Entry.view mode`. The future world interpreter must run the existing source record handlers, shared primitives and production logging without changing their behavior.

## Successful installed kernels

The hidden seed is a pair of 32-byte words `(next32, right32)`. `next32` is already the Server-to-Beacon chain after sequence one. The successful Server kernel has send/receive counters `(1, 0)`, send chain `next32`, receive chain `right32`, and empty receive slots. The successful Beacon kernel has counters `(0, 1)`, send chain `right32`, receive chain `next32`, and empty receive slots. The outer Beacon sender ID stays separate from the control's assigned ID; no assigned-ID equality is assumed.

The brief's proposed use of `PqxdhInitialReplyErasure.kernelOf` needs a source equality: that initializer alone sets counters to zero. Initializing with `next32` and then running a real first KDF step advances the chain twice. The proposed named kernels instead abbreviate the existing extracted `ConcreteRatchetKernel.from_counters` at the counters above, with source sequence-one transition equalities proved separately in `PqxdhRecordLiftSeed`. That proof is in progress and is not an assumption of this interface. Constructor failure remains represented by `RustM`; existing totality theorems provide the route to proving its probability zero. Ordinary protocol rejection is a different event.

## Failed registration receives and the candidate capability

Production `Beacon::finish_registration` runs a full raw receive before checking that the opened sequence is one (`beaconcrypt/src/beacon.rs`, the `decrypt_message` call and subsequent sequence check). The central model has the same order in `PqxdhBeaconPhase2Publication.afterRoot` and `afterOpening`. An initial sequence from two through 51 may derive additional chain values and query the shared commitment hash before registration ultimately rejects. Discarding its local kernel does not discard these primitive effects. An environment that only opens with its own first key and nonce cannot reproduce that execution.

The proposed `candidate` capability handles this privately. It receives a slot, owner, expected sender, associated data, first-record key and nonce, and arbitrary raw bytes. The interpreter must sample the slot seed on its first hidden use, which can precede successful installation. It must run the source raw-receive program, supplying the factored first KDF response and using the evolving chain for subsequent responses, with all parser/validation rejections and primitive effects retained. Only after that complete receive does it apply the sequence-one gate. The checked `candidateReply_some` theorem establishes that any returned plaintext preserves the supplied successful sequence-one optional result; it does not prove the missing receive interpreter.

A successful reply contains an opaque ticket and registration plaintext. The environment performs the remaining binding and pin checks. `commitCandidate` must consume that exact ticket and install the retained private kernel with its source metadata; it must bind the ticket to its slot, owner, owner phase/generation, expected sender, associated data and retained kernel, and reject mismatched owners, changed associated data, changed pinned sender, stale tickets, already established owners and duplicate role installations. Direct installation must reject role-tag mismatches. `advanceOwner` must never reset an established kernel. `discardCandidate` discards only the private candidate, preserving the seed/table/hash effects. Publicly constructible ticket numbers are checked references, not an unforgeability assumption. The interpreter must preserve candidate ownership and metadata itself. It must never return a later record's plaintext to the environment through this registration capability.

This refines H2, F1, F4 and F5 of the task brief. Seed independence means a fresh uniform draw at the first allocation, independent of the then-current environment view. It does not mean a second role's installation draws again, nor that adaptive environment state remains statistically independent of ciphertexts it has already observed. The environment's post-run reveal receives only its own state; later-quantum theorems are deferred until LQ-F is reviewed and integrated.

## Frame conditions and accounting

The checked `Frame` definition bounds startup uniform calls and gives pointwise bounds on every actual environment handler program, for coins, shared hashes, private sends, candidate receives and administrative capabilities. It is a resource property, not a claim of secrecy, authentication, freshness, noninterference, small alias probability, or closeness of games. The private interpreter must enforce and prove vacant-key installation, legal phase progression, one committed installation per slot/role and ticket consumption. Those obligations remain open; the current definition must not be cited as discharging them.

`Caps` preserves CE's original `Budget` and separately names environment-private sends, candidate receives and the global shared-hash cap. `Caps.derivations` is the proposed conservative expression `Budget.sends + privateSends + 51 * (Budget.receives + candidateReceives)`. It is a definition awaiting transport bounds, not a theorem that a program respects this expression. It counts the first callback of each candidate conservatively even though the initial record key belongs to item 2. A later tighter bound may separate that callback.

The brief's `P(b) ≤ sends + 51 * receives` omits transient finish work unless an additional argument removes it. `Budget.receives` is only `serverRaw + beaconRaw`; it excludes `finish`. The proposal therefore leaves the extra term explicit for CE-11 review and an owner decision if the maintained plan's bound changes. The shared-hash cap also stays a parameter; neither a revised CE cap nor a fixed number of hidden slots is assumed. Every logical sample and base primitive evaluation requires its eventual reduction bill; no ambient environment work is declared free.

## Remaining implementation and proof

R1 must still obtain Claude's cross-review and interface freeze. The real world interpreter must own dynamic record state, the persistent hidden-seed table, role flags, candidate tickets, the shared BLAKE2b cache, production logs and refusal instrumentation. R2 proves its correspondence to the existing native handlers and dynamic role addressing. R3 constructs the ordered evolving-chain hybrids with persistent per-position samples, both directions, rollback, skipped keys, alias/refusal terms and explicit Extract/HMAC reductions. R4 compiles the resulting raw operations to the existing selected-key CTX endpoints, preserving the challenger's optional plaintext. R5 composes their two-sided event and boolean bounds and proves the appropriate ideal-world facts. None of these security statements follows from the three elementary interface lemmas.

This proposal adds no primitive contract. The eventual theorem contracts remain the approved component interfaces: modified nonce-AEAD IND$ and INT-CTXT, functional AEAD correctness, BLAKE2b ROM, HMAC PRF, Extract on a uniform 32-byte input, `SourceFullCorrect`, `FrameReadBack` and `DecoderAgreement`. Their use in a CE headline is a separate owner scope decision. No primitive implementation, snapshot, persistence or restoration proof is attempted.
