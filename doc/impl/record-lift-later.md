# Record-world disclosure continuation and accounting

This additive component gives the frozen record World an executable second phase. It proves the record-event frame and query-accounting laws needed to use that phase later. It does not yet prove a later-quantum chain or record security reduction. No frozen interface, World definition or production Rust changes.

`program` first executes the existing `PqxdhRecordLiftInterface.program`, including startup, constructor failure, the exact first-phase secrecy wrapper and its private ledger. Failure remains `none`. On success, `reveal : E → R` is evaluated on the run-final environment state, and `second output (reveal state)` runs through the existing `postEmbed` and the same `native env`, starting from that state. The returned value retains the original constructor metadata and ledger, replaces the first output by the second output, and contains the post-final environment state. There is no second ledger wrapper or reset of the environment.

The reveal type `R` is generic. The CE application must instantiate it with the complete reviewed LQ-F Beacon-and-Server reveal, including the Server seed and the accept-ephemeral log required by that experiment. This module does not substitute the earlier Beacon-only reveal type. The pure reveal function and second-phase client have no World-state argument; this is a typed access boundary, not an independence assumption. No honest-secret reveal query is added to the run interface. Proving that the CE reveal is preserved by its post execution remains on the CE side.

`run` executes both phases through one actual `World.handler` and one initial World state. Its private result retains the final seed table, kernels, CTX cache and counters. `game` applies the existing `World.observed` projection verbatim with the second-phase output type. The existing `World.analysis` projection also accepts this result type. Because `game` discards the environment state and reveal, later security reductions must use `run` and `post`, retaining the E-only continuation. Neither projection turns the ledger into a public mode-P transcript: the final origin or hiding event still must enforce its intended projection discipline.

The post embedding has three query classes. Uniform queries follow the actual World coin route; BLAKE2b queries use the continuing shared CTX cache; HMAC queries go to environment command class six. An arbitrary environment can issue every allowed capability while servicing that HMAC query, including owner append/advance and hidden-kernel installation. Such work may draw fresh seeds. This module therefore makes no blanket claim that post execution changes only caches or that its administrative cost is zero.

`install_server_view`, `resolve_view`, `install_beacon_view`, `capability_view` and `effects_view` prove the narrow frame directly through successful, failed and refused operational branches: produced frames and raw-attempt counters do not change. Peer kernels, owner state and private cost counters are outside that frame. `nonrecord_view` covers the remaining non-record World request, including initialization. `schedule_view` follows every adaptive reply and continuation with zero send and raw-request bounds. `post_record_bound` proves those zero bounds from the exact embedding and native dispatch, and `post_view` supplies the resulting record-view frame (produced frames and raw counters) of the complete post computation without `Frame`, query-budget or cryptographic premises.

`eventView` retains constructor metadata, the run ledger, produced frames and raw counters, and drops phase outputs and private environment/World fields. `run_event` proves equality of the resulting Boolean-event distributions before and after the entire post phase, including constructor failure. It uses the actual supported post executions and their frame. The event can describe a run-phase authentication outcome on those retained coordinates; it cannot inspect the final private cache, seed table, environment, uniform count or hash count. This theorem does not assert a later authentication guarantee or a security theorem about the disclosed value or second-phase output.

Accounting uses the existing `PostBudget` separately from the first-phase `Caps`. For allowance `A` and post budget `P`, the additional effect costs are `P.coin + A 6 .coin * P.hmac`, `P.hash + A 6 .hash * P.hmac`, and `A 6 .administrative * P.hmac`. `postCost_partition` derives these expressions from the three actual query classes. `post_effect_bound` transports the existing environment `Frame` through the post embedding. `program_effect_bound` adds that bill to the established startup, wrapper and environment bill, requiring the same post budget for every first output and disclosed value. A CE specialization with class-six cost 64 coins and no hashes or administrative work must prove that specialization explicitly.

`program_record_bound` takes a plain `budget : Budget` and shows that the complete program still has at most `S = budget.sends` joint sends and `R = budget.receives` joint raw attempts, including test/fresh sends and both roles. Post execution needs no query cap for this result. `run_native` connects it to the literal executed primitive counters: seals and writers are bounded by `S`, openings by `R`, native hashes by `S + R`, and `run_kdf` keeps `S + 51 * R` with `budget = caps.outer`. These conclusions need only the first adversary's `Budget.Respects`, with no environment `Frame` or post budget. They count ordinary-record calls; environment HMAC and registration processing are separate routes.

`run_effects` bounds the actual restricted-effect counters. For `B = caps.outer` and `Ehash = caps.envTotal A .hash`, `run_hash` gives `effects.hash + native.hash ≤ B.hash + S + R + Ehash + postCost A P .hash`. The same cache is threaded through both phases; this bound counts calls and does not alter hit or miss behavior. `run_uniform_counts` bounds actual underlying uniform draws by direct coins, 64 per shared-hash call and 64 per actual fresh seed draw. The hash allowance also covers hits and is an upper bound, not a claim that a hit executes fresh sampling.

`run_seed_draws` proves that the two phases share a single finite seed table: fresh draws equal final occupied slots and are at most `n`. This covers post installations without a reachability, alias-injectivity or no-new-seed assumption. For `Ecoin = caps.envTotal A .coin`, `run_uniform` combines the supported counter laws into `uniform ≤ startupCoins + B.coin + B.test + bounds.max * B.fresh + Ecoin + postCost A P .coin + 64 * (B.hash + S + R + Ehash + postCost A P .hash) + 64 * n`. Startup and the finite seed contribution are each charged once across the whole execution.

These are generic source-execution and accounting facts. The CE still owns its complete reveal construction and frame, source and erasure joins, and its concrete allowance proof. The chain and CTX compilers, key replacement, alias and nonce losses, selected reductions, and final later origin/hiding bounds remain separate obligations. In particular this component supplies no HMAC-PRF, Extract, AEAD or ROM security conclusion and assumes no new cryptographic contract.
