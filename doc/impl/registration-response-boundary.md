# Arbitrary registration responses, moved handles and public allocation

This package extends the arbitrary consumed-pair admission boundary with the actual response lifecycle of one live Server. Admission returns a private pending registration and already consumes the exact identity/one-time pair. Each build moves that pending value, checks the current public identifier counter and binding, initializes both chains, authenticates the assigned ID and arbitrary nonempty application bytes, seals the first record, serializes the outer response, and only then publishes the advanced peer and counter. Arbitrarily many admissions and builds may interleave. The scope is the registration API, not a completed model of every later record or every replicated Server.

## Source pending handles

`PqxdhRegistrationPending.Spent` records that an index is below the actual allocated-attempt count and its pending token is absent. The allocation condition matters: a guessed future index that previously rejected may legitimately be allocated by a later admission. No such future request is incorrectly treated as permanent compromise or consumption.

`accept_spent` derives preservation from the original accept handler's exact fresh-index update. `build_spent` preserves every previously disposed index, and `build_consumes` derives disposal for the attempted allocated index on every source outcome, including a failed response writer. `quiet_spent` checks all remaining original capabilities, including full Beacon receive, public HMAC/hash and installed-state reveal. `handler_spent` combines those actual cases. `program_spent` lifts disposal through any adaptive continuation, with its complete original replies and state.

`missing_build` is the exact source equation for an absent token: it returns `none` with the entire state unchanged before any tail callback. `no_rebuild` applies that equation after a first allocated build and any adaptive continuation, without assuming either response succeeds or the registration belongs to an honest identity. `native_build_consumes` consumes the previously checked literal native-builder equality and preserves the same primitive-family state in its execution. The allocation invariant is an operational source fact, already supplied by the original reachable-state construction; it is not a new authentication or freshness assumption.

## Source allocation and publication

`PqxdhRegistrationResponse.next_id` extracts the mathematical successor from the actual checked U64 operation. `prepared_counter` derives the actual candidate's prior control, next control and assigned ID from successful extracted preparation. IDs are public predictable counters. They are not fresh secret names, and equality of counter values across different Servers is not excluded.

`Publication` describes the exact optional Server result, retaining the advanced kernel on successful publication. `after_publication` consumes the existing complete first-send support theorem, including erasure, the inner frame result and the outer writer result. `candidate_publication` carries it through identity checking, reservation, real 64-byte initialization, nonempty payload admission, checked allocation and the eight-byte binding. `build_publication` adds the actual current-counter, pending Server-binding and peer-availability gates and retains the exact successful extracted candidate. These statements quantify over arbitrary supported primitive and auxiliary poststates. They neither reset those poststates on failure nor infer the absence of a cryptographic seal from a missing final response.

`build_counter` derives the concrete outcome: ordinary failure retains the whole original Server, while a returned response publishes counter `old + 1`, returns that same assigned ID and retains the consumed-registration set. `build_oracle_counter` applies it to the original adaptive API with its actual pending lookup, token disposal, shared cache and seal log. A failed outer writer retains successful inner frame/log effects even though Server publication fails.

`accept_control` and `finish_control` prove that neither admission nor complete Beacon receive allocates a response ID. `quiet_control` supplies the same result for every non-build capability. `handler_counter` establishes a zero-or-one increment for every actual API step; `program_counter` proves monotonicity for arbitrary adaptive continuations. `program_counter_bound` bounds the increase by the all-attempt build cap `qBuild`, including missing handles and failed writes. `ordered_response_ids` concludes that two successful responses separated by any such continuation have strictly increasing assigned IDs on this same Server. Its two successful observations are the events being compared, not an assumption that arbitrary requests succeed.

`native_build_counter` transfers the result to the literal native builder. `source_ordered_counter` starts from the actual source-order constructors and derives `serverKeyId ≤ finalCounter ≤ serverKeyId + qBuild`, using the original full Phase1 and native scheduler. It derives the needed operational invariant from that setup rather than assuming a selected honest registration. All constructor, KEM, callback and cache work remains inside the same source experiment.

## Replicated symbolic response service

`registration-set-response.pv` runs the reviewed arbitrary admission service and a replicated response builder under the same private live-owner mutex. A private channel retains the current counter. The initial counter and upper limit are public natural-number parameters; the production U64 instance uses the actual initial Server ID and limit `2^64 − 1`. The public constructor `registration_response_identifier(n)` represents the predictable encoding of an admitted counter value. The process does not create fresh assigned IDs.

A pending handle must exist and must not have been used. The used marker is inserted before counter, peer, identity, allocation or writer gates, representing the moved `RegistrationOutput`. Historical pending entries remain private instrumentation; they do not provide a read, restore or root-disclosure API. The peer table is updated only after outer serialization. An honest-origin lookup never authorizes a build. The model currently represents one Server binding; admission on another Server and moving foreign tokens across owners are not silently included.

The seven explicit failure stages overapproximate optional identity parsing, peer reservation, plaintext size/allocation, AEAD sealing, inner serialization and outer serialization failure in source order. They are environment choices, not extra fields in the wire format or new cryptographic premises. Some selected failures on a well-formed fixture may be impossible under stronger functional primitive contracts; retaining them is conservative. The default/empty/nonempty constructors represent the typed optional API argument, not bytes added to the production wire. The malformed-wrapper control rejects an ill-formed abstract API datum; it does not assert that production rejects any nonempty application byte string. The default witness is represented by the same nonempty byte value that a caller can supply explicitly. It is not given a disjoint symbolic value. The first 64-byte initialization and later 76-byte step use the existing fixed HKDF equations, preserving both directional chains and the shared projections.

Eight checked correspondences cover prior exact registration consumption for a used handle, the published successor counter, successful inner-writer origin, the predictable assigned ID, failure preserving the reinstalled counter, success incrementing it, the exact initial receive/advanced send state, and an arbitrary nonempty application suffix after the eight-byte assigned-ID binding. `RegistrationResponseCompleted` observes exactly the value output back onto the private counter channel. These are registration-boundary correspondences; none asserts a new authentication, secrecy, later assigned-ID agreement or cryptographic session identity result.

The query file uses ProVerif 2.05's documented `maxHyp = 2` strategy. It drops Horn-clause premises, producing a sound overapproximation of the same unbounded process; it does not bound sessions, counter values or the adversary, and is not a trusted axiom. The [official manual](https://bblanche.gitlabpages.inria.fr/proverif/manual.pdf), section 6.6.2, documents that this may lose precision while preserving sound proved results. The full-process publication reachability query remains inconclusive under this approximation. Its derivations with assumed hypotheses are not reconstructed executions and are not reported as attacks or nonvacuity proofs.

## Controls, costs and remaining boundary

`check-registration-response.py` checks exact primary and summary query strings and verdicts. Four deliberate changes to the counter increment, advanced chain, binding prefix and failure counter invalidate the expected correspondence results. These sensitivity checks produce five explicit unknown results; they are not claimed as reconstructed attacks. A separate concrete supplied-root tail harness checks ordinary nonempty and default payloads, empty input, an ill-formed abstract API datum, and all seven failure stages. Its 33 results include fourteen fully reconstructed finite traces. In particular, outer-writer failure reaches the inner-writer event and failed completion but never final publication. These component controls do not replace the unbounded registration process. The checker also checks the reviewed Rust admission/response order textually; this is a drift gate, not a compiler proof. Twelve checker regressions reject missing, duplicated or changed outcomes, warnings, and attempts to count assumed traces as actual traces. The earlier admission checker and every preexisting query/control file remain unchanged.

The new Lean statements and private observations introduce no primitive advantage, sampling call or selection loss. The only new numerical statement is the coefficient-one counter-increase bound by all attempted builds. Existing complete source and reduction ledgers still account for key generation, KEM, uniform sampling, Extract, HMAC, CTX, native callbacks and writers; a logical API or counter bound does not make that work free. No new primitive algorithm or implementation theorem is attempted.

This closes the stated moved-token and public-allocation projections of the original registration API. It does not establish a complete Rust/applied-pi trace compiler, unbounded later-record authentication, a new computational interpretation of symbolic constructor injectivity, or replicated multi-Server session origin. Those remain separate composition obligations. Primitive, compiler, abstract codec and native runtime contracts retain their existing scope. Saved-state restoration and persistence are excluded.
