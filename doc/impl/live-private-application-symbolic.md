# Unbounded private-application observation in the ideal material service

The new `live-private-application-service.pvl` component extends the existing HB-103 material bank with honest private application messages and two distinct receive capabilities. Each installed endpoint serves unbounded chosen-plaintext seals, private honest-message requests, privileged raw opening requests, acceptance-only network deliveries and key reveals. The bank still supports arbitrary same-key aliases and publicly imported key values. Its primitive equations come from the unchanged production transcript interface and `crypto.pvl`.

Each honest request creates a fresh private symbolic message, records `LiveHonestMessage(key, plaintext)`, seals it with the requested nonce/AD/sequence/sender and publishes the resulting symbolic frame. The plaintext is not part of the request. The explicit `[key]` argument of the fresh name retains that key correlation for ProVerif's proof representation; it does not disclose the key, alter freshness or impose a cryptographic security premise. A diagnostic omitting that annotation did not classify the privacy query within 30 seconds; retaining it classified both queries immediately. No result from the unclassified diagnostic is counted as a proof.

A privileged opening executes the original `open_frame` destructor. On success it records `PS1PrimitiveOpen` and `LiveApiPlaintext(key, plaintext)` before returning a tagged optional result containing that exact destructor plaintext. Failure returns a tagged None. The distinct network delivery executes the same destructor and origin event but returns only a success/failure tag tied to the endpoint and complete original request. It records no plaintext disclosure and never outputs the recovered plaintext. The two reply modes remain separate in both the applied-pi process and the native `LiveApplicationObservation` interface.

The positive main proves two unbounded correspondences. First, a successful opening has a prior seal of the same actual key, nonce, AD, sequence, sender, plaintext and decoded symbolic frame, or a prior actual-key disclosure. Second, if an honestly generated message becomes attacker-known, its key was disclosed or a privileged opening returned that message under that key. The latter is a conditional symbolic secrecy statement: unrestricted optional-plaintext API access is deliberately present, and its disclosure is an explicit alternative.

`PS1PrimitiveReveal(key)` includes both explicit key reads and prior public knowledge when installing an imported value. Aliases retain the same key term and therefore share the same disclosure and origin condition. The component does not infer agreement between owners or sessions from separate endpoint handles.

| Main | Exact record origin | Private-message condition | Reconstructed negative traces |
| --- | --- | --- | --- |
| `live-private-application-origin.pv` | TRUE | Key disclosure or privileged plaintext return: TRUE | 0 |
| `live-private-application-no-api.pv` | TRUE | Key disclosure alone: FALSE | 1 |
| `live-private-application-no-key.pv` | TRUE | Privileged plaintext return alone: FALSE | 1 |

All three mains execute the identical process and use the identical service library; only the second query's alternative changes. The no-API control returns the honest ciphertext through the genuine opening service and learns its plaintext without key disclosure. The no-key control uses a known imported key and decrypts locally, without a privileged API return. That import records the omitted prior-key-knowledge event. These controls demonstrate both declassification boundaries, rather than treating a solver timeout as a false result. The positive process also contains acceptance-only deliveries throughout.

The locked ProVerif 2.05 executable returned zero for all three final inputs. Each input has exactly two classified queries and corresponding summary entries; four classifications are TRUE and two are FALSE, with exactly one reconstructed trace in each negative control. The direct logs are `/tmp/live-private-application-{origin,no-api,no-key}-pv.log`. This supplemental component does not alter the 32 production scenarios, their existing main/control/registration/post-registration queries, the HB-103 material-service processes, or any Rust source. HB-116 adds a maintained supplemental Make/CI gate and locks exact query summaries, matching result lines and reconstructed trace counts in the shared classifier and inventory. The 32 production scenarios and existing five material-service gates are preserved.

## Exact source event map and consuming obligations

The compiled native application service already preserves complete source execution and public observations through arbitrary finite adaptive schedules. It retains actual optional plaintext for `.source` receive calls and acceptance alone for the additional delivery calls. `LiveRecordEvents` and `LivePublicObservation` supply actual source-selected material, stored AD, decoded sequence and sender, returned plaintext, original raw buffer, callback history and successful consumed positions on the same execution. The symbolic component is an intended target-relative image of those interfaces; no theorem identifying the entire production trace with this applied-pi process is claimed here.

| Applied-pi item | Required native/ideal-source interpretation |
| --- | --- |
| `LiveHonestMessage(key, plaintext)` | The chosen target's actual private application payload, before its actual source sealing call. The present symbolic sampler creates a fresh name per request; an arbitrary native callback must be instantiated with its real joint message distribution or a conventional message-privacy challenge. Symbolic fresh-name secrecy is not a finite-byte entropy theorem. |
| `PS1PrimitiveSeal(key, nonce, ad, sequence, sender, plaintext, frame)` | The exact successful inner CTX sealing result, with the first32 message key and final12 nonce from the same full76 source response. A subsequent optional writer may fail. Inner seal origin is not automatically prior successful network/API publication. |
| `PS1PrimitiveOpen(...)` | A successful actual selected-key opening, with the same source decoder, exact parsed record and challenger-produced optional plaintext. The original raw buffer remains separately retained; symbolic frame origin does not prove identical Cap'n Proto byte encoding. |
| `LiveApiPlaintext(key, plaintext)` | The actual privileged optional-plaintext response becomes visible. Acceptance-only delivery does not produce this event. The target freshness/declassification predicate must exclude or account for the exact response that reveals a confidential target. |
| `PS1PrimitiveReveal(key)` | Existing actual knowledge of the selected key, including explicit skipped-key/material reads, applicable root/ancestor/current-chain disclosures and their publicly computable consequences, or public import. Merely logging an unrelated reveal is insufficient. |
| Same-key alias installation | Repeated source derivations and cached entries with the same actual selected message key must use the same selected-key service. Different positions or owners do not imply distinct bytes. Source alias/collision events retain their existing reductions and losses. |
| Network reply tags | The source's actual Some/None result projected to acceptance, keeping its original request. The source still enforces its own cache, consumption, replay and parser rules; the material component grants a stronger unbounded opening service. |

For a noninjective record-origin result, the live source's admission/cache restrictions can be overapproximated by this unrestricted service once the cryptographic interface and event map are proved. Injective receive origin additionally uses the already checked no-repeat source consumption facts, starting from the actual sequence-one committed state with consumed position zero. This component itself permits replay and proves no injective correspondence, cache invariant, registration origin or endpoint agreement.

The target-relative computational route uses the reached uniform first32 result and the actual complete full76 continuation, with next-chain and nonce projections retained. It must compile cached and fresh selected material into one ordinary CTX endpoint, preserve all other dynamic known-key work on the shared hash cache, account for aliases and forbidden reveals, and maintain the original event through the source publication boundary. The ordinary nonce-AEAD endpoint also requires its actual per-key nonce policy; this symbolic service accepts arbitrary nonce arguments and does not prove native nonce uniqueness. Public fixed HKDF evaluations must remain real. Neither the finite source query budget nor the symbolic service's fresh key declaration discharges those requirements.

A concrete obstruction rules out a global replacement by an independent material bank. After a permitted current-chain disclosure returns `c`, the public fixed-HKDF recipe for `ratchet_material(c)` must match the next source record material. An independent fresh bank draw destroys that equality: a frame constructed with the public recipe opens in production and is rejected by the unrelated bank key. This is a normal compromise consequence, not a production vulnerability. Target freshness can exclude that key from a protected event, while the same common branch still has to execute the real public derivation. Accordingly, this component is a target-relative later ideal obligation, never the rejected public-HKDF/random-table interpretation.

The source writer boundary remains explicit. This process publishes each successful symbolic seal immediately. Production's generic optional writer can withhold a frame after inner sealing and may depend on the actual ciphertext. A consuming abstraction may expose additional inner frames as a stronger adversary for an inner-origin or privacy property, but that still requires a checked observation mapping. A theorem asserting prior successful production publication needs either an instantiated codec success/roundtrip contract for the source's admitted inputs or an explicit unpublished-frame analysis. It cannot rename every inner seal event to `Sent`.

These results close the ideal service's private-message and receive-observation classifications. They do not close the native-to-applied-pi compiler, the global KDF/CTX composition, replicated session assignment, or the symbolic constructor-injectivity mismatches. In particular, the existing ML-KEM cross-public-key injectivity and X25519 encoding distinctions retain their separately documented limits. No primitive implementation proof, new primitive hardness assumption, snapshot or persistence behavior is introduced.
