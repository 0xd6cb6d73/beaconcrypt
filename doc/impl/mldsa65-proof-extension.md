# ML-DSA-65 proof extension

This work starts from `6d6ec443`, the mandatory CBOR version-two registration implementation on the Lean 4.35 branch. The owner authorized treating ML-DSA security as an assumption and explicitly forbade proving ML-DSA or using VCVio unfinished theorems. The owner also forbade `verify-in-shell` until further instruction and required `/tmp/bc-coord` for compile coordination. New proof code uses current APIs without deprecation suppressions.

## Authentication scope

The beacon pins the server Ed25519 and ML-DSA public keys at construction. The server learns the beacon keys from the request. Attacker-owned beacons are allowed to register. A request-origin claim therefore identifies the exact honest ML-DSA public key being verified; it does not assert an enrollment binding between an Ed25519 identity and a separately presented ML-DSA key. A response-origin claim uses the pinned server ML-DSA key. Claims concern unsigned transcript contents, not uniqueness of signature bytes.

## First increment

`Model/Pqxdh/TranscriptAuth.lean` transcribes the Rust byte concatenations: BLAKE2b-512 remains opaque, variable fields use checked LE64 lengths, request and response domains differ, and ML-DSA receives the role-specific 64-space CertificateVerify-style input and its separate fixed context. The request binds both server pins and both ML-DSA keys. The response binds the request digest, decoded identity/ephemeral/KEM fields, raw application `C || T || U`, and assigned identifier. Neither CBOR headers nor the signature itself are hashed. The same hash function supplies transcript digests and public-key fingerprints.

`Computational/MldsaTranscriptAuth.lean` separates successful verification of an unissued unsigned transcript into weak-EUF message freshness or an actual unequal-input BLAKE2b collision. Signing history includes attempted signing queries even if signing or subsequent publication fails. Primitive security bounds are explicit premises. The trace-distribution interface permits an external post-quantum assumption but does not construct quantum execution semantics or prove that an arbitrary supplied distribution is generated by the native implementation.

The new focused ProVerif profile models mandatory ML-DSA wrappers around the classical four-field request and raw response fields. It checks exact honest-ML-key request provenance, pinned-server response provenance, honest and attacker-owned request verification reachability, key-compromise controls, role/context/request-digest separation, and both ordered ML-key hashes in associated data. Its perfect symbolic signature verifier and collision-free constructor hashes are external idealizations. Symbolic quantum capabilities concern recovery of classical keys; successful ProVerif queries are not a computational QPT or QROM theorem.

Source-fidelity checks must separately identify the four-field classical projection and the mandatory ML-DSA wrapper, including verification order, failed-publication history, private authentication metadata, exact CBOR field widths, AD281 and CTX357. Passing these checks does not upgrade a theorem over the old projection to a theorem about the full implementation.

## Production transcript construction in the core

`beaconcrypt-core/src/authentication.rs` now contains the production byte constructors and the five domain/context/role literals. For well-formed decoded fields, its byte concatenations match the former adapter construction. Its typed request fields exclude the signature field and produce the exact 5,495-byte Init preimage. The response constructor checks conversion of the borrowed application ciphertext's length to `u64`, then retains three ordered parts: a 1,293-byte fixed prefix through that LE64 length, the same borrowed application ciphertext, and the eight-byte assigned-ID suffix. Their concatenation has length `1301 + application_ciphertext_length`. The application bytes remain borrowed, so this construction introduces no allocation proportional to the possible 32 MiB response. The core also builds the 163-byte role-separated signing input and overwrites both fingerprint slots in the existing 281-byte AD array.

The adapter converts each decoded fixed-width field to a reference to its checked array before calling these constructors. It hashes the core Init array with one update and the response's three parts in their returned order. Both ML-DSA signing and verification use the core signing-input builder and fixed context; AD construction delegates to the core slot-overwrite function. BLAKE2b state creation, streaming updates and finalization, ML-DSA key generation/signing/verification, and native-library failures remain in the adapter. The deterministic core neither hashes nor signs. In particular, hashing the three ordered response parts must have the same effect as hashing their concatenation; that SDK interface law is external to the byte-construction proof.

The pinned Hax/Charon/Aeneas pipeline now extracts `beaconcrypt_core::authentication` into the separate `beaconcrypt_authentication_core` namespace in `AuthenticationExtraction/`. `proofs/extract-authentication.py` and the dedicated `extract-authentication-lean` and `check-generated-authentication-lean` Makefile targets regenerate or compare only this cohort. Its six Lean files are generator output, with empty external templates copied unchanged to their import targets; there are no new external implementation holes. A scoped Git whitespace rule accepts the templates' trailing blank lines so the generator output remains byte for byte unchanged. Provenance records the extractor/library pins and hashes of the authentication source, constants, crate root and manifest, workspace lockfile and Hax configuration. The new files expose the moved constructors for checking; the historical global extraction was not rewritten. A fresh pinned regeneration matched all six generated Lean files byte for byte.

Three refinement modules prove 14 guarded facts about those actual generated functions. `Refinement/TranscriptAuth.lean` proves preservation of the assigned-ID value, exact LE64 encoding, successful construction of the complete Init preimage and response prefix, and successful construction of a response whose actual returned parts concatenate to the complete pure response transcript. `TranscriptAuthInputs.lean` identifies the five literal arrays and proves the exact role-separated signing input and AD fingerprint-slot overwrite. `TranscriptAuthParts.lean` proves the actual parts order and composes the checked body length with the same borrowed body and assigned-ID suffix, covering the supported 32-bit and 64-bit index widths. The complete Init and response theorems have no cryptographic or output-success premises. Every dependency guard permits only `propext`, `Classical.choice` and `Quot.sound`. Historical refinement imports supply checked generic byte/scalar facts and the identical LE64 helper; they do not supply an old AD-width refinement.

This closes the deterministic constructor correspondence to the pure authentication model. It still trusts the Rust/compiler and extraction pipeline to connect Rust execution to the generated semantics. Adapter wiring is covered by reviewed source checks and runtime tests, rather than a complete extracted adapter proof. The SDK streaming law, native primitive behavior and failures, and the interpretation of actual signing histories remain external; moving the constructors proves no ML-DSA security property.

## Remaining composition

The existing global record and deployment proof still contains 153-byte AD and 229-byte CTX types in generated extraction and approximately 115 handwritten modules. Those must be migrated to the current 281/357-byte core before claiming a current full-protocol refinement or computational headline. Regeneration must use the pinned extractor, with reviewed diffs; a textual width replacement is insufficient. The authentication wrapper then needs a source execution/signing-history simulation and composition with the existing registration, key schedule, record, compromise, and query-accounting proofs. Nested request-digest collisions and public-key fingerprint collisions must remain explicit wherever byte-origin statements are strengthened to typed transcript or key identity statements.
