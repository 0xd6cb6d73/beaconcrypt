# Durable persistence component benchmark

The `persistence_bench` Rust example compares three resident native APIs: `PersistentServer` backed by a complete snapshot, `RowServer` backed by individual rows, and `CachedRowServer` backed by the same row adapter with every eligible peer cached before timing. Select either file-backed SQLite or PostgreSQL over loopback TCP with `--backend`. All three arms run the same Beaconcrypt revision and cryptography, preserve ratchet state durably before releasing output, and use the same backend durability settings. The experiment measures the cost of the native persistence boundary. It does not measure the Mythic provider, its transport, or its application result journal. Database clients remain development dependencies; neither database is a library requirement.

The [2026-10-25 results](row-persistence-results.md) archive the earlier two-arm, SQLite-only collection (raw schema version 1). Its row adapter held a SQLite transaction throughout the operation and its warmup/order schedule differed from the present three-arm design (raw schema version 2). Those measurements are not results for this extension. The summarizer accepts both versions without merging their experiments. No performance result follows from this design alone. Keep the generated JSON and the exact build and run commands with any reported measurements. Do not start this benchmark, including a reduced smoke measurement, on the shared development machine until the orchestrator confirms that all other `/tmp/bc-coord` leases have ended and a quiet measurement window is available. Compilation and correctness testing must finish before that window.

## Reference integration and choice of baseline

The workload reference is [mythic-beaconcrypt at `200af54bd8500d6d619b98d952fd4851e540ce10`](https://github.com/0xd6cb6d73/mythic-beaconcrypt/tree/200af54bd8500d6d619b98d952fd4851e540ce10). That revision is evidence about the integration's work and workload shape, not a claim that its pinned native library has the same wire protocol as this branch.

The provider caches its native owner after activation: [`owner.go`](https://github.com/0xd6cb6d73/mythic-beaconcrypt/blob/200af54bd8500d6d619b98d952fd4851e540ce10/Payload_Type/mythic_beaconcrypt/internal/engine/owner.go#L147) returns when the native handle already exists. Its normal request path still loads the current stored owner record, checks prior immutable results, exports a complete native checkpoint after a native mutation, serializes provider metadata including request history, and commits the checkpoint, metadata, and result together. See [`engine.go`](https://github.com/0xd6cb6d73/mythic-beaconcrypt/blob/200af54bd8500d6d619b98d952fd4851e540ce10/Payload_Type/mythic_beaconcrypt/internal/engine/engine.go#L37) and its [commit path](https://github.com/0xd6cb6d73/mythic-beaconcrypt/blob/200af54bd8500d6d619b98d952fd4851e540ce10/Payload_Type/mythic_beaconcrypt/internal/engine/engine.go#L427). The engine's campaign mutex serializes that path. Storage travels through [JSON RPC over AMQP](https://github.com/0xd6cb6d73/mythic-beaconcrypt/blob/200af54bd8500d6d619b98d952fd4851e540ce10/Payload_Type/mythic_beaconcrypt/internal/storage/client.go), including binary values represented in JSON.

The appropriate primary native baseline is therefore a resident `PersistentServer`, not an artificial full restore before every message. The SQLite snapshot adapter selects only the current 72-byte lineage/generation/digest head inside its write transaction. The PostgreSQL snapshot adapter sends the expected head in a single prepared conditional `UPDATE`, using one implicit durable transaction and one query/acknowledgement exchange. Both validate the replacement envelope and replace the complete snapshot. The resident API still serializes all peers and consumed registrations, sorts those collections, and hashes the resulting full snapshot on every successful message operation. The benchmark does not add an avoidable full-value database read to that path.

The row arm loads, validates, mutates, serializes, and replaces the selected peer row. The cached arm obtains that peer's decoded state and prior encoded row from memory, records an `expect` precondition, and serializes its replacement. Both use the same buffered adapter: complete read/absence expectations and writes are checked and applied atomically at commit. A cache hit avoids fetching the old value across the adapter boundary; the database still validates that old value before releasing output. This is a conditional durable write, not deferred persistence. Immutable identity is loaded at open. Registration replay markers and the key allocator remain separate rows. All three arms use equal peer counts, equal consumed-registration counts, equal identity seed inputs, equal messages, and independent freshly registered beacons. Every fixture receives a fresh random 32-byte lineage outside message timing, recorded with its fixture metadata and reused only to reopen that fixture's authoritative database. Random lineages, peer keys, and handshake randomness are independently generated; their byte values are not deterministic fixtures.

None of the measured arms stores an application request/result journal. The comparison consequently establishes neither retry-result recovery equivalence with the reference provider nor a provider-wide speedup. A provider migration must also preserve immutable request results, request-body identity checks, campaign/session metadata, owner fencing, and atomic result/state commitment. Those costs require a separate application-level experiment. A reload-per-operation deployment, if relevant, is a separate baseline and must be labeled as such.

## Workload matrix

Defaults use 1, 100, and 1,000 registered peers, three independent matched trials, and every registered peer active in round-robin order. Before timing, every arm sends and receives one message for every eligible peer, then performs 16 additional send/receive exchanges. The cached arm's capacity equals the eligible peer count and every eligible peer must be present in its cache. The following cases are measured independently for server send and server receive:

| Case | Messages | Plaintext size per message | Plaintext volume per arm and direction |
| --- | ---: | ---: | ---: |
| Small stream | 1,024 | 1,024 bytes | 1 MiB |
| Larger stream | 128 | 65,536 bytes | 8 MiB |
| Mixed stream | 1,024 | 1,024 bytes, with every 16th message 65,536 bytes | 4.9375 MiB |
| Burst 64 | 64 | 512,000 bytes | 32.768 MB / 31.25 MiB |
| Burst 256 | 256 | 512,000 bytes | 131.072 MB / 125 MiB |
| Burst 512 | 512 | 512,000 bytes | 262.144 MB / 250 MiB |

The reference's [installed Poseidon tests](https://github.com/0xd6cb6d73/mythic-beaconcrypt/blob/200af54bd8500d6d619b98d952fd4851e540ce10/integration/poseidon/installed/README.md#L214) exercise 1 KiB, 64 KiB, 1 MiB, and 10 MiB values. Its [chunking description](https://github.com/0xd6cb6d73/mythic-beaconcrypt/blob/200af54bd8500d6d619b98d952fd4851e540ce10/integration/poseidon/installed/README.md#L270) gives **512,000 decimal bytes**, rather than 512 KiB, as the usual output chunk size. Actual JSON, base64, delegation, and batching can produce larger wire messages; this benchmark deliberately measures exact native plaintext sizes and records actual encoded wire byte counts separately.

The burst repeats the exact same immutable payload bytes for every message and all arms. Small and large payloads also repeat within their classes. All payloads are generated once before timing using the documented SplitMix64 byte generator with seeds 1, 2, and 3 for the small, large, and burst classes. This is reproducible test data, not cryptographic randomness; the protocol uses its normal randomness and sequence-dependent ciphertext. No compression or deduplication layer is present.

`--extra-registrations N` adds N accepted registrations whose response fails because the explicitly supplied response plaintext is empty. Their consumed replay markers persist without creating peers, allowing registration-history growth to be varied independently of peer count. `--active-peers N` restricts the eligible round-robin working set to `min(N, registered_peers)` while retaining the other peer records. The result's `active_peers` records that eligible limit; `touched_peers` records `min(active_peers, messages)`, because a short batch may not reach every eligible peer. These are useful separate axes: for example, one active peer among 1,000 total peers, or 100 peers with 5,000 additional replay markers. The benchmark's registration history is not the provider's application request journal.

Cases run without intentional sleeps or rate limiting. The small and larger streams are saturated single-worker workloads, with the latter using regularly sized larger messages. The bursts are consecutive native operations, not transport batching. This measures service capacity under continuous demand; it does not measure latency at a chosen arrival rate, queueing, or many-worker throughput. A paced or concurrent experiment should be reported separately. SQLite's writer serialization does not demonstrate parallel throughput across independent peers even though the row API allows a different database to provide it.

The default matrix contains 162,432 measured server operations and moves 23,792,320,512 bytes (approximately 22.16 GiB) of plaintext per backend, before client verification and wire overhead; full-snapshot persistence can write substantially more. Running both backends doubles those totals. Use a reduced matrix to check the harness during an approved quiet window, then run the intended matrix with sufficient time and disk space. Do not combine reduced and default runs into one summary.

For a shared-host collection, each backend's peer-count axes can run as three independent complete reports with `--peers 1`, `--peers 100`, and `--peers 1000`, retaining three trials and every default workload in each report. This preserves the total workload while allowing completed clean reports to survive an interruption during a later axis. Fix the retry rule before collecting valid timings: monitor the entire invocation, retain every completed uncontaminated report, and discard and rerun any interrupted or contaminated axis from fresh fixtures. Do not select reports or trials by their timings. Record each axis's window separately and compare matched arms within that report. Independent invocations reset the peer-axis index, but the three-arm rotations still put every arm in every position exactly once over three trials. This balances positions, not all six possible order permutations or every predecessor effect. Differences in allocator state, temperature, and filesystem cache between windows limit absolute cross-axis and cross-backend scaling comparisons.

For the planned three-arm shared-host collection, the declared order is SQLite/1, PostgreSQL/1, PostgreSQL/100, SQLite/100, SQLite/1000, PostgreSQL/1000. All six reports use one recorded release binary and the complete default workloads. Freeze a collection plan after the final validation, commit, and build receipts; record the binary, compiled source, collection scripts, and summarizer hashes. Each attempt writes to a new directory and preserves its raw report, monitor journal, logs, and disposition. Retain the first complete, validated, uncontaminated report for each axis. Retry an interrupted or contaminated axis in full, with at most three attempts per axis; stop on a correctness failure, binary/source/configuration drift, or a 45-minute axis runtime limit. Waiting without a lease is limited to 12 hours per attempt. These rules are fixed before inspecting any new timings.

The collection watcher first requires 180 continuous quiet seconds without a memory lease, queued request, Lean slot, recognized heavy process, ProVerif activity, or integration lease. It then reserves the full 19,800 MiB coordination budget and requires another 60 quiet seconds, with at least 50 GiB free disk space at admission and throughout measurement. For a PostgreSQL axis, its explicitly owned server starts as the guard's child and its configuration is archived before that second quiet interval; `finally` cleanup signals only that child after rechecking its identity. SQLite axes have no PostgreSQL daemon. PostgreSQL process exemptions require the exact owned server executable, owned postmaster identity or its children, and the same lease cgroup. Unix sockets are disabled by a recorded startup override. Stable client-side socket entries from both `/proc/net/tcp` and `/proc/net/tcp6` must belong to the benchmark process's file descriptors; sharing the owned postmaster does not exempt a foreign client. The socket check takes snapshots around the descriptor read to avoid treating a connection closed during inspection as foreign. No monitoring SQL is issued during measured batches.

During the entire benchmark invocation, the guard samples every five seconds, rejects monitor gaps over ten seconds, and checks both memory-lease and Lean ticket sequences as well as active/queued work. A queued contender invalidates the report even when the full-budget reservation prevents that job from starting. Interference stops only the benchmark child, discards the entire current axis report, and releases its reservation after owned-server cleanup. Completed earlier axes remain retained. PostgreSQL startup/configuration, persistent data-directory filesystem, actual durability settings, server executable/version, and process allowlist are archived alongside the ordinary environment/build receipt. Existing fixture schemas are recorded; interrupted schemas are preserved for separate ownership review, never deleted merely because their names match a prefix. The initial collection-plan hash is checked before and after every runner and in each accepted receipt. Monitor snapshots retain system-wide CPU jiffies including steal time, swap counters, memory, and disk statistics; those are context, not per-arm measurements. Five-second sampling cannot prove the absence of every short or unrecognized process or connection, and the guest cannot exclude host-level interference.

Known heavy process names are immediate vetoes. The guard also measures user-plus-system CPU tick deltas for every visible process, identified by PID and start time, so a sustained unregistered Python job is covered. Only the exact benchmark and owned PostgreSQL identities are exempt from these CPU checks. An interval is invalid when any outside process averages at least 0.25 CPU core, all outside processes together average at least 0.5 core, system-wide steal time averages at least 0.25 core, or swap-in plus swap-out reaches 256 pages per second. One core means one CPU-second per elapsed wall second; clock-tick frequency and swap page size are recorded. Rate gates apply to intervals of at least one second, ordinarily the five-second monitoring interval. An older recorded CPU sample covers short start/finish boundaries, so CPU windows can overlap and must not be summed; known-process, ticket, socket, and reservation checks still use successive samples. Startup/provenance work precedes the reserved quiet minute and resets the CPU baseline. New processes born since the CPU baseline count from zero, and reused PIDs never inherit an earlier process's counters. A newly observed older process without a baseline or unavailable accounting for a visible process fails the guard. Processes that exit entirely between observations, hidden processes, and below-threshold activity remain measurement limits. These thresholds are declared in the immutable collection plan and are not tuned after seeing benchmark results.

## Persistence and timing boundaries

All SQLite adapters use file-backed databases with `journal_mode=WAL`, `synchronous=FULL`, 4,096-byte pages, a 20,000 KiB page-cache target, a 1,000-page automatic WAL checkpoint threshold, and a five-second busy timeout. They use one connection per resident server and commit once per ordinary message operation. The row adapter performs fetches outside the write transaction, then starts `BEGIN IMMEDIATE`, validates every expected key/value or absence under the writer lock, applies all buffered writes, and commits. The same validation is required for read-only operations. SQLite compares missing values as SQL `NULL`, keeping absence distinct from a present empty BLOB. The row table uses its binary key as its primary key with `WITHOUT ROWID`; the snapshot table has a single integer primary key plus separate trusted head columns. Database errors abort the experiment instead of being counted as successful operations or silently retried.

PostgreSQL uses explicit loopback TCP (`127.0.0.1` or `::1`), one resident connection per arm, prepared statements established outside timing, and `fsync=on`, `synchronous_commit=on`, and `full_page_writes=on`. Server version, address, port, isolation, buffer/checkpoint/WAL settings, and autovacuum policy are recorded. PostgreSQL 16 matches the reference integration's CI major version. A dedicated benchmark server/database is required; its process and background workers are authorized components of the measurement window. Its data directory must be on persistent storage, recorded independently of the harness's temporary workspace. No credentials are written to the report.

The PostgreSQL row adapter fetches needed values with prepared queries and submits the whole expected-read/write batch in one prepared call to a `VOLATILE` PL/pgSQL function. That function obtains transaction-scoped advisory locks for the union of read and write keys, including absent keys and blind writes, deduplicated and sorted by numeric lock ID. It then validates every expectation before writing anything. All writers to those tables must use this protocol; ordinary `READ COMMITTED` reads followed by an upsert alone do not provide the required contract. Hash collisions can serialize unrelated keys but do not bypass validation. `READ COMMITTED` and `VOLATILE` are essential here: statements inside the function obtain fresh snapshots after an advisory-lock wait, so validation observes an intervening commit. See PostgreSQL's [function volatility documentation](https://www.postgresql.org/docs/16/xfunc-volatility.html) and [advisory lock documentation](https://www.postgresql.org/docs/16/explicit-locking.html#ADVISORY-LOCKS). An error rolls back the entire statement; a false result reports a conflict without writing. Read-only batches are validated too.

For a successful ordinary message with a hot cache, the expected PostgreSQL application exchange counts are snapshot 1, row 2 (fetch plus commit), and cached row 1 (commit). The synchronous client's `execute` and `query_one` paths drain the response through PostgreSQL's `ReadyForQuery` message before returning, so the implicit transaction's commit acknowledgement is inside the method and timer; see the underlying [client response handling](https://docs.rs/tokio-postgres/latest/src/tokio_postgres/query.rs.html). `network_exchanges` counts explicit prepared query/acknowledgement calls, not network packets, SQL statements executed inside the function, or connection preparation. `loads`, `expects`, and `stores` count calls at the row-transaction API boundary; `reads` counts fetch queries, while `validation_rows` records database-side validation separately. SQLite has zero network exchanges. These counters make a saved fetch observable without describing it as elimination of all database reads.

Before each batch, SQLite completes an explicit WAL `TRUNCATE` checkpoint; PostgreSQL completes `CHECKPOINT` on the dedicated server, requiring an appropriately privileged benchmark role. Storage footprints are sampled outside timing. Automatic checkpoints or other authorized database background work during the subsequent batch remain included. The preparation checkpoint makes the starting condition more comparable; it does not make the filesystem cache cold. Database contents are warm after setup and preceding cases. Workloads retain state across cases in the same trial, with equivalent operation sequences in all arms; each next trial receives fresh SQLite databases or isolated PostgreSQL schemas.

Fixture creation, registration, additional replay-history creation, native reopen, warmup, and deterministic payload generation are outside message timing. For receives, all beacon ciphertext is generated before the server batch. For sends, beacons decrypt and check all returned ciphertext after the batch. Every output is checked against its exact payload, peer key ID, and expected sequence number. A failed operation or verification fails the run.

Each operation latency includes the native method, its SQL transaction, commit acknowledgement, and construction of its returned result. The batch timer additionally includes loop bookkeeping, two clock reads per operation, and insertion into preallocated measurement/result vectors. It excludes client crypto, registration, payload construction, verification, SQL footprint scans, reporting, and preparation checkpoints. Throughput is computed from the entire server batch duration; it is not the reciprocal of a latency percentile. Individual latency percentiles use the nearest-rank definition and are reported separately.

The three arms execute consecutively for each case. Initial fixture order rotates by trial and peer-count axis; case/direction order also rotates the first arm. Over three trials every arm occupies every position once. Reports retain the field name `pair_order`, now ranging from 0 through 2. The same fixed case order is used for all arms. Raw results are written after the complete matched trial, avoiding report-file writes between the paired measurements. No concurrent workload generator runs during the timed region.

The harness retains frames and results so validation can occur outside timing. A receive burst can retain both ciphertext and plaintext buffers, and all three initialized arm fixtures coexist. Its process memory is therefore not a server-memory comparison. The report's environment memory readings are context only, not peak-resident-memory measurements attributable to an arm.

Native open time is reported separately after closing and reopening the initialized server. Connection establishment, PRAGMA setup, statement preparation, and durability-setting checks are excluded. The database and OS cache are warm. Snapshot restoration performs its activation write; row open reads identity without an activation write. Label this field `warm_database_open_ns`, not cold-start latency. `cold_open_database` records counters for this initially empty native peer cache, not a cold database. `cache_fill_database` records the mandatory all-peer send/receive pass; `warm_database` records the additional warmup. The cached arm reports its capacity and actual cached-peer count. These phases are outside hot-operation timings.

## Running and interpreting the report

Build the example from a clean, recorded revision before the measurement window:

```bash
cargo build --release -p beaconcrypt --example persistence_bench
```

After the shared-machine coordinator has confirmed that no other leases or background builds remain, run the release binary directly. Choose a persistent database filesystem representative of the deployment, not a memory-backed temporary directory:

```bash
target/release/examples/persistence_bench --run \
  --backend sqlite \
  --output persistence-default.json \
  --database-directory /path/to/persistent/benchmark-space
```

The default database parent is the invocation's current working directory. Temporary fixture databases are removed when the process exits normally; the JSON report remains. The program refuses an existing output file and refuses detected Linux `tmpfs` or `ramfs` database locations. Filesystem detection is best-effort on other platforms. These benchmark identity seeds are fixed, publicly visible fixtures and must never be used as a deployed identity; each fixture owns a fresh independent database lineage.

For a separately provisioned PostgreSQL server, set a dedicated database DSN in the environment and select the backend. Provisioning, initialization, server startup, schema creation, and SQL preparation must finish outside measured batches. The harness owns only randomly named fixture schemas and removes them on normal exit. Its `--database-directory` option does not configure PostgreSQL's data directory.

```bash
export BEACONCRYPT_BENCH_POSTGRES='host=127.0.0.1 port=55439 user=benchmark dbname=benchmark'
target/release/examples/persistence_bench --run --backend postgres \
  --output persistence-postgres.json --peers 1,100,1000 --trials 3
```

For a reduced functional measurement, still subject to the same quiet-window requirement:

```bash
target/release/examples/persistence_bench --run \
  --output persistence-reduced.json --peers 1,10 --trials 2 \
  --small-messages 32 --large-messages 8 --mixed-messages 32 \
  --burst-chunks 4 --warmup-messages 4 \
  --database-directory /path/to/persistent/benchmark-space
```

For the history/working-set axis, retain the ordinary default payload sizes and change only the specified variables:

```bash
target/release/examples/persistence_bench --run \
  --output persistence-history.json --peers 100 --trials 3 \
  --active-peers 1 --extra-registrations 5000 \
  --database-directory /path/to/persistent/benchmark-space
```

The JSON records configuration, source revision and dirty state, executable and command line, Rust version found on `PATH`, runtime Rust flags, SQLite version, OS/CPU/memory information where available, CPU governor where available, filesystem type, raw per-operation nanoseconds, batch durations, observed wire/plaintext byte counts, SQL operation counts, logical value bytes, and database footprints. Source status is captured before creating the report and temporary databases, so those generated artifacts do not make a previously clean checkout appear dirty. The Rust version and flags reflect the run environment and do not prove which toolchain or flags built the binary; archive the build command and build log as well. Debug builds are rejected.

The adapter's `value_bytes_read` and `value_bytes_written` count opaque fetched and successfully committed persisted values. `value_bytes_expected` counts values supplied to `expect` calls; `validation_bytes_sent` counts expected values or snapshot heads submitted for commit validation, including ordinary row values fetched earlier. These are overlapping logical metrics, not additive traffic totals. SQLite snapshot compare-and-swap head reads are separate `head_bytes_read` counters; PostgreSQL supplies that head with its conditional update. The counters omit SQL keys, protocol framing, head writes, index entries, WAL/page amplification, fsync calls, and filesystem behavior. SQLite main-database/WAL lengths and PostgreSQL table/index/TOAST sizes are instantaneous allocated footprints, not cumulative disk bytes written. Do not describe either metric as physical I/O savings. Row counts include identity, allocator, replay markers, and peer rows; the snapshot arm stores one row containing the aggregate state.

Compare pairs with the same peer count, trial, scenario, direction, active-peer count, and history count. Report per-trial batch durations and throughput, then summarize the distribution of paired ratios or differences. Keep tail latencies per case and trial visible; pooling every message across trials hides run-level variation and is not a substitute for repeatability. Three trials are a practical default, not sufficient evidence for a narrow confidence interval. A difference near the observed run-to-run spread is inconclusive.

The standard-library-only `summarize.py` validates the complete configured matrix, rejects missing or duplicate arms and mismatched workload axes, checks latency summaries against raw samples, and recomputes throughput from positive batch durations. It accepts archived two-arm schema-1 reports and new three-arm schema-2 reports. For schema 2 it emits each trial's arm order, durations, throughput, p95/p99/max latencies, logical storage bytes, and application/query counters, plus median/min/max paired ratios for snapshot/row, snapshot/cached-row, and row/cached-row. Ratios above one mean the denominator arm finished sooner in that pair; they are not an end-to-end provider performance claim. Configuration axes must be unique, and reports with `running` or `failed` status are rejected. JSON output additionally preserves all per-trial latency summary fields and SQL counters.

```bash
python3 beaconcrypt/examples/persistence_bench/summarize.py persistence-default.json \
  --output persistence-default-summary.md
python3 beaconcrypt/examples/persistence_bench/summarize.py persistence-default.json \
  --format json --output persistence-default-summary.json
```

The summarizer refuses to overwrite an output file. Its schema and failure-path tests use synthetic in-memory values only and do not execute or publish any benchmark measurement:

```bash
python3 -m unittest discover -s beaconcrypt/examples/persistence_bench -p test_summarize.py
```

Before publishing results, record storage hardware and mount options, power/CPU policy, CPU affinity if used, free space, thermal state, and whether swapping or competing processes were observed. Keep those choices identical between arms. For PostgreSQL also archive server startup/configuration, data-directory filesystem, server binary/version, and the allowlist of its authorized processes. Do not change host cache policy, drop OS caches, disable durability, or tune one arm after inspecting its timings without defining a new experiment. SQLite `FULL` and local PostgreSQL synchronous commits measure durability exposed by the local filesystem and hardware. Loopback TCP introduces a real client/server boundary but does not represent remote network latency, replicated durability, AMQP latency, or the reference provider's complete recovery contract. Fully warm cached-peer measurements do not establish benefits under eviction, external-writer conflicts, or bounded caches smaller than the working set.
