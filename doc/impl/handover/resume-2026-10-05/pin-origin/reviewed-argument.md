# Pin independence for the current bounded Beacon-to-Server model

This is a draft for independent review, not a maintained result. It concerns only the current `FsRecordsB2sMain` and `FsRecordsB2sMainAnyPin` processes with the exact T0 constructor/destructor theory, source-purpose binding library, either existing send library, and the existing finite receive macros. It supplies no Rust trace theorem, computational reduction or new primitive assumption. In particular it does not infer constructor injectivity from ordinary primitive security. The source abstractions L1–L4 and E19 remain separate.

The intended transfer is exactly C2 (injective Beacon-to-Server record agreement, with its `attacker(k)` disjunct) and C3 (at most one Server receive of a sequence in one queried session). Both formulas are copied without strengthening from their existing query files. A C2 match must name the honest Server public key, because every Server receive names that key. C3 mentions only Server receives. No statement transfers queries observing `FsBeaconStarted`, other-pin finishes, all-direction sends, receive-input labels or API reply bits.

## Exact output and reduction ledger

Write `S = ed_public(s)` for the one honest Server public key and `I` for `SERVER_KEY_ID`. All model Server objects use the same unrevealed fresh atom `s`. A Beacon samples distinct fresh identity, prekey, one-time and KEM secret atoms. There is no secret reveal, private-state getter, arbitrary DH service, HKDF-result output, root/chain/material output or returned plaintext oracle in these exact processes. Ghost events do not add attacker knowledge. Those missing interfaces are part of this local symbolic scope, not claims about the final computational experiment.

The only honest public outputs are `S`; a Beacon's identity-tagged three-signature registration bundle; a Server response containing its identity, public ephemeral, KEM ciphertext, initial `crypto_frame` and assigned ID; and the two Beacon record frames. The initial Server plaintext is the exact registration binding paired with one independently fresh application atom. Each Beacon record plaintext is either an independently fresh application atom or the exact already attacker-derivable chosen input. No honest process outputs a secret key, HKDF stream/projection, record material or DH shared value except strictly inside the listed opaque primitive constructors. No application callback inserts unobserved secret values into plaintext. This ledger concerns the existing model, where these facts follow directly from the output sites.

In the exact theory HKDF, its three projections, `aead_cipher`, `aead_tag`, `blake2b512`, `ed_public`, `x25519_public`, `sign` and `ratchet_key_nonce` have no implicit `[data]` projections. Public frame, tuple, binding and encoding projections only expose their explicitly stored children. The explicit reductions either return an existing variable/subterm (`verify_signature`, material projections, `open_frame` and structural accessors), compute a public-key conversion, or compute the stated DH/KEM shared constructor. None creates an HKDF constructor/projection or an `aead_cipher` constructor on its right-hand side. `x25519_shared` is private. These finite syntax facts must be checked against the exact loaded libraries; the arbitrary-derivation arguments below are separate from that audit.

## Derivation and occurrence lemmas

An occurrence has an origin in a finite derivation/history, not merely a syntactically present subterm. Trace an observed constructor occurrence backwards through public construction, projections, successful destructors and honest outputs. Public construction either creates that outer constructor using derivable arguments or carries the occurrence from an argument. A structural projection returns an existing occurrence. A verification or opening returns a message from a prior signature/cipher occurrence. DH/KEM rules introduce only their own shared constructors. A new fresh atom cannot contain a constructor occurrence. A backward path therefore ends at a public construction of the selected occurrence or at an actual honest creation of that occurrence. This well-founded induction uses the finite history together with the finite recipe tree; it never grants the attacker access to all syntactic subterms of an opaque value.

First, for this output ledger, if a root, HKDF stream, chain projection or record-key projection is derivable, its immediate KDF input ancestors are derivable too, as far back as the root's six-field root input and its first DH value. This is an origin claim for this process, not a consequence of one-wayness alone. A public creation of an HKDF/projection occurrence needs its argument. No honest output releases such an occurrence through a data projection. A material projection must trace to a material constructor; honest material is only a private argument of seal/open, so a derivable material is publicly assembled from its key/nonce arguments. A signature verification returns either the fixed honest public-key/tag payload, which contains no KDF occurrence, or a message used by an earlier public signing construction. An opening returns an initial binding/fresh atom, an independently fresh record atom, or an earlier attacker-known chosen plaintext. None first introduces the selected KDF occurrence to knowledge. If the relevant constructor appears nested in an attacker-chosen plaintext, follow that earlier input recipe rather than treating the later honest seal as its origin. Repeating this descent reaches a public KDF construction and all its input ancestors.

Second, if the attacker derives a ground ciphertext `aead_cipher(k,n,ad,m)`, either it could derive `k` before creating that occurrence or that occurrence is one of the actual honest seal outputs. The same occurrence induction proves this disjunction. No reduction creates a ciphertext constructor. A ciphertext nested in a chosen plaintext has an earlier attacker recipe; the other honest plaintexts are fresh atoms or binding/fresh-atom pairs and cannot introduce a ciphertext. Ciphertexts carried under signatures, hashes, fields or subsequently opened records are handled by following the same occurrence, not by assuming every ciphertext was built directly in the last recipe. The honest-origin alternative preserves exact `k`, `n`, `ad` and `m`.

A parallel occurrence lemma is needed for the commitment, independently of ciphertext origin. If the attacker derives `blake2b512(ctx_preimage(k,n,ad,tag,sequence_le64(t),sender_id_le64(j)))`, either this exact hash occurrence originated at an honest seal or a public hash construction previously required its full preimage. In the latter case the public `[data]` projections of `ctx_preimage` give a recipe for `k`, and the key-ancestor lemma gives its root. The same backward descent handles hashes carried in fields, signatures or chosen plaintexts. No reduction creates a `blake2b512` constructor. The exact T0 preimage stores `k` directly; there is no separate key-padding constructor in this theory. For an honest origin, equality of the complete hash/preimage constructors preserves every field, including the sender encoding. Ciphertext provenance alone would not establish this: an adversary can copy a cipher and supply a different commitment field.

Third, neither the honest Server seed nor an honest Beacon's prekey seed is derivable in this process. A protected-atom induction suffices: every occurrence of either secret in an honest output is below a nonprojectable public-key constructor, a private shared constructor, or a signature-key position. Public DH operations require an explicit scalar argument and return the shared value, not a scalar; no destructor removes the protecting argument to reveal that atom. Honest opened plaintexts have the restricted forms in the ledger, and attacker-chosen plaintexts were already derivable. Consequently the particular shared value `x25519_shared(s,p)` for honest Server seed `s` and honest Beacon prekey seed `p` is also not derivable: its private constructor cannot be applied publicly; either DH rule would require `s` or `p`; and no honest output releases this shared value through a projection/open/verification. This last shared-value conclusion needs the output-origin argument in addition to atom protection.

All these assertions are about derivability at the specified finite cut. Later honest outputs do not justify an earlier recipe. The descent through a chosen plaintext always moves to its input before the corresponding seal output. No reveal or additional service may be silently added to this lemma.

## Consequences for a completed Beacon

Consider an actual successful Beacon finish with pinned identity `P`, pinned ID `J`, prekey seed `p` and computed root `R`. Conversion and pin comparison imply `P = ed_public(a)` and its first root-input DH value is `x25519_shared(a,p)`, even if `a` is a compound ground term. The accepted frame at sequence one has material `ratchet_material(server_to_beacon_chain(R))`, associated data naming `(P,B)` and sender `J`; all are arguments to the existing exact opening rule.

Apply ciphertext origin to the cipher component of that attacker-delivered frame. If it was created publicly, the key-ancestor lemma gives an attacker recipe for `R` before the finish. If it came from an honest Server initial seal, equality of its key and the Beacon opening key gives equality of the two roots, then equality of their serialized root inputs, and hence equality of their first DH fields. Freeness of the private `x25519_shared` constructor gives `a = s`, and therefore `P = S`. The cipher equality does not itself determine the separately supplied commitment or sender; the commitment-origin lemma will be used independently below. If the ciphertext came from an honest Beacon record, key equality is impossible: its initial chain or a successor has outer `hkdf_second_32`, while the finish's initial chain has outer `hkdf_first_32`. The subsequent material-key layer is identical, so constructor disjointness exposes that mismatch. This argument covers both existing Beacon send positions and arbitrary roots; it does not assume root uniqueness across sessions.

It follows that `P != S` and successful finish imply that `R` was attacker-derivable before the finish. It does not follow merely from calling the HKDF constructors one-way. If `P = S` but `J != I`, apply the commitment-origin lemma to the exact commitment required by this successful open. A public construction gives a recipe for its key/root and then the honest shared value `x25519_shared(s,p)`, contradicting its unavailability. An honest Beacon commitment has the same directional key mismatch as its cipher. An honest Server commitment has sender `I`, and equality of the complete `blake2b512` and `ctx_preimage` terms and injectivity of `sender_id_le64` force `J = I`. Thus copying an honest cipher/tag and replacing its commitment cannot avoid the argument. Such a Beacon cannot finish. The same unavailability argument rules out a public construction even if other Beacons have attacker-controlled pins.

## Finite violation-preserving construction

Take a finite AnyPin trace through a selected C2 or C3 violation. Preserve every Server object and every Beacon pinning `(S,I)`, including their complete model variables, input terms, outputs and event occurrences. For any other Beacon, run an honest-pin Beacon with the same fresh identity/prekey/one-time/KEM names up to its identical registration bundle, and leave its finish unscheduled. The bundle computation is pin-independent. Its `FsBeaconStarted` field changes, which is why this is not a full event-trace equivalence.

A Beacon pinning `(S,J)` with `J != I` never outputs a record by the preceding result, so removing its attempted finish removes no public knowledge or queried event. For a Beacon with `P != S`, delete its finish and its later send steps. If it had no successful finish, it had no record output. Otherwise its root was derivable before the source finish. At each original record-output position the comparing attacker can compute the exact frame from that root, the known pin/public identity, the public assigned ID and the same sequence. A chosen plaintext is already a mapped recipe. For a fresh plaintext, allocate a new attacker atom at that original output position and map the original independent atom injectively to it. This preserves creation-before-use and every later equality. In the original trace the plaintext is derivable as soon as that frame is output, because the already-known root supplies its key/nonce and the exact frame can be opened. Thus this replacement does not secretly disclose a plaintext earlier than the source attacker could obtain it.

Induct over the retained finite history. Before and after each retained Server/honest-pin step the two attacker knowledge closures agree up to this injective renaming, including the added already-computable other-pin frames. In particular the same input recipe remains available, every retained equality/failure branch stays the same, and the comparing attacker does not gain a selected signing key absent in the original closure. The fresh-atom replacement is scheduled at the output cut, not at an earlier ghost send event or fresh-name allocation. Internal steps of a removed Beacon can be ignored because its state is private and its only shared effects are the listed outputs/events. No fairness condition forces a suppressed finish to run.

Every Server receive occurrence remains in the same order with the same fields. Every Beacon-to-Server send naming `S` that can match C2 remains in the same order with the same fields: removed `P != S` sends name a different identity, and removed wrong-ID/honest-key Beacons never send. Hence a matching injective send assignment in the constructed trace would reflect to one in the original trace. Knowledge-closure reflection retains the falsity of `attacker(k)` for the selected C2 violation, including compound or attacker-owned candidate keys. C3's two distinct receive occurrences and their queried field equality are unchanged. Either violation therefore produces a violation in the honest-pin process. Exact maintained TRUE results for C2/C3 then transfer to this AnyPin process at the same bounds and send/receive variant.

The transfer retains all Server receive attempts, including failures; it is independent of the separate E21 deletion argument. It can be applied to the fresh failure-interleaving C2 target, chosen fail-stop C2 target and chosen failure-interleaving C3 target individually. Applying E21 afterwards to chosen C2 requires the already reviewed exact C2 scope. There is no new computational query bound, loss, secrecy claim, raw-plaintext oracle, protocol source abstraction, or claim about the omitted opposite-direction workers.
