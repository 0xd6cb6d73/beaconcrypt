# Actual selected seal production and optional publication

`RawCtxSelectedSealReceipt` establishes provenance for the successful selected seals in the ordinary authentication observer. It retains the actual produced typed record and the source frame writer's optional result separately. This distinction is necessary because the ordinary INT-CTXT endpoint excludes every successful seal output from freshness, including an output whose subsequent writer fails.

`selected_call` exposes the actual selected CTX request, unchanged nonce/sequence/sender/associated-data/plaintext input, actual challenger record and exact writer result. `selected_production` distinguishes explicit nonce refusal from a produced record. Refusal preserves the observer state; production appends the successful seal before any optional writer outcome. These are executable-interface statements without a selected-key argument, not claims that arbitrary supplied contexts are independent of that key.

`step_seals` and `monitor_seals` show that operations with zero selected sealing queries preserve the selected sealing history. They allow all actual raw replies, public requests and known-key calls, including byte aliases. They do not discard those operations' computation or forwarded hash/uniform costs. `sealing_selected` carries the result through the actual pending source capability, preserving the outer nonce stop separately from the inner optional writer result. `sealing_provenance` proves that every entry appearing after any source sealing callback is either an earlier entry or the record produced by that exact pending capability. Invalid associated data, known material and refused nonces cannot create a selected receipt.

`send_provenance` lifts this result through the complete original send. It identifies the actual old-kernel request, retained-table derivation and ready capability, and retains the advanced kernel even when the optional writer fails. Exhausted sends leave the history unchanged. The result does not assume that an admitted send succeeds or that every history entry is newly produced; repeated equal record values remain possible.

`produced_publication` and `produced_has_publication` state the exact additional local codec fact needed to obtain a successful API publication: the writer returns `some` for the actual produced frame. The returned bytes, target ID and prepared sequence then match the original API result exactly. The encoded sender remains the caller's sender field and is distinct from the target route. Generic writer totality is not inferred. A separate proof of the production serializer's behavior on normal return can supply this local fact while retaining panic, allocation, representability and native library boundaries.

The production source supplies a narrower normal-return codec fact. In `beaconcrypt/src/ratchet.rs:371–406`, `seal_frame` creates a fresh `Vec<u8>` buffer, passes it to `capnp::serialize::write_message`, and returns `Some(Encrypted)` after the write succeeds. The locked Cap'n Proto version is 0.26.2; the unmodified `capnp = "0.26"` dependency enables its default `std` and `alloc` features. In that version, `src/serialize.rs:574–679` propagates errors only from `Write::write_all` while writing the segment table and segments. The `std` blanket implementation in `capnp/src/io.rs:78–86` delegates to `std::io::Write::write_all`. The inspected installed Rust `nightly-2026-06-01` library source, `library/std/src/io/impls.rs:504–507`, implements `Vec<u8>::write_all` by appending the bytes and returning `Ok(())`; the `&mut W` implementation delegates to the same operation. Thus this actual Vec-backed serialization path has no normal-return `Err` from writing. This source audit justifies a precise native codec functional contract for the local writer-success premise. The Lean theorem remains conditional: it does not extract or prove Cap'n Proto or the native standard library, and correspondence to the compiler and standard library actually used in deployment remains an explicit boundary. Allocation failure, panic, segment-size conversion and representability checks are not converted into successful normal returns. Reader availability, canonical wire encoding and equality of arbitrary raw encodings do not follow.

`full_tuple_fields` identifies exactly what a match against this produced CTX tuple proves: nonce, complete authenticated associated data, sequence, encoded sender and protected payload agree. It does not prove equality of installation identity, cryptographic session, direction, receiver label or serialized raw bytes. Multiple valid wire encodings may have identical decoded fields. Plaintext equality on a genuine replay additionally consumes the existing primitive correctness and real sealing-history invariant; it is not inferred from arbitrary oracle replies.

The mathematical `production` instrumentation retains the typed CTX record together with the unchanged optional writer result. `production_source` erases only that record annotation and recovers the actual native source seal before arbitrary shared-ROM interpretation and continuation. Primitive algorithms are not proved. The shared cache and downstream stateful interpretation use the existing source equalities, with real public HKDF and the explicitly retained private KDF hybrid unchanged.

No new oracle call is introduced: the observer's generic exact per-class bound remains applicable, and source sealing retains its separate derivation, hash, seal and writer costs. A selected refused attempt still consumes its selected sealing query. The existing authentication bound already constructs a reduction for every possible selected raw attempt; a later global proof must not charge that same record ordinal twice.

The remaining global correspondence must connect these produced-record receipts to actual role and installation labels and compare accepted records with the advertised symbolic origin. Its failure decomposition must distinguish a fresh CTX tuple, a matching produced tuple whose writer did not publish, and a matching published tuple with a different required origin. Production codec behavior can eliminate the second case where proved; source initialization, lineage and alias/collision accounting must handle the third. Original Gate and byte-Fresh do not by themselves eliminate any of these origin obligations. Finite session/key selection and the uniform selected-key distribution remain separate consuming work.

Validation consists of a direct Lean 4.34 module check and guarded axiom output for all eleven statements. No Rust change or mutation run is involved. Central imports, inventory and complete Make verification remain part of integration.
