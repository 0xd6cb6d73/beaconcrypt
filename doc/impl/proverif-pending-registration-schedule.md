# Delayed registration and moved pending tokens

This model extension addresses the concrete L1 scheduling mismatch recorded in [the source audit](proverif-fs-source-abstraction.md). Acceptance and response construction are distinct source calls. A response token accepted on one live Server may be built on another live Server with the same binding; several tokens may be built in an order different from their creation order. The earlier adjacent accept/build process does not express those schedules. Nothing here changes the production protocol, adds a cryptographic assumption, or declares its authentication properties false.

The design started from `codex/full-proof-composition` at `73682c26b72a1509a9a58e36388f06fc2faa45e4`; the reviewed integration basis is `76a47a4ff5182e395e1a3faa362f523d8e8625d3`, with the same Rust and ProVerif dependency sources. It adds a symbolic scheduler and finite operational fixtures. The scheduler itself has no established replicated authentication or secrecy result. The existing fs results and their pending global abstraction qualifications remain unchanged.

## Source state and public handles

[`fs-pending-registration.pvl`](../../beaconcrypt-core/proofs/pro-verif/fs-pending-registration.pvl) separates each live object's consumed registration set, successful-allocation counter and installed peers from the application's pending tokens. The binding remains the existing fixed honest Server identity and Server ID. Object handles are public, but the root and pending context are stored only in a private table. A public `sched_token(i)` names an acceptance attempt; it is not a constructor containing the root. The index advances on every admitted acceptance attempt, including failure. It follows the attempt-index convention of `PqxdhServerAuthNative.nativeAccept`, and does not assert that Rust exposes an integer representation of `RegistrationOutput`.

Predictability permits a caller to mention a missing or future handle. A build consults the private pending table at its actual position in the serial schedule. An absent handle returns `None`; it does not wait for a later acceptance. A returned token carries its accepting object as private provenance. That object does not restrict which builder can consume it. The source binding, rather than object identity, is checked when building.

Every archived token has one private service channel and one nonreplicated first-use input. The first build delivered to that channel moves the token before any binding, occupancy, identity, payload, seal or writer rejection. A spent service answers all later requests with `None`; it does not block or invoke the builder again. The channel is allocated per token, never per building object. This expresses the by-value `RegistrationOutput` argument in `Server::build_registration_response`; the public struct has private fields and no cloning implementation. The immutable private receipt remains only for provenance and handle-to-service routing. It is neither a reusable source value nor an erasure guarantee, and there is no reveal, snapshot or persistence operation in this model.

The dispatcher serializes operations, while separately counting acceptance and build requests on each live object. It is parameterized by both attempt caps and an allocation limit; `SchedMain` instantiates all three at two. An object can build imported tokens without accepting a registration itself. A request rejected for a nonexistent object or exceeded model bound does not call the source method and does not consume its token. A build naming a missing or spent handle counts against the build-request cap but cannot invoke Rust's typed method: this is the managed-handle oracle boundary, as in the existing native computational scheduler. These refusals are bound/interface behavior, not additional production admission checks. The fixed two-attempt bound has not been justified as an abstraction of arbitrary source schedules.

The allocation counter represents the offset from the configured Server key ID. A build consumes its token before testing `counter < limit`. Setting `limit` to the remaining `u64` identifier capacity represents source exhaustion. The concrete two-build fixtures have room for two assignments. This distinction avoids assuming that acceptance count, build-request count, successful publication count and remaining identifier capacity are equal.

Each request is `sched_call(label, operation)`, where the caller selects its public label. Every reply echoes the complete call with its optional result. Acceptance returns either a handle or `None`; construction returns either the complete response or `None`. Distinct labels let the caller distinguish repeated identical operations even when public replies become visible in a different order. This does not restrict the caller to fresh labels or add a secret request field. Malformed calls also receive an associated `None` reply. The model describes serial source operations; no theorem about arbitrary overlapping source calls is claimed.

## Acceptance and complete response construction

Acceptance reuses `registration_set_verify` and `registration_set_root`. Their existing source signature order, verified registration ID, root-input construction, generation order and primitive theory are retained. Only the accepting object's consumed set is consulted and updated. Successful acceptance publishes a pending receipt and its handle after that update. It installs no peer and does not advance the builder's allocation counter.

[`fs-pending-response.pvl`](../../beaconcrypt-core/proofs/pro-verif/fs-pending-response.pvl) is checked against the complete existing response-tail source, with only three textual substitutions after removing comments: the tail's name, sequence one as `fs_seq(1)`, and the predictable assigned ID as `fs_kid(next)`. The two initial chains still come from the same root, and the first send uses the original ratchet material and next-chain equations. The associated data retains Server/Beacon order. The authenticated plaintext includes the assigned-ID binding and an arbitrary nonempty application suffix; default payload and explicit empty payload remain distinct paths. All seven modeled tail failure points remain. Installation and counter publication happen only after successful inner and outer writing.

`SchedTail` waits for both the actual tail reply and returned counter before reporting completion to the calling schedule. Its commit event names the building object, and its separate provenance field names the accepting object. The current builder's counter determines the assigned ID. Neither the accepting object's current consumed set nor its counter is substituted into response construction. This is consistent with the seven checked `PqxdhRegistrationBuildContext` theorems, but those local theorems do not by themselves prove the global scheduler abstraction.

The inherited symbolic primitive theory and abstract serialization boundary remain explicit limitations. In particular, using an existing helper is not a proof that arbitrary symbolic KEM public terms are accepted by the native parser. The finite witnesses therefore construct attacker-owned public keys from secret seeds and sign their correctly tagged fields. They do not obtain a witness by selecting an unconstrained public-key name outside the native key domain.

## Structural scheduling relation

There is a local paper forward simulation for this Server subinterface, with arbitrary finite attempt caps and remaining identifier capacity. It is a scheduling statement, not a cryptographic interpretation theorem. Its source side is the serial, managed-handle interface for the source's separate accept/build calls. The per-call boundary interprets decoded fields and primitive results in the existing symbolic message theory. Agreement at that boundary must include verified fields, rejection, all retained root/response inputs, both initial chains, frame/response values and the complete logical state effect. It must not include authentication, secrecy, root independence or an honest-origin premise. The native byte/primitive interpretation remains an explicitly open prerequisite; this argument does not establish it by naming an interface.

Fix any reached state with live Server objects sharing the configured binding. Each object has a consumed set `C[o]`, allocation offset `n[o]`, installed-peer map `P[o]`, and counts `a[o]` and `b[o]` of admitted acceptance and build requests. A global natural `k` counts admitted acceptance attempts. The application owns a partial map `T[i]` of still-live pending handles. Its domain need not be contiguous: failed accepts leave holes, and builds remove entries. Each entry retains its accepting object, binding, verified fields and the actual root/response inputs. Neither `a[o]` nor the set of accepted handles constrains which tokens `o` may build.

At a quiescent scheduler boundary the relation has five clauses:

1. Each source object is associated injectively with one public symbolic object handle and its private state channel. That channel contains exactly `(a[o], b[o], n[o])`. The shared lock contains exactly `k`. The channel association is not a map of all objects to one object.
2. `registration_set_consumed` has exactly the interpreted pairs `(o, rid)` in the source consumed sets. `registration_response_peers` has exactly the interpreted installed entries, including each peer's identity, associated data and both current chain values. Registration-only operation never deletes or overwrites an assigned peer.
3. The private archive contains at most one receipt for each attempt index, and each receipt has a distinct private service channel. Every receipt index is below `k`; the absent indices include all failed acceptance attempts. Let `U` be the handles whose first-use input has fired. These are service phases, not an extra public state or a table-absence assumption. Each handle outside `U` has exactly its one initial service; each handle in `U` has the spent responder. The live map `T` is exactly the archive restricted to handles outside `U`. The archived accepting object remains unchanged when another object builds the token.
4. Source and model handles, roots, fields and frames are related by the same per-call interpretation, with consistently fresh names for generated symbolic values. Public caller labels and optional replies are preserved. Private receipts and return channels are not observable values.
5. Source and model counters satisfy the same remaining attempt and allocation budgets. The theorem considers schedules within the chosen attempt caps. A cap-excess refusal belongs to the managed bounded interface and is not claimed to be a Rust refusal.

The empty state satisfies the relation, and object creation extends its injective association without changing any existing object or pending receipt. For an acceptance within its cap, the dispatcher increments that object's acceptance count and runs the unchanged acceptance helper on its current consumed set. A refusal changes neither `C`, `P`, `n` nor `T`; it increments `k`, leaving a handle hole, and returns `None`. Successful acceptance inserts exactly the verified registration ID in `C[o]`, stores the source-returned fields at the old `k`, increments `k`, and returns that handle. No other object or allocation counter changes. These are all acceptance cases, including replay, validation, primitive and allocator refusal. The environmental `failure_stage` represents a refusal at the corresponding existing call point; it cannot make an otherwise failing primitive validation succeed.

For a build within its cap, increment the current building object's request count. A missing or spent handle is absent from `T`, so both managed interfaces return `None` without a Rust method call or logical state change. For a live handle, its private first-use input fires exactly once, removing it from `T` and putting it in the ghost phase set `U` before any response-building decision. The original builder runs in parallel with installation of the spent responder; the global operation lock is not released until that builder returns its real result. Source by-value ownership and the symbolic service phase then agree regardless of the later result. The accepting object's identity is only retained provenance. Counter exhaustion, a binding mismatch, occupied next ID, identity/reservation failure, empty payload, sealing failure or either writer failure returns `None` without installing a peer or advancing the counter. Successful construction uses the current building object's next offset, installs the exact tail's identity/AD/advanced-send/initial-receive entry, advances only that object's counter, and returns the same complete response. The accepting object's consumed set is never read by this call. All other consumed sets, peers, counters and pending receipts remain related.

Each case uses the existing handler's actual result; the simulation does not recover a secret plaintext, force a successful open, replace a root, or assume an honest selected candidate. Waiting for the response tail's result and counter establishes the same return boundary before the next case. The public result can be scheduled before the next input; private channel publication and unlocking add only unobserved steps at that boundary. Induction on a finite admitted command sequence therefore preserves the relation and all returned values, including delays, abandoned tokens, reversed builds and same-binding imports. It preserves the declared acceptance, consumption and publication event fields, with their separate accepting/building coordinates. It does not move an acceptance next to its build.

This is a conditional paper argument over serial logical operations; it has not been checked by Lean or by ProVerif as a general trace theorem. The exact tail comparison and source-footprint theorems support its local cases, and the finite checks below exercise the previously missing schedules. The argument neither proves a correspondence query in the new dispatcher nor lifts the old adjacent-call queries into it. Native random-generator state, oracle logs, allocation behavior, primitive query bills, timing, overlapping API calls, arbitrary Beacon lifecycle calls and additional reveal interfaces are outside this local relation. They cannot be discarded from a later computational or whole-protocol simulation.

## Focused operational checks

[`fs-pending-fixtures.pvl`](../../beaconcrypt-core/proofs/pro-verif/fs-pending-fixtures.pvl) invokes the same acceptance and construction handlers as the dispatcher. Fresh private return channels distinguish successive synchronous calls; they are callback slots, not cryptographic randomness. Each continuation receives the actual preceding state and attempt counter. The fixtures never substitute a chosen root or a forced success result.

| Target | Intended statement | Scope |
| --- | --- | --- |
| `pending-CROSS` | The proposed invariant that accepting and building objects always coincide is false | One valid attacker-owned acceptance on one object followed by a build on another |
| `pending-REVERSE` | A token created first can be built at assigned position two | Two valid acceptances, then construction in reverse token order on one object |
| `pending-LINEAR` | Two consumption events for the same handle have the same occurrence time | One acceptance and two sequential build attempts on distinct objects, including an adversarial first payload |
| `pending-C-REUSE` | The preceding one-use property fails if the token service permits a second consumption | Exactly the same fixture and handlers, changing only the constant hook that enables one additional first-use-style input |

These are finite witnesses and a structural lifetime check, not protocol security queries. A negative witness or control is accepted only with a reconstructed trace; an inconclusive result is a failure of the check. The initial replicated scheduler smoke test exhausted a 180-second development budget. An earlier spent-table encoding was operationally correct but its normal lifetime query remained inconclusive because the Horn approximation ignored the earlier insertion when considering a later absent-table branch. Built-in precise annotations did not fix that result. The maintained private-service encoding makes the moved lifetime explicit; it introduces no lemma, axiom or restriction. Both encodings retain the same source callback body and optional replies. The maintained four verdicts and exact input hashes accompany publication; the inconclusive diagnostics are not passed results.

The finite command counts are one accept and one build for CROSS, two accepts and two builds for REVERSE, and one accept plus two builds for LINEAR and its control. The general dispatcher counts all admitted requests against the two separate per-object caps, including rejection; its global handle counter counts acceptance attempts across all objects. Replication supplies no finite global request cap by itself. This stage adds no cryptographic reduction or primitive-query allowance. Its logical request counts must not be substituted for the source primitive bills in the computational experiment.

The checker also verifies the exact response-tail derivative, linear first-use service, spent `None` replies, controlled second-use mutation, critical consumption/provenance ordering, request/reply association and the corresponding source move, payload and publication boundaries. Its Python regression tests intentionally alter these boundaries. These are drift checks plus independently reviewed source arguments; they do not turn text comparison into a formal Rust-to-ProVerif compiler.

## Remaining lift

This extension supplies the missing operational vocabulary and reproducible tests for the original L1 counterexamples. It does not establish the global violation-preserving translation for A1, A2, S2 or S3, nor a many-peer record scheduler. That translation must preserve attacker recipes, optional observations and query matches, account for distinct accepting/building objects, and retain all assigned IDs and authenticated bindings. The source-to-symbolic parser/primitive interpretation is also still needed. No old gate is removed, no security result is relabeled, and no finite fixture is substituted for an unbounded or replicated protocol theorem.
