# Durable row operations and Mythic integration

The beaconcrypt library now implements generic transaction composition over individual cryptographic rows and application-owned records. This document records that implemented API and the separate design for integrating it with Mythic. The external baseline reviewed here is `0xd6cb6d73/mythic-beaconcrypt` at [`200af54bd8500d6d619b98d952fd4851e540ce10`](https://github.com/0xd6cb6d73/mythic-beaconcrypt/tree/200af54bd8500d6d619b98d952fd4851e540ce10). References to Mythic behavior below describe that pinned baseline; the proposed atomic storage-service endpoint and deployed delivery guarantees require their own implementation and validation. Beaconcrypt adds no database driver or protocol wire-format change for composition.

## What the integration actually requires

Mythic deliberately uses beaconcrypt's compatibility constructors so native mutations remain private until the engine commits the checkpoint, routing metadata, and exact response together. The comment in [`internal/native/native.go:43`](https://github.com/0xd6cb6d73/mythic-beaconcrypt/blob/200af54bd8500d6d619b98d952fd4851e540ce10/Payload_Type/mythic_beaconcrypt/internal/native/native.go#L43) explains why a native snapshot callback cannot implement that transaction: the callback runs before the native result is returned. The row convenience methods have the same limitation. The implemented transaction-composition callbacks expose pending native results inside the active transaction so the application can store its exact response before commit.

[`Engine.commit`](https://github.com/0xd6cb6d73/mythic-beaconcrypt/blob/200af54bd8500d6d619b98d952fd4851e540ce10/Payload_Type/mythic_beaconcrypt/internal/engine/engine.go#L420) stores `StateBlob`, `ProviderJSON`, and the encoded response in one storage operation, guarded by `ExpectedRevision` and `OwnerEpoch`. Its immutable request key is `RequestID` with `InputDigest`. An uncertain commit is followed by `LookupResult`, and only a recovered committed result is released. Native output alone is insufficient: registration also creates a random application session reference and an outer staging response, and the session-to-key-ID mapping must be committed with that response.

The pinned native adapter returns `Update{Data, KeyID, Seq}`. [`Engine.perform`](https://github.com/0xd6cb6d73/mythic-beaconcrypt/blob/200af54bd8500d6d619b98d952fd4851e540ce10/Payload_Type/mythic_beaconcrypt/internal/engine/engine.go#L274) checks the authenticated returned peer ID against the authorized routed session. The implemented row bindings provide metadata-bearing message variants without exporting a `RatchetSnapshot`. A convenience method returning only bytes cannot directly implement this interface.

The storage service is remote. [`storage.Client`](https://github.com/0xd6cb6d73/mythic-beaconcrypt/blob/200af54bd8500d6d619b98d952fd4851e540ce10/Payload_Type/mythic_beaconcrypt/internal/storage/client.go#L58) offers `load`, `create`, `acquire`, `commit`, and `get_result` RPCs. [`CommitStateRequest`](https://github.com/0xd6cb6d73/mythic-beaconcrypt/blob/200af54bd8500d6d619b98d952fd4851e540ce10/Payload_Type/mythic_beaconcrypt/internal/wire/state_types.go#L60) updates one `StateKey`, rather than an arbitrary set of independently versioned rows. Opening a local SQL transaction is consequently not a drop-in implementation of Mythic's current store.

There are application bottlenecks in addition to the native snapshot: [`Engine.Handle`](https://github.com/0xd6cb6d73/mythic-beaconcrypt/blob/200af54bd8500d6d619b98d952fd4851e540ce10/Payload_Type/mythic_beaconcrypt/internal/engine/engine.go#L35) holds one campaign mutex, loads the complete stored state on every request to verify ownership, and eventually serializes all profiles, sessions, and request indexes. The [`ownerData` structure](https://github.com/0xd6cb6d73/mythic-beaconcrypt/blob/200af54bd8500d6d619b98d952fd4851e540ce10/Payload_Type/mythic_beaconcrypt/internal/engine/owner.go#L52) must also be split into records before one campaign can obtain independent-peer concurrency. Preserving a campaign-wide revision update or mutex on every message would retain the serialization bottleneck.

## Implemented library composition

[`row_persistence.rs`](../../beaconcrypt/src/row_persistence.rs) implements `RowServer::transaction` and `RowServer::registration_transaction`, with matching native C, Go, and Python binding surfaces. Existing durable convenience methods remain available. Request IDs, input digests, authorization rules, receipt formats, expiry, tombstones, broker destinations, and response encoding remain application policy; beaconcrypt defines none of these records.

`RowServer::transaction<T>` invokes an `FnOnce(&mut RowSession<'_>) -> Result<T, RowError>` callback and returns its value only after the actual outer transaction commits durably. The borrowed session exposes `load_application` and `store_application` for opaque bytes, plus `encrypt_message` and `decrypt_message`. Application keys are isolated from private cryptographic keys and scoped by the server lineage. Absence is distinct from a present empty byte string. No public callback receives a peer codec, checkpoint, or `RatchetSnapshot`, and no mutable ratchet remains cached in the handle after the operation.

Each callback permits zero or one attempted native operation, including a rejected attempt. Application preflight can therefore return a cached result without cryptography, or invoke one transition and then store the exact response and associated records. Native calls return `RowTransition { message, changed }`; its optional `RowMessage` exposes read-only bytes, peer ID, and consumed sequence. A failed send can have no message while `changed` is true. A rejected receive has no native state change. Every storage or native-method error is sticky: the session rejects subsequent I/O and the outer call aborts even if the application catches the error. A wrong-phase or repeated native call produces `RowError::InvalidSession`.

Session methods use the existing transaction and never recursively begin or commit one. `RowStore` must invoke its callback exactly once, atomically validate every read and write, and report success only after durable outer commit. It must not retry a callback, convert a storage failure to absence, or report an uncommitted savepoint as success. A remote adapter may buffer a logical transaction and submit one atomic optimistic commit; implementing that backend remains the application's responsibility.

These callbacks are part of the trusted persistence boundary. They may encode and store pending plaintext or ciphertext in the active transaction, but may not publish it or perform irreversible external effects before the outer call succeeds. Callback failure can roll back a tentative consumed send because its output must still be private. Native `RowMessage` buffers are wiped on drop, including commit failure. Arbitrary application copies, Rust callback return values, and foreign-language buffers need the application's own erasure policy; callback scoping cannot revoke copied bytes.

| Library entry point or phase | Native calls permitted in its session | Durable boundary |
| --- | --- | --- |
| `RowServer::transaction` | Zero or one encrypt/decrypt attempt | Selected peer and all application writes commit together before the callback result returns. |
| `registration_transaction` acceptance callback | Zero or one `accept_registration` attempt | Replay marker and application writes commit before private pending registration material can reach completion. |
| `registration_transaction` completion callback | Zero or one `complete_registration` attempt | Allocator, peer, and application writes commit together; earlier acceptance remains committed if completion fails. |

Rust callbacks return generic application values; the C, Go, and Python composition bindings return opaque application byte strings. C receives a session pointer valid only on the callback thread and copies its eventual result through a sink. Go and Python expose temporary sessions whose methods reject use after callback return. Callbacks must not reenter the owning server. The maintained [persistence API reference](../persistence.md#composing-application-transactions) describes the language surfaces and storage contract.

## Proposed Mythic application transaction

The following receipt and authorization rules belong in the Mythic provider. They illustrate use of the implemented library primitive and do not introduce beaconcrypt-owned request or delivery policy.

The proposed Mythic send/receive transaction is:

1. Load its request receipt, current authorization records, and any required fencing row into the transaction's validated read set. Validate the actual request and current session scope. A fresh request and a cached request must both pass authorization.
2. If a matching completed receipt exists, return its exact stored application result without invoking a native transition. If the digest differs, reject the conflict. If a receipt is incomplete or its result has expired, return the corresponding terminal recovery status instead of repeating cryptography.
3. For an absent receipt, invoke the native transition through the active session. Validate its authenticated returned peer ID against the session mapping. A normally rejected unauthenticated receive creates no receipt, preserving Mythic's policy that invalid traffic does not consume durable request capacity.
4. Construct the exact provider response and stage the session/request metadata, input fingerprint, and immutable response bytes in application rows. Return those bytes as the callback's pending result. If native processing consumed state but produced no message, record the applicable terminal failure rather than assuming no message means no state effect.
5. The library commits all native and application row writes together. Only after success does it release the callback's result. A finalizer/encoding/storage failure releases no result. Registration's separately committed acceptance is the explicit exception to full rollback described below.

Mythic can use its existing [`Request.Digest`](https://github.com/0xd6cb6d73/mythic-beaconcrypt/blob/200af54bd8500d6d619b98d952fd4851e540ce10/Payload_Type/mythic_beaconcrypt/internal/wire/contract.go#L158), which binds the serialized method, operation scope, peer/session routing, and inputs while excluding transient `AuthContext`. Its request UUID is distinct from the storage RPC correlation ID, which `storage.Client` regenerates for each call. Never use delivery tags or a fresh RPC correlation ID as the durable deduplication key. The application must verify that its digest actually covers the native kind, routed peer, exact input bytes, and authorization scope; beaconcrypt should not guess that contract. A duplicate encrypted frame under a different request ID remains a protocol replay and cannot retrieve previous plaintext through a ciphertext-only lookup.

Authorization remains active on replay. Mythic already calls `authorizeIndex` and `authorize` before releasing a cached response and rejects results for revoked sessions. For cached registration, the original request names a profile but its durable receipt names the newly created session; authorization must inspect both. Receipt lookup without the current authorization read set would release accepted plaintext or a session response after revocation. Preserve [`restoreResponse`](https://github.com/0xd6cb6d73/mythic-beaconcrypt/blob/200af54bd8500d6d619b98d952fd4851e540ce10/Payload_Type/mythic_beaconcrypt/internal/engine/engine.go#L392)'s separation between immutable stored response fields and the current request's transient authorization and correlation fields.

The same generic transaction can implement Mythic's authorized result lookup without invoking any native transition. An uncertain commit is resolved by that lookup, returning the committed response, an explicit incomplete/expired state, or absence. Transport failure and malformed storage responses never mean absence. A remote commit can finish after a caller timeout, so absence does not prove that an earlier attempt can no longer commit. Atomic receipt insertion, read-set validation, and fencing prevent competing retries from committing divergent responses. The existing transport additionally retires a worker after uncertain RPC outcomes.

## Registration remains a distinct two-stage operation

`RowServer::registration_transaction<A, T>` implements the two-stage contract: acceptance commits before response construction. Its first callback returns `RowRegistrationDecision::Return(result)` to commit its current application writes and finish, or `Continue(context)` after a successful `accept_registration`. Continuing without an accepted pending token fails before the first commit. The token remains private to the library and reaches the second callback only after confirmed acceptance commit; a failed or uncertain first commit drops it. Both callbacks use the same `RowSession` type with phase-specific native methods and generic application-row access. A callback may choose zero native calls, including recording a terminal policy result during completion. The library does not require or interpret a receipt format.

For the proposed Mythic integration, the first transaction authorizes and deduplicates the application request before acceptance. A matching completed receipt can return a cached response without accepting again. On fresh accepted input, the acceptance finalizer stages an application-owned `accepted/incomplete` receipt with its request ID, digest, scope, and any chosen session reference, atomically with the cryptographic replay marker. A preflight or acceptance-finalizer callback failure aborts that first transaction. A consumed registration marker still causes native replay rejection regardless of the application request ID.

The second transaction revalidates authorization and the accepted receipt, then atomically commits the allocator, established peer, application session mapping, and exact complete registration response. The implemented `complete_registration` returns an unchanged transition with no message when response construction is rejected, allowing the callback to record a terminal application failure while retaining the already committed marker. An uncertain successful second commit is recoverable from its exact saved result, including the originally chosen application session reference.

A crash after the first commit leaves no reusable pending cryptographic token. A retry reports the incomplete accepted operation instead of treating a missing response as permission to accept again. A second-phase database or callback failure similarly leaves the accepted receipt and marker. The implemented `RowRegistrationError` identifies `Acceptance` or `Completion`. An acceptance-phase error means the first commit was not confirmed; it may nevertheless have succeeded if its acknowledgement was lost. A completion-phase error establishes that acceptance definitely committed, while the completion commit itself may be uncertain. The provider must inspect its authoritative application records after either uncertain outcome.

Recovering interrupted registration to success requires a separate mechanism such as protected persisted pending material. Combining acceptance and completion into one new transaction would instead change when acceptance becomes durable. Neither belongs in the minimal composition extension, and neither should silently weaken the replay-marker contract.

## Database and transport composition

`RowStore` does not require a literal long-lived transaction over RPC. An application adapter can implement a logical transaction by reading versioned rows, buffering writes, and sending one atomic commit batch containing the complete expected read set, absence checks, replacements, operation receipt, and application metadata. The database validates that set and commits all writes or none. Reads of authorization/fencing metadata must be included even when the transaction does not write those records. Never implement this as independent remote reads followed by unconditional upserts.

The pinned Mythic baseline's single-`StateKey` storage API needs a batched-row extension or an equivalent server-side transaction operation. That service extension is separate from the implemented beaconcrypt API and is not supplied by a client adapter alone. Serializing all rows back into its existing `StateBlob` would preserve the original cost, and committing each row through its existing endpoint independently would lose atomicity. A failed optimistic commit may be returned as a conflict; Mythic can retry its application operation under the same ID and recover a competing winner's result. The adapter must not automatically reinvoke a one-use native callback. Enable this extension only after an explicit capability handshake that confirms atomic multirow commit, read-set validation including absence, authorization/fencing checks, and supported row and batch limits. An old server or partial implementation must reject row mode before any state mutation; never fall back to independent commits.

For this RPC integration, an immutable durable reply journal is the essential outbox. A background dispatcher is not required to recover responses to retried requests. [`handleConcurrentRPC`](https://github.com/0xd6cb6d73/mythic-beaconcrypt/blob/200af54bd8500d6d619b98d952fd4851e540ce10/Payload_Type/mythic_beaconcrypt/internal/transport/concurrent.go#L115) publishes the response, waits for broker confirmation, and only then acknowledges the request. A crash between those steps can cause a duplicate delivery, so every retry must reproduce the committed response without repeating cryptography. Direct Reply-To addresses, current correlation IDs, and transient authorization tokens belong to delivery attempts, not to the immutable result payload. Broker confirmation is not proof of application receipt.

If another application needs push delivery, it can add delivery-attempt rows in the same finalizer transaction and dispatch committed messages later. Those rows reference the immutable operation result. Their delivery status must not control whether the ratchet operation is executed again. The composition API enables atomic application state and result recording; it does not promise exactly-once external delivery.

## Bounds, retention, and migration

Bound request IDs, input digests, receipt metadata, result bytes, and total admitted operations. Reuse application-specific admission policy rather than embedding Mythic UUIDs or campaign limits in beaconcrypt. The pinned Mythic baseline limits the state blob to 16 MiB, provider metadata to 1 MiB, and a JSON/base64 result to 64 MiB; the library's frame limit is 32 MiB. Benchmark and validate the final encoded response size, not just plaintext size.

For the proposed Mythic receipt policy, result expiration retains a compact tombstone containing the request fingerprint and enough application scope metadata for authorization. Deleting the receipt entirely would allow a retry to send another ciphertext or incorrectly treat an accepted receive as a fresh request. Mythic's existing request index deliberately survives a missing result and returns `result_unavailable` without executing native code again. Receipt pruning therefore needs an explicit application retirement and replay-horizon policy. Tombstones are Mythic-owned rows, and its maintenance tasks must not delete beaconcrypt-private keys. Expiring response payloads does not authorize pruning consumed registration markers.

The implemented session API has load and replacement operations only. An application can overwrite a complete receipt with a compact tombstone; if the body and tombstone occupy separate keys, it can replace the body with an empty or compact terminal value while retaining the tombstone. Present-empty remains distinct from absence. This reduces retained payload size but leaves an application key and tombstone per admitted request. The library supplies no delete or scan operation, expiry scheduler, physical reclamation guarantee, or automatic bound on the number of records. Admission limits, scope retirement, and tombstone retention belong to the provider. Backend compaction controls reclamation of obsolete value versions; backups and historical copies have their own lifetime. Removing current tombstones safely requires a policy that retires or fences their request scope so old requests cannot execute again. Administrative cleanup must protect native peer and registration rows and cannot assume a public application-key enumeration or codec API.

The row format and provider metadata cannot be migrated by swapping constructors. Fence existing snapshot owners, transfer all identities/ratchets/replay markers and routing metadata consistently, preserve durable request fingerprints and unexpired exact results, and activate only the new authoritative store. Mythic's pinned native adapter targets an older upstream commit and version-two checkpoints; the ML-DSA branch additionally requires updating identity provisioning and registration validation. That protocol adaptation is separate from row persistence.

## Concrete implementation split

Beaconcrypt now contains the callback-scoped transaction/session primitive, registration phase callbacks, metadata-bearing binding methods, and focused tests of atomic commit and output suppression. Existing durable per-operation methods remain useful for applications that do not require an application result journal and retain their delivery limitation. The library implements no Mythic receipt schema, authorization policy, remote storage capability negotiation, broker workflow, or migration tooling.

The proposed Mythic provider work is to add a separately negotiated row storage contract and a logical transaction adapter with immutable read versions, buffered replacements, and one atomic commit batch. That adapter can share authorization context and the existing RPC correlation/error handling. Add a row engine/native path whose application records hold profiles, session mappings and revocation, request fingerprints, terminal tombstones, and exact response bodies. Move request deduplication and response encoding into the native transaction callback. Do not reuse `Native.Export`, serialize `ownerData` wholesale, or update one campaign revision on every message. Existing snapshot mode can remain the default while row support is unavailable or existing state requires migration.

The provider repository cannot by itself implement the storage server's atomic endpoint. The upstream Mythic service must authenticate the provider and authorize the namespace, validate every read version and absence expectation, check the owner/fencing record if the deployment uses exclusive ownership, and commit replacements atomically. A provider-side reference/fake endpoint can validate this contract in tests, but is not proof that a deployed server supports it. A provider change should state this dependency explicitly and fail closed when the capability is absent. An optional new local SQL deployment would avoid that upstream boundary only by changing who owns Mythic persistence; that deployment rewrite is not the smallest change here.

The pinned native dependency also predates the ML-DSA branch. Updating its API calls, identity/configuration provisioning, registration framing checks, and development dependency/build setup is necessary before the new path can run against this beaconcrypt branch. This compatibility work is separate from the atomic-row endpoint and should be tested independently.

## Language surface and validation

The metadata methods are `EncryptToBeaconWithMetadata` and `DecryptBeaconMessageWithMetadata` in Go, `encrypt_to_beacon_with_metadata` and `decrypt_beacon_message_with_metadata` in Python, and `beaconcrypt_row_server_encrypt_with_metadata` and `beaconcrypt_row_server_decrypt_with_metadata` in C. They return message bytes, authenticated peer ID, and consumed sequence, including cached-key receives, without ratchet snapshots. Existing byte-returning methods remain available.

The implemented generic transaction callbacks expose the same phase and native-operation limits across Rust, C, Go, and Python. C session pointers must be callback-scoped; Go and Python wrapper sessions must reject use after return. No callback can reenter its owning `RowServer`. A callback's exception or error aborts its active transaction and is preserved as the binding-level cause. Registration reports which phase was attempted and which earlier commit is known to have completed. The application translates its own receipt states into conflict, incomplete registration, expired result, or cached response; those names need not become beaconcrypt status codes.

The library's focused tests in [`row_persistence.rs`](../../beaconcrypt/src/row_persistence.rs) cover native/application atomicity, cached-result preflight without another transition, received plaintext suppression on commit failure, delayed receive metadata, wrong-phase and repeated native calls, sticky errors, acceptance rollback, completion rollback retaining acceptance, zero-native terminal completion, response-construction rejection, and lost commit acknowledgements in both registration phases. [`row_persistence.rs` integration tests](../../beaconcrypt/tests/row_persistence.rs) exercise file-backed SQLite recovery, concurrent replay and ID allocation, and failure inserting the peer after the allocator write. Binding test sources include [`row_session_cgo_test.go`](../../row_session_cgo_test.go) and [`test_row_transactions.py`](../../tests/test_row_transactions.py). These describe existing test cases; successful compile, runtime, and mutation executions must be reported from their actual run results.

The proposed Mythic provider/service validation additionally needs identical request retries returning byte-identical application responses; same ID with changed input, peer, method, or scope; different IDs carrying the same received frame; concurrent duplicate requests; stale read-set and owner-epoch rejection; authorization/revocation before cached replay; expired-result tombstones preventing reexecution; and AMQP publish-confirm/ack crash boundaries. Assert that application session mapping, peer row, and final response commit together, apart from the explicitly earlier acceptance marker/incomplete receipt. Exercise a real file-backed database and a logical optimistic remote-store adapter without requiring a running Mythic deployment. Capability rejection must perform no mutations. Those provider-specific policies and an actual storage-service endpoint are not validated merely by passing library tests.

## Considered alternatives

| Candidate | Integration consequence |
| --- | --- |
| Trusted typed finalizer only | Can stage exact application bytes with native writes, but cannot skip crypto on a concurrently discovered cached request. Add transaction preflight to make deduplication safe. |
| Built-in opaque native-result journal | Recovers native ciphertext/plaintext but misses the random session reference, authorization, routing metadata, and exact outer application response. Adding those policies to the library contradicts the generic API requirement. |
| Escaping uncommitted capability or unrestricted batch | Offers composition, but imposes ownership, cancellation, and output-publication obligations across every FFI and complicates registration acceptance. |
| Trusted callback-scoped session | Lets application preflight, perform one native transition, and finalize exact application state under one commit. Supports app-owned receipts and remote optimistic stores without defining a database or delivery protocol. Registration keeps explicit phase callbacks. |

The implemented choice is the callback-scoped session. The alternatives above record the integration tradeoff; application receipt and delivery behavior remains outside the library.
