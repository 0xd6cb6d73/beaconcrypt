# Server registration prefix with a private identity seed

`PqxdhServerRootPreparation` spells out the callback order in `Server::get_shared_secret`. It reads and decodes the registration, checks the identity width and purpose tag, queries the `identityPoint` predicate at the position of Rust's length-only `PublicKey::from_bytes` call (constantly `true` for Rust), and reads and verifies the PQ, prekey and one-time fields in that order. It then checks the verified payload widths and tags. No verification is moved after key generation. Rust's Ed25519, X25519 and ML-KEM public-key constructors check only the byte length; the corresponding model predicates are constantly `true` for Rust, except `kemKey`, which stands for the ML-KEM encapsulation-key admission inside `encapsulate`. Point-dependent rejection comes from signature verification, conversion and the DH operations at their own positions.

The remaining prefix uses the exact identity/one-time concatenation for the registration identifier, reads its consumed status, reserves capacity, constructs the two received DH public keys, generates the ephemeral pair, constructs and encapsulates to the KEM key, performs the public and private identity conversions, and calls DH1 through DH4 in source order. Every native rejection exits at that point and retains the effects of all preceding callbacks. The verifier/getter prefix has at most nine callbacks; the remaining prefix has at most thirteen, for twenty-two in total. The callbacks expose actual local material and ephemeral secret only where the Server generates and owns it. They do not return the Server's selected identity seed.

`PqxdhServerStaticDhSource` compiles this prefix with the unavailable static-DH output replaced by its actual public input reference. Its `PublicDomain` is an ordinary functional native-DH correctness contract: for every correctly generated identity seed, the optional converted-static-DH result is present exactly when the stated public peer-validation function accepts. It must cover the actual Ed25519-to-X25519 converted identity scalar and arbitrary supplied peer encodings. The older agreement equation only for generated peer keys is insufficient to establish this law. The law asserts no protocol authentication, pseudorandomness, independent coordinates, unique encodings or security-event exclusion. It expresses the required native invalid-point rejection assumed for the primitive implementations; this work does not prove the validation algorithm or converted-scalar implementation.

Both interpretations execute the same supplied instrumentation at the original static-DH call position. Their remaining auxiliary callbacks are identical. `collectVerified_realization` proves equality for all optional post-verification outcomes, and `verifyInput_realization` preserves all raw parsing and attached-signature positions. `collect_realization` and `collect_continuation` retain the complete source result, generator order, all private primitive state, and the full subsequent computation. The mathematical realization of the selected output appears only on the source side of the equality. The executable prefix contains no selected seed, selected raw DH output, guessed output or derived-root oracle disguised as a local callback.

`collectVerified_references` and `collect_references` prove that every supported success contains precisely the received prekey reference and its reached native availability fact. These are consequences of the executed prefix, not caller-supplied authentication or honest-candidate premises. All other DH and KEM coordinates remain the actual local source outputs, including attacker-owned registrations and aliases of raw public encodings.

This package establishes the ordered callback driver and its private-static-DH simulation. The ordinary codec, attached-verification, generator, KEM and local-DH callbacks still require their stated native functional interpretations when this driver is installed in the common experiment. The [exact-input layer](server-related-root-input.md) and [complete root consumer](server-related-root-consumer.md) connect these reached data to extracted Server acceptance, exact 192-byte input, the related-root family, root erasure, consumed-registration insertion and the existing response-publication tail. Source callback budgets count logical calls; their full randomness, byte work and runtime must be charged by those interpreters. No callback is declared free. The separately maintained related-input Extract endpoint has an explicit additional advantage with no asserted smallness; this prefix does not prove that assumption or end-to-end authentication. No Rust behavior, primitive algorithm, persistence or snapshot model changes.
