# HB-89: Registration authentication without unique response encodings

This topic changes proof instrumentation and query scope without changing production code, wire fields, primitive choices, message scheduling or acceptance. The observed X25519 high-bit alias is one example of why exact response-field provenance is stronger than the registration protocol needs. The proof must also avoid assuming that scalar representatives, accepted point encodings or DH inputs are injectively determined by a DH result. This topic does not attempt to prove X25519 internals or derive such injectivity from CDH.

## Source-shaped projection

`Beacon.finish_registration` decodes the response identity, ephemeral input and ML-KEM ciphertext, evaluates the actual primitive calls, and supplies their output values to the extracted finish candidate. It derives the root and initializes a candidate ratchet, opens the supplied CryptoFrame with the exact associated data and pinned server sender ID, checks a nonempty application suffix after the eight-byte binding, and finally checks the pinned Ed25519 identity and server ID before publishing the candidate. It does not separately authenticate the raw ephemeral encoding or retain that encoding in its established state.

`establishment_authenticated_session` retains eleven fields: server identity, beacon identity, authenticated Phase-1 InitKex, registration ID, signed prekey, signed one-time key, signed ML-KEM public key, actual root bytes, exact associated data, pinned server ID, and registration origin. The prekey, one-time and ML-KEM fields are retained explicitly even though the InitKex also contains their tagged values. Their provenance belongs to the separate Phase-1 signature/replay argument; their inclusion does not make the X25519 point representation injective.

The projection excludes the response ephemeral encoding, raw KEM ciphertext, pre-Extract root input, original frame, full response, server-assigned routing ID and its old session label. All those values remain in the existing observed establishment tuple and diagnostic events. In particular, the projection does not infer equality of the pre-Extract input from equality of the derived root. Raw KEM-ciphertext origin might be available from an explicit CCA simulation, but this projected authentication statement does not require it or obtain it from symbolic constructor injectivity.

`BeaconAuthenticatedRegistrationCompleted` separately records the projected session, accepted sequence, entire authenticated plaintext, decoded CryptoFrame and claimed routing ID. `AuthenticatedRegistrationRecordSent` records the same session and record values together with the server's assigned routing ID. Exact frame origin refers to decoded ciphertext, retained tag, commitment, sequence and sender fields, rather than identical Cap'n Proto serialization bytes. The application suffix can reveal its length; no length-hiding statement is introduced.

Changing a response representation while preserving the actual retained root, associated data, identity and authenticated-record values preserves this projection. That statement requires no choice of a unique normalized point, no injectivity of scalar multiplication, and no classification of all native aliases. Proving that a successful fresh registration has the claimed server origin remains a separate computational simulation obligation; equality by projection is not an authentication proof.

## Query scope and retained regressions

The main model keeps fourteen queries. Its three registration authentication statements become: a first-sequence completion has the exact authenticated record origin with the same assigned ID; every modeled completion has a server origin for its projected cryptographic session; and every modeled completion has an origin for its exact accepted authenticated record. The last statement intentionally permits distinct claimed and originally assigned IDs, preserving production's reachable later-record relabel behavior. The original eight main controls, eighteen-query later-registration gate and twenty-seven-query post-registration gate remain present.

The ghost `session_label` used by traffic events now carries actual root bytes rather than their pre-Extract input, together with the same ordered identities and assigned ID. All seven call sites use their already-computed root; primitive and network behavior is unchanged. Raw root inputs remain in the observed establishment tuple. The eighteen- and twenty-seven-query files are unchanged textually, but their session coordinate now has this revised meaning, so both complete gates must be rerun. This change prevents their session equalities from silently asserting an inverse for Extract.

The old exact-field events remain unchanged. `exact-registration-origin-queries.pvl` preserves the three original query bodies verbatim as diagnostic regressions, rather than treating their canonical-constructor success as production authentication. Their response-alias controls must continue reconstructing counterexamples. The new projected events are emitted immediately beside the corresponding old events, using the same actual local values and success conditions; they add no primitive call or public message.

## Computational obligations and validation

This projection removes unsupported equality claims about discarded response representations. It does not close the global computational/symbolic bridge. Same-root session binding, target selection, query accounting, actual joint primitive distributions, KDF/evolving-key collisions, permitted reveals and the raw adapter boundary still require the checked common experiment. The symbolic X25519 and other primitive theories must be interpreted through their stated interfaces and explicitly accounted idealizations; successful canonical ProVerif runs alone do not establish those simulations.

The exact fourteen-query main gate, eight main controls, eighteen-query later-registration gate and twenty-seven-query post-registration gate pass after the ghost-label change. The complete Make matrix also passes all thirty-one scenarios and both auxiliary result groups. The alias runner uses the unchanged single-instance HonestBeacon/Server control, whose registration completion is at sequence one. It checks twelve results: the original three are TRUE canonically and FALSE with reconstructed alias traces, while the corrected three are TRUE under both interfaces. Its five raw-result and six projected-result rejection controls pass. The sixteen source-fidelity tests pass, preserving the independently counted 409 and 297 mutation matrices and the sixteen runner-wiring mutation probes. All results use the unchanged production source. The final inventory gate, Rust formatting check, Python syntax/Black checks and scoped Clippy check pass; Clippy reports 38 existing warnings in unchanged core source. The attempted stricter `-D warnings` diagnostic therefore fails and is not represented as passing. The complete Lean extraction and runtime source remain byte-for-byte unchanged from the already reviewed HB-88 parent; no new Lean statement or runtime cryptographic operation is introduced.
