# Registration admission by the exact consumed pair

This package closes the consumed-registration admission mismatch at one live Server object. The production boundary is `ProviderServer::get_shared_secret` in `beaconcrypt/src/server.rs`: it accepts arbitrary callers, verifies their supplied identity and three signatures, and checks a set keyed by the exact 64-byte concatenation of the identity and one-time public keys. An origin table is not an admission rule. Different one-time keys under the same identity are separate registrations; changing only the prekey or KEM key does not create a fresh registration ID.

The new ProVerif service is replicated over arbitrary requests and attacker-owned identities. The Lean module proves the native source's fresh-append and replay properties over arbitrary adaptive API programs, then connects its consumed-set projection to a volatile owner/mutex abstraction. This is an admission-state result, not the completed global cryptographic/symbolic composition. The original finite-schedule models and every existing query/control retain their existing scope; they are not silently promoted to arbitrary-registration theorems.

## Actual source order and consumption

`get_shared_secret` takes exclusive mutable access to one Server. After the abstract message read, it checks the identity tag and width, verifies the PQ signature, then prekey signature, then one-time signature, and validates the core field widths/tags. The extracted `registration_id` projects identity and one-time bytes. An existing pair rejects before reservation, ephemeral generation or KEM encapsulation. For a fresh pair, allocation, prekey/one-time width parses, ephemeral generation, KEM public-key construction and encapsulation, public/private conversion and DH1–DH4 occur in their original order. The core accepts the shared input, clears the shared material, and the actual root derivation runs. Only a successful root causes consumed-set insertion. Response construction is later and does not undo consumption when it fails. Key-dependent rejections come from the abstract verification, conversion and DH results and from the ML-KEM encapsulation-key admission at their original positions.

The list in the computational experiment is a private ordered representation of the source set. Correct set membership/insertion and exclusive ownership are existing adapter contracts; no HashSet implementation, allocator, primitive implementation or compiler correctness is proved here. The new symbolic `failure_stage` parameter represents an environment-controlled optional rejection at allocation or the subsequent source callbacks. It is not a wire field or a new production capability. Its values 1–14 retain failure order and allow arbitrary early rejection without bypassing the ordinary symbolic primitive reductions. Stage 0 permits the ordinary path. The source success and rejection statements are independently checked against the actual native handlers, so no ideal success conclusion is inferred from this failure instrumentation.

`registration_width` proves that the real ID is 64 bytes. `registration_eq_iff` proves that equality of IDs is exactly equality of the two 32-byte fields. It uses their lengths and concatenation projections, with no digest, injectivity or collision-resistance assumption.

## Checked source statements

`PqxdhRegistrationAdmission` has 33 guarded statements. `state_bind` and `lifted_state` expose ordinary state sequencing and the state-preserving probabilistic lift. `prefix_step_preserves` and `prefix_program_preserves` retain the complete consumed list through every preparation callback. `collect_consumed` establishes immediate rejection of a used pair; `collect_verified` retains the exact parsed signed fields; `prefix_fresh` derives freshness from the actual raw prefix rather than assuming it.

`client_consumed` follows the concrete root interpreter through erasure, optional derivation and consumption. `pending_registration_bytes` identifies the exact pending-token bytes. `accept_consumed` then states the complete disjunction: a failed admission leaves consumption unchanged, or a successful admission stores and returns its matching pending token and appends precisely its previously absent ID. Neither a successful execution nor an honest identity is a premise.

`build_consumed` and `finish_consumed` retain the set through the complete source response builder and Beacon finish, including optional failures and all cache effects. `handler_consumed_quiet` covers every other original capability, including public HMAC/hash queries, adversary coins and installed-kernel reveals. `handler_admission` derives the fresh-append relation for each full API step. `admission_invariant` and `program_consumed` preserve the entire old consumed prefix and uniqueness through any adaptive continuation. `accepted_id` recovers the exact ID of a returned token. `no_reacceptance` proves that two successful admissions separated by any such continuation have different IDs, even when neither response is built and both callers are malicious.

`native_accept_consumed` transports that result to the literal native operation with its complete primitive state. `source_ordered_unique` consumes the actual constructor-ordered native experiment, deriving its original reachable invariant internally and starting from its real empty set. It retains the arbitrary adversary and seed-disclosure switch; no extra freshness premise is imposed. Its scope is the approved experiment's capabilities, not arbitrary secret disclosure or a theorem about every possible application adapter.

`handler_consumed_count` and `program_consumed_count` charge at most one insertion to each attempted accept and none to other APIs. `source_ordered_count` obtains the same bound for the actual native experiment: an all-input adversary accept cap `qAccept` bounds the final number of entries by `qAccept`. Failed accepts remain counted. These proofs introduce zero primitive queries or cryptographic loss. Existing complete source/KEM/base/uniform bills remain in the resource modules; deterministic validation, membership, allocation and root work are not declared free runtime work.

## Volatile owner abstraction

The `Owner` state consists only of a consumed history and optional held registration lease. `ownerStep` models an idle owner's membership check, a held owner's refusal to admit another concurrent caller, failure release and successful commit. `LeaseFresh` states that the held pair remains absent until commit. `owner_step_fresh` derives that invariant from the actual acquire/check/release transitions; `owner_step_admission` derives fresh append. `owner_run_unique` and `owner_empty_unique` cover every finite prefix of the unbounded service, not a selected list of schedules.

`admission_owner_trace` gives an explicit idle-to-idle trace for every actual source-set transition. `owner_run_append` composes these traces. `program_owner_trace` and `source_ordered_owner` instantiate this abstraction with full supported executions of the original adaptive and literal constructor-ordered native experiments. Only the consumed-set projection is abstracted by these theorems. They do not erase cryptographic work from the source program, prove equality of entire applied-pi traces, or mechanically compile Rust/Cap'n Proto to ProVerif.

The ProVerif process implements this ownership discipline using one private mutex token acquired before parsing and returned on every success/rejection path, and a persistent table partitioned by the private Server-object handle and exact registration ID. Its held operation has no intervening public input. A source response may be delayed after release, just as a caller may delay observing a completed exclusive call. The original private root/pending values remain private. Attempt and origin names are instrumentation, not authenticated session identifiers inferred from equal public keys.

## ProVerif results and controls

The four new correspondences are noninjective and deliberately narrow:

- Returned admission has a prior matching consumed event for the same owner, attempt and ID.
- Consumption has a prior matching fresh check.
- Replay rejection has a prior consumption for the same owner and ID.
- Acceptance observed under an honest identity has the exact signed InitKex origin under the existing symbolic signature theory.

Honest-origin observation runs as a parallel observer after admission; it may block on an unknown identity without blocking the accepted source operation. No honest or malicious origin table is consulted by admission itself. The process uses the existing primitive symbolic theory and abstract typed message boundary, including their already documented idealizations. This package neither strengthens a computational primitive contract nor closes their global computational interpretation.

Five reachability queries have reconstructed traces: attacker-owned admission absent from all origin tables; two admitted one-time keys under one identity; replay rejection; a failed operation; and a fresh failure followed by successful admission of the same pair. Reintroducing an honest-origin admission gate makes the first, second and fifth controls unreachable. Removing mutex acquisition produces a reconstructed trace with two consumptions of the same pair. These six negative-control results are distinct from the nine baseline results.

ProVerif 2.05 reports the baseline mutex uniqueness correspondence as **cannot be proved** and reconstructs no attack. This is recorded as an inconclusive diagnostic, never a passing replay-security theorem. Its Horn abstraction can lose private-channel ordering and state precision; see the [official ProVerif manual, sections 4.1.5 and 6.7.5](https://bblanche.gitlabpages.inria.fr/proverif/manual.pdf). The native no-reacceptance theorem and checked finite-prefix owner invariant supply the admission-state proof. There is no added ProVerif axiom, restriction, assumed uniqueness correspondence or disabled gate.

`check-registration-set.py` requires the exact primary and summary queries and polarities, reconstructed traces for negative results, and the explicit inconclusive diagnostic. It also detects drift in the reviewed production callback order; that textual check is not an extraction theorem. The checker regression tests reject omitted/extra results, altered arguments or verdicts, summary disagreement, missing attack traces and misleading treatment of inconclusive output.

This process currently ends at the opaque pending-token return. Connecting it to the complete existing registration-response and post-registration processes, replacing their older origin-gated selected-schedule roles, and composing the arbitrary-registration symbolic trace with the common computational experiment remain subsequent work. The original sequence-1 response scope, claimed-versus-assigned-ID distinction and later relabel behavior remain unchanged. No serialization, persistence, snapshot, rollback-storage or primitive implementation proof is added.
