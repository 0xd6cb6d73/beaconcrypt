# Formal verification

Lean verifies panic freedom for the complete default `beaconcrypt-core` extraction and behavioral refinement for the documented synchronous core API semantics against the existing ideal PQXDH and symmetric-ratchet models. The extraction uses Hax, Charon, and Aeneas. ProVerif and SSProve provide complementary symbolic and finite probabilistic results. Concrete primitive implementations, adapters, codecs, persistence, and compiler correspondence remain outside the extracted-core proof.

For the concrete dependency, constructor, erasure and storage contracts, see [the deployment boundary](deployment-boundary.md). For detailed explanations and assumptions, see [What the proofs establish](formal-verification-analysis.md) and the [reviewed trust boundary](../beaconcrypt-core/proofs/trusted-boundary.md). The earlier staged plan and historical F* milestone descriptions are preserved in the [design history](impl/formal-verification-design-history.md).

The production protocol refutes three historical exact registration correspondences because a public X25519 encoding alias changes the raw response while preserving the actual root and authenticated record. HB-89 replaces those authentication queries with an eleven-field session projection retaining the pinned identities, authenticated Phase-1 fields, actual root, associated data and registration origin, together with exact accepted-record fields. The original three query bodies remain explicit negative regression controls. The canonical main model proves the projected statements for its first/third-sequence schedules, and the unchanged single-instance first-sequence control proves all three under the alias interface; this does not establish the still-open computational simulation. See the [projection record](impl/registration-event-projection.md) and [native, symbolic and Lean counterexample record](impl/phase2-x25519-alias-counterexample.md). No production change or plaintext-secrecy break is claimed.

## Other verification layers

ProVerif checks the maintained active-classical, passive-classical, passive-quantum capability, compromise, receive-rejection/capacity, identity-binding, and negative-control scenarios. Its network and cryptographic operations are symbolic. HB-95 requires authenticated initial sequence 1 before registration commit; later records may reach successful general opening but cannot establish the Beacon. The main fourteen-query process retains the corrected cryptographic-session and exact authenticated-record origin projection. Its controls additionally pin the sequence-one admission policy and reachable pre-gate later opening. The later-registration suite compares production rejection with an explicitly omitted-gate control. The post-registration suite starts from a genuine sequence-one commit, receives ordinary sequence 3, consumes cached sequence 2, rejects its replay and then accepts sequence 4. The generated initial family tests sequence 1 acceptance and other target rejection separately from the unchanged generic raw-receiver 1–51 capacity. Claimed outer and authenticated sender IDs retain their different meanings; the former later-record registration relabel path is now rejected. The raw-response X25519 alias controls remain a separate boundary. A persistent symbolic abstraction for arbitrary subsequent record schedules and the common computational interpretation remain open. See [the sequence-one change record](impl/beacon-initial-sequence-one.md).


The Lean computational development gives the documented CTX and PQXDH inequalities with explicit games and query accounting. The public-input fixed-HKDF/random-table endpoint is efficiently distinguishable, so those conditional inequalities do not establish negligible production advantage; a new checked counterexample has advantage at least one half in that public game. The replacement root game retains public real computation and, under its explicit source-to-HMAC functional equation, proves a coefficient-one decomposition into distribution-specific fixed-salt Extract pseudorandomness and ordinary HMAC PRF advantage for the single 32-byte root. HB-82 now composes the retained source-ordered signing proof, selected-key IND-CCA reduction and secret-input root decomposition for one actual typed all-candidate server execution, with four coefficient-one advantages, no honest-selected-key premise, exact source DH/root input and explicit query bounds. Further checked components retain correlated private roots, full 64/76-byte expansion, ordered finite chains, adaptive bidirectional next-material scheduling, and all-key shared-cache raw CTX integrity/privacy. The actual-source signature lane uses the explicit joint Ed25519/X25519 interface. The additional Extract endpoints and primitive security remain stated contracts; complete native evolving-key/reveal/restore and common symbolic composition remain open; see the [composition ledger](composition-assumptions.md). SSProve independently checks finite ROM, binding, privacy, and protocol games. Neither proves the security or correctness of the concrete primitive libraries, and the documented production-width, adapter, cross-prover, and broader computational-composition gaps remain.

## Reproducible checks

Run the locked aggregate verification and the separate trust-boundary inventory from the repository root:

```bash
make -C beaconcrypt-core verify
make -C beaconcrypt-core check-inventory
```

`verify-lean` checks the extraction and complete Lean project independently. `check-generated-lean` additionally rejects drift in the generated extraction. `check-lean-panic-freedom` reconstructs unconditional theorem signatures for every extracted operation and rejects missing or stale coverage; `check-lean` compiles those certificates and every handwritten module. The root module and all-module Lake glob are guarded. Repository-owned Lean files cannot contain unfinished proofs or custom axioms.

The reviewed inventory hashes the complete monitored source, generated, proof, control, and validation file sets. Its digest updates require review of the changed artifacts. After the final Nix verification, run `nix-collect-garbage` only when no other repository Nix build or shell is active.
