# Deployment and primitive implementation boundary

This document records the concrete dependency and execution contracts reviewed for the security-gap remediation. These are implementation requirements, not a proof that the named primitives compose into protocol security; see [formal verification analysis](formal-verification-analysis.md).

## Reviewed dependency configuration

The production adapter uses the workspace `beaconcrypt-crypto` crate with RustCrypto and Dalek primitives. The repository lockfile resolves `ed25519-dalek 3.0.0`, `curve25519-dalek 5.0.0`, `ml-kem 0.3.3`, `ml-dsa 0.1.1`, `chacha20poly1305 0.11.0`, `blake2 0.11.0`, `hkdf 0.13.0`, `sha2 0.11.1`, `getrandom 0.4.3` and `zeroize 1.9.1`. Transport serialization uses `beaconcrypt-parse`. Preserve the resolved graph with `--locked` when reproducing validation. A downstream Cargo consumer has its own lockfile and must check its resolved graph.

The adapter and primitive crate support `no_std + alloc`; the default `std` feature supplies hosted entropy through `getrandom`. Role selection and caller-RNG APIs are described in [portable Rust usage](no-std.md). The public `beaconcrypt` package produces an `rlib`; the `beaconcrypt-ffi` package compiles the same adapter sources into `staticlib` and `cdylib` artifacts with the existing `beaconcrypt` library name. Native C/Go builds use `cargo build -p beaconcrypt-ffi --release --features gobinds --locked`, and Python packaging selects that package's manifest through `pyproject.toml`. Production builds require no native libsodium library, initializer or C-crypto toolchain. Native ABI packaging and the optional header generator retain their separate hosted build requirements. Secret-bearing primitive wrappers redact debug output and support zeroization; the selected Dalek, ML-KEM, ML-DSA, SHA-2, BLAKE2 and AEAD features enable supported secret-state clearing. These measures do not establish physical erasure of every upstream temporary or compiler-created copy.

Pinned `libsodium-rs = "=0.3.0"` and `libsodium-sys-stable 1.24.3` remain development-only compatibility oracles. Their bundled `LATEST.tar.gz` source declares libsodium 1.0.22 and has SHA-256 `eb9873cc5ccd7b26ef058394264663c99e9c047b423be1ffd484071774198f26`. Building those tests still requires the oracle's native toolchain; selecting `SODIUM_LIB_DIR`, `SODIUM_USE_PKG_CONFIG` or another native source changes the test oracle. The production dependency graph and portable target builds exclude it. Differential tests cover deterministic key material, conversions, malformed input, KEM implicit rejection, KDF/hash/AEAD outputs and independently composed legacy protocol peers in both directions. These checks provide compatibility evidence rather than an implementation proof.

The runtime crates declare Rust 1.99.1 and compile checked-in EverCDDL-generated Rust CBOR codecs without running a schema compiler for ordinary builds. `beaconcrypt-core` retains Rust 1.92 compatibility for Aeneas, and the existing verification shell separately pins its extraction compiler and proof tools; those sources and artifacts were not updated or reverified for this backend migration. The old Windows GNU libsodium compatibility shims have been removed from production; the native oracle test retains its own test-only symbols. Target-specific compiler, entropy and runtime behavior still require validation on the deployed platform; the portable build checks do not instantiate an application's allocator, startup or storage implementation.

## Primitive-call contracts

| Call family | Contract used by production | What remains outside the formal core |
| --- | --- | --- |
| Ed25519 and X25519 | Exact-width keys; signatures cover the tagged bytes selected by core requests; invalid conversions and DH failures reject the operation. | Signature security in the joint signing/converted-DH interface, implementation correctness and leakage. Separate Ed25519 EUF-CMA and X25519 assumptions do not by themselves justify shared-secret-key use. |
| ML-KEM-768 | Matching encapsulation and decapsulation agree; ciphertext/key sizes match the wrapper API. | IND-CCA instantiation and the additional cross-public-key binding assumption used by the symbolic theory. Invalid-ciphertext implicit rejection must not be confused with an authenticity decision. |
| HKDF-SHA-512 | No salt, exact production domain bytes, deterministic common output stream, initial 64-byte split and 76-byte record split. | Extraction for the actual secret-input distribution and side information, which the proofs state as additional fixed-zero-salt Extract games, including the non-standard correlated Extract family described in [the composition ledger](composition-assumptions.md#primitive-guarantees-additional-assumptions-and-idealizations); expand pseudorandomness, evolving-key composition and output collision losses. Public deterministic HKDF evaluation cannot be replaced globally by an indistinguishable random table. |
| ChaCha20-Poly1305 IETF | 32-byte key, 12-byte nonce, 16-byte retained tag; opening authenticates the exact AD/ciphertext and returns recovered plaintext or failure. | Primitive security with the required nonce discipline and its lift from one uniform key to actual correlated ratchet keys. |
| BLAKE2b-512 CTX and comparison | The full 64-byte commitment binds the core-built transcript; `memcmp` compares equal-length commitments. | Concrete hash assumptions, random-oracle idealizations and whole-protocol timing. No demonstrated timing attack is inferred from data-dependent protocol branches. |

[Libsodium's conversion documentation](https://doc.libsodium.org/advanced/ed25519-curve25519) explains the shared Ed25519/X25519 seed conversion and recommends separate signing and encryption keys where possible. Changing this protocol to independent identity keys would require a versioned signed-bundle/wire migration; the current conversion API alone is not a composition proof.

## Entropy and construction

With `std`, `Beacon::try_new` and `Server::try_new` use the operating-system entropy source and return `KeyGenError` for reported entropy, input-length and key-generation failures. Existing hosted `new` methods remain compatibility wrappers that panic on those errors. Portable callers pass `beaconcrypt::crypto::TryCryptoRng` implementations to `try_new_with_rng` and the registration methods ending in `_with_rng`. Persistent-server creation similarly accepts an RNG for identity material and fresh lineage generation. C returns null and Python raises `ValueError` for malformed constructor inputs; Go preserves its error-returning constructors.

Production RustCrypto primitives require no global initialization and contain no libsodium load-time constructor. Fallible entropy-taking paths report RNG failures, including generators that modify their destination before returning an error. The guarantee remains limited to reported errors: allocation can terminate the application, hosted panicking wrappers remain available, and release builds use `panic = "abort"`.

Fresh identities, prekeys, one-time keys, KEM keys, encapsulation randomness and snapshot lineages require a securely initialized cryptographic RNG. Hosted entry points use `getrandom`; portable applications supply and maintain the entropy implementation for their target. A deterministic server seed must contain 32 secret uniformly generated bytes, rather than a password or predictable identifier. Tests with fixed seeds and test generators are reproducibility fixtures. Initialization must complete after the selected entropy source is ready, and repeated VM or application snapshots must not duplicate live cryptographic state or RNG state. ML-DSA signing retains the existing deterministic domain/context construction.

The portable backend deliberately rejects inconsistent local Ed25519 keypair encodings during signing and malformed expanded ML-KEM keys during decapsulation, including invalid public-key coefficients or stored public-key hashes. The former sodium wrappers admitted these width-correct local byte strings. Normal role construction uses canonical keys, and generated key encodings and protocol traffic retain the existing behavior.

## State ownership, persistence and erasure

`ServerSnapshot::validate_successor` supplies a reusable envelope check for the expected lineage, exact next generation and complete parent digest. The binding store uses it before replacing state. A store must perform this validation and comparison against its protected current head within a linearizable durable transaction; checking a supplied head cannot establish that it is current. A malicious store can satisfy every public byte check while replaying an old authentic history. Integrity requires protected storage or authenticated encryption/MAC with a protected key, rollback resistance requires an authoritative monotone head outside the rollback domain, and linearizability requires actual coordination. These are distinct obligations. See [persistence](persistence.md) for output-before-commit fencing and restore activation.

The C buffer destructor now uses `zeroize` to wipe the complete allocation capacity before freeing it. Go's temporary C input allocation is wiped with volatile stores before `free`; Rust-returned C buffers use the same native destructor. These changes reduce residual foreign allocations for plaintext, seeds and snapshots. They do not erase Go/Python-managed copies, previous reallocations, application logs, crash dumps, swapped pages, snapshots or secrets copied elsewhere. The Rust example's file store is a single-process demonstration, not a durable multi-owner rollback-resistant store.

The symmetric ratchet has no post-compromise recovery from a disclosed current chain. Retained skipped keys, snapshots, copied secrets and application plaintext limit past-message confidentiality. The 279 extracted-core normal-return certificates do not establish whole-application memory or runtime safety. Finally, validating a self-signed beacon identifies the signer; recipient authorization and task routing remain application policy.
