## What the checked statements establish

`verification_source` compares complete oracle programs before interpreting their callbacks. `verification` reads the registration, identity and required identity-constructor outcome; obtains and verifies the PQ, prekey and one-time signed fields in that production order; and only then validates their payload widths and purpose tags. It keeps the original signed candidate alongside the typed payloads. The final pure parser block uses B10's `parsedBytes`. Rechecking the already parsed identity inside this pure block adds no callback or state effect. `validated_fields` applies the scan-cleared B10 component: on arbitrary byte strings, this block accepts exactly when an extracted fixed-width bundle with those same four fields is accepted by `validate_init_kex`, with the same typed identity and key tuple. Wrong widths have no representing bundle. Signature and curve implementation correctness remain the existing primitive contract, not a new theorem about those algorithms.

`registration_id` proves that the identity/one-time concatenation used for source admission is exactly the extracted `registration_id` output. It uses the core equation, never the Rust `debug_assert_eq!` at publication. Changing only the prekey or PQ key does not create a different registration-set key. `collection_source` then restores the original post-verification callback order: consumed-ID status, reservation, prekey and one-time constructors, ephemeral generation, KEM construction and encapsulation, public/private conversions, and DH1 through DH4. `collect_replay` states the exact early rejection after verification for a previously consumed identity/one-time pair; it does not remove the preceding parsing and signature work.

`prefix_native` instantiates that exact program in the original native callback interpreter. Codec rejection, admission failure and actual ephemeral/KEM work remain in place. `accept_native` identifies the complete adapter operation with the original `nativeAccept`: each invocation allocates its attempted-session ghost ordinal, passes the complete collected input to the unchanged `nativeClient`, and publishes only its actual successful optional token. The ordinal and pending-token map are experiment/application bookkeeping; the ordinal is not a Rust wire identifier.

`accept_consumption` retains the actual full supported output: rejection leaves the consumed list unchanged; success appends exactly the returned token's previously absent extracted registration ID. This append occurs in the original successful root client. `accept_footprint` gives the exact attempted ordinal, unchanged peer map and identity key ID, preservation of every unrelated pending token, preservation of the entire pending map on rejection, and the actual source-read identity in the published token. It reuses the existing native operational footprint after the input scans. No honest-origin or successful-prefix premise is added.

`deployment_accept` connects this adapter operation to the CE handler. `accept_continuation` keeps any continuation of the actual optional handle and complete reinstalled CE state: both primitive caches, all owner objects, pending tokens, consumed state, counters, produced-frame list and existing analysis fields. This is equality of complete programs, not equality of a selected output distribution. The same original root request backend is used throughout; the result never equates the Extract ROM with fixed HKDF.
