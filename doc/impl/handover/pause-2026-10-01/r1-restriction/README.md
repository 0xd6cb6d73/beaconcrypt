### Resolved fidelity item: pin admission timing

The central scheduler model's `PqxdhRegistrationSchedule.parsePin` (`PqxdhRegistrationScheduleSurface.lean:15`) admits a pin only if it has exactly 32 bytes and satisfies `checks.identityPoint`, so the model can refuse Beacon construction because of an invalid point. Rust `Beacon::try_new` (`beaconcrypt/src/beacon.rs:66-68`) runs `ensure_init` and then `crypto_sign::PublicKey::from_bytes`, which in libsodium-rs 0.2.4 checks only the 32-byte length; Rust never point-validates the pin. During `finish_registration`, Rust converts the response's own identity key with `crypto_sign::ed25519_pk_to_curve25519` (`beacon.rs:432`) and then requires that key to equal the pin byte-wise in `beacon_prepare_finish` (`beacon.rs:455`, `beaconcrypt-core/src/pqxdh.rs:545`). The later comparison of the pin with the authenticated binding (`beacon.rs:499`) cannot fail, because that binding is derived from the pin itself. The net effect is that with a pin that is not a valid point, Rust construction succeeds and every finish fails (the first finish after the bundle aborts the Beacon), whereas the model refuses construction. On 2026-10-03 the owner ruled the Rust code authoritative, so this is a confirmed model defect, not a lane assumption. The central fix, which aligns `parsePin` to Rust's length-only construction, is in progress on branch `codex/registration-pin-width`, owned by the scheduler owner; this lane does not edit `parsePin`. The R1 equations hold for every `checks`, and for the honestly derived singleton pin the refusal branch is unreachable when `checks.identityPoint` is correct, so the content of the R1 equations is unaffected by the realignment. The lane must merge the central fix when it lands. The lane's point-branch statement, definitions and proofs, namely `parse_public`, `prefixAudit`, `prefixAuditWith` and the proofs of `initial_audit` and `initialWith_audit`, will then need a mechanical update; §4.1 of the machine-local plan `/tmp/bc-arc-scratch/c-work/pin-gate/plan.md` describes it.

Resolved on 2026-10-03 by the merge of `codex/registration-pin-width-lanes` (`d5a6ffd`), which brings in the width-only `parsePin` of `codex/registration-pin-width` and the ProVerif creation-gate removal, and commit `2708919`.
