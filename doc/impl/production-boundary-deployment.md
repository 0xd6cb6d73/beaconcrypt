# PB-D: classical source join of the whole deployment game

`PqxdhBoundaryDeployment` closes survey rows PB-12 and PB-14 for the classical common deployment experiment. It defines the adaptive source game `sourceGame` and proves nine guarded statements that equate it with the frozen CE game `PqxdhDeploymentSecrecy.game` at the production codec on the full returned value, plus the whole-program join, an index-0 instance, a normal-return statement, and generic continuation, observation and event transfers for item 8 (the event transfer both in the evaluation-measure form `𝒟[·]` of the CE-12 headlines and in the deprecated `Pr[·]` form). They are exact operational equalities; they add no security game, primitive contract or cryptographic conclusion.

The source game. `sourceGame setup codec reader erased checks ensureInit identityIndex bounds mode A` runs, from a runtime state, the source-ordered Server birth `PqxdhBoundaryBirth.serverBirth setup.joint ensureInit identityIndex setup.serverKeyId` (runtime initialization, then one generated identity seed; a failed initialization returns no outcome with the runtime it returned and draws nothing). On a created Server it runs `PqxdhBoundaryProgram.execute` of the per-command source step `PqxdhBoundaryDeploymentStep.sourceStep setup codec reader erased checks created.seed` (`doc/impl/production-boundary-deployment-step.md`) on the adversary wrapped by CE's own secrecy layer, `PqxdhDeploymentSecrecy.wrap setup.source.crypto codec′ setup.serverKeyId bounds (asModeO mode A)`, from `PqxdhDeploymentNative.initial created`. The secrecy layer is CE's (classification E): it keeps the transcript, the hidden test bit and the fresh messages, and issues only coins and sends for the test and fresh commands. As in the step module, codec′ is `PqxdhBoundaryRecordPrelude.withReader codec reader` and route′ is `RawCtxFrameDecoding.sender reader.model` (decision D-2, message #511).

Its returned value has type `Outcome KemSK X × A`: on a successful birth, the encoded created Server, the literal Rust result of the adaptive execution (on success the adversary output together with its final ledger, which is where `wrap` returns them) and the complete final deployment state (owners, Server, pending tokens, both caches, raw-attempt counters, produced frames), then the runtime. `okMap` turns a CE game value `(created, output, (ledger, state))` into `(created, ok (output, ledger), state)`, the inverse of the ledger move of `PqxdhDeploymentSecrecy.run_wrap`, and keeps the runtime; `unwrap` reads a source value back and is a left inverse of `okMap` (`unwrap_okMap`), so no part of the game value is lost.

Statements. `execute_exact`: for every native-interface program and complete deployment state, `PqxdhBoundaryProgram.execute (sourceStep …) work state` equals the CE native simulation `simulateQ (PqxdhDeploymentNative.handler setup codec′ checks route′ serverSeed) work` run from that state, with every reply wrapped in `ok` and the complete final state (`PqxdhBoundaryProgram.source_exact` with `step_exact`). `classical`: for every setup, codec, frame reader, buffer, `checks`, `ensureInit`, identity index, fresh bounds, mode, adversary and runtime, `(sourceGame setup codec reader erased checks ensureInit identityIndex bounds mode A).run runtime = okMap <$> (PqxdhDeploymentSecrecy.game setup codec′ checks route′ ensureInit identityIndex bounds mode A).run runtime`, on the full returned value with no projection, conditioning or event premise; the proof uses `PqxdhDeploymentSecrecy.game_wrap`, `PqxdhBoundaryBirth.server_source` and `execute_exact`. `classical_zero` is the identity-index-0 instance used by the CE-12 headline games (PB-D pin #415). `classical_normal`: every supported source outcome is `okMap` of a supported CE game outcome, so the source game never returns a Rust `fail` or `div` (a fact about the source model: the extracted local steps and the reviewed adapter transcriptions). `classical_continuation`: any continuation of the source game sees exactly the CE game's value through `okMap`. `classical_observe`: for every observation `observe` of the CE game's value, `(fun outcome => observe (unwrap outcome)) <$> source = observe <$> game` as computations, which is the form the CE-12 headlines use (`𝒟[decision <$> game] {true}`). `classical_evalDist`: for every observation `observe` into a measurable space, `𝒟[(fun outcome => observe (unwrap outcome)) <$> source] = 𝒟[observe <$> game]`; with a Boolean decision and the set `{true}` this is the event form `𝒟[decision <$> game] {true}` of the CE-12 headlines, so item 8 does not depend on the probability API that VCVio deprecated. `classical_probEvent`: for every event `event`, `Pr[event ∘ unwrap | source] = Pr[event | game]`, in that deprecated form.

`checks` stays a universally quantified parameter of every statement (PB-14): executions whose allocation outcomes vary per call and are not represented by one fixed `Checks` instance are outside these theorems, as the survey states, and the seven-site mapping of `Checks` to the Rust code stays reviewed transcription with the proposed PB-CHECKS pin not implemented (decision D-4). Item 8 instantiates the CE-12 headlines at codec′ and route′ and composes them with `classical_observe` or `classical_evalDist` (or, in the deprecated form, `classical_probEvent`); at that instance `DecoderAgreement` and the Phase 1 and Phase 2 read-back laws are provided by the step module, while `FrameReadBack codec′` and `ReadWritable codec′.frameWrite codec′.frameRead` stay carried codec contracts (E).

The `.crypto` allowance (decision D-1(b)). `sourceGame` passes `setup.source.crypto` to `PqxdhDeploymentSecrecy.wrap`, exactly as the CE game does through its handler; the direct-reference scan therefore finds the projection `PqxdhJointKdfGame.FixedHkdfSha512NoSaltSource.crypto`, which the exclusion of `PqxdhJointKdfGame` would reject. Under scan specification version 3 (no allowance for this module) the direct scan of this module fails with exactly three hits, all this projection, in `sourceGame`, its equation lemma `sourceGame.eq_1` and `classical`. A site probe over all constants of both I3 modules (theorem bodies included) finds 64 occurrences, 62 of them in the proof term of `classical`, and every one is the first explicit argument of `PqxdhDeploymentSecrecy.wrap` applied to the setup's `source`; the step module has none. This is the D-1(b) case (CE passing the source crypto to its own ledger, test and fresh wrapper), so scan specification version 4 extended the one-name allowance by module name to this module only; the allowlist itself stays that one name. Both D-6 reviewers confirmed the condition and noted that a module-wide allowance would also excuse a later use outside `wrap`, which only the one-off probe checked. Scan specification version 5 therefore restricts the allowance to a table of sites: for this module the `crypto` parameter of `PqxdhDeploymentSecrecy.wrap` (argument 3) and of `PqxdhDeploymentSecrecy.ledgerImpl` (argument 2), checked against each function's type, applied to `Setup.source`; for `PqxdhBoundaryRegistrationBuild` the `initialResponse` argument of decision D-1(a). The direct scan enforces the table on every run: it records every occurrence of the projection in the types and values of all constants of the module (theorem bodies included) and every primitive projection over the source record, and fails on any site outside the table and on any excused reference without a recorded site. On the current source it records 64 sites in `sourceGame`, `sourceGame.eq_1` and `classical`, all at `wrap` argument 3; its live controls show that the allowed-site shape of the other allowance module, an unapplied projection and a primitive projection are flagged, and a mutation run with the `wrap` entry removed fails on all 64 sites. No use touches the root input: the step's accept command is the published `deploymentAccept` with the CE root client and its approved request interpreter unchanged, and its HMAC command is CE's native public HMAC oracle at the Extract-ROM point, so there is no functional extract and no `Correct` premise on a ROM-answered call. Both D-6 reviewers confirmed this condition independently: `wrap` uses the record only through `crypto.verify` in the session designation of its transcript (`PqxdhDeploymentTranscript.acceptedKeys`, reached through `designate` and `SameSession`).

What stays outside. The commands of the source game are the common deployment experiment's approved interface under its deviations D1-D5 (classification E: the survey's deviation table, to be collected in the PB-E ledger), not every Rust entry point: in particular `create` is `Beacon::try_new` after D1, with no second `ensure_init`, and generation failures of the native key generators are not modeled; the `build` payload is the adversary's choice (D4), so no source adversary is claimed to have a literal build-payload network oracle; D2, D3 and D5 (omitted public getters, omitted helpers and state export, no initial Server public-key input) bound the command surface. The adapter transcriptions behind the per-command equalities stay reviewed transcription as recorded in the step guide and in each row's guide; the secrecy layer, the model oracles and the observation modes are CE's (E); the later-quantum game (PB-13) is increment I4 (`PqxdhBoundaryDeploymentLater`), not covered here. Persistence, snapshots and Cap'n Proto are out of scope. No Rust code or test was changed.
