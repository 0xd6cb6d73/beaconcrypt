# A constructive public-host routing context

Status: proposed paired operational interpretation of the existing strong comparison interface, for independent review. No equivalence or source-transfer conclusion is claimed yet. This addresses host routing; the initial-response lookup and all omitted-operation recipes are separate obligations below.

The comparison already exposes a caller-selected `builder` parameter at each pending build and tests that parameter as `owner` at every installed b2s receive or s2b send. A complete use audit must show that this owner is used only in that guard, its continuation and ghost event arguments. It is never the Server signing identity, own numeric ID, assigned peer ID, associated data, KEM input, HKDF input or frame field. Thus the source interpreter can use a different analysis owner for each installed peer worker without rewriting any protocol value. It need not ask an unobservable scheduler to distinguish workers sharing the actual Server object.

Use one adaptive interpreter, with the same program in both worlds. It maintains real host-object lifetimes, source public counters and IDs, a pending-value lifetime map, a peer routing map and a fresh analysis-label counter. Labels are public names selected by the interpreter at the corresponding host call. A source value in one world and the corresponding value in the other are paired values produced by this same computation; the interpretation does not prescribe identical later ciphertext-dependent inputs.

For an accept call, allocate a new analysis token and call label. Submit the original raw candidate and actual Server own ID, preserving the actual candidate verification and root computation. The replicated accept workers have no persistent per-object state and all use the same protected signing identity in this selected-identity profile. They differ only by their newly sampled per-accept material, which is associated with this source call. Register the returned token only after Some. A source public/scoped token handle is not used as the analysis token: lifetime bookkeeping preserves reuse and missing-handle behavior without allowing another pending continuation with the same analysis token.

For a build call, remove its pending lifetime from the interpreter map before any guard, including failure. Allocate a fresh analysis owner and call label. Supply the actual builder signing identity, actual builder own ID, actual next assigned ID, original application data and the source public failure decision, together with the unique analysis token. Exactly one pending input can consume this token. The public native counter and availability tests remain the interpreter's source control state; unavailable, exhausted, binding-mismatched and host-failed builds use the failure branch and install no peer. Production rejects an occupied next ID; it does not overwrite a peer. A successful reply creates the map entry `(real Server lifetime, actual assigned peer ID) -> analysis owner`, storing the corresponding accept/build occurrence and public response. The stronger comparison permits additional assignments or old-worker access; the source interpreter does not use them.

For a Server send, use the caller's real Server lifetime and original requested peer ID to look up that entry. Submit the worker's analysis owner and original call arguments. For a Server receive, perform the source public frame/sender decoding, look up its actual sender ID on the selected real Server, and submit the original frame to exactly that worker. Missing peers and malformed pre-routing inputs are handled by the same public source failure operation and produce None; their actual primitive/macro costs remain in the source bill. Every issued worker call consumes the corresponding source/worker attempt slot, including open/parser failure, and every send consumes its allocation including seal failure. Successful source peer removal or object destruction discards its routing map; the stronger comparison worker can remain available but the interpreter never routes a later source call to it. No restored state is in scope.

Repeated caller labels are safe because the interpreter supplies a fresh internal call label, waits for that exact reply and returns the original caller label. It never identifies pending values or peers by a caller label. The selected Beacon has one nonreplicated lifecycle and a single installed direction worker, so its source lifetime directly identifies that worker; no private origin witness is used to choose it.

The interpreter encapsulates the comparison channel and forwards the production transcript and API replies on the external host interface. Comparison disclosures are additional input to the interpreter, not automatically output as production messages. Each source call is completed before the next primitive call on the same mutable object; independent-object calls may be serialized in their chosen public host order. This is the already selected managed serial-call interface, not a theorem about native data races or arbitrary simultaneous mutation. A proof must account for every autonomous comparison output before using serialization to associate it with a call.

In particular, one accept emits its direction-specific chain pair before its unique accept reply. Only one accept is initiated at a time in this interpreter, and the selected Beacon's other public output phases are also explicitly driven. Thus the interpreter can save that pair under the pending lifetime without comparing secret roots. For a nonselected accepted identity the parallel root disclosure must also be drained and saved before the next accept; whether that output exists is the public exact-identity test on the verified candidate. Failed accepts return None and install no receipt. This protocol for collecting disclosures must be shown as an explicit public program, including both destructor branches; per-world deduction membership is insufficient.

A successful finish under the protected Server pin still needs a public lookup of the corresponding accept receipt. The proposed additional checked lemma is exact initial response origin: every selected protected-pin successful finish consumes a public response equal to a response emitted by an earlier successful build. An immutable receipt list indexed by the full original response then provides one deterministic public lookup in both worlds. Repeated equal responses can use the first matching list entry only if all such entries give the same omitted-direction recipe material; that is a separate exact-T0 equality lemma, not an inference from native IND-CCA. The two new ordinary-message auxiliary checks establish exact full-response/root origin in the direction-specific Kr3 projections; their safety use for both bit worlds and the duplicate-response material argument are recorded in paired-source-argument.md. The older root/assigned-ID/application-payload correspondence alone did not establish this exact public response lookup.

Every omitted opposite/far operation must use one fixed public evaluator on these saved paired values and the original adaptive paired request, retaining result-bit failures and the source state/cost transitions. The first far success still ends the selected near experiment. This host-routing context does not close the public optional-plaintext IND$ experiment, the global identity hybrid or the computational primitive interface.
